文件系统、持久化与崩溃一致性

内存管理关注运行期间的地址和页面，文件系统则必须让有名字的状态跨进程、重启和设备故障继续存在。一次简单 write() 可能只修改 page cache；真正持久化还要经过分配、元数据更新、写回、设备缓存与恢复协议。

本章把文件系统视为多层契约：路径名解析为对象，描述符维持打开状态，inode 与 extent 映射数据，VFS 统一实现，page cache 延迟 I/O，journal 或 COW 确保崩溃后只暴露可恢复状态。核心问题不是“数据写了吗”，而是：写到哪一层、以什么顺序、哪一个调用承诺了什么故障模型下的耐久性？

持久化必须提供什么？

命名、共享、耐久性与恢复

  • 命名：把稳定路径解析为对象，并处理目录、链接、mount 和并发重命名。
  • 共享：定义多个进程和描述符如何观察同一 inode、偏移和更新。
  • 耐久性：明确何时数据与元数据在声明的故障模型下可在重启后恢复。
  • 恢复：面对任意写入子集、撕裂写、设备错误或掉电，重建自洽状态并报告无法恢复的损失。

持久化不是二元属性。应用可能只需要进程崩溃后可见、操作系统崩溃后可见、掉电后可见，或在存储设备也诚实执行 flush/barrier 时可见。设计和测试必须写清故障边界。

文件与目录 API

文件、目录、链接与元数据

普通文件是带元数据的字节序列；目录把名字映射到 inode/object；硬链接让多个目录项指向同一 inode；符号链接自身保存路径文本，解析时再从适当目录上下文继续。

unlink() 删除一个名字，不会立即销毁被打开文件。对象通常在 link count 为零且最后 open reference 关闭后才回收。这使进程可创建临时、无名字文件，也解释了为何删除日志后磁盘空间可能要等进程关闭描述符才释放。

Metadata 包括类型、大小、所有者、权限、时间戳、link count、扩展属性和块映射。目录操作修改的也是持久元数据，需要与文件数据一起考虑崩溃顺序。

文件描述符与打开文件表

每进程 fd table 指向 open file description，后者保存当前 offset、访问模式和状态 flags，再引用 inode。dup() 与 fork() 可让多个描述符共享同一 open description 和 offset；独立 open() 通常建立独立 offset，即使路径相同。

C：共享偏移与已 unlink 但仍打开的文件 
#define _POSIX_C_SOURCE 200809L
#include <errno.h>
#include <fcntl.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/stat.h>
#include <unistd.h>

static void die(const char *what) {
    perror(what);
    exit(EXIT_FAILURE);
}

static char read_one(int fd) {
    char value;
    for (;;) {
        ssize_t n = read(fd, &value, 1);
        if (n == 1) return value;
        if (n < 0 && errno == EINTR) continue;
        if (n == 0) {
            fprintf(stderr, "unexpected EOF\n");
            exit(EXIT_FAILURE);
        }
        die("read");
    }
}

int main(void) {
    char path[] = "/tmp/open-state-XXXXXX";
    int original = mkstemp(path);       // Creates and opens one unique file.
    if (original == -1) die("mkstemp");

    const char contents[] = "ABCDE";
    if (write(original, contents, sizeof contents - 1) !=
        (ssize_t)(sizeof contents - 1)) {
        die("write");
    }
    if (lseek(original, 0, SEEK_SET) == -1) die("lseek");

    int duplicate = dup(original);      // Shares original's open description/offset.
    if (duplicate == -1) die("dup");

    int independent = open(path, O_RDONLY | O_CLOEXEC); // New open description.
    if (independent == -1) die("open independent");

    if (unlink(path) == -1) die("unlink"); // Remove the only directory name.

    struct stat status;
    if (fstat(original, &status) == -1) die("fstat");
    printf("link count after unlink: %ju\n", (uintmax_t)status.st_nlink);

    // original 读取 'A'，并把共享偏移量推进到 1。
    printf("original:    %c\n", read_one(original));
    // duplicate 从该共享偏移量开始，因此读取 'B'。
    printf("duplicate:   %c\n", read_one(duplicate));
    // independent 拥有独立且初始为零的偏移量，因此读取 'A'。
    printf("independent: %c\n", read_one(independent));

    close(independent);
    close(duplicate);
    close(original);                     // Last reference: storage is reclaimable.
    return EXIT_SUCCESS;
}
cc -std=c11 -Wall -Wextra -O2 open_state.c -o open_state
./open_state

原始描述符： A
复制描述符： B
独立描述符： A

Offset 共享使流水式读取自然，但并发 lseek()+write() 组合可能竞态。pread/pwrite 显式传入偏移，不修改共享 offset；O_APPEND 让每次写入的定位与写动作由文件系统原子处理，但多次 write 之间仍可交错。

Inode 与目录结构

路径解析从根或 dirfd 开始，逐个目录分量查询名字到 inode 的映射，检查每级目录 search 权限、处理 symlink 和 mount，最后得到稳定对象引用。目录项缓存（dentry cache）加速重复查找，但必须与 rename/unlink 保持一致。

Inode 不保存“一个绝对文件名”，因为它可有多个硬链接；它保存对象身份、元数据和数据块映射。目录负责名字。Extent 用 (logical start, length, physical start) 记录连续范围，稀疏 hole 不分配块，读取返回零。

# 逻辑大小变为 1 GiB，但空洞本身不需要数据块。
truncate -s 1G sparse.img

# ls/stat 报告逻辑大小；du 报告实际分配的存储。
ls -lh sparse.img
du -h sparse.img
stat sparse.img

磁盘上的文件系统布局

超级块、inode 表、数据块与日志

超级块描述文件系统几何、特性和根信息；group descriptor/bitmap 记录空闲 inode 与块；inode table 保存对象；data block 保存文件与目录内容；journal/log 保存事务恢复记录。关键元数据常有冗余副本或校验和。

磁盘布局不仅影响容量，也影响局部性与恢复。把 inode 放在相关数据附近减少寻道；把频繁更新元数据集中又可能产生热点；校验和能检测损坏，却必须有冗余或上层副本才能恢复内容。

文件分配与空闲空间管理

连续、链式、索引与 Extent 分配

  • 连续分配：顺序和随机访问快、元数据少，但文件增长困难并产生外部碎片。
  • 链式分配：增长容易，但随机访问需遍历，指针损坏影响后续链。
  • 索引分配：inode/索引块保存数据块地址，支持随机访问，但大文件需要多级索引。
  • Extent：用范围压缩连续映射，适合大文件和延迟分配；碎片后 extent 数增多。

空闲空间可用 bitmap 快速检查与寻找连续 run，也可用按地址/大小组织的 free-extent tree。Delayed allocation 先在 page cache 聚合写入，稍后按更完整大小选择连续 extent，改善布局，但增加尚未物理分配的脏数据量。

虚拟文件系统与 Mount Namespace

VFS 定义 file、dentry、inode、superblock 和 operation table 等共同对象，让 open/read/write/stat 可分派到 ext4、tmpfs、procfs、NFS、FUSE 或 overlay。统一 API 不消除底层语义差异，例如远程缓存一致性、FUSE 用户态故障和 procfs 动态内容。

Mount 把一个文件系统根连接到 namespace 中的 mount point。不同进程可拥有不同 mount namespace，因此同一路径字符串解析到不同对象。安全敏感代码应使用可信 dirfd 和受约束的相对解析，而不是先检查字符串路径再打开。

缓存、写回与持久化语义

Page Cache 与 Buffer Cache

Linux 常把文件数据缓存在 page cache 中；块元数据和缓冲概念在实现中可能与 folio/page cache 结合。Buffered write() 把用户字节复制到缓存页、标 dirty 后即可返回，后台 writeback 稍后映射块并提交设备。

读取命中缓存不会访问设备；readahead 可提前读取预测范围；direct I/O 尝试绕过 page cache，却有对齐、一致性和设备约束。缓存与 direct I/O 混用必须理解实现的 coherency 规则。

fsync、顺序与耐久性

fsync(fd) 请求同步文件数据和恢复所需元数据，fdatasync 可省略与数据检索无关的元数据。成功含义仍依赖文件系统、设备 flush/FUA 和故障模型。同步文件本身不一定使新目录项或 rename 持久；目录变更通常还需对父目录 fsync()。

一个常用的同目录耐久替换协议是：创建唯一临时文件；写入并检查 partial/error；fdatasync 临时文件；rename 原子替换名字；fsync 父目录。原子可见性与掉电耐久性是两个不同保证。

C：Linux/POSIX 风格本地文件系统上的崩溃感知同目录替换 
#define _POSIX_C_SOURCE 200809L
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <unistd.h>

static int write_all(int fd, const char *data, size_t length) {
    size_t done = 0;
    while (done < length) {
        ssize_t n = write(fd, data + done, length - done);
        if (n > 0) {
            done += (size_t)n;           // Successful writes can be partial.
        } else if (n < 0 && errno == EINTR) {
            continue;
        } else {
            return -1;
        }
    }
    return 0;
}

static void fail_before_rename(int dirfd, int tempfd,
                               const char *temp_name, const char *what) {
    int saved = errno;
    if (tempfd >= 0) close(tempfd);
    if (dirfd >= 0 && temp_name != NULL) {
        unlinkat(dirfd, temp_name, 0);   // Best-effort removal of unpublished temp.
    }
    if (dirfd >= 0) close(dirfd);
    errno = saved;
    perror(what);
    exit(EXIT_FAILURE);
}

int main(int argc, char **argv) {
    if (argc != 4 || strchr(argv[2], '/') != NULL) {
        fprintf(stderr, "usage: %s DIRECTORY TARGET_BASENAME CONTENT\n", argv[0]);
        return EXIT_FAILURE;
    }

    int dirfd = open(argv[1], O_RDONLY | O_DIRECTORY | O_CLOEXEC);
    if (dirfd == -1) {
        perror("open directory");
        return EXIT_FAILURE;
    }

    char temp_name[128];
    int used = snprintf(temp_name, sizeof temp_name,
                        ".replace-%ld.tmp", (long)getpid());
    if (used < 0 || (size_t)used >= sizeof temp_name) {
        errno = ENAMETOOLONG;
        fail_before_rename(dirfd, -1, NULL, "temporary name");
    }

    int tempfd = openat(dirfd, temp_name,
                        O_WRONLY | O_CREAT | O_EXCL | O_CLOEXEC, 0644);
    if (tempfd == -1) fail_before_rename(dirfd, -1, NULL, "openat temp");

    if (write_all(tempfd, argv[3], strlen(argv[3])) == -1) {
        fail_before_rename(dirfd, tempfd, temp_name, "write temp");
    }

    // 持久化字节以及重新取得它们所需的元数据，包括文件大小。
    if (fdatasync(tempfd) == -1) {
        fail_before_rename(dirfd, tempfd, temp_name, "fdatasync temp");
    }

    if (close(tempfd) == -1) {
        fail_before_rename(dirfd, -1, temp_name, "close temp");
    }
    tempfd = -1;

    // 同目录 rename 会原子地改变运行时命名空间可见性。
    if (renameat(dirfd, temp_name, dirfd, argv[2]) == -1) {
        fail_before_rename(dirfd, -1, temp_name, "renameat");
    }

    // rename 已成功，因此此后失败表示持久性结果不确定；
    // 删除新目标会是一次错误的回滚尝试。
    if (fsync(dirfd) == -1) {
        int saved = errno;
        close(dirfd);
        errno = saved;
        perror("fsync directory (rename visible, durability uncertain)");
        return EXIT_FAILURE;
    }

    if (close(dirfd) == -1) {
        perror("close directory");
        return EXIT_FAILURE;
    }
    return EXIT_SUCCESS;
}

即使 API 返回成功，硬件若谎报 flush 或断电保护失效仍可能丢数据。分布式/网络文件系统还可能拥有不同服务器与复制语义，不能把本地 ext4 经验无条件推广。

崩溃一致性问题

故障模型与更新依赖

文件追加可能需要写数据块 D、更新 allocation bitmap B、更新 inode I。若 I 先持久而 D 未写，会暴露旧数据；B 未持久可能让块被重复分配；B 持久而 I 未持久会泄漏空间。正确顺序或原子协议必须维护依赖。

故障模型需要说明：进程崩溃、内核 panic、整机掉电、单块 torn write、设备丢写/重排、bit rot 哪些在范围内。Crash consistency 通常保证重启后结构可恢复，不一定保证最近应用数据全部存在。

恢复技术

文件系统检查

fsck 离线扫描 superblock、inode、目录和块引用，重建“实际观察到的所有权”，与 bitmap/link count 比较，再执行保守修复或把孤儿对象移入隔离目录。

检查文件系统(image)
    验证并选择可用的超级块副本
    observed_blocks <- 空的所有权映射
    observed_links  <- 每个 inode 的初始值均为零

    对每个已分配 inode i：
        验证类型、大小、时间戳与块映射
        对 i 引用的每个块 b：
            记录 i 声明拥有 b
            若 b 越界或被重复声明，则进行标记

    从根目录开始遍历：
        验证每个 name -> inode 条目
        递增 observed_links[目标 inode]
        检测异常环与不可达子树

    将观察结果与 inode/块分配图比较
    修复无歧义的不一致
    隔离有歧义的对象或请求人工决定
    重新计算摘要并安全写回修复后的元数据

全盘扫描时间与容量增长，且损坏严重时无法知道用户意图；因此现代文件系统常用 journal/COW 把常见恢复限制在近期事务，同时保留 fsck 处理异常损坏。

日志与预写日志

Journal 先把事务描述和新元数据写入日志，持久化 commit record 后事务才可恢复，随后把内容 checkpoint 到 home location。重启只 replay 完整已提交事务，忽略未提交尾部。

提交日志事务(T)
    追加描述符（T 将修改哪些主位置块）
    追加 T 中各日志块的新副本
    强制把描述符与副本写入稳定存储
    追加并强制写入 COMMIT(T)
    确认 T 已提交到日志

    稍后把 T 的块写入其主位置                         // checkpoint
    checkpoint 持久化后，回收 T 的日志空间

恢复(journal)
    使用序列号与校验和扫描记录
    对每个带有效 COMMIT 的完整事务：
        把其日志块复制回主位置                           // redo
    忽略不完整或无效的尾部事务

Metadata journaling 只记录元数据，因此仍需 ordered mode 等保证相关数据先于暴露它的 metadata；full data journaling 恢复语义更强但写放大更高。日志自身需要校验、序号和空间回收，commit 还必须真正跨越设备持久化边界。

写时复制文件系统

COW 文件系统不覆盖当前树节点，而是为修改叶和祖先写新块，保留未变子树共享，最后原子发布新 root/superblock。崩溃前根指向旧一致树，成功提交后指向新树。

COW-更新(key, value)
    L1 <- 分配 L0 的副本，并修改其中的 (key, value)
    write_and_verify(L1)

    A1 <- 分配 A0 的副本，使其指向 L1
    write_and_verify(A1)

    R1 <- 分配新根，使其指向 A1 与未改变的子树
    write_and_verify(R1)

    publish_new_root(R1)       // 小型且受到严密保护的提交记录

COW 便于 snapshot、checksum 和原子多结构更新，但随机覆写会造成空间碎片和写放大；引用计数、后台清理和空间耗尽时的保留策略也复杂。COW 内存页与 COW 文件系统相似之处是“延迟复制”，但生命周期和持久化协议不同。

日志结构与 SSD 感知文件系统

Log-structured filesystem 把数据和元数据新版本顺序追加到 segment，通过 inode map 等定位最新版本。它把随机写转为大顺序写，但旧版本占空间，cleaner 必须选择 live 比例低的 victim、复制仍活数据并回收 segment。

SSD 无机械寻道，但有 erase block、FTL、garbage collection、write amplification 和 endurance。文件系统的写入模式与设备内部映射/回收会叠加，discard/TRIM 可通知不再使用的逻辑块。顺序逻辑写不保证设备内部完全顺序，测量必须考虑 FTL 与稳态 GC。

沿文件系统追踪贯穿案例

原命令的 input.txt 和 result.txt 都经路径解析、inode 与 page cache。Shell 在启动子进程前打开输出并可能截断旧文件；cat 读取 input，cache miss 才触发块 I/O；grep 写入 result 的缓存页，进程退出或 close() 不自动等价于持久化。

若应用需要“旧结果或完整新结果，掉电后也成立”，应采用临时文件 + sync + rename + 目录 sync，而不是直接截断目标。Journal 或 COW 负责文件系统内部恢复，但应用仍要使用正确同步协议表达意图。

对比与总结

机制 主要解决的问题 强项 压力点
Inode + directory 对象与名字分离 硬链接、稳定打开对象 路径竞态、链接与生命周期
Extent/index 逻辑偏移到物理块 随机访问和连续范围压缩 碎片与树元数据
Page cache/writeback 缓存与批量设备 I/O 低延迟、共享读页 dirty 节流、错误和耐久误解
fsync + directory sync 应用表达持久化边界 可构造耐久更新协议 文件系统/设备故障模型依赖
fsck 从全盘状态重建一致性 可处理非事务损坏 大容量扫描慢、意图不明确
Journal/WAL 近期原地更新的原子恢复 快速 replay、成熟 写放大、日志 ordering
COW tree 保留旧树并发布新根 snapshot、checksum、原子结构更新 碎片、引用和空间管理
Log structured 顺序追加新版本 写吞吐和恢复局部性 segment cleaning 与写放大

最重要的区分是：write() 表示字节被内核接受，rename() 表示 namespace 原子切换，fsync()/fdatasync() 表达持久化请求，父目录同步负责名字更新，而 journal/COW 决定内核崩溃后如何恢复结构。应用正确性需要把这些契约组合起来，不能把“调用成功”笼统等同于“永远不会丢”。
