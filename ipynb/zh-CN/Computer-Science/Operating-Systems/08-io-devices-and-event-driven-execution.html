I/O 设备与事件驱动执行

CPU 可以直接执行指令，设备却通过寄存器、队列、DMA 和异步完成与系统交互。操作系统必须把磁盘、终端、网卡、计时器和管道的不同语义整理为可组合接口，同时处理等待、并发、错误、取消、热插拔和不可信硬件输入。

本章把一次 I/O 分为提交路径与完成路径：进程提出请求并可能睡眠；设备独立工作；中断或轮询发现完成；内核更新对象并唤醒线程。理解这条因果链后，blocking/nonblocking、readiness/completion、epoll/io_uring 和 DMA 才能放进同一个模型。

操作系统的 I/O 问题

设备在传输单位、延迟、并发、错误和是否可寻址方面差异巨大。内核要隐藏无关细节，却不能抹去对应用语义重要的区别，例如文件可 seek、管道有 EOF、终端可能逐字符处理、UDP 保留消息而 TCP 是字节流。

异构设备上的统一接口

文件描述符提供统一命名和生命周期，read/write/close 提供常见数据操作，ioctl、mmap 和特定 socket 选项表达无法统一的控制。统一接口的价值是组合，而不是让所有对象行为完全相同；调用者仍需检查 partial I/O、EOF、记录边界和错误。

Little 定律把稳定系统中的平均在途数 \(L\)、到达率 \(\lambda\) 与平均停留时间 \(W\) 联系起来：

\[L=\lambda W.\]

它提醒我们队列长度、吞吐和时延不可独立优化。生产者持续快于设备时，有限缓冲只能推迟过载，必须建立背压或拒绝策略。

设备控制器与驱动程序

寄存器、队列与命令完成

控制器暴露 MMIO/port 寄存器、descriptor ring、doorbell 和 completion queue。驱动准备包含操作、DMA 地址、长度和 request ID 的描述符，用内存屏障确保内容先于 doorbell 对设备可见，随后设备独立消费并写回完成。

descriptor[i] <- 操作、DMA 地址、长度、request_id
memory_barrier()              // descriptor 必须先变得可见
submission_tail <- next(i)    // 向控制器发布所有权
write_mmio(DOORBELL, tail)    // 通知控制器检查队列

... 控制器并发运行 ...

等待 completion[j].request_id 变为有效
memory_barrier()              // 复用前先观察完成项字段
消费结果
completion_head <- next(j)

CPU 虚拟地址、CPU 物理地址与设备 DMA 地址可能不同：

\[\text{CPU virtual }X\longrightarrow\text{CPU physical }Y\longrightarrow\text{device DMA }Z.\]

IOMMU 把设备 DMA 限制到获准映射，既支持虚拟化和 scatter/gather，也降低错误或恶意设备读写任意内存的风险。

驱动职责与信任

驱动生命周期包括发现/probe、申请中断和 MMIO、初始化队列、稳定服务、超时与 reset、suspend/resume、热移除和最终释放。它同时面对用户输入、设备返回数据和并发完成，必须验证长度/索引、管理 DMA 所有权、避免 double completion 与 use-after-remove。

单体内核中的驱动拥有内核权限，错误可破坏全系统；用户态驱动或 IOMMU 可缩小故障范围，但会引入 IPC、映射和恢复设计。隔离强度应与设备风险和性能需求共同选择。

I/O 系统调用路径

以 cache miss 的 read(fd, buf, n) 为例：系统调用入口验证描述符、用户缓冲和权限；VFS/对象层解释偏移与语义；page cache miss 生成块请求；调度/驱动映射 DMA 并提交设备；线程睡眠；完成路径经中断或 polling 标记请求，唤醒等待者；线程重新调度后复制数据并返回。

端到端时间可概念分解为

\[T_{operation}=T_{setup}+T_{queue}+\frac{B}{R}+T_{completion},\]

其中 setup 是软件准备，queue 是排队，\(B/R\) 是载荷传输，completion 包含通知、唤醒和重新调度。只优化某一层无法消除另一层主导的延迟。

程序控制 I/O、轮询、中断与 DMA

PIO 与 DMA 回答“数据由谁移动”；polling 与 interrupt 回答“CPU 如何知道状态变化”，两组概念相互独立。

  • PIO：CPU 对设备寄存器逐项读写载荷，适合少量控制数据。
  • DMA：CPU 配置缓冲和描述符，设备直接在内存与设备之间传输，降低每字节 CPU 工作。
  • Polling：CPU 主动反复读取状态，低负载时浪费周期，高速稳定流量下可避免大量中断。
  • Interrupt：设备在事件时通知 CPU，空闲成本低，但高事件率会造成入口与缓存开销。

DMA 不表示零成本：页需映射/pin，缓存一致性和 IOMMU 需维护，描述符与完成仍由 CPU 管理。

在中断与轮询之间选择

若窗口 \(T_w\) 内每隔 \(\Delta\) 轮询、每次成本 \(c_p\)，近似成本为

\[C_{poll}\approx\frac{T_w}{\Delta}c_p.\]

若有 \(N\) 次事件、每次中断成本 \(c_i\)，则

\[C_{interrupt}\approx Nc_i.\]

稀疏事件通常适合中断，持续高负载可能适合 polling。Linux NAPI 使用混合路径：首个网卡中断触发后临时屏蔽进一步中断，按预算轮询批量分组，队列排空再重新开启中断。

Interrupt coalescing 和 polling budget 会在 CPU 效率与尾延迟间折衷，必须按负载分布测量。

阻塞与非阻塞 I/O

阻塞描述符在暂时无法推进时把线程加入等待队列并睡眠；非阻塞描述符立即返回 EAGAIN/EWOULDBLOCK。二者都可能返回部分字节、EOF 或永久错误，非阻塞只改变“现在不能推进”这一情形。

一个 read() 返回正数不保证完整应用消息，write() 也可能部分完成。EINTR、关闭、half-close 和超时都必须纳入状态机。对普通磁盘文件，O_NONBLOCK 的行为与 socket/pipe 不同，因为 page cache 与存储 I/O 语义并非简单 readiness。

I/O 多路复用与就绪通知

Readiness API 让一个线程等待多个描述符“某操作现在可能不阻塞”，然后逐个执行非阻塞操作。就绪是提示而非预留：另一个线程可能先消费数据，错误/关闭也常表现为可读，因此实际调用仍要处理 EAGAIN、EOF 与错误。

select、poll、epoll 与 kqueue

select 每次传递位集合并受 fd 集合大小限制；poll 每次传递数组，避免位上限但仍需扫描；Linux epoll 在内核维持注册集合与 ready list；BSD kqueue 用 filter 统一多类事件。持久注册减少重复复制，但不会让应用免于管理连接状态和公平性。

Level-triggered 只要条件仍成立就继续报告；edge-triggered 只报告变化，通常要求循环操作直到 EAGAIN，否则未排空数据可能没有新边沿。One-shot 模式还需显式 rearm。

C 示例：edge-triggered epoll 与非阻塞管道 
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/epoll.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

static void die(const char *what) {
    perror(what);
    exit(EXIT_FAILURE);
}

static void child_write_all(int fd, const char *text) {
    size_t used = 0;
    size_t length = strlen(text);

    while (used < length) {
        ssize_t n = write(fd, text + used, length - used);
        if (n > 0) {
            used += (size_t)n;          // A successful write may be partial.
        } else if (n < 0 && errno == EINTR) {
            continue;                   // Retry only because this demo has no cancellation policy.
        } else if (n < 0 && errno == EAGAIN) {
            struct timespec pause = {.tv_sec = 0, .tv_nsec = 1000000};
            nanosleep(&pause, NULL);     // Real code would wait for writable readiness.
        } else {
            die("write");
        }
    }
}

int main(void) {
    int pipefd[2];
    if (pipe2(pipefd, O_NONBLOCK | O_CLOEXEC) == -1) {
        die("pipe2");
    }

    pid_t child = fork();
    if (child == -1) die("fork");

    if (child == 0) {
        close(pipefd[0]);
        const char *bursts[] = {"first burst\n", "second burst\n", "final burst\n"};

        for (size_t i = 0; i < sizeof bursts / sizeof bursts[0]; ++i) {
            child_write_all(pipefd[1], bursts[i]);
            struct timespec pause = {.tv_sec = 0, .tv_nsec = 150000000};
            nanosleep(&pause, NULL);     // Make separate readiness transitions visible.
        }

        close(pipefd[1]);                // Reader will eventually observe EOF.
        _exit(EXIT_SUCCESS);
    }

    close(pipefd[1]);
    int epfd = epoll_create1(EPOLL_CLOEXEC);
    if (epfd == -1) die("epoll_create1");

    struct epoll_event registration = {
        .events = EPOLLIN | EPOLLET,
        .data.fd = pipefd[0],
    };
    if (epoll_ctl(epfd, EPOLL_CTL_ADD, pipefd[0], &registration) == -1) {
        die("epoll_ctl");
    }

    int finished = 0;
    while (!finished) {
        struct epoll_event events[8];
        int ready = epoll_wait(epfd, events, 8, -1);
        if (ready < 0 && errno == EINTR) continue;
        if (ready < 0) die("epoll_wait");

        for (int i = 0; i < ready; ++i) {
            if (events[i].data.fd != pipefd[0]) continue;

            // EPOLLET 规则：读尽当前所有可用字节。
            for (;;) {
                char buffer[16];
                ssize_t n = read(pipefd[0], buffer, sizeof buffer);

                if (n > 0) {
                    // 教学示例对写入 stdout 的 write() 保持简化。
                    if (write(STDOUT_FILENO, buffer, (size_t)n) < 0) die("stdout");
                } else if (n == 0) {
                    finished = 1;        // All writers closed and buffered data is gone.
                    break;
                } else if (errno == EINTR) {
                    continue;
                } else if (errno == EAGAIN || errno == EWOULDBLOCK) {
                    break;               // Fully drained; return to epoll_wait().
                } else {
                    die("read");
                }
            }

            if (events[i].events & EPOLLERR) {
                fprintf(stderr, "epoll reported an error condition\n");
            }
            // HUP 可能与可读字节同时存在，因此先读尽数据再处理 EPOLLHUP。
        }
    }

    close(pipefd[0]);
    close(epfd);
    if (waitpid(child, NULL, 0) == -1) die("waitpid");
    return EXIT_SUCCESS;
}

./epoll_pipe

高流量端点若每轮无限 drain，会饿死其他端点；事件循环需要每连接预算、批量上限和计时器优先级。

异步 I/O 与完成接口

Readiness 表示“现在尝试可能有进展”，应用随后调用操作；completion 表示“先前提交的具体操作已经完成”，结果必须与请求关联。

完成式接口适合批量、异步设备和减少系统调用，但引入请求生命周期、取消竞态、缓冲区在途所有权和完成队列过载问题。收到 completion 前不能随意释放或复用关联内存。

io_uring 与提交-完成队列

Linux io_uring 通过共享 submission queue（SQ）和 completion queue（CQ）交换 SQE/CQE。用户准备 SQE、发布尾指针并通知内核；内核执行后把 res 与 user_data 写入 CQE，用户收割并推进 CQ head。user_data 是应用关联请求状态的关键。

共享 ring 需要正确内存序，固定文件/缓冲可降低查找或 pin 成本，却增加注册生命周期。并非所有操作都真正异步，内核版本、安全策略与文件系统也会影响行为。

C 示例：提交并收割一次 io_uring 读取 
#include <errno.h>
#include <fcntl.h>
#include <liburing.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

struct request {
    char *buffer;
    size_t capacity;
};

static void fail_liburing(const char *what, int negative_errno) {
    fprintf(stderr, "%s: %s\n", what, strerror(-negative_errno));
    exit(EXIT_FAILURE);
}

int main(int argc, char **argv) {
    if (argc != 2) {
        fprintf(stderr, "usage: %s FILE\n", argv[0]);
        return EXIT_FAILURE;
    }

    int fd = open(argv[1], O_RDONLY | O_CLOEXEC);
    if (fd == -1) {
        perror("open");
        return EXIT_FAILURE;
    }

    struct io_uring ring;
    int rc = io_uring_queue_init(8, &ring, 0);
    if (rc < 0) fail_liburing("io_uring_queue_init", rc);

    struct request *req = calloc(1, sizeof *req);
    if (req == NULL) {
        perror("calloc request");
        return EXIT_FAILURE;
    }
    req->capacity = 4096;
    req->buffer = malloc(req->capacity);
    if (req->buffer == NULL) {
        perror("malloc buffer");
        return EXIT_FAILURE;
    }

    struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
    if (sqe == NULL) {
        fprintf(stderr, "submission queue is full\n");
        return EXIT_FAILURE;
    }

    // 描述从文件偏移 0 开始的读取；此时操作尚未完成。
    io_uring_prep_read(sqe, fd, req->buffer, req->capacity, 0);
    io_uring_sqe_set_data(sqe, req);  // Copied into CQE user_data for correlation.

    rc = io_uring_submit(&ring);
    if (rc < 0) fail_liburing("io_uring_submit", rc);
    if (rc != 1) {
        fprintf(stderr, "expected one submitted SQE, got %d\n", rc);
        return EXIT_FAILURE;
    }

    struct io_uring_cqe *cqe = NULL;
    rc = io_uring_wait_cqe(&ring, &cqe);
    if (rc < 0) fail_liburing("io_uring_wait_cqe", rc);

    struct request *completed = io_uring_cqe_get_data(cqe);
    int result = cqe->res;             // Nonnegative byte count or negative errno.

    if (result < 0) {
        fprintf(stderr, "asynchronous read: %s\n", strerror(-result));
    } else {
        size_t written = 0;
        while (written < (size_t)result) {
            ssize_t n = write(STDOUT_FILENO,
                              completed->buffer + written,
                              (size_t)result - written);
            if (n > 0) written += (size_t)n;
            else if (n < 0 && errno == EINTR) continue;
            else { perror("write stdout"); break; }
        }
    }

    io_uring_cqe_seen(&ring, cqe);     // Return this CQ slot to the kernel/user ring.
    free(completed->buffer);           // Safe only after the operation completed.
    free(completed);
    io_uring_queue_exit(&ring);
    close(fd);
    return result < 0 ? EXIT_FAILURE : EXIT_SUCCESS;
}

缓冲、缓存与背压

缓冲吸收 burst、匹配不同粒度并允许批处理；缓存保存可重用数据以避免设备访问。二者都使用有限内存，并会改变数据何时真正传到下一层或持久化。

无界队列不会消除过载，只会把拒绝变成更晚的高延迟或 OOM。常见策略是容量上限、high/low watermark、停止读取上游、降低 admission、丢弃可丢数据或把错误返回生产者。

Little 定律 \(L=\lambda W\) 说明在吞吐固定时，更多在途请求意味着更长平均停留。批量虽提高每次提交效率，却可能增加等待批次凑齐的延迟，需根据尾延迟目标设置。

字符、块与网络设备

字符设备通常提供字节/记录流和设备特定控制；块设备提供可寻址 sector/block，请求可合并、排序并经 page cache/文件系统；网卡使用分组队列、协议栈和 descriptor ring，应用通常通过 socket 而非直接设备文件访问。

“一切皆文件”表达共同句柄和部分操作，而不承诺所有描述符支持 seek、mmap、同样 EOF 或 durability。

错误、超时、取消与热插拔

请求可能在准备、已提交、in-flight、设备完成、内核完成和用户收割之间转换。超时/取消可与真实完成竞态；正确实现必须保证终态只提交一次、缓冲只释放一次，并明确取消成功是否表示设备不再访问内存。

热拔插要求先阻止新请求，再使已有请求完成或失败，撤销用户映射和 DMA，等待引用归零后释放驱动状态。设备 reset 可能使所有 in-flight 请求状态不确定，恢复策略必须知道哪些操作可重试、哪些可能已产生外部副作用。

超时预算应覆盖端到端路径，而不是每层各自重新给完整超时；否则重试叠加会放大负载并形成 retry storm。

观察 I/O 行为

应从应用症状向下逐层验证：strace -T 观察调用和等待；/proc/<pid>/io 与 scheduler 状态区分读写量和阻塞；iostat/pidstat 看块队列与设备利用；/proc/interrupts/softirqs 看完成负担；ethtool -S/ss 看网络队列；perf/ftrace/eBPF 关联内核时序。

Shell：从 API 边界向下检查 I/O-bound 进程 
# 1. 观察相关系统调用及其耗时。
# 生产环境中应短暂附加；跟踪每次调用可能扰动工作负载。
sudo strace -ttT -p "$PID" \
  -e trace=read,write,pread64,pwrite64,poll,ppoll,epoll_wait,io_uring_enter

# 2. 比较进程级逻辑 I/O 与实际存储 I/O 统计。
cat "/proc/$PID/io"
pidstat -d -w -p "$PID" 1

# 3. 检查中断或延迟网络处理是否集中在少数 CPU。
cat /proc/interrupts
cat /proc/softirqs

# 4. 检查块设备排队与延迟；请明确替换 DEVICE。
iostat -xz 1
cat "/sys/block/$DEVICE/stat"

# 5. 检查网卡丢包与驱动计数；请明确替换 IFACE。
ip -s link show dev "$IFACE"
sudo ethtool -S "$IFACE"

# 6. 先确定具体问题与时间窗口，再使用内核跟踪。
# 可用事件名称随内核而异；启用前先列出事件。
sudo perf list 'block:*'
sudo perf trace -p "$PID"

工具输出是采样且实现相关的。高设备利用率可能是健康批处理，也可能是排队瓶颈；低吞吐可能源于同步写、队列过浅、CPU completion 饱和或上游根本没有足够请求。

沿 I/O 栈追踪贯穿管道

cat input.txt | grep kernel > result.txt 包含三种不同 I/O：输入文件读取、内核 pipe 字节流、输出文件写入。输入 cache hit 时不访问设备；cache miss 才经文件系统和块层提交 DMA。cat 写满 pipe 会阻塞并形成背压；grep 读取后在用户空间计算，再把脏页写入 page cache，真正持久化可能晚于 write() 返回。

概念延迟分解为

\[T_{read}=T_{entry}+T_{lookup}+T_{queue}+T_{device}+T_{completion}+T_{copy}+T_{schedule}.\]

这解释了为何“磁盘服务 1 ms”不等于应用 read() 只需 1 ms：排队、唤醒、重新调度和复制同样可主导；也解释了 page-cache hit 为何跳过设备路径，却仍要做权限、对象和复制工作。

对比与总结

机制 CPU 如何获知/推进 优势 主要代价
PIO CPU 搬运每个数据单位 控制简单、适合少量数据 每字节 CPU 工作高
DMA 设备直接访问映射内存 大传输效率高 pin/IOMMU/一致性与生命周期
Interrupt 设备在事件时通知 稀疏事件空闲成本低 高频入口、缓存和风暴
Polling CPU 主动查队列 高负载批量低延迟 空闲时浪费 CPU
Blocking I/O 无进展时线程睡眠 顺序代码易推理 大量等待流需要线程/栈
Readiness 先通知可能有进展，再非阻塞尝试 少线程管理多端点 部分状态、drain 与公平性
Completion 先提交具体操作，后收结果 批量异步与设备并行 请求/缓冲生命周期和取消竞态

稳定的 I/O 心智模型是：对象语义 -> 请求验证 -> 有界排队 -> 驱动与设备所有权转移 -> 完成通知 -> 状态更新与唤醒 -> 用户可见结果。任何层都可能阻塞、失败或被取消；只有明确所有权、容量和唯一终态，事件驱动系统才能在高并发下保持正确。
