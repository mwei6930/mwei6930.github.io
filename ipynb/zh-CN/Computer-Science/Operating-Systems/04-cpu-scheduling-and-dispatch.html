CPU 调度与分派

cat input.txt | grep kernel > result.txt

管道中的 cat、grep、shell 以及系统中其他线程都可能同时可运行，但一个 CPU 核在某一时刻只能执行一个硬件线程。调度器（scheduler）决定谁应获得 CPU，分派器（dispatcher）则把这个决策落实为真正的执行状态切换。

调度不存在脱离目标的“最好算法”。批处理关心吞吐和周转时间，交互程序关心首次响应，服务器关心尾延迟与隔离，实时控制还要求可证明的截止期限。本章用统一工作负载比较经典策略，再把结果连接到多核、NUMA、实时和 Linux CFS/EEVDF。

CPU 调度问题

调度对象通常是线程，而不是整个多线程进程。线程进入就绪队列、被选中运行，随后可能因 I/O 或锁阻塞、时间片到期被抢占、主动让出或退出。调度器需要在新到达、唤醒、定时器中断和 CPU 空闲等事件上重新评估选择。

策略与分派机制

操作 含义 与策略相关的问题
enqueue(thread) 让线程具备运行资格 放在哪个队列、排在什么位置？
dequeue(thread) 移除阻塞、退出或迁移线程 已获得的部分服务如何保留？
pick_next() 选择一个合格线程 按到达、剩余时间、优先级还是 deadline？
account(thread, delta) 核算已用 CPU 真实时间、加权虚拟时间、预算还是 quantum？
should_preempt(current, new) 比较当前与新事件 紧迫性是否值得支付切换成本？ 
发生调度事件(event)时：
    update_accounting(current, event.time)
    update_runnable_set(event)

    next = policy.pick_next(runnable_set)
    如果 next != current：
        dispatcher.switch(current, next)
    否则：
        return_to(current)

策略给出排序和公平规则，机制负责定时器、寄存器保存、运行队列、地址空间切换与受保护返回。好的分析必须把算法改善的等待时间与实际抢占、缓存和迁移成本一起计算。

工作负载模型与调度假设

贯穿示例包含四个作业：

作业 到达时间 \(r_i\) CPU burst \(p_i\) 角色
A 0 8 长 CPU 工作
B 1 4 中等请求
C 2 2 短请求
D 4 1 极短交互工作

教科书模型常假设单处理器、精确已知 burst、零切换成本、作业独立且负载平稳。现实中这些条件分别引入多核放置、在线决策与预测误差、切换开销、锁与流水线依赖以及阶段变化。算法结论只能在声明的模型内成立。

调度目标与指标

周转、响应、等待与吞吐量

令作业 \(i\) 的到达时间、首次运行时间和完成时间分别为 \(r_i\)、\(S_i\) 与 \(C_i\)：

\[ \begin{aligned} \text{turnaround}_i &= C_i-r_i,\\ \text{response}_i &= S_i-r_i,\\ \text{waiting}_i &= \text{处于可运行但未执行状态的总时间}. \end{aligned} \]

若简化模型中作业到达后只会“运行或在就绪队列等待”，则

\[\text{waiting}_i=(C_i-r_i)-p_i.\]

真实线程阻塞在 I/O 或同步上的时间属于周转时间，却不属于就绪队列等待，因此测量工具必须区分状态。

吞吐量是单位时间完成的作业数，CPU 利用率是观察区间内 CPU 执行有效调度工作的比例。持续过载也可让 CPU 100% 忙碌，却使队列与尾延迟无限增长，因此高利用率不是良好服务的充分证据。

归一化周转或 slowdown 为

\[\text{slowdown}_i=\frac{C_i-r_i}{p_i},\]

它能区分同样十单位周转对一单位与九单位作业的不同影响。平均值还应配合中位数、p95/p99 和饥饿上界，否则更好的平均响应可能掩盖更差的长尾。

公平性、可预测性与截止期限

公平没有唯一含义。加权公平可把可运行集合 \(R\) 中线程 \(i\) 的目标份额定义为

\[s_i=\frac{w_i}{\sum_{j\in R}w_j}.\]

公平主体也可能是用户或容器，应先在组之间分配，再在组内线程间分配，否则创建更多线程就能放大份额。观察到的分配 \(x_1,\ldots,x_n\) 可用 Jain 指数概括：

\[J(x_1,\ldots,x_n)=\frac{(\sum_i x_i)^2}{n\sum_i x_i^2}.\]

它位于 \(1/n\) 与 \(1\) 之间，但接近 1 只表示分配相似，不能证明预期权重或 SLA 被满足。

可预测性关注响应方差、抖动和合格线程最长延迟。Deadline 评估则关心 \(C_i\le d_i\)、miss ratio、最大 lateness \(\max(C_i-d_i)\) 和 tardiness \(\max(0,C_i-d_i)\)。短作业优先、频繁轮转、严格优先级、缓存亲和、吞吐最大化和硬 deadline 之间都有明确冲突。

非抢占式调度

非抢占调度让被选中的作业一直运行到阻塞、退出或主动让出。它减少决策与切换，保留一个 burst 内的局部性，但新到达的紧急工作不能替换当前作业。

先来先服务

FCFS/FIFO 按到达顺序运行，无需预测 burst，可用队列实现 \(O(1)\) 入队和出队：

入队(job)：
    ready.push_back(job)

选择下一个任务：
    返回 ready.pop_front()
时间  0--------8----12--14-15
CPU   |   A    | B  | C |D|

示例等待时间为 A=0, B=7, C=10, D=10，平均 6.75。短作业被长 A 阻挡形成护航效应（convoy effect）。FCFS 简单、顺序透明，适合作业大小相近、抢占昂贵或作为更大策略中的队列纪律；但只有当所有先到 burst 都有限时才能避免饥饿。

最短作业优先

SJF 在当前就绪作业中选择预测 burst 最短者，并非抢占运行。所有作业同时可用且时长已知时，短到长排序可最小化平均等待；交换相邻的 \(a>b\) 为 \(b,a\) 会减少后者等待 \(a-b\)，而不影响更早作业。

选择下一个任务(ready)：
    返回 (predicted_burst, arrival_time, id) 最小的任务
时间  0--------8-9--11----15
CPU   |   A    |D| C | B  |

因为时间 0 只有 A，SJF 不能挽回非抢占决策；A 完成后顺序为 D、C、B，平均等待降至 5.25。现实中下一 burst 未知，经典指数平滑预测为

\[\tau_{n+1}=\alpha t_n+(1-\alpha)\tau_n,\qquad 0\le\alpha\le1.\]

较大 \(\alpha\) 反应快但噪声大，较小值稳定却难以跟上阶段变化。预测错误和持续短作业都可能让长作业饥饿，需要 aging 或最低服务保证。

抢占式调度

抢占允许系统在作业阻塞或完成前停止它，以响应短任务、quantum 到期、优先级或 deadline。收益必须与内核入口、核算、队列、寄存器、缓存和 TLB 成本一起权衡。

最短剩余时间优先

SRTF 是 SJF 的抢占版本：每次到达或完成事件后运行剩余服务最短的作业，新作业若短于当前剩余量就立即抢占。

任务到达(job)时：
    ready.insert(job, key=remaining_time)
    如果 job.remaining < current.remaining：
        preempt(current)

选择下一个任务：
    返回 ready.remove_min()

示例中 A 运行一单位后被 B 抢占，C 又在时间 2 抢占 B，随后 C、D、B、A 完成，平均等待为 2.50。在已知服务时间的理想单核模型中，SRTF 最小化平均 flow time；但它可能饿死长作业，对预测误差敏感，并因估计接近而频繁切换。实际变体常引入最小粒度或抢占阈值。

轮转调度

Round Robin（RR）让每个可运行同行最多执行时间片 \(q\)；提前阻塞或结束就立即离开，耗完整 quantum 的线程被放到队尾。

ready.push_back(new_job)

当 ready 非空时：
    job = ready.pop_front()
    运行 job，持续 min(q, job.remaining)
    将此时间片内到达的任务入队
    如果 job 仍有工作：
        ready.push_back(job)
A 0-2，B 2-4，C 4-6，A 6-8，
D 8-9，B 9-11，A 11-13，A 13-15

当 \(q=2\) 时，示例平均等待 4.75，不如 SRTF，但平均首次响应 1.75，远好于 FCFS 的 6.75。时间片边界上的到达与重新入队先后必须写入策略规范。

当 \(q\to\infty\)，RR 接近 FCFS；较小 \(q\) 缩短轮转等待，但若切换成本为 \(s\)，极端情况下有效执行比例约为 \(q/(q+s)\)，还会破坏缓存局部性。RR 只定义线程间轮转，不自动提供用户/容器组公平。

优先级调度与老化

优先级可以静态设置，也可由 deadline、反馈、资源所有者或组策略产生。严格优先级会让高优先级线程唤醒后立即抢占，但连续高优先级到达可导致低优先级饥饿。

老化（aging）随等待时间改善有效优先级。若数值越小优先级越高，一种示意规则是

\[q_i^{\text{effective}}(t)=\max(q_{\min},q_i-\lfloor W_i(t)/A\rfloor),\]

其中 \(W_i(t)\) 为累计就绪等待，\(A\) 为老化间隔。

老化解决等待者得不到 CPU 的饥饿，却不解决优先级反转：高优先级线程等待低优先级线程持有的锁，需要 priority inheritance 或 ceiling protocol。

多级反馈队列调度

MLFQ 在不知道 burst 长度时，用历史 CPU 消耗近似短作业优先。短运行后频繁阻塞的交互任务留在高层，反复耗尽配额的 CPU 任务逐步降到量子更长的低层。

1. 新任务进入最高优先级队列 Q0。
2. 始终从最高的非空队列中选择任务。
3. 同一队列内部使用时间片轮转。
4. 将 CPU 使用量计入该层级的配额。
5. 任务用完配额后降级，即使期间曾主动让出 CPU。
6. 定期把所有可运行任务提升回 Q0。

设计稳健性取决于两点：核算必须跨越主动 yield，防止任务在时间片结束前让出以“作弊”；还需周期性全局 boost 或等价 aging，防止低层在高层持续到达时饥饿。队列数量、quantum 增长、I/O 唤醒待遇和组权重都属于具体策略，不存在唯一 MLFQ。

按比例共享调度

按比例共享关注长期服务份额。权重 60:30:10 表示三者持续可运行时目标为 60%、30%、10%。权重通常只在竞争时分配空闲容量，quota 才是上限；层次调度应先在用户或 cgroup 之间分配，再在组内分配。

彩票调度与步长调度

彩票调度把权利表示为 tickets，每轮均匀抽取，客户端 \(i\) 获胜概率为

\[P(i)=\frac{t_i}{\sum_j t_j}.\]

winner = random_integer(1, total_tickets)
对 runnable_clients 中的每个 client：
    winner -= client.tickets
    如果 winner <= 0：
        运行 client 一个时间片
        退出循环

它灵活但保证是统计性的，短窗口可能明显偏离目标。步长调度用确定性虚拟进度替代随机性，选择常数 \(K\)，令

\[\text{stride}_i=\frac{K}{t_i},\]

每次运行 pass 最小者，再增加自身 stride：

client = remove_min_by_pass()
运行 client 一个时间片
client.pass += client.stride
insert_by_pass(client)

步长短期方差较小，但动态加入、权重变化、溢出和 pass 归一化必须处理。两者都不是 deadline 调度器：正确长期份额并不能保证下一次何时获得 CPU。

抢占、定时器中断与分派

定时器使内核即使面对不合作用户程序也能重新取得控制权。入口保存 trap frame，内核核算已用时间、处理计时器和唤醒，再判断是否需要重新调度。若继续当前线程，只发生内核往返；若切换，才保存线程上下文、改变运行队列和必要的内存上下文。

dispatch latency 是工作具备运行资格到真正开始执行的延迟，包含中断关闭区、不可抢占内核区、当前高优先级工作、调度和切换。实时保证要求这些干扰都有上界，只有平均时间很小远远不够。

多处理器调度

多核系统还要决定任务放在哪个 CPU。一个全局队列容易平衡但争用集中；每 CPU 队列可扩展并保留局部性，却需要周期负载均衡和空闲 CPU 拉取工作。

亲和性、负载均衡与缓存局部性

保持线程在最近 CPU 上运行可复用私有缓存和 TLB；迁移可修复负载不均，却要重新升温缓存，并可能远程访问原 NUMA 内存。调度器应在等待时间收益超过迁移成本时才移动任务。

Linux：检查并限制 CPU 亲和性 
# 显示当前 shell 可以运行的 CPU。
taskset -pc $$

# 只在逻辑 CPU 0 和 2 上启动 CPU 密集型命令。
taskset --cpu-list 0,2 ./worker

# 显示各线程、最近运行的 CPU、调度类别、nice 值与状态。
ps -eLo pid,tid,psr,cls,rtprio,ni,stat,comm --sort=pid,tid
C：把当前 Linux 线程固定到一个 CPU 
#define _GNU_SOURCE
#include <errno.h>
#include <sched.h>
#include <stdio.h>
#include <string.h>

int main(void) {
    cpu_set_t allowed;
    CPU_ZERO(&allowed);
    CPU_SET(0, &allowed);  // The calling thread may run only on CPU 0.

    if (sched_setaffinity(0, sizeof(allowed), &allowed) == -1) {
        fprintf(stderr, "sched_setaffinity: %s\n", strerror(errno));
        return 1;
    }

    CPU_ZERO(&allowed);
    if (sched_getaffinity(0, sizeof(allowed), &allowed) == -1) {
        fprintf(stderr, "sched_getaffinity: %s\n", strerror(errno));
        return 1;
    }

    printf("CPU 0 allowed: %s\n", CPU_ISSET(0, &allowed) ? "yes" : "no");
    return 0;
}

亲和性是约束或提示，并非免费优化。固定线程可能提高重复性，也可能把工作困在繁忙核心、过载共享缓存或冲突于容器策略，必须同时测量迁移、缓存未命中与延迟。

NUMA 与异构核心

NUMA 中内存访问成本取决于 CPU 与物理页所在节点。只迁移线程会把本地访问变成远程访问，迁移页面也有成本。异构处理器还具有不同计算容量与能耗；大核可能更快完成延迟敏感任务，小核更适合后台工作，但温度、频率、利用率、亲和性与唤醒电源域成本都会改变答案。

稳定原则是：按容量归一化负载，而非只数线程；在失衡或紧迫性超过成本前保留缓存和 NUMA 局部性；显式尊重管理约束，调度策略无法修复一个不允许任何在线 CPU 的 affinity mask。

实时调度

实时系统的正确性同时取决于结果和完成时间。“实时”不等于平均很快。硬实时 deadline 在所声明故障与负载模型下不能错过；firm deadline 的迟到结果无价值；软实时可容忍少量迟到但质量下降。

周期或 sporadic task 常由执行预算 \(C_i\)、相对 deadline \(D_i\) 和 period/最小到达间隔 \(T_i\) 描述。可信分析需要 WCET、阻塞和中断上界、CPU 模型及 admission test，平均执行时间不能证明硬保证。

速率单调与最早截止期限优先

RMS 按 period 分配固定优先级，周期越短优先级越高。在经典单核、独立、可抢占、\(D_i=T_i\) 且开销可忽略的模型中，利用率

\[U=\sum_{i=1}^{n}\frac{C_i}{T_i}\]

满足

\[U\le n(2^{1/n}-1)\]

即可保证可调度。上界随 \(n\) 增大趋近 \(\ln2\approx0.693\)，它是充分而非必要条件，超过不代表一定失败。

EDF 动态选择绝对 deadline 最早的就绪作业；在相同理想单核且隐式 deadline 模型中，任何 \(U\le1\) 的任务集都可调度。更强利用率结果不消除 admission、过载策略、deadline 队列和有界内核延迟成本。

示例 T1: C=2,D=T=5、T2: C=4,D=T=7，\(U\approx0.971\)。RMS 在时间 5 总让 T1 抢占，导致 T2 在 deadline 7 仍差一个单位；EDF 看到 T2 的 deadline 7 早于新 T1 的 10，因此先完成 T2。若 deadline 不等于 period、共享锁、存在不可抢占区或使用多核，就必须加入阻塞、抖动、迁移与多处理器干扰分析。

Linux 调度：从 CFS 到 EEVDF

Linux 提供不同类：普通 SCHED_OTHER/BATCH/IDLE、实时 SCHED_FIFO/RR 和显式 runtime/deadline/period 的 SCHED_DEADLINE。实时类可让普通工作完全得不到 CPU，因此实验必须设置资源边界和恢复路径。

CFS 的心智模型是模拟连续按权重分享 CPU 的理想处理器。任务积累 virtual runtime；权重更大时，同样真实执行使 vruntime 增长更慢。选择 vruntime 最小者，就是服务最落后于加权权益的任务。

Linux 从 6.6 起逐步让 fair class 转向 EEVDF。它分离两个问题：lag 衡量应得服务与实际服务之差，只有 lag 非负的任务具备资格；再从合格任务中选择 virtual deadline 最早者，使较短请求 slice 可以表达延迟敏感性，而不丢弃比例公平。

nice 与 cgroup cpu.weight 都是竞争下的相对权重，并非绝对预留；cpu.max 一类带宽控制才可施加 quota。其他组空闲时，有权重的组通常可以使用更多空闲 CPU。

Linux：检查调度策略与实际执行 
# 查看逐线程调度类别、实时优先级、nice 值、最近 CPU 与状态。
ps -eLo pid,tid,cls,rtprio,ni,pri,psr,stat,comm --sort=pid,tid

# 读取当前 shell 的调度策略与优先级。
chrt -p $$

# 检查为指定进程导出的调度器统计。
cat /proc/$$/sched

# 在 perf 可用时记录并显示一段简短调度时间线。
sudo perf sched record -- sleep 2

模拟并比较调度策略

离散事件模拟比手工甘特图更容易统一处理到达、抢占、完成和时间片边界，也能让 tie-breaking 成为显式规则。下面的 Python 实现对相同工作负载计算 FCFS、SJF、SRTF 与 RR。

Python：离散事件比较 FCFS、SJF、SRTF 与 Round Robin 
from collections import deque
from dataclasses import dataclass
from statistics import mean


@dataclass(frozen=True)
class Job:
    name: str
    arrival: int
    burst: int


JOBS = [
    Job("A", arrival=0, burst=8),
    Job("B", arrival=1, burst=4),
    Job("C", arrival=2, burst=2),
    Job("D", arrival=4, burst=1),
]


def append_segment(timeline, name, start, end):
    """追加一个区间，并合并同一任务的相邻运行段。"""
    if timeline and timeline[-1][0] == name and timeline[-1][2] == start:
        old_name, old_start, _ = timeline[-1]
        timeline[-1] = (old_name, old_start, end)
    else:
        timeline.append((name, start, end))


def run_non_preemptive(jobs, policy):
    """运行 FCFS 或 SJF；任务一旦被选中便占用 CPU 直至完成。"""
    pending = list(jobs)
    timeline = []
    now = min(job.arrival for job in pending)

    while pending:
        ready = [job for job in pending if job.arrival <= now]
        if not ready:
            # 没有可运行任务：把模拟时间推进到下一次到达。
            now = min(job.arrival for job in pending)
            ready = [job for job in pending if job.arrival <= now]

        if policy == "FCFS":
            job = min(ready, key=lambda item: (item.arrival, item.name))
        elif policy == "SJF":
            job = min(ready, key=lambda item: (item.burst, item.arrival, item.name))
        else:
            raise ValueError(f"unknown non-preemptive policy: {policy}")

        append_segment(timeline, job.name, now, now + job.burst)
        now += job.burst
        pending.remove(job)

    return timeline


def run_srtf(jobs):
    """在每个整数时间单位重新选择剩余时间最短的任务。"""
    remaining = {job.name: job.burst for job in jobs}
    by_name = {job.name: job for job in jobs}
    timeline = []
    now = min(job.arrival for job in jobs)

    while any(value > 0 for value in remaining.values()):
        ready = [
            job for job in jobs
            if job.arrival <= now and remaining[job.name] > 0
        ]
        if not ready:
            now = min(
                job.arrival for job in jobs
                if remaining[job.name] > 0 and job.arrival > now
            )
            continue

        job = min(
            ready,
            key=lambda item: (remaining[item.name], item.arrival, item.name),
        )
        append_segment(timeline, job.name, now, now + 1)
        remaining[job.name] -= 1
        now += 1

    return timeline


def run_round_robin(jobs, quantum):
    """先加入时间片期间到达的任务，再把时间片耗尽的任务重新入队。"""
    pending = deque(sorted(jobs, key=lambda item: (item.arrival, item.name)))
    ready = deque()
    remaining = {job.name: job.burst for job in jobs}
    timeline = []
    now = pending[0].arrival

    while pending or ready:
        while pending and pending[0].arrival <= now:
            ready.append(pending.popleft())

        if not ready:
            now = pending[0].arrival
            continue

        job = ready.popleft()
        duration = min(quantum, remaining[job.name])
        append_segment(timeline, job.name, now, now + duration)
        now += duration
        remaining[job.name] -= duration

        # 边界时刻到达的任务先入队，随后才重新加入刚耗尽时间片的任务。
        while pending and pending[0].arrival <= now:
            ready.append(pending.popleft())
        if remaining[job.name] > 0:
            ready.append(job)

    return timeline


def calculate_metrics(jobs, timeline):
    """从执行轨迹推导首次开始时间与完成时间。"""
    first_start = {}
    completion = {}
    for name, start, end in timeline:
        first_start.setdefault(name, start)
        completion[name] = end

    rows = []
    for job in jobs:
        turnaround = completion[job.name] - job.arrival
        waiting = turnaround - job.burst
        response = first_start[job.name] - job.arrival
        rows.append((job.name, waiting, response, turnaround))
    return rows


def print_report(name, jobs, timeline):
    rows = calculate_metrics(jobs, timeline)
    gantt = " | ".join(f"{job} {start}-{end}" for job, start, end in timeline)
    print(f"{name:4}  {gantt}")
    print(
        "      averages: "
        f"wait={mean(row[1] for row in rows):.2f}, "
        f"response={mean(row[2] for row in rows):.2f}, "
        f"turnaround={mean(row[3] for row in rows):.2f}"
    )


experiments = {
    "FCFS": run_non_preemptive(JOBS, "FCFS"),
    "SJF": run_non_preemptive(JOBS, "SJF"),
    "SRTF": run_srtf(JOBS),
    "RR": run_round_robin(JOBS, quantum=2),
}

for policy_name, execution_trace in experiments.items():
    print_report(policy_name, JOBS, execution_trace)

模拟结果只有在模型一致时才可比较。应记录到达顺序、同时间事件规则、是否计算切换开销、burst 是否已知、I/O 阻塞和测量窗口。把理想算法排名直接映射到生产内核通常是类别错误。

对比与总结

策略 抢占？ 所需信息/状态 主要优势 主要风险
FCFS 否 到达顺序 开销低、顺序透明 护航效应，短作业响应差
SJF 否 完整 burst 预测 理想条件下平均等待最小 预测误差、饥饿、无法中途反应
SRTF 是 剩余时间预测 已知大小时平均 flow time 优秀 长作业饥饿、频繁抢占
RR 是 FIFO 队列与 quantum 同行轮转有界、首次响应好 小 quantum 开销，缺少组公平
严格优先级 可选 可信优先级 保护明确紧急类别 饥饿与优先级反转
MLFQ 是 多队列加使用历史 适应交互与 CPU-bound 阶段 参数复杂，需防作弊
Lottery 通常是 tickets 与随机数 比例份额灵活 短期方差
Stride 通常是 tickets、stride、pass 确定性比例份额 动态成员与归一化复杂
RMS 是 period 与 WCET 固定优先级可分析 充分上界保守、假设严格
EDF 是 deadline 与预算 理想单核利用率强 过载和实现需严格控制
CFS/EEVDF 是 权重、虚拟时间、lag、虚拟 deadline 实用的加权公平与延迟感知 仍受层次、放置和实现细节影响

调度分析应先声明目标和模型，再报告多项指标及分布。平均等待最小不等于响应、公平、尾延迟、能耗或 deadline 最优；多核上还必须把迁移与局部性纳入决策。
