虚拟化、容器与现代内核设计

cat input.txt | grep kernel > result.txt

进程虚拟化 CPU 和地址空间，虚拟机进一步虚拟化整台机器，使客户机内核也成为受约束的软件；容器则不创建客户机硬件，而是用 namespace、cgroup、capability、文件系统和安全策略隔离共享宿主内核的进程。

本章把这些技术放在“边界位于哪里”这一坐标上，而不是比较营销标签。我们还回到内核架构、xv6/Linux/seL4、RCU、eBPF、confidential computing 和 serverless microVM，理解现代系统如何在兼容性、性能、TCB、可验证性和启动成本之间移动边界。

为什么要虚拟化计算机？

整合、隔离、可移植性与管理

  • 整合：在一台物理机上运行多个相互独立系统，提高利用率并控制配额。
  • 隔离：把客户机故障和管理权限限制在虚拟硬件边界内；边界强度仍取决于 hypervisor、固件与共享设备。
  • 可移植性：把软件连同 OS 环境封装为镜像，在兼容虚拟硬件或 runtime 上部署。
  • 管理：支持 snapshot、clone、live migration、弹性供应和不同内核版本共存。

虚拟化不是免费抽象。它增加地址翻译层、虚拟 I/O、调度嵌套、镜像状态和新的管理面。收益来自更强边界与操作能力，而不是所有工作负载都更快。

Hypervisor 架构

Type 1 与 Type 2 Hypervisor

Type 1/bare-metal hypervisor 直接控制硬件并承载 guest；Type 2/hosted hypervisor 作为宿主 OS 上的应用运行。分类有助理解主要控制层，但现实系统会分布职责：Linux KVM 把 CPU/内存虚拟化放在内核，QEMU 用户进程提供设备模型和管理。

评价时应具体问：谁调度 vCPU，谁模拟设备，谁管理 guest 物理内存，哪个组件能访问 guest 数据，管理 daemon 是否属于 TCB，而不是只依赖类型编号。

全虚拟化与半虚拟化

全虚拟化向 guest 暴露与真实硬件兼容的接口，使未修改 OS 运行；敏感操作由 trap/emulation 或硬件辅助处理。半虚拟化让 guest 知道自己在虚拟环境中，使用 hypercall 或 virtio 等高效接口，减少昂贵模拟。

现代 VM 常混合两者：CPU 和内存依赖硬件虚拟化，启动保留兼容设备，性能路径使用 virtio，特定设备再采用 passthrough。

检查 Linux 主机是否暴露硬件虚拟化 
# 首先识别运行环境；结果可能是 none、kvm、vmware、
# microsoft、wsl、docker、podman 或其他已识别环境。
systemd-detect-virt || true

# 当处理器与固件暴露硬件虚拟化支持时，CPU 标志通常在 Intel 上
# 包含 vmx，在 AMD 上包含 svm。
lscpu | grep -E 'Virtualization|Hypervisor vendor|Flags'

# KVM 用户空间会打开 /dev/kvm；其权限决定谁可以
# 创建 VM，仅存在该设备并不代表当前用户有权访问。
ls -l /dev/kvm 2>/dev/null || echo '/dev/kvm is not available'

# 已加载模块显示通用 KVM 核心与体系结构后端。
lsmod | grep -E '^kvm(_intel|_amd)?\b' || true

# 不要把 VM 内缺少标志视为物理 CPU 不支持的证据；
# 外层 hypervisor 可能隐藏了嵌套虚拟化能力。

容器或嵌套 VM 中看不到 virtualization flag 不一定代表物理 CPU 不支持，可能只是上层未暴露。

CPU 虚拟化

Trap-and-Emulate 与硬件辅助

经典 trap-and-emulate 让普通 guest 指令直接执行，敏感操作陷入 VMM，由其模拟效果。某些旧 ISA 的敏感指令并不总会 trap，曾需要 binary translation 或 paravirtualization。Intel VT-x/AMD-V 增加 root/non-root 模式与 VM control structure，让 guest 内核可在受约束的“特权态”运行。

VM exit 可能来自 I/O、敏感寄存器、中断窗口、二级页故障或管理请求。VMM 检查 exit reason、模拟或更新状态，再 VM-entry。过多 exit 会破坏缓存和流水，因此现代虚拟设备与 interrupt virtualization 尽量减少频率。

x86 Linux 上的最小 KVM 控制循环 C 示例 
// 这是面向 Linux/x86 的紧凑教学 VMM：创建一个 vCPU，映射一页
// 客户机 RAM，运行少量实模式指令，处理端口 I/O，
// 并在 HLT 时停止。生产 VMM 还需要稳健的设备、中断、内存、
// 迁移、固件、并发与安全模型。

#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <linux/kvm.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <unistd.h>

static void fail(const char *what) {
    perror(what);
    exit(EXIT_FAILURE);
}

int main(void) {
    // mov dx, 0x3f8; mov al, 'H'; out dx, al; hlt
    const uint8_t guest_code[] = {0xba, 0xf8, 0x03, 0xb0, 0x48, 0xee, 0xf4};

    int kvm = open("/dev/kvm", O_RDWR | O_CLOEXEC);
    if (kvm < 0) fail("open /dev/kvm");
    if (ioctl(kvm, KVM_GET_API_VERSION, 0) != KVM_API_VERSION) {
        fprintf(stderr, "unexpected KVM API version\n");
        return EXIT_FAILURE;
    }

    // VM 文件描述符拥有虚拟机范围的状态。
    int vm = ioctl(kvm, KVM_CREATE_VM, 0);
    if (vm < 0) fail("KVM_CREATE_VM");

    // 用户空间分配 RAM，并告知 KVM 它支撑哪个客户机物理地址范围。
    size_t ram_size = 0x1000;
    uint8_t *ram = mmap(NULL, ram_size, PROT_READ | PROT_WRITE,
                        MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (ram == MAP_FAILED) fail("mmap guest RAM");
    memcpy(ram, guest_code, sizeof guest_code);

    struct kvm_userspace_memory_region region = {
        .slot = 0,
        .guest_phys_addr = 0,
        .memory_size = ram_size,
        .userspace_addr = (uintptr_t)ram,
    };
    if (ioctl(vm, KVM_SET_USER_MEMORY_REGION, &region) < 0)
        fail("KVM_SET_USER_MEMORY_REGION");

    // vCPU 文件描述符拥有体系结构 CPU 状态。
    int vcpu = ioctl(vm, KVM_CREATE_VCPU, 0);
    if (vcpu < 0) fail("KVM_CREATE_VCPU");
    int run_size = ioctl(kvm, KVM_GET_VCPU_MMAP_SIZE, 0);
    if (run_size < (int)sizeof(struct kvm_run)) fail("KVM_GET_VCPU_MMAP_SIZE");
    struct kvm_run *run = mmap(NULL, (size_t)run_size,
                               PROT_READ | PROT_WRITE, MAP_SHARED, vcpu, 0);
    if (run == MAP_FAILED) fail("mmap kvm_run");

    // 从客户机地址 0 的简单实模式布局开始。
    struct kvm_sregs sregs;
    if (ioctl(vcpu, KVM_GET_SREGS, &sregs) < 0) fail("KVM_GET_SREGS");
    sregs.cs.base = 0;
    sregs.cs.selector = 0;
    if (ioctl(vcpu, KVM_SET_SREGS, &sregs) < 0) fail("KVM_SET_SREGS");

    struct kvm_regs regs = {.rip = 0, .rflags = 0x2};
    if (ioctl(vcpu, KVM_SET_REGS, &regs) < 0) fail("KVM_SET_REGS");

    for (;;) {
        // KVM_RUN 进入客户机模式；遇到用户空间出口时 ioctl 返回。
        if (ioctl(vcpu, KVM_RUN, 0) < 0) {
            if (errno == EINTR) continue;
            fail("KVM_RUN");
        }

        switch (run->exit_reason) {
        case KVM_EXIT_IO:
            // 本演示接受向串行 I/O 端口写入一个字节。
            if (run->io.direction == KVM_EXIT_IO_OUT &&
                run->io.port == 0x3f8 && run->io.size == 1) {
                uint8_t *data = (uint8_t *)run + run->io.data_offset;
                fwrite(data, 1, run->io.count, stdout);
                fflush(stdout);
            } else {
                fprintf(stderr, "unexpected I/O exit\n");
                return EXIT_FAILURE;
            }
            break;
        case KVM_EXIT_HLT:
            putchar('\n');
            return EXIT_SUCCESS;
        case KVM_EXIT_FAIL_ENTRY:
            fprintf(stderr, "failed VM entry: 0x%llx\n",
                    (unsigned long long)run->fail_entry.hardware_entry_failure_reason);
            return EXIT_FAILURE;
        case KVM_EXIT_INTERNAL_ERROR:
            fprintf(stderr, "KVM internal error\n");
            return EXIT_FAILURE;
        default:
            fprintf(stderr, "unhandled KVM exit reason: %u\n", run->exit_reason);
            return EXIT_FAILURE;
        }
    }
}
cc -std=c11 -Wall -Wextra -O2 tiny_kvm.c -o tiny_kvm
./tiny_kvm
# 预期输出：H

示例只展示 /dev/kvm、VM、vCPU、guest memory 和 exit loop 的骨架，不是安全完整 VMM；真实系统还需设备、固件、中断、并发和生命周期管理。

内存虚拟化

影子页表与嵌套翻译

Guest virtual address（GVA）先由 guest 页表映射到 guest physical address（GPA），再由 hypervisor 映射到 host physical address（HPA）。

Shadow page table 由 VMM 在软件中合成 GVA->HPA 映射，guest 修改页表时需 trap 或跟踪；nested paging（Intel EPT/AMD NPT）让硬件联合遍历 guest 和二级页表，减少页表写 trap，但 miss 时潜在访存次数更多。

TLB 会缓存组合后的翻译，ASID/VPID/PCID 减少切换 flush。Huge page 可增加 reach，但两级页大小、内存碎片和迁移 dirty tracking 都会影响是否可用。

Python：模拟两级翻译与权限交集 
from dataclasses import dataclass


@dataclass(frozen=True)
class Mapping:
    frame: int
    read: bool = True
    write: bool = False
    execute: bool = False


PAGE_SIZE = 4096


def translate(gva: int, access: str,
              guest_pt: dict[int, Mapping],
              nested_pt: dict[int, Mapping]) -> int:
    """完成 GVA -> GPA -> HPA 转换，并执行两阶段权限检查。"""
    guest_vpn, offset = divmod(gva, PAGE_SIZE)

    # 阶段 1 由客户机 OS 为其某个进程选择。
    guest = guest_pt.get(guest_vpn)
    if guest is None:
        raise MemoryError("guest page fault: no GVA -> GPA mapping")

    # 客户机页框号就是客户机物理页号。
    guest_pfn = guest.frame

    # 阶段 2 由 hypervisor 控制，并强制执行 VM 所有权。
    nested = nested_pt.get(guest_pfn)
    if nested is None:
        raise MemoryError("nested fault: GPA has no host backing")

    # 只有两个阶段都授权时，访问才被允许。
    permission = {
        "read": guest.read and nested.read,
        "write": guest.write and nested.write,
        "execute": guest.execute and nested.execute,
    }
    if not permission[access]:
        raise PermissionError(f"{access} denied by composed permissions")

    return nested.frame * PAGE_SIZE + offset


guest_pt = {
    0x4: Mapping(frame=0x20, read=True, write=True),
}
nested_pt = {
    # Hypervisor 刻意把该页暴露为只读。
    0x20: Mapping(frame=0x9A, read=True, write=False),
}

gva = 0x4 * PAGE_SIZE + 123
print(hex(translate(gva, "read", guest_pt, nested_pt)))  # 0x9a07b

try:
    translate(gva, "write", guest_pt, nested_pt)
except PermissionError as error:
    print(error)  # 客户机写权限无法覆盖嵌套页表的只读限制

最终权限是 guest 与 hypervisor 两级允许集合的交集。Guest PTE 可写但 EPT 只读时，访问仍会二级 fault；这让 VMM 能追踪 dirty page 或保护共享内存。

I/O 虚拟化

模拟、半虚拟化设备与直通

  • 设备模拟：呈现已知硬件寄存器，guest 无需专用驱动，兼容好但每次访问模拟成本高。
  • Paravirtualized device：guest 驱动与后端用共享 descriptor ring/virtqueue 交换缓冲，减少寄存器 exit 与复制。
  • Passthrough：IOMMU 把物理设备或 SR-IOV virtual function 直接分配给 guest，性能接近原生，但迁移、共享和后端观察更难。

直通安全依赖 IOMMU 正确限制 DMA、interrupt remapping 和设备 reset 隔离；有缺陷设备或共享物理功能仍可能扩大故障域。

检查 Linux guest/host 的虚拟设备与 assigned device 
# 查看 PCI 身份、已选内核驱动与候选模块。
lspci -nnk

# Virtio 设备通常绑定到名称含 virtio 的驱动。
find /sys/bus/virtio/devices -maxdepth 2 -type l -name driver \
  -exec sh -c 'printf "%s -> " "$1"; readlink "$1"' sh {} \; 2>/dev/null

# IOMMU 组是 VFIO 暴露的隔离单位；同组设备可能
# 无法由平台拓扑独立隔离。
for group in /sys/kernel/iommu_groups/*; do
  [ -d "$group/devices" ] || continue
  printf 'group %s: ' "${group##*/}"
  find "$group/devices" -mindepth 1 -maxdepth 1 -printf '%f '
  printf '\n'
done

虚拟机生命周期与迁移

VM 生命周期包括创建镜像、分配 vCPU/内存/设备、启动、pause、snapshot、restore、迁移和销毁。Snapshot 必须协调 CPU、内存和设备状态；只复制磁盘而不 quiesce 应用可能等价于突然掉电，而不是一致备份。

Live migration 的 pre-copy 在 VM 运行时反复复制内存，追踪每轮 dirty page，最后短暂停机复制剩余状态；dirty rate 接近网络复制率时可能不收敛。Post-copy 先迁移最小 CPU 状态并恢复目标，缺页时从源拉取，其停机短但迁移期间源/目标任一失败风险更高。

模拟一个 pre-copy 工作负载是否收敛 
def precopy_rounds(memory_gib: float, dirty_mib_s: float,
                   bandwidth_mib_s: float, stop_mib: float,
                   max_rounds: int = 12):
    """返回每轮简化预复制结果与估计的最终停机时间。"""
    remaining = memory_gib * 1024
    rounds = []

    for number in range(max_rounds):
        transfer_seconds = remaining / bandwidth_mib_s
        dirtied_during_round = dirty_mib_s * transfer_seconds
        rounds.append({
            "round": number,
            "sent_mib": remaining,
            "seconds": transfer_seconds,
            "redirtied_mib": dirtied_during_round,
        })

        remaining = min(memory_gib * 1024, dirtied_during_round)
        if remaining <= stop_mib:
            break

    # stop-and-copy 阶段会暂停 vCPU，并迁移最后一批页面。
    downtime_seconds = remaining / bandwidth_mib_s
    return rounds, remaining, downtime_seconds


for dirty_rate in (50, 300, 900):
    rounds, final_dirty, downtime = precopy_rounds(
        memory_gib=8,
        dirty_mib_s=dirty_rate,
        bandwidth_mib_s=1000,
        stop_mib=64,
    )
    print(
        f"dirty={dirty_rate:>3} MiB/s "
        f"rounds={len(rounds):>2} final={final_dirty:7.1f} MiB "
        f"downtime~{downtime * 1000:6.1f} ms"
    )

迁移还需处理共享存储、网络地址、设备状态、时间、NUMA 与目标 CPU 特性。兼容 CPU baseline 会牺牲部分新指令以换取迁移范围。

容器隔离

容器是宿主上的普通进程，其边界由多种内核机制交集形成。Namespace 改变系统视图，cgroup 治理资源，capability 与 no_new_privs 削减权限，seccomp/LSM 限制操作，layered root filesystem 提供镜像与每容器可写层，OCI runtime 配置并启动进程。

Namespaces、cgroups、Capabilities 与分层文件系统

Namespace 不限制资源；cgroup 不改变路径视图；capability 削减不替代 syscall/object policy；只读镜像不阻止内存或网络攻击。容器必须以组合方式配置，并避免 privileged、host PID/network、危险 mount、设备和过宽 capabilities。

OverlayFS 将多个只读 lower layer 与每容器 writable upper 合并。读取先看到 upper，否则 lower；首次修改 lower 对象时 copy-up 到 upper；删除 lower 对象可用 whiteout 隐藏。

Copy-up 会造成首次写延迟和空间放大，inode/metadata、rename 和 hard link 语义也需理解。容器镜像层适合部署，不等于持久数据卷或备份。

虚拟机与容器比较

维度 容器 虚拟机
内核 共享宿主内核 每个 guest 有独立内核
边界 进程/namespace/策略组合 虚拟硬件与 hypervisor
启动与密度 通常更快、更密集 通常更多状态和内存
OS 兼容 需与宿主内核 ABI 兼容 可运行不同 guest OS/内核
攻击面 宿主 syscall 面直接可达 主要是虚拟设备、hypercall 与 VMM
管理 镜像层、runtime、编排 VM 镜像、固件、虚拟设备、迁移

边界强度并非绝对：错误配置的 VM 可通过共享目录/管理面暴露，强化容器可用用户 namespace、最小 syscall、只读 root、LSM 和 microVM 包装增强。选择取决于租户互信、内核兼容、启动时延、设备和运维。

比较内核架构

单体、微内核、Exokernel 与 Unikernel

  • 单体：大多数服务和驱动共享特权地址空间，调用高效、生态成熟，但 TCB 和故障域大。
  • 微内核：只保留调度、地址空间、IPC 等最小机制，服务在隔离用户进程中，故障可控、分析边界清晰，但 IPC 与协调更多。
  • Exokernel：内核保护并复用低层资源，library OS 为应用实现抽象，专用化强，兼容与共享复杂。
  • Unikernel：把单个应用和所需 OS 库链接为专用镜像，状态和攻击面可小，调试、更新、多进程隔离和通用兼容较弱。

架构名称不决定质量。高性能微内核可优化 IPC，单体内核可用语言安全、模块边界和验证缩小风险；应比较具体保护域、接口、TCB 和故障恢复。

教学内核与生产内核

xv6、Linux 与经过验证的微内核

xv6 以小而完整的 Unix-like 路径展示 trap、进程、页表、锁和文件系统，适合从头阅读，但缺少生产硬件、SMP 扩展、安全和兼容复杂度。Linux 覆盖广泛设备、文件系统、网络、调度、容器和观测，优化与兼容使路径更难整体阅读。

seL4 以 capability 微内核和形式化验证著名。验证证明的是明确模型、代码版本、编译/硬件假设下的属性，不意味着驱动、用户服务器、配置和物理平台自动安全。真正价值在于把保证边界写清并机器检查。

现代内核机制

RCU、eBPF 与可扩展观测

RCU 让读者在很少同步开销下读取已发布指针；更新者创建新版本、原子发布，并等待所有可能看到旧版本的既有读者经过 grace period 后回收。

内核风格 C 中的 RCU 保护替换模式 
// 这是简化的内核风格模式；真实代码必须选择正确的 RCU
// 变体、分配上下文、链表原语、锁与错误处理。

struct config {
    int threshold;
    struct rcu_head rcu;
};

static struct config __rcu *current_config;

int read_threshold(void)
{
    int value;

    // 读侧临界区保证，通过 RCU 指针取得的对象在
    // rcu_read_unlock() 之后才可能被回收。
    rcu_read_lock();
    struct config *cfg = rcu_dereference(current_config);
    value = cfg->threshold;
    rcu_read_unlock();

    return value;
}

int replace_threshold(int new_value)
{
    struct config *new_cfg = kmalloc(sizeof(*new_cfg), GFP_KERNEL);
    if (!new_cfg)
        return -ENOMEM;

    // 发布指针前完成初始化。
    new_cfg->threshold = new_value;

    // 如果多个写者可能竞争，还需要独立的更新锁。
    struct config *old = rcu_replace_pointer(current_config, new_cfg, true);

    // 替换前开始的读者可能仍在使用 old，因此应把它的
    // 释放推迟到宽限期之后，而不是立即回收。
    if (old)
        kfree_rcu(old, rcu);

    return 0;
}

eBPF 允许程序装入内核定义 hook。Verifier 检查控制流、类型、边界、helper 和终止性等约束，通过后 JIT/解释执行；map 在内核程序与用户控制器之间交换状态。

Verifier 降低但不消除风险：内核/verifier/JIT bug、过宽 attach 权限、敏感数据外泄和高事件开销仍需治理。生产观测应限制程序来源、map 容量、采样和符号隐私。

研究与演进前沿

机密计算、Library OS 与 Serverless 隔离

Confidential VM 用内存加密和 attestation 降低宿主/hypervisor 读取 guest 私有内存的能力，但仍需信任 CPU/firmware、guest 软件和 attestation 验证，I/O 与 side channel 也有边界。Library OS 在窄 PAL 上提供应用所需 OS 接口，适合 enclave、unikernel 或兼容层。Serverless microVM 通过精简设备模型、预热 snapshot 和快速恢复，在比容器更强边界下追求毫秒级启动。

这些方向都不是“同时获得全部优点”。加密内存增加 attestation/设备复杂度，library OS 缩小接口却承担兼容，microVM 快速启动依赖镜像优化和池化。研究问题应具体到威胁模型、启动分布、内存密度与可操作性。

原生、容器和 VM 中运行贯穿管道

cat input.txt | grep kernel > result.txt

管道内部 Unix 语义保持相似：shell 创建进程和 pipe，cat/grep 使用 fd，内核调度和处理 page fault/I/O。变化的是这些操作由哪一层负责和在哪里受到约束。

  • 原生：宿主内核直接解析路径、调度线程和访问设备。
  • 容器：同一宿主内核执行系统调用，但 namespace 改变路径/PID/network 视图，cgroup 和策略限制资源与权限，overlay/volume 决定存储路径。
  • VM：guest 内核处理进程、页表、文件系统和虚拟设备；hypervisor 再调度 vCPU、翻译 guest memory 并把虚拟 I/O 送到宿主后端。
在三种环境中运行并比较管道 
# 在新的工作目录中准备一份确定性输入。
demo_dir=$(mktemp -d)
cd "$demo_dir"
printf '%s\n' \
  'user code enters through a system call' \
  'the kernel creates and schedules both processes' \
  'a container shares the host kernel' \
  'a virtual machine has a guest kernel' > input.txt

# 1. 原生：主机 shell、主机进程、主机内核与主机文件系统。
cat input.txt | grep kernel > result.native.txt

# 观察进程/文件描述符系统调用，不跟踪每个库调用。
strace -f -o native.trace \
  -e trace=pipe,pipe2,clone,fork,vfork,execve,dup2,close,openat,read,write \
  sh -c 'cat input.txt | grep kernel > result.native.traced.txt'

# 2. 容器：命令来自镜像，而当前目录作为数据
# 被挂载；进程仍进入主机 Linux 内核。
podman run --rm \
  --network none --cap-drop all --security-opt no-new-privileges \
  --memory 128m --pids-limit 32 \
  -v "$PWD:/work:Z" -w /work \
  docker.io/library/alpine:latest \
  sh -c 'cat input.txt | grep kernel > result.container.txt'

# 3. VM：把输入复制到准备好的 Linux VM，并通过客户机内核运行。
# 将 VM_HOST 设置为你管理的 SSH 目标，例如 student@192.0.2.10。
: "${VM_HOST:?set VM_HOST to your Linux VM SSH target}"
scp input.txt "$VM_HOST:/tmp/os11-input.txt"
ssh "$VM_HOST" \
  "cat /tmp/os11-input.txt | grep kernel > /tmp/os11-result.txt"
scp "$VM_HOST:/tmp/os11-result.txt" result.vm.txt

# 尽管执行路径不同，语义输出应保持一致。
sha256sum result.native.txt result.container.txt result.vm.txt

# 主机侧观察会暴露不同层次。
printf 'native/container host: '; uname -r
podman inspect --format \
  'container pid={{.State.Pid}} image={{.ImageName}}' \
  --latest 2>/dev/null || true
ssh "$VM_HOST" 'printf "guest kernel: "; uname -r; cat /proc/1/cgroup'

比较应控制输入、缓存状态、CPU/内存配额、存储 backing 和观测开销。一次短命令的启动差异不能代表长期服务的稳态吞吐与隔离质量。

对比与总结

设计 主要虚拟化/隔离对象 边界优势 主要成本与风险
原生进程 地址空间、凭据、fd 最少额外层、POSIX 组合自然 共享宿主内核与系统视图
容器 进程视图、资源、权限、根文件系统 启动快、密度高、部署一致 组合配置复杂、共享内核攻击面
VM CPU、物理内存、设备与完整 guest OS 独立内核、OS 兼容与强边界 更多状态、嵌套翻译和虚拟 I/O
MicroVM 精简 VM 边界 较强隔离与较快启动折衷 功能/设备受限、池化复杂
Microkernel 最小特权机制与用户态服务 小 TCB、服务故障隔离 IPC 和系统级协调
Unikernel/Library OS 应用专用 OS 服务 小镜像、专用化 通用兼容、调试和共享弱

完整操作系统体系最终回到边界选择：硬件 privilege 隔离用户与内核；进程隔离地址空间；容器组合共享内核中的视图和资源边界；VM 在虚拟硬件处隔离 guest 内核；微内核和 library OS 又重新安排哪些服务进入特权域。没有抽象能消除底层成本，只能把它移动到更适合当前安全、性能与运维目标的位置。
