同步、并发正确性与活性

cat input.txt | grep kernel > result.txt

线程和 IPC 让多个活动重叠，但也使结果取决于看不见的交错、编译器优化、CPU 内存序和调度。同步（synchronization）不是“给代码加锁”的同义词，而是建立可证明的原子性、可见性、顺序和进展条件。

本章从丢失更新出发，依次建立 memory model、原子读改写、锁、条件变量、信号量、屏障、经典问题、死锁与 lock-free/RCU。阅读任何并发设计时都应先写出不变量，再问：哪些操作必须原子发生？哪个事件使另一个线程可见？等待条件由谁改变？若线程暂停或崩溃，其他线程还能否前进？

并发程序为何困难？

交错与非确定性

高级语句常展开为多个机器操作：

register = load(counter)       // 从共享计数器加载
register = register + 1       // 在寄存器中递增
store(counter, register)      // 写回共享计数器

两个线程都执行 counter++ 时，可以同时读到旧值，再各自写入同一个新值，于是两次增量只保留一次。

操作系统调度、缓存未命中、中断和 I/O 会改变交错；编译器还可在语言规则允许时重排或删除访问。调试输出常改变时序，因此“加一行日志后错误消失”并不表示问题解决。

C：故意制造的 pthread 数据竞争 
#include <pthread.h>
#include <stdio.h>

enum { ITERATIONS = 1000000 };
static long counter = 0;

static void *increment(void *unused) {
    (void)unused;
    for (long i = 0; i < ITERATIONS; ++i) {
        counter++;  // Data race: read-modify-write is not synchronized.
    }
    return NULL;
}

int main(void) {
    pthread_t first;
    pthread_t second;

    if (pthread_create(&first, NULL, increment, NULL) != 0) {
        fputs("first pthread_create failed\n", stderr);
        return 1;
    }

    if (pthread_create(&second, NULL, increment, NULL) != 0) {
        fputs("second pthread_create failed\n", stderr);
        pthread_join(first, NULL);
        return 1;
    }

    int first_join = pthread_join(first, NULL);
    int second_join = pthread_join(second, NULL);
    if (first_join != 0 || second_join != 0) {
        fputs("pthread_join failed\n", stderr);
        return 1;
    }
    printf("counter = %ld; expected = %d\n", counter, 2 * ITERATIONS);
    return 0;
}

安全性与活性属性

安全性（safety）表示坏事永远不会发生，例如队列计数不越界、两个线程不会同时处于互斥临界区。活性（liveness）表示好事最终会发生，例如等待者最终获得锁、已提交请求最终完成。

进一步可区分：deadlock-free 保证系统中至少有人推进；starvation-free 保证每个持续合格参与者最终推进；wait-free 则要求每个操作在有限自身步骤内完成。越强的保证通常需要更严格的算法与资源假设。

正确性必须说明观察模型。仅在一次测试中输出正确，不能证明所有允许调度都安全；“没有死锁”也不能证明没有饥饿或 livelock。

竞态条件与临界区

竞态条件（race condition）是结果或正确性依赖不受控时序。语言层面的 data race 通常更具体：不同线程并发访问同一内存位置、至少一个写入，且访问既非原子也没有 happens-before 关系。在 C/C++ 中，data race 会造成未定义行为，而不只是偶尔得到旧值。

临界区（critical section）是访问共享不变量、必须受协议保护的代码。目标不是把整段程序串行化，而是让从一个合法共享状态到下一个合法状态的转换具有所需原子性。

原子性、可见性与顺序

  • 原子性：其他线程不能观察操作的中间状态。
  • 可见性：一个线程完成的写入何时能被另一个线程观察到。
  • 顺序：不同操作之间哪些先后关系必须保留。

三者互不替代。单个原子 flag 不会自动让附近普通数据安全；互斥锁既提供排他，也通过 acquire/release 语义发布临界区内写入。修复计数器可用锁：

static pthread_mutex_t counter_lock = PTHREAD_MUTEX_INITIALIZER;
static long counter;

void increment_counter(void) {
    pthread_mutex_lock(&counter_lock);
    counter++;
    pthread_mutex_unlock(&counter_lock);
}

锁保护的是“计数器不变量”，而不是某一行语法。所有访问该不变量的路径都必须遵守同一协议。

内存模型

内存模型定义哪些执行和观察是允许的。sequenced-before 描述单线程语言顺序；原子 release 与观察到它的 acquire 之间建立 synchronizes-with；二者的传递闭包形成 happens-before。

写线程：普通初始化 -> RELEASE 发布
读线程：ACQUIRE 观察 -> 普通使用
C11：使用 release/acquire 安全发布初始化数据 
#include <stdatomic.h>
#include <stdbool.h>
#include <stdio.h>

struct payload {
    int value;
    char message[32];
};

static struct payload shared_payload;
static atomic_bool ready = ATOMIC_VAR_INIT(false);

void producer(void) {
    // 这些普通写入在发布之前仅对写线程可见。
    shared_payload.value = 42;
    snprintf(shared_payload.message, sizeof shared_payload.message,
             "initialized");

    // 向执行匹配 acquire 的读线程发布此前的全部写入。
    atomic_store_explicit(&ready, true, memory_order_release);
}

bool try_consume(void) {
    if (!atomic_load_explicit(&ready, memory_order_acquire)) {
        return false;
    }

    // acquire 已观察到 release 发布，因此这里的读取是安全的。
    printf("%d %s\n", shared_payload.value, shared_payload.message);
    return true;
}

Relaxed atomic 只保证该原子对象自身读写不可撕裂和修改顺序，不发布周边普通数据。Sequential consistency 最易推理但可能限制优化；正确做法是先证明所需关系，再选择最弱且仍正确的序，而不是凭性能直觉削弱。

同步的硬件支持

关闭中断及其局限

单核内核可在很短区域关闭本地中断，避免同一 CPU 上中断处理器抢占当前代码；用户程序无权这样做，多核上也不能阻止其他 CPU 并发访问。长时间关闭中断会损害时延并可能丢失服务，因此它只适合底层、局部且有严格上界的机制，不是通用互斥方案。

Test-and-Set、Compare-and-Swap 与 Fetch-and-Add

原子 read-modify-write 在一个不可分割动作中读取旧值并写新值：exchange/test-and-set 适合简单锁；CAS 仅在当前值等于预期时更新，是许多 lock-free 算法基础；fetch-and-add 返回旧值并加增量，可分配唯一票号。

#include <stdatomic.h>

typedef struct {
    atomic_flag held;
} spinlock_t;

#define SPINLOCK_INIT { ATOMIC_FLAG_INIT }

void spin_lock(spinlock_t *lock) {
    while (atomic_flag_test_and_set_explicit(&lock->held,
                                              memory_order_acquire)) {
        // 在生产环境中，应使用体系结构的暂停提示与有界等待策略。
    }
}

void spin_unlock(spinlock_t *lock) {
    atomic_flag_clear_explicit(&lock->held, memory_order_release);
}

原子指令仍会引发缓存行所有权转移和争用。CAS 循环还面临 ABA、内存回收和失败重试问题；“无锁”并不等于没有同步成本。

内存屏障

屏障约束编译器和处理器对内存操作的重排，并配合缓存一致性形成可见顺序。屏障不是刷新全部缓存，也不能把非原子数据竞争变安全。语言级原子和锁应是应用首选，因为编译器能把其语义正确映射到不同体系结构；直接使用硬件 fence 需要同时理解语言模型、编译器和 CPU。

互斥锁

自旋锁与互斥量

自旋锁在等待时持续检查，避免睡眠/唤醒开销，适合临界区极短、持有者会很快运行且不能睡眠的内核路径；过度自旋会浪费 CPU 和共享互连带宽。mutex 在长等待时让线程睡眠，常见实现先尝试用户态原子 fast path，争用时才进入 futex 等内核等待机制。

pthread_mutex_lock(&mutex);
while (!predicate()) {
    pthread_cond_wait(&condition, &mutex);
}
use_state_that_satisfies_predicate();
pthread_mutex_unlock(&mutex);

锁的契约还包括所有权、是否可递归、取消行为、优先级协议和进程共享属性。不能根据“通常能工作”混用不同语义。

锁粒度与争用

粗粒度锁容易证明但并行度低；细粒度锁减少无关争用，却增加锁数量、顺序约束和生命周期复杂度。优化前应测量等待时间、持锁时间和争用路径。拆锁后必须重新定义不变量，因为跨多个锁的状态快照可能不再一致。

减少临界区工作、避免在持锁时执行阻塞 I/O、分片数据、使用每 CPU 状态或读多写少机制，往往比盲目换“更快的锁”有效。

信号量、条件变量与监视器

计数信号量表示可用许可数，wait/P 在许可为零时等待并消耗一个，post/V 增加许可并唤醒等待者；二值信号量可表现互斥，但通常不要求释放者就是获取者。

条件变量本身不保存业务条件，它与 mutex 保护的谓词配合：持锁检查谓词；不成立时 wait 原子释放 mutex 并睡眠；醒来后重新获得锁并在 while 中重查。必须循环是因为虚假唤醒、多个消费者竞争以及通知到真正运行之间状态可能再次改变。

monitor 把共享状态、互斥进入和条件等待封装在一个抽象中。无论语法是否直接支持 monitor，设计核心都是让每个操作在持有正确锁时维护表示不变量。

C：带关闭语义的有界 pthread 队列 
#include <errno.h>
#include <pthread.h>
#include <stdbool.h>
#include <stddef.h>

enum { QUEUE_CAPACITY = 8 };

struct queue {
    int items[QUEUE_CAPACITY];
    size_t head;
    size_t tail;
    size_t count;
    bool closed;
    pthread_mutex_t mutex;
    pthread_cond_t not_empty;
    pthread_cond_t not_full;
};

#define QUEUE_INITIALIZER {                         \
    .head = 0, .tail = 0, .count = 0, .closed = false, \
    .mutex = PTHREAD_MUTEX_INITIALIZER,             \
    .not_empty = PTHREAD_COND_INITIALIZER,           \
    .not_full = PTHREAD_COND_INITIALIZER             \
}

// 成功返回 0；若队列已关闭，则返回 EPIPE。
int queue_put(struct queue *queue, int value) {
    pthread_mutex_lock(&queue->mutex);

    while (queue->count == QUEUE_CAPACITY && !queue->closed) {
        pthread_cond_wait(&queue->not_full, &queue->mutex);
    }

    if (queue->closed) {
        pthread_mutex_unlock(&queue->mutex);
        return EPIPE;
    }

    queue->items[queue->tail] = value;
    queue->tail = (queue->tail + 1) % QUEUE_CAPACITY;
    queue->count++;

    pthread_cond_signal(&queue->not_empty);
    pthread_mutex_unlock(&queue->mutex);
    return 0;
}

// 仅当已关闭队列变为空时返回 false。
bool queue_get(struct queue *queue, int *value) {
    pthread_mutex_lock(&queue->mutex);

    while (queue->count == 0 && !queue->closed) {
        pthread_cond_wait(&queue->not_empty, &queue->mutex);
    }

    if (queue->count == 0) {
        pthread_mutex_unlock(&queue->mutex);
        return false;
    }

    *value = queue->items[queue->head];
    queue->head = (queue->head + 1) % QUEUE_CAPACITY;
    queue->count--;

    pthread_cond_signal(&queue->not_full);
    pthread_mutex_unlock(&queue->mutex);
    return true;
}

void queue_close(struct queue *queue) {
    pthread_mutex_lock(&queue->mutex);
    queue->closed = true;

    // 每个等待者都必须重新检查数据是否可用或队列是否关闭。
    pthread_cond_broadcast(&queue->not_empty);
    pthread_cond_broadcast(&queue->not_full);
    pthread_mutex_unlock(&queue->mutex);
}

屏障与读写协调

屏障要求一代中的所有参与线程到达后才能进入下一阶段。可复用屏障必须带 generation，避免快线程把下一轮到达误计入上一轮。参与者退出或取消时，协议还要说明计数如何调整。

读写锁允许多个读者同时进入，写者独占。读者优先可饿死写者，写者优先可放大读延迟，公平策略增加管理成本。只有读临界区足够长、读多写少且争用明显时，读写锁才可能优于 mutex。

pthread_rwlock_rdlock(&table_lock);
const struct record *record = lookup_without_mutation(key);
copy_record_for_caller(record);  // Do not return an unprotected pointer.
pthread_rwlock_unlock(&table_lock);

pthread_rwlock_wrlock(&table_lock);
insert_or_replace_record(key, value);
pthread_rwlock_unlock(&table_lock);

经典同步问题

生产者-消费者

有界缓冲区不变量是 \(0\le count\le capacity\)，生产者等待 not_full，消费者等待 not_empty，所有队列索引与计数在同一 mutex 下更新。关闭状态必须唤醒所有等待者，并让消费者区分“暂时为空”和“永久不会再有数据”。

读者-写者

读者-写者问题不是简单允许并发读，还要定义到达顺序、升级/降级、取消和饥饿策略。若读者持续到达而总能越过等待写者，写者永远无法进入；反之严格写者优先会造成读尾延迟。选择必须由工作负载和服务目标决定。

哲学家就餐

所有哲学家先拿左叉再等右叉会形成环路。常见修复包括全局锁顺序、最多允许 \(N-1\) 人竞争、由服务员原子授予一对叉子，或让一人反向获取。重点不是餐具，而是多个资源请求如何形成循环等待。

死锁

必要条件与资源分配图

死锁需要四个 Coffman 条件同时成立：互斥、持有并等待、不可抢占、循环等待。资源分配图中，进程到资源是请求边，资源实例到进程是分配边；单实例资源下环意味着死锁，多实例下环只表示可能。

线程 A：lock(X) -> lock(Y)
线程 B：lock(Y) -> lock(X)

预防、避免、检测与恢复

  • 预防：破坏必要条件，例如全局锁顺序、一次请求全部资源或允许回滚。
  • 避免：如 Banker 算法，只接受仍处于安全状态的请求，需要知道最大需求。
  • 检测：允许死锁发生，周期构建 wait-for graph 或检测无可满足请求。
  • 恢复：终止/回滚参与者、抢占资源或重启子系统，并处理副作用。

超时只是怀疑和恢复策略，不是死锁证明；太短会误杀慢操作，太长又延迟恢复。数据库、内核和分布式系统会根据可回滚性与故障范围选择不同策略。

饥饿、活锁与优先级反转

饥饿是某个参与者持续合格却长期得不到资源；活锁是参与者不断改变状态和重试，却没有完成有用工作；优先级反转是高优先级线程等待低优先级持锁者，而中优先级工作又抢占持锁者。

priority inheritance 临时把等待者优先级传给持锁者，缩短间接阻塞；priority ceiling 为资源预设上限并限制获取。两者都要求锁实现与调度器协作，且不能修复任意长临界区。

无锁技术与读-复制-更新

Lock-free 保证系统整体持续推进，wait-free 才保证每个操作在有限步骤完成。CAS 循环是常见基础：

#include <stdatomic.h>

void increment_with_cas(atomic_long *counter) {
    long observed = atomic_load_explicit(counter, memory_order_relaxed);

    while (!atomic_compare_exchange_weak_explicit(
        counter,
        &observed,
        observed + 1,
        memory_order_relaxed,
        memory_order_relaxed)) {
        // 失败时，observed 会被替换为导致本次比较失败的值。
    }
}

算法还必须解决 ABA 和安全回收。一个节点从结构中移除，不代表没有线程仍持有指针；hazard pointer、epoch-based reclamation 和 RCU 都是在确定何时可释放。

RCU 让读者进入极轻的 read-side 临界区，更新者构造新版本并原子发布，旧版本等待一个 grace period，确认所有可能看见旧指针的既有读者退出后再回收。

/* 读线程 */
rcu_read_lock();
item = rcu_dereference(current_item);
use_immutable_fields(item);
rcu_read_unlock();

/* 写线程；多个写线程之间另行串行化 */
new_item = copy_and_modify(old_item);
rcu_assign_pointer(current_item, new_item);
synchronize_rcu();
free(old_item);

RCU 优化读多写少路径，但写者复制、版本管理和延迟回收更复杂，并不适合所有数据结构。

诊断与测试并发代码

有效流程是：先写不变量和进展条件；在代码中加入断言与有界超时；使用 ThreadSanitizer 等动态检测真实执行中的 data race；通过压力、随机延迟或系统性调度探索扩大交错覆盖；保留最小失败轨迹；修复协议并加入回归。

clang -O1 -g -fsanitize=thread -fno-omit-frame-pointer \
  race.c -pthread -o race-tsan
./race-tsan

检测器各自只覆盖模型的一部分：TSan 不证明无 race；一次压力测试不覆盖所有调度；模型检查的抽象也可能遗漏实现细节。工具证据必须与 happens-before 和不变量推理结合。

pthread_mutex_lock(&queue->mutex);
assert(queue->count <= QUEUE_CAPACITY);
assert(queue_representation_is_consistent(queue));
pthread_mutex_unlock(&queue->mutex);

对比与总结

机制 等待方式 主要用途 关键风险
原子操作 重试或无等待 单变量状态、lock-free 基础 内存序、ABA、回收与争用
自旋锁 忙等 极短且不能睡眠的临界区 浪费 CPU、缓存行抖动
Mutex 争用时睡眠 通用互斥与不变量保护 死锁、优先级反转、粗粒度争用
Semaphore 许可计数等待 有界资源与事件计数 所有权不明显，易出现许可泄漏
Condition variable 原子释放锁并睡眠 等待受 mutex 保护的谓词 必须循环检查、处理关闭
Barrier 等待同代参与者 阶段同步 参与者丢失、代际混淆
RW lock 共享读/排他写 读多写少且临界区较长 读者或写者饥饿
RCU 读者极轻，写者等宽限期 读极多、更新少的指针结构 延迟回收和更新复杂度

可靠同步始于协议而不是原语名称：共享状态的不变量是什么，谁在什么锁或原子序下读写，等待谓词由谁改变，关闭/取消如何唤醒，资源获取顺序是否成环，调度优先级是否会被锁依赖颠倒。只有同时满足安全性与活性，程序才算并发正确。
