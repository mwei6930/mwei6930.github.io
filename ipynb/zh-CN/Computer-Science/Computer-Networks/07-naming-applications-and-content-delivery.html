命名、应用与内容分发

网络为进程提供传输能力，但用户真正接触的是名称、请求、页面、邮件、视频和服务 API。应用层协议决定消息如何表示、何时重试、状态放在哪里，以及如何把一个逻辑服务分布到许多端点。DNS 把稳定名称映射到变化的部署，HTTP 定义 Web 语义，缓存与 CDN 把内容靠近用户，P2P 和实时通信则采用不同的分发与时延策略。

本章把应用设计看成端到端系统问题：协议语法必须能够在 TCP 任意字节分块上重新成帧；超时与重试必须考虑幂等性；缓存必须定义新鲜度与验证；多副本系统必须区分命名、选择和健康；流媒体必须在吞吐波动、缓冲和画质之间闭环控制。贯穿案例是一条从 DNS 到 CDN、源站的 Web 请求。

注记

“应用层”不等于“只写业务数据”。DNS、HTTP、SMTP、DASH 和 WebRTC 都包含分布式状态、失败语义和性能控制。一个协议能解析报文，只是正确应用协议的起点。

应用层体系结构

客户端—服务器系统

服务器在已知地址或名称上提供服务，客户端主动发起请求。集中服务便于统一数据、认证、更新与审计，也会形成容量、地域和故障集中点，因此生产系统通常在负载均衡器之后部署副本、缓存和多区域故障切换。

对等系统

P2P 中节点既是客户端又是服务器，上传能力可随参与者增加，内容可从多个来源并行获取。代价是成员动态、信任、发现、NAT 穿越、一致性和激励机制更复杂。实际系统常是混合式：中心服务负责身份、索引或协调，数据由对等节点直接传输。

进程、套接字与传输选择

应用通过套接字使用 TCP、UDP 或 QUIC。选择应由消息边界、可靠性、顺序、时延、移动、多流和部署约束决定。TCP 提供有序字节流，应用必须成帧；UDP 保留数据报边界但不保证交付；QUIC 提供安全连接和多条独立可靠流。

有状态与无状态协议

无状态请求携带处理所需上下文，便于任意副本处理、缓存和重试；有状态会话在服务器保存登录、事务或流进度，能支持丰富交互，却需要粘性、复制或恢复。现实中常把短期连接状态与持久业务状态分离：访问令牌随请求携带，业务记录放共享存储，临时连接状态留在边缘节点。

分发容量

若一份大小 \(F\) 的对象要分给 \(N\) 个客户端，服务器上行速率为 \(u_s\)、客户端最低下载为 \(d_{min}\)，纯客户端—服务器分发至少需要

\[ D_{CS}\geq\max\left(\frac{NF}{u_s},\frac{F}{d_{min}}\right). \]

P2P 还可利用各对等上行 \(u_i\)：

\[ D_{P2P}\geq\max\left(\frac{F}{u_s},\frac{F}{d_{min}},\frac{NF}{u_s+\sum_i u_i}\right). \]

这些是理想下界，未计协议开销、分块可用性和节点离开，却清楚说明了 P2P 容量为何能随参与者增长。

代码 
def distribution_lower_bounds(file_gib, clients, server_upload_mbps,
                              slowest_download_mbps, peer_upload_mbps):
    """返回理想客户端—服务器与 P2P 分发时间下界（分钟）。"""
    file_bits = file_gib * (1024 ** 3) * 8
    us = server_upload_mbps * 1_000_000
    dmin = slowest_download_mbps * 1_000_000
    peer_sum = clients * peer_upload_mbps * 1_000_000

    client_server = max(clients * file_bits / us, file_bits / dmin)
    peer_to_peer = max(
        file_bits / us,
        file_bits / dmin,
        clients * file_bits / (us + peer_sum),
    )
    return client_server / 60, peer_to_peer / 60

for clients in (10, 100, 1000):
    cs, p2p = distribution_lower_bounds(
        file_gib=1,
        clients=clients,
        server_upload_mbps=100,
        slowest_download_mbps=50,
        peer_upload_mbps=10,
    )
    print(f"{clients:7d} | {cs:23.1f} min | {p2p:14.1f} min")

设计应用协议

消息语法与语义

协议需定义字段编码、长度、必选/可选项、错误表示、版本和状态转换。语法回答“字节怎样解析”，语义回答“请求意味着什么、响应承诺什么”。仅有 JSON 示例不是完整协议；还要说明未知字段、重复请求、并发更新、超时与权限。

在字节流上划分消息边界

TCP 可能任意拆分或合并应用写入，因此接收方不能假定一次 recv 等于一条消息。常见成帧方式是固定长度、分隔符、长度前缀，或“首部给出正文长度”。长度前缀接收器应先缓冲固定首部，验证长度上限，再等待完整载荷并循环处理剩余字节。

不验证长度会让攻击者声明巨大正文耗尽内存；分隔符协议则要处理转义、编码和缺失终止符。成帧设计同时是正确性与安全边界。

代码 
import json
import struct


HEADER = struct.Struct("!IBQ")  # 正文长度、1 字节类型、8 字节请求 ID
MAX_BODY = 1_000_000


def encode_frame(message_type, request_id, payload):
    payload_bytes = json.dumps(payload, separators=(",", ":")).encode("utf-8")
    body_length = 1 + 8 + len(payload_bytes)
    return HEADER.pack(body_length, message_type, request_id) + payload_bytes


class FrameDecoder:
    def __init__(self, max_body=MAX_BODY):
        self.buffer = bytearray()
        self.max_body = max_body

    def feed(self, chunk):
        self.buffer.extend(chunk)
        messages = []

        while len(self.buffer) >= HEADER.size:
            body_length, message_type, request_id = HEADER.unpack_from(self.buffer)
            if body_length < 9 or body_length > self.max_body:
                raise ValueError(f"invalid body length: {body_length}")

            frame_length = 4 + body_length
            if len(self.buffer) < frame_length:
                break  # 不完整的帧继续保留在缓冲区中

            payload_bytes = bytes(self.buffer[HEADER.size:frame_length])
            del self.buffer[:frame_length]
            messages.append(
                (message_type, request_id, json.loads(payload_bytes.decode("utf-8")))
            )

        return messages


wire = (
    encode_frame(1, 42, {"op": "put", "value": 7})
    + encode_frame(2, 43, {"op": "get"})
)

for index, chunk in enumerate(chunks, start=1):

序列化与内容类型

序列化把结构化值映射为字节。文本格式（JSON、XML）可读、易调试，但体积与解析成本较高，数字/时间语义可能模糊；二进制格式（Protocol Buffers、CBOR）紧凑且带 schema，却需要工具和版本管理。Content-Type、字符集与 schema 版本应显式声明，接收方不能仅凭扩展名猜测。

兼容演进通常要求旧实现忽略未知可选字段、新实现为缺失字段提供默认值，并避免复用旧字段编号或改变既有含义。版本号并不能替代兼容规则。

超时、重试、幂等性与背压

超时表示“在期限内没看到结果”，不证明服务器没有执行。若客户端重试非幂等操作，可能重复扣款或创建资源。GET/PUT 等语义可设计为幂等；POST 可使用唯一请求 ID/幂等键，让服务器返回原结果而非重复执行。

重试应设总截止时间、指数退避和抖动，并只针对可恢复错误；否则大量客户端同时重试会形成重试风暴。背压让慢消费者通过窗口、队列上限、拒绝或速率信号限制生产者，避免无限缓冲把局部慢速扩大成系统故障。

from collections import deque


class IdempotentCounterService:
    def __init__(self, queue_capacity=2):
        self.value = 0
        self.completed = {}
        self.pending = deque(maxlen=queue_capacity)

    def submit(self, request_id, amount):
        if request_id in self.completed:
            return "replayed", self.completed[request_id]
        if len(self.pending) == self.pending.maxlen:
            return "backpressure", None
        self.pending.append((request_id, amount))
        return "accepted", None

    def process_one(self):
        request_id, amount = self.pending.popleft()
        self.value += amount
        self.completed[request_id] = self.value
        return request_id, self.value


service = IdempotentCounterService(queue_capacity=2)
print(service.submit("payment-42", 10))
print(service.submit("other", 5))
print(service.submit("too-many", 1))
print("processed:", service.process_one())

# 调用方超时后重复同一个逻辑操作。
print("retry before completion record is queried:", service.submit("payment-42", 10))
print("processed:", service.process_one())
print("retry after completion:", service.submit("payment-42", 10))
print("final counter:", service.value)

域名系统

名称、地址与 DNS 命名空间

DNS 把分层域名映射为资源记录，而不只是“域名转 IP”。同一名称可拥有 A、AAAA、MX、TXT、SRV、HTTPS 等记录；地址可随位置、时间和健康变化。名称表达服务身份与管理结构，IP 地址表达网络位置，两者分离使服务迁移和复制成为可能。

根、顶级域与权威名称服务器

根区把顶级域委派给 TLD 服务器，TLD 再把子域委派给权威服务器。区域（zone）是由一组权威服务器负责的数据与委派边界，不等同于整棵域名子树。父区通过 NS 和必要 glue 地址把解析引向子区。

递归与迭代解析

终端通常向递归解析器提出“请给我最终答案”的递归查询。缓存未命中时，解析器从根提示开始，对根、TLD、权威服务器发出迭代查询，每次得到更接近答案的 referral，最终返回 RRset 并按 TTL 缓存。

资源记录

资源记录包含 NAME, TYPE, CLASS, TTL, RDATA。A/AAAA 给出地址，CNAME 给出别名，NS 指定权威服务器，MX 指定邮件交换及优先级，TXT 携带验证/策略文本，PTR 用于反向映射，SRV/HTTPS/SVCB 可表达服务端点与参数。一个回答中的多条记录形成 RRset，应作为整体缓存。

缓存、TTL、否定回答与一致性

缓存降低延迟和权威负载，却产生最终一致性。TTL 是缓存最长寿命而非“全球传播时间”；修改前提前降低 TTL 只能影响之后重新获取的缓存。不存在名称或类型的否定回答也可依据 SOA 信息缓存。过短 TTL 增加查询和权威依赖，过长 TTL 延长故障与迁移收敛。

负载分配与任播 DNS

权威 DNS 可返回多个地址、按地域/网络调整回答或结合健康检查。递归解析器的位置和缓存意味着服务看到的“客户端”未必是真实用户；EDNS Client Subnet 可传递部分前缀但有隐私与缓存复杂度。DNS 服务器自身常用任播，让多个站点通告同一地址并由路由选择实例。

代码 
class DnsCache:
    """用于 DNS 正/负数据的小型确定性 TTL 缓存。"""
    def __init__(self):
        self.entries = {}

    def put(self, name, record_type, value, ttl, now):
        key = (name.rstrip(".").lower(), record_type.upper())
        self.entries[key] = (value, now + ttl)

    def get(self, name, record_type, now):
        key = (name.rstrip(".").lower(), record_type.upper())
        entry = self.entries.get(key)
        if entry is None:
            return "MISS", None, 0
        value, expires_at = entry
        if now >= expires_at:
            del self.entries[key]
            return "EXPIRED", None, 0
        return "HIT", value, expires_at - now


cache = DnsCache()
cache.put("www.example.com.", "A", ["203.0.113.20"], ttl=60, now=0)
cache.put("missing.example.com.", "A", "NXDOMAIN", ttl=30, now=0)

for now in (0, 20, 35, 70):
    positive = cache.get("WWW.EXAMPLE.COM", "a", now)
    negative = cache.get("missing.example.com", "A", now)
    print(f"t={now:2d}s positive={positive}; negative={negative}")

Web 与 HTTP 语义

URL、请求、响应、方法与状态码

URL 由方案、主机、端口、路径、查询和片段等组成；片段通常只在客户端解释。HTTP 请求包含方法、目标、版本/协议语义、首部与可选正文，响应包含状态、首部与表示。

方法表达意图：GET 获取表示且应安全、幂等；HEAD 只取元数据；POST 提交处理；PUT 用给定表示替换/创建资源并应幂等；PATCH 局部修改；DELETE 通常应幂等。状态码类别 1xx 信息、2xx 成功、3xx 重定向、4xx 客户端请求问题、5xx 服务端失败。客户端应依据具体语义决定缓存和重试，而非把所有非 200 都当作相同错误。

首部、表示元数据与内容协商

首部携带 Host/authority、Content-Type、Content-Length、Accept、Content-Encoding、缓存条件、认证和追踪信息。资源与表示不同：同一资源可根据语言、媒体类型和编码返回不同表示。服务器驱动协商依赖 Accept-*，缓存需用 Vary 区分变体，否则可能把错误语言或压缩格式交给其他客户端。

Cookie、会话与认证状态

服务器用 Set-Cookie 设置名称、值、Domain、Path、Expires/Max-Age、Secure、HttpOnly 与 SameSite；浏览器按作用域在后续请求携带。Cookie 常保存不透明会话 ID，真实状态留在服务器。Secure 限制 HTTPS，HttpOnly 降低脚本窃取，SameSite 缓解部分 CSRF，但都不能替代输入验证、会话轮换和权限检查。

持久连接与流水化

HTTP/1.1 默认复用 TCP，避免每个对象重新握手。流水化允许在前一个响应完成前发送后续请求，但响应必须按序，慢响应会阻塞后续，而且代理兼容问题限制了广泛使用。浏览器更多采用多个连接，后来由 HTTP/2 多路复用取代。

def parse_http_text(raw_message, is_response=False):
    """解析教学用 HTTP/1.x 起始行与 RFC 风格首部块。"""
    normalized = raw_message.replace("\r\n", "\n")
    head, _, body = normalized.partition("\n\n")
    start_line, header_text = head.split("\n", 1)
    headers = Parser().parsestr(header_text)
    return start_line, dict(headers.items()), body

HTTP 的演进

HTTP/1.1 与队头阻塞

HTTP/1.1 在单连接上按序返回响应，一个大或慢响应阻挡后续响应；浏览器用多连接缓解，却增加握手、拥塞状态和服务器负载。文本首部重复发送也产生额外开销。

HTTP/2 帧、流与首部压缩

HTTP/2 把消息拆成二进制帧，并在一个 TCP 连接上交错多个带 stream ID 的流；HPACK 压缩重复首部。应用层慢流不再必然阻挡其他流，但所有字节仍属于一个有序 TCP 流，任一 TCP 段丢失会让后续所有 HTTP/2 流等待缺口恢复。

基于 QUIC 的 HTTP/3

HTTP/3 把 HTTP 语义映射到 QUIC 独立流。一个流的数据丢失不会阻止其他流交付，并整合 TLS 1.3、连接迁移和更快恢复。QPACK 必须避免动态首部表重新引入不必要跨流阻塞。UDP 被阻断时客户端仍需回退到其他版本。

连接复用、优先级与 Web 性能

连接复用减少 DNS/传输/TLS 启动成本并让拥塞窗口保持热态；过度合并也可能扩大单连接故障影响。优先级应让关键 CSS、字体和可见内容先于非关键资源，但服务器、代理和 CDN 必须共同尊重信号。性能还取决于缓存、压缩、对象数量、服务器计算、第三方依赖和页面渲染，不能仅凭 HTTP 版本判断。

def simplified_http_completion(resource_ms, setup_ms=50, loss_resource="A", recovery_ms=80):
    """在有意简化的阻塞规则下比较完成时间。"""
    names = list(resource_ms)

    # HTTP/1.1 流水响应必须按请求顺序完成。
    h1 = {}
    clock = setup_ms
    for name in names:
        clock += resource_ms[name]
        if name == loss_resource:
            clock += recovery_ms
        h1[name] = clock

    # HTTP/2 流可重叠，但一次 TCP 丢失会延迟所有流的交付。
    h2 = {
        name: setup_ms + resource_ms[name] + recovery_ms
        for name in names
    }

    # HTTP/3 流可重叠；模型只让受影响的 A 承担恢复时间。
    h3 = {
        name: setup_ms + resource_ms[name] + (recovery_ms if name == loss_resource else 0)
        for name in names
    }
    return h1, h2, h3


resources = {"A": 120, "B": 40, "C": 60}
h1, h2, h3 = simplified_http_completion(resources)
print("resource | HTTP/1.1 pipeline | HTTP/2 + TCP loss | HTTP/3 stream loss")
for name in resources:
    print(f"{name:8s} | {h1[name]:17d} ms | {h2[name]:17d} ms | {h3[name]:17d} ms")

缓存、代理与内容分发网络

浏览器缓存与共享缓存

私有浏览器缓存服务单个用户，共享代理/CDN 缓存服务多个客户端。缓存键通常包含 URL 与 Vary 指定的请求首部。正确缓存减少 RTT、带宽和源站负载；错误缓存可能泄露个性化内容或长期提供陈旧响应。

验证、新鲜度与 Cache-Control

Cache-Control: max-age、s-maxage 等定义新鲜期；新鲜对象可直接使用。过期后客户端可带 ETag 的 If-None-Match 或时间的 If-Modified-Since 条件请求，未改变时服务器返回 304 Not Modified。no-store 禁止保存，no-cache 表示使用前必须验证，并非完全不存。

正向代理与反向代理

正向代理代表客户端访问外部资源，可做访问控制、缓存和隐私出口；反向代理代表服务器接收请求，完成 TLS、负载均衡、缓存、认证或路由。两者都终止一段连接并发起另一段，必须正确传递客户端身份、协议和追踪信息，并明确信任边界。

CDN 请求映射与边缘缓存

CDN 通过 DNS、任播或应用重定向把用户映射到边缘站点，选择依据网络位置、容量、健康、缓存和成本。边缘命中直接返回；未命中向源站或上层缓存取回并填充。

源站屏蔽、复制与缓存失效

Origin shield 在许多边缘与源站之间再设共享缓存，合并并发 miss，防止热门对象让源站雪崩。内容复制提高可用性，却使失效和一致性困难：可以等待 TTL、主动 purge、版本化 URL，或使用 stale-while-revalidate/stale-if-error 在新鲜度与韧性间权衡。

def cache_decision(entry, now, shared_cache, request_allows_stale=False):
    """分类一个简化 HTTP 缓存状态。"""
    if entry is None or entry.no_store:
        return "MISS"
    if shared_cache and entry.private:
        return "MISS: private response"

    current_age = now - entry.stored_at
    if current_age <= entry.max_age:
        return f"FRESH HIT (Age={current_age}s)"
    if entry.etag:
        return f"REVALIDATE with If-None-Match: {entry.etag}"
    return "STALE: fetch a new representation"

def cache_effect(hit_ratio, edge_latency_ms, miss_latency_ms,
                 requests_per_second, coalesced_misses=1):
    """计算一阶时延与源站请求负载。"""
    expected_latency = (
        hit_ratio * edge_latency_ms
        + (1 - hit_ratio) * miss_latency_ms
    )
    raw_misses = requests_per_second * (1 - hit_ratio)
    origin_requests = raw_misses / coalesced_misses
    return expected_latency, raw_misses, origin_requests


for hit_ratio in (0.50, 0.90, 0.99):

电子邮件与消息系统

SMTP、邮件传输与中继

用户代理把邮件提交给发送方邮件服务器，服务器查询收件域 MX，再用 SMTP 中继到接收方。SMTP 是存储转发协议：临时失败进入队列并稍后重试，永久失败产生退信。信封发件人/收件人与消息头 From/To 不同，这一点对路由、退信和反垃圾分析很重要。

IMAP、POP3 与邮件访问

IMAP 在服务器维护文件夹、标志与多设备同步；POP3 更偏向下载消息，功能较简单。现代客户端还通过 Web API 或 Webmail 访问。传输安全、用户认证与邮件身份验证（SPF、DKIM、DMARC）解决不同问题，不能互相替代。

消息队列与交付语义

消息系统通常提供至少一次、至多一次或近似恰好一次处理语义。网络失败使“请求执行但确认丢失”不可避免，因此所谓 exactly-once 往往依赖幂等键、去重记录与事务边界。消费者需要确认、重试、死信队列和背压，并区分消息已交付、已处理与业务副作用已提交。

class AtLeastOnceConsumer:
    def __init__(self):
        self.processed_ids = set()
        self.balance = 0

    def handle(self, message):
        """依据稳定消息 ID 只执行一次外部可见副作用。"""
        message_id, amount = message
        if message_id in self.processed_ids:
            return "duplicate suppressed"
        self.balance += amount
        self.processed_ids.add(message_id)
        return "effect committed"


consumer = AtLeastOnceConsumer()
deliveries = [
    ("order-17", 25),
    ("order-17", 25),  # ACK 丢失，因此代理重新投递消息
    ("order-18", 10),
]

for message in deliveries:
    print(message, "->", consumer.handle(message))
print("final balance:", consumer.balance)

多媒体与实时通信

存储式流媒体与自适应码率

存储视频可预取并缓冲，允许客户端把短时网络波动与连续播放解耦。文件被编码为多个码率/分辨率并切成短片段，清单描述可选版本。播放器通过 HTTP/CDN 获取片段，利用缓冲抵抗变化。

DASH 与客户端自适应

自适应码率（ABR）根据近期片段吞吐、播放缓冲、设备能力和质量切换成本选择下一片段。选择过高会耗尽缓冲并卡顿，过低会浪费可用容量。目标通常组合画质、卡顿时间、启动时延和切换平滑度，而不是最大化瞬时码率。

def choose_bitrate(available_mbps, estimate_mbps, buffer_seconds):
    """小型吞吐/缓冲混合 ABR 策略。"""
    if buffer_seconds < 4:
        return available_mbps[0]
    safety_budget = 0.75 * estimate_mbps
    eligible = [rate for rate in available_mbps if rate <= safety_budget]
    return max(eligible, default=available_mbps[0])


def simulate_abr(throughputs, segment_seconds=4):
    rates = [0.5, 1.5, 3.0, 6.0]
    estimate = throughputs[0]
    buffer_seconds = 4.0
    trace = []

    for index, throughput in enumerate(throughputs, start=1):
        selected = choose_bitrate(rates, estimate, buffer_seconds)
        download_time = selected * segment_seconds / throughput
        stall = max(0.0, download_time - buffer_seconds)
        buffer_seconds = max(0.0, buffer_seconds - download_time) + segment_seconds
        estimate = 0.7 * estimate + 0.3 * throughput
        trace.append((index, throughput, selected, download_time, stall, buffer_seconds, estimate))

    return trace

RTP、WebRTC、抖动缓冲与交互时延

实时媒体通常不能等待所有丢失数据。RTP 提供序号、时间戳和载荷类型，RTCP 反馈质量；接收端用抖动缓冲延迟播放，以吸收网络到达变化。缓冲太小会丢弃迟到帧，太大则增加对话时延。

WebRTC 把媒体编解码、加密、拥塞控制与 NAT 穿越组合起来。应用信令交换 offer/answer 和 ICE candidates；STUN 帮助发现公网映射，ICE 对候选路径做连通性检查，无法直连时通过 TURN 中继。

实时优化需要联合考虑捕获、编码、排队、传输、抖动缓冲、解码和渲染；只测 ping RTT 不足以解释端到端口型同步或卡顿。

def jitter_buffer_playout(arrival_ms, start_ms, packet_interval_ms=20):
    """在固定播放截止时间返回已交付或被隐藏的分组。"""
    highest_sequence = max(arrival_ms)
    trace = []
    for sequence in range(highest_sequence + 1):
        deadline = start_ms + sequence * packet_interval_ms
        arrival = arrival_ms.get(sequence)
        if arrival is None:
            outcome = "conceal missing packet"
        elif arrival <= deadline:
            outcome = "play packet"
        else:
            outcome = f"late by {arrival - deadline} ms -> conceal"
        trace.append((sequence, arrival, deadline, outcome))
    return trace

体验质量

QoE 是用户感知，不等于单一网络指标。视频常关注启动时间、卡顿比例、平均画质和切换；语音关注端到端时延、抖动、丢包隐藏与音质；交互应用关注尾时延。应把应用事件时间线与网络遥测关联，并按设备、地区、接入类型和内容分层，避免平均值掩盖少数用户的严重问题。

对等与覆盖网络系统

BitTorrent 与群集下载

文件被拆成经哈希验证的分块，节点从多个对等体并行下载并上传已有分块。稀有优先选择保持分块可用性，tit-for-tat 类策略鼓励贡献。Tracker 或 DHT 帮助发现对等体。安全仍需可信内容哈希/元数据，因为任何节点都可能提供损坏数据。

分布式哈希表

DHT 把资源名称哈希为键，并按一致规则把键分配给对等节点。结构化覆盖网络让查询通常在 \(O(\log N)\) 跳内到达负责节点，但节点频繁加入/离开需要复制、稳定化和重分配。

覆盖路由与 NAT 穿越

覆盖边是底层 IP 路径，覆盖“相邻”节点在物理上可能很远。覆盖可以按应用标识路由、复制状态并绕开故障，但无法突破底层容量和传播限制。NAT 会阻止未经请求的入站流量，因此系统使用打洞、端口映射或中继；对称 NAT 和严格防火墙会降低直连成功率。

from bisect import bisect_left
from hashlib import sha1


RING_SIZE = 128
NODES = [5, 18, 40, 72, 90, 113]


def identifier(text):
    return int.from_bytes(sha1(text.encode()).digest(), "big") % RING_SIZE


def successor(value):
    index = bisect_left(NODES, value)
    return NODES[index] if index < len(NODES) else NODES[0]


def clockwise_distance(start, end):
    return (end - start) % RING_SIZE


def finger_table(node):
    return sorted({successor((node + 2 ** power) % RING_SIZE) for power in range(7)})


def chord_like_route(start, key):
    target = successor(key)
    current = start
    path = [current]

    while current != target:
        remaining = clockwise_distance(current, target)
        candidates = [
            node for node in finger_table(current)
            if 0 < clockwise_distance(current, node) <= remaining
        ]
        current = max(candidates, key=lambda node: clockwise_distance(path[-1], node))
        path.append(current)
    return target, path


for object_name in ("lecture.mp4", "notes.pdf", "dataset.csv"):
    key = identifier(object_name)
    owner, path = chord_like_route(start=5, key=key)
    print(f"{object_name:12s} -> key={key:3d}, owner={owner:3d}, route={path}")

编码 DNS 查询并解析回答

import ipaddress
import secrets
import socket
import struct


def encode_dns_name(name):
    labels = name.rstrip(".").split(".")
    encoded = bytearray()
    for label in labels:
        part = label.encode("idna")
        if not 0 < len(part) <= 63:
            raise ValueError("DNS label must contain 1..63 encoded bytes")
        encoded.append(len(part))
        encoded.extend(part)
    encoded.append(0)
    return bytes(encoded)


def build_dns_a_query(name, transaction_id=None):
    transaction_id = secrets.randbits(16) if transaction_id is None else transaction_id
    flags = 0x0100  # 请求递归查询
    header = struct.pack("!HHHHHH", transaction_id, flags, 1, 0, 0, 0)
    question = encode_dns_name(name) + struct.pack("!HH", 1, 1)  # A, IN
    return transaction_id, header + question


def parse_single_a_response(packet, expected_id):
    transaction_id, flags, qd, an, ns, ar = struct.unpack("!HHHHHH", packet[:12])
    if transaction_id != expected_id or not (flags & 0x8000):
        raise ValueError("mismatched transaction or not a response")
    rcode = flags & 0x000F
    if rcode != 0 or qd != 1 or an < 1:
        raise ValueError(f"DNS failure: rcode={rcode}, answers={an}")

    # 在这个受控示例中安全跳过未压缩问题名称。
    offset = 12
    while packet[offset] != 0:
        length = packet[offset]
        offset += 1 + length
    offset += 1 + 4  # 终止字节以及 QTYPE/QCLASS

    name_pointer, rr_type, rr_class, ttl, rdlength = struct.unpack(
        "!HHHIH", packet[offset:offset + 12]
    )
    offset += 12
    if name_pointer != 0xC00C or rr_type != 1 or rr_class != 1 or rdlength != 4:
        raise ValueError("unexpected answer shape")
    return str(ipaddress.IPv4Address(packet[offset:offset + 4])), ttl

向本地源站发送一个 HTTP/1.1 请求

示例在回环地址启动最小服务器，客户端通过 TCP 发送带 Host 与 Connection: close 的 HTTP/1.1 请求，并读取到 EOF。它展示请求行、CRLF、首部结束空行以及 TCP 字节流循环读取。

真正 HTTP 客户端必须处理 Content-Length、chunked 编码、持久连接、重定向、压缩、代理、TLS、多个地址和输入上限。该例的目的不是替代 requests/httpx，而是让线上的字节与高层 API 对应起来。

代码 
import socket
import threading


def local_origin(listener):
    connection, _ = listener.accept()
    with connection:
        request = bytearray()
        while b"\r\n\r\n" not in request:
            chunk = connection.recv(4096)
            if not chunk:
                return
            request.extend(chunk)

        body = b'{"source":"local-origin","ok":true}'
        response = (
            b"HTTP/1.1 200 OK\r\n"
            b"Content-Type: application/json\r\n"
            + f"Content-Length: {len(body)}\r\n".encode()
            + b"Connection: close\r\n\r\n"
            + body
        )
        connection.sendall(response)


with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as listener:
    listener.bind(("127.0.0.1", 0))
    listener.listen(1)
    host, port = listener.getsockname()
    server = threading.Thread(target=local_origin, args=(listener,), daemon=True)
    server.start()

    with socket.create_connection((host, port), timeout=2) as client:
        client.sendall(
            b"GET /status HTTP/1.1\r\n"
            + f"Host: {host}:{port}\r\n".encode()
            + b"Accept: application/json\r\nConnection: close\r\n\r\n"
        )
        wire_response = bytearray()
        while chunk := client.recv(4096):
            wire_response.extend(chunk)

    server.join(timeout=2)

追踪一条 Web 请求穿过 DNS、CDN 与源站

追踪应记录同一时间窗口内的 DNS RRset/TTL、所选 IPv4/IPv6 地址、连接与 TLS 计时、HTTP 状态与缓存首部、CDN 标识、响应大小和重复请求差异。第一次请求可能包含 DNS、握手和 cache miss，第二次可能复用连接并命中缓存，两者不能直接平均。

后面的测量代码把阶段结果整理为结构化记录。实际调查应从多个受控位置重复，并保存原始输出；DNS 答案和 CDN 映射会随解析器位置、时间和负载变化。不要根据一个边缘 IP 断言真实源站位置。

代码 
def trace_web_request(browser_hit=False, dns_hit=False, connection_reused=False,
                      edge_hit=False, validator_matches=False):
    events = []
    elapsed = 0.0

    def add(label, duration):
        nonlocal elapsed
        elapsed += duration
        events.append((label, duration, elapsed))

    add("URL parse + browser cache lookup", 0.3)
    if browser_hit:
        add("fresh browser-cache body", 0.2)
        return events

    add("DNS cache lookup" if dns_hit else "recursive DNS resolution", 1.0 if dns_hit else 28.0)
    add("reuse HTTP connection" if connection_reused else "transport + secure setup", 0.2 if connection_reused else 42.0)
    add("request reaches CDN edge", 12.0)

    if edge_hit:
        add("fresh edge-cache response", 7.0)
    elif validator_matches:
        add("shield/origin validation", 38.0)
        add("304 metadata + cached body delivery", 9.0)
    else:
        add("shield/origin miss fetch", 85.0)
        add("body delivery and cache fill", 35.0)

    add("decode representation", 4.0)
    return events


scenarios = {
    "browser hit": dict(browser_hit=True),
    "warm edge": dict(dns_hit=True, connection_reused=True, edge_hit=True),
    "stale validate": dict(dns_hit=True, connection_reused=True, validator_matches=True),
    "cold miss": dict(),
}

for name, settings in scenarios.items():
    trace = trace_web_request(**settings)
    print(f"\n{name}: total={trace[-1][2]:.1f} ms")
    for label, duration, cumulative in trace:
        print(f"  +{duration:5.1f} ms -> {cumulative:6.1f} ms  {label}")

观察与排查应用交付

# 查询 DNS 回答、TTL 与权威信息
Resolve-DnsName example.com
Resolve-DnsName example.com -Type NS

# 输出连接、TLS、请求和响应首部细节
curl.exe -v -I https://example.com/

# 分阶段计时并保存响应（curl 版本支持时）
curl.exe -o NUL -s -w "dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first=%{time_starttransfer} total=%{time_total}`n" https://example.com/

建议按依赖顺序排查：名称是否解析、选中了哪个地址、传输是否建立、TLS 是否验证、HTTP 是否得到预期状态、缓存是否命中、正文是否完整、页面依赖中哪一项阻塞。浏览器开发者工具的 waterfall 能揭示队列、DNS、连接、TTFB 与下载，但服务端 trace 才能把 TTFB 分解为代理、应用和数据库时间。

常见模式：DNS SERVFAIL 与 NXDOMAIN 含义不同；TLS 主机名失败不是路由问题；304 是成功验证而非无内容错误；高 TTFB 但握手正常常指向服务器或上游；边缘命中快而 miss 慢提示源站/盾缓存；重试非幂等请求导致重复业务结果则是协议语义错误。

总结

层面 核心问题 代表机制
应用体系结构 状态与容量放在哪里 Client-server、P2P、复制
协议设计 字节怎样成为有语义消息 成帧、序列化、超时、幂等、背压
命名 稳定身份怎样映射到动态位置 DNS 委派、RR、缓存、TTL
Web 请求和表示如何交互 HTTP 方法、状态、首部、Cookie
性能演进 如何复用连接并缩小阻塞范围 HTTP/2、HTTP/3、QUIC
内容分发 如何减少距离和源站负载 缓存、代理、CDN、失效
实时媒体 如何在变化网络中控制体验 ABR、RTP、WebRTC、抖动缓冲
覆盖网络 如何利用参与节点与逻辑拓扑 BitTorrent、DHT、NAT 穿越

应用层把底层连通性转化为用户可理解的服务。可靠设计必须同时定义消息语义、状态、失败、缓存、一致性、安全与测量；只知道协议端口或报文格式，无法解释真实应用为何快、慢、重复或失效。
