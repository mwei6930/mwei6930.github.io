网络测量、运维与故障排查

协议知识告诉我们系统应当怎样工作，测量与运维则回答它此刻实际上怎样工作。网络是分布式、异步且部分可观察的：同一个分组在主机、网卡、交换机镜像口和远端抓包中可能呈现不同时间与封装；超时既可能是丢包，也可能是过滤、限速、慢服务或错误测量点。

本章建立从问题到证据的完整流程：把用户症状写成可证伪假设，选择指标、观察点与独立样本；正确解释延迟、损失、吞吐、尾时延；使用抓包、主动探测、流记录与遥测；识别时钟、采样、缓存、负载均衡和卸载造成的偏差；最后通过分层排障、安全变更、SLO、可复现实验和事后复盘把一次调查变成长期系统改进。

注记

工具输出不是事实本身，而是某个观察点、时间窗口和协议策略下的证据。好的排障过程会记录“从哪里测、何时测、如何测、测量本身改变了什么”。

从运维问题到测量计划

可达性、性能、可靠性与安全问题

先把模糊症状转成具体问题：“哪些用户从何时开始无法完成 HTTPS 请求？”“p95 变慢来自 DNS、握手、服务器还是传输？”“路径是否只在某地址族失败？”“异常流量是攻击还是业务增长？”不同问题需要不同证据，ping 无法回答证书身份，平均吞吐也无法解释短流尾时延。

指标、单位、基线与成功标准

指标必须包含定义、单位、统计总体与窗口。例如“过去 5 分钟，澳洲移动用户结账请求的 p95 总时延（ms）”。基线应与星期、地区、版本和负载可比；成功标准应在实验前声明，如“错误率恢复到 0.1% 以下且 p95 不高于健康对照 10%”。否则很容易在结果出现后挑选支持原假设的指标。

测量点、时间窗口与独立单位

客户端、服务器、瓶颈前后、镜像口和云流日志看到的是不同事件。测量窗口要覆盖热身、稳态和变化；样本的独立单位可能是用户、连接、部署、故障域或实验运行，而不是每个分组。一个运行中的一百万分组不能替代多次独立运行来估计部署变化的不确定性。

主动测量与被动测量

主动测量发送受控探测，能够设计输入并直接比较，但会消耗资源且可能与真实业务不同；被动测量观察现有流量，覆盖真实用户，却受工作负载和隐私限制，也难以建立因果。常见做法是用被动遥测发现症状，用低风险主动探测检验假设，再用日志/追踪定位服务内部阶段。

from dataclasses import dataclass
from typing import Optional


@dataclass(frozen=True)
class MeasurementPlan:
    question: str
    hypothesis: str
    predicted_evidence: str
    falsifier: str
    metric: str
    unit: str
    population: str
    vantage_point: str
    window_minutes: int
    independent_unit: str
    baseline: str
    success_rule: str
    active_rate_per_second: Optional[float] = None

    def validate(self):
        """在产生任何流量之前返回测量计划中的遗漏。"""
        problems = []
        required_text = {
            "hypothesis": self.hypothesis,
            "predicted evidence": self.predicted_evidence,
            "falsifier": self.falsifier,
            "metric": self.metric,
            "unit": self.unit,
            "population": self.population,
            "vantage point": self.vantage_point,
            "independent unit": self.independent_unit,
            "baseline": self.baseline,
            "success rule": self.success_rule,
        }
        for label, value in required_text.items():
            if not value.strip():
                problems.append(f"missing {label}")
        if self.window_minutes <= 0:
            problems.append("window must be positive")
        if self.active_rate_per_second is not None and self.active_rate_per_second <= 0:
            problems.append("active probe rate must be positive")
        return problems


plan = MeasurementPlan(
    question="Why did checkout become slower for Sydney mobile users?",
    hypothesis="a routing change added an inter-region path before the TLS endpoint",
    predicted_evidence="TLS and TCP phases rise together; server processing is unchanged",
    falsifier="handshake RTT is unchanged while server span duration rises",
    metric="client p95 TCP+TLS setup duration",
    unit="milliseconds",
    population="Sydney mobile checkout sessions",
    vantage_point="synthetic clients in two Sydney access networks",
    window_minutes=10,
    independent_unit="new transport connection",
    baseline="same weekday/hour plus Melbourne control probes",
    success_rule="p95 returns within 10% of baseline for two windows",
    active_rate_per_second=0.05,  # 每个观测点每 20 秒发送一个探测包
)

核心网络指标

时延、RTT 与单向时延

单向时延包含处理、排队、传输和传播；RTT 还包含返回路径和端点响应。RTT 不是单向时延的精确两倍，因为路径、队列和处理可不对称。应用时间还可能包含 DNS、连接、TLS、服务器和渲染，因此必须说明计时边界。

单向测量需要两个端点时钟同步；若时钟偏差为 \(\epsilon\)，观测值为 \(d+\epsilon\)，甚至可能出现负时延。RTT 只需一个时钟，通常更稳健。

丢失、重复、乱序与损坏

丢失率必须定义分母和观察点：发送分组中未到达比例、应用请求失败比例和 TCP 重传比例不是同一个指标。重复可来自重传或复制路径，乱序可来自负载均衡、并行队列与重传，损坏通常被链路/传输校验发现后表现为丢失。捕获点本身丢包也会伪造网络丢失。

吞吐量、有效吞吐量、利用率与容量

容量是资源最大服务能力，吞吐量是观测交付速率，goodput 只计有用应用载荷，利用率是某窗口内负载/容量。高利用率可以是健康繁忙，也可能形成深队列；低吞吐可能来自应用供数、窗口、CPU、磁盘或接收端，而非链路容量不足。

计数器差分的速率为

\[ r=\frac{C_2-C_1}{t_2-t_1}, \]

计算时需处理计数回绕、设备重启、接口替换与缺失样本。

抖动、尾时延与可用性

抖动描述时延变化，实时媒体会用播放缓冲换取稳定。p95/p99 尾时延反映少数慢请求，必须有足够样本并避免把不同用户总体混合。可用性应以用户成功事件定义，例如“在 2 秒内完成正确响应”，而不只是进程存活或 ping 成功。报告区间、错误预算和连续故障长度，平均百分比会掩盖集中中断。

from collections import Counter
from statistics import mean, median


def percentile(values, q):
    """为小型教学数据集线性插值一个百分位数。"""
    ordered = sorted(values)
    position = (len(ordered) - 1) * q
    lower = int(position)
    upper = min(lower + 1, len(ordered) - 1)
    fraction = position - lower
    return ordered[lower] * (1 - fraction) + ordered[upper] * fraction

分组捕获与协议分析

捕获点与接口选择

发送主机抓包可能发生在校验和/分段卸载之前，交换机镜像看到线上帧但可能在拥塞时丢镜像，远端看到经过 NAT、隧道和负载均衡后的数据。首先画出路径，明确需要观察哪一段、哪个方向、哪种 VLAN/虚拟接口；“在服务器抓包没看到”只证明该观察点未见到。

tcpdump 与 Berkeley Packet Filter

BPF 在内核尽早筛选，减少捕获量与隐私暴露。表达式可按 host/net/port/proto、方向和布尔组合过滤。过滤要匹配问题：只抓 DNS UDP 可能漏掉截断后的 TCP；只抓某服务器 IP 可能漏掉 DNS 返回的其他 CDN 地址。

# 只捕获与受控解析器相关的 UDP DNS
tcpdump -i eth0 -nn -s 0 -w dns.pcap 'udp port 53 and host 192.0.2.53'

# 不解析名称，显示绝对时间与详细字段
tcpdump -r dns.pcap -nn -tttt -vvv

Wireshark 解码与跟踪流

Wireshark 将捕获分为分组列表、协议字段树与原始字节；显示过滤器基于已解析字段，可跟踪 TCP/HTTP 流、统计重传、会话和 I/O 图。解码器是解释器而非神谕，非标准端口、损坏输入或加密可能导致误识别。

校验和、卸载、Snap Length 与捕获伪影

发送端抓包显示“错误校验和”可能因为网卡稍后才计算；TSO/GSO 可能让本机看到比 MTU 大的逻辑段，接收合并也可能把多个包呈现为一个。Snap length 截断只保存前若干字节，PCAP 同时记录 captured length 与 original length。还要监控抓包程序丢弃计数，避免把观察器过载误判为线路丢包。

使用 Scapy 检查与构造分组

Scapy 适合教学、离线解析和经授权实验，可显式读写协议字段、计算校验和并保存 PCAP。构造分组可能绕过正常协议栈保护，只应在回环/实验网和明确许可范围使用。生产证据应优先采用维护良好、能处理恶意输入和重组的解析器。

import ipaddress
import struct
from io import BytesIO


def internet_checksum(data):
    """计算 IPv4 使用的 16 位反码校验和。"""
    if len(data) % 2:
        data += b"\x00"
    words = struct.unpack(f"!{len(data) // 2}H", data)
    total = sum(words)
    while total >> 16:
        total = (total & 0xFFFF) + (total >> 16)
    return (~total) & 0xFFFF


src_ip = ipaddress.IPv4Address("192.0.2.10").packed
dst_ip = ipaddress.IPv4Address("198.51.100.20").packed
payload = b"measurement-probe"
udp_header = struct.pack("!HHHH", 53000, 9999, 8 + len(payload), 0)

# 先用零校验和构造 IPv4 首部，再写入计算结果。
ipv4_without_checksum = struct.pack(
    "!BBHHHBBH4s4s",
    0x45, 0, 20 + len(udp_header) + len(payload), 7, 0,
    64, 17, 0, src_ip, dst_ip,
)
ipv4_header = ipv4_without_checksum[:10] + struct.pack(
    "!H", internet_checksum(ipv4_without_checksum)
) + ipv4_without_checksum[12:]

ethernet_header = bytes.fromhex("00112233445566778899aabb0800")
frame = ethernet_header + ipv4_header + udp_header + payload

# 在内存中把帧包装为最小的小端 PCAP 结构。
pcap = BytesIO()
pcap.write(struct.pack("<IHHIIII", 0xA1B2C3D4, 2, 4, 0, 0, 65535, 1))
pcap.write(struct.pack("<IIII", 1_720_000_000, 250_000, len(frame), len(frame)))
pcap.write(frame)

# 解析同一记录，并暴露分组工具会解码的字段。
raw = pcap.getvalue()
record_offset = 24
ts_sec, ts_usec, captured_len, original_len = struct.unpack_from("<IIII", raw, record_offset)
packet = raw[record_offset + 16:record_offset + 16 + captured_len]
ethertype = struct.unpack_from("!H", packet, 12)[0]
version_ihl, _, total_len, identification, _, ttl, protocol, checksum, src, dst = struct.unpack_from(
    "!BBHHHBBH4s4s", packet, 14
)
src_port, dst_port, udp_len, _ = struct.unpack_from("!HHHH", packet, 34)

print(f"timestamp: {ts_sec}.{ts_usec:06d}; captured/original: {captured_len}/{original_len}")
print(f"EtherType: 0x{ethertype:04x}; IPv{version_ihl >> 4}; TTL: {ttl}; protocol: {protocol}")
print(f"{ipaddress.IPv4Address(src)}:{src_port} -> {ipaddress.IPv4Address(dst)}:{dst_port}")
print("IPv4 checksum valid:", internet_checksum(packet[14:34]) == 0)
print("payload:", packet[42:].decode())

教学解析器有意区分捕获长度与原始线上长度，这正是 PCAP 表达 snap-length 截断的方式。真正协议分析器还需支持链路类型、选项、IPv6 扩展首部、分片、传输校验和、畸形输入与有状态重组。生产证据应使用成熟解析器，而不是不断扩展这个教学实现。

主动测量工具

ping 与 ICMP 可达性

ping 测试 ICMP Echo 往返、样本 RTT 与丢失。成功说明该协议在当时可往返，不证明 DNS、TCP 端口或应用正常；失败可能是过滤、限速、返回路径或目标禁用 Echo。设置有界次数、间隔和载荷，记录解析出的地址与时间。

# 有界、低速示例；参数会因操作系统而异
ping -n 10 example.com

traceroute 与路径推断

traceroute 递增 TTL/Hop Limit，并用 ICMP Time Exceeded 推断逐跳设备。它显示的是返回控制消息的接口，不一定是数据面的所有节点；MPLS、隧道、负载均衡、ICMP 限速和非对称返回会产生星号或变化路径。

使用 Paris traceroute 类方法可让五元组保持稳定，减少按流 ECMP 把不同探测送往不同路径造成的假象。

代码 
from collections import defaultdict


# 合成重复探测：同一 TTL 出现不同响应者，可能表示 ECMP
# 或响应路径变化；星号并不自动意味着转发失败。
trace_probes = [
    (1, 0, "10.0.0.1", 1.2), (1, 1, "10.0.0.1", 1.1),
    (2, 0, "203.0.113.1", 8.5), (2, 1, "203.0.113.1", 8.7),
    (3, 0, "198.51.100.9", 17.0), (3, 1, "198.51.100.14", 19.4),
    (4, 0, None, None), (4, 1, None, None),
    (5, 0, "192.0.2.80", 31.2), (5, 1, "192.0.2.80", 31.8),
]

by_ttl = defaultdict(list)
for ttl, probe_id, responder, rtt_ms in trace_probes:
    by_ttl[ttl].append((responder, rtt_ms))

for ttl in sorted(by_ttl):
    replies = by_ttl[ttl]
    responders = sorted({address for address, _ in replies if address})
    rtts = [rtt for _, rtt in replies if rtt is not None]
    status = "no ICMP response" if not responders else ", ".join(responders)
    if len(responders) > 1:
        status += "  [multiple responders: test a flow-stable trace]"
    rtt_text = "" if not rtts else f"; median-like RTT {sum(rtts) / len(rtts):.1f} ms"
    print(f"TTL {ttl}: {status}{rtt_text}")

print("\nDestination replied after the silent hop, so TTL 4 did forward the probes.")

安全速率限制与测量伦理

主动测量既有流量预算，也有社会边界。必须获得授权、确认运营联系人、列出源与目标、估计 pps/bps、限制并发、设置停止条件，并避免收集与问题无关的内容。例子使用文档地址，分组构造放在实验网。随机目标或分布式探测不会让未授权扫描变得合法。

接口计数器与系统统计

接口累积字节、分组、错误、CRC、丢弃、链路变化和优先级统计。单个计数值不是速率，两次读数差除以时间才是速率，并需处理回绕、重启与缺样。比较相邻接口和入/出方向：设备输出丢弃在接收端不会表现为错误，因为分组根本没离开队列。

主机还提供套接字状态、重传、队列、CPU、中断和内存。相关不等于因果，部署可能同时增加业务计算与流量，使 CPU 与网络时延一起上升。

def counter_delta(previous, current, bits=64, restarted=False):
    """在保留复位/回绕语义的情况下计算单调计数器差值。"""
    if restarted:
        return None, "device restarted; interval is not comparable"
    if current >= previous:
        return current - previous, "normal"
    modulus = 1 << bits
    wrapped_delta = current + modulus - previous
    # 合理回绕应接近计数边界，而不是任意复位。
    if previous > 0.90 * modulus and current < 0.10 * modulus:
        return wrapped_delta, f"{bits}-bit wrap"
    return None, "counter reset or interface replacement"

    (9_000_000, 12_000, 64, True),
]

    rate = "unknown" if delta is None else f"{delta * 8 / interval_seconds / 1e6:.3f} Mbit/s"

SNMP 管理器轮询代理 MIB 或接收 trap/inform，生态成熟但周期轮询可能漏掉短暂峰值。流式遥测由设备按订阅推送结构化状态，频率更高、模型更明确，却要求控制背压、模式版本、序列与收集器容量。

测量陷阱

时钟同步与时间戳误差

跨主机单向时延、日志和 trace 依赖时钟。NTP/PTP 可降低偏差，却仍有 offset、drift、step/slew 和虚拟化调度误差。记录同步源与不确定度；当预期事件差只有 1 ms 而时钟误差可能 5 ms 时，不能声称先后关系。单机单调时钟适合持续时间，墙上时钟适合跨系统关联。

代码 
from statistics import mean


# 参考交换表明：接收时钟 = 1.0002 * 真实时间 + 35 ms。
# 拟合直线，把接收方时间戳映射回发送方时间。
reference_pairs = [
    (0.0, 35.0),
    (10_000.0, 10_037.0),
    (20_000.0, 20_039.0),
    (30_000.0, 30_041.0),
]


def linear_fit(points):
    xs = [x for x, _ in points]
    ys = [y for _, y in points]
    x_bar, y_bar = mean(xs), mean(ys)
    slope = sum((x - x_bar) * (y - y_bar) for x, y in points) / sum(
        (x - x_bar) ** 2 for x in xs
    )
    intercept = y_bar - slope * x_bar
    return slope, intercept


clock_rate, clock_offset_ms = linear_fit(reference_pairs)
send_sender_ms = 12_000.0
receive_receiver_ms = 12_064.4
naive_delay = receive_receiver_ms - send_sender_ms
receive_in_sender_time = (receive_receiver_ms - clock_offset_ms) / clock_rate
corrected_delay = receive_in_sender_time - send_sender_ms

print(f"estimated receiver clock: {clock_rate:.7f} * t + {clock_offset_ms:.2f} ms")

采样、聚合与观察者偏差

分组/流采样会漏掉短流与稀有事件；固定间隔轮询可能与周期负载混叠；平均值掩盖尾部和双峰。观察点选择也有偏差：只看成功请求无法解释连接前失败，只看一个区域无法代表全球。保存分布、分层维度与采样机制。

ICMP 过滤与限速

路由器可以正常转发数据，却不回复或低优先处理 ICMP。中间跳 RTT 高而终点正常，常说明控制平面限速而非该跳转发慢。反之，ping 正常也不证明应用策略允许 TCP/UDP。探针协议应尽量匹配真实业务。

负载均衡、非对称路径与中间盒

ECMP 按流散列，改变端口可能改变路径；正反向路由常不同；NAT、防火墙、代理和 CDN 会终止或改写连接。连续探测不一定观察同一实例。记录五元组、地址族、解析结果和连接复用状态，并从多个观察点交叉验证。

热身、缓存与非平稳流量

第一次请求可能含 DNS、TLS、缓存 miss、JIT 与连接池启动，后续请求则命中热状态。流量还随时间、部署和用户组成变化。实验要区分冷/热状态、设热身期、随机化方案顺序并使用同期对照；昨日平均值不一定是今天的有效基线。

分层故障排查流程

定义症状与影响范围

先写出用户可见失败、开始时间、地区/网络/版本/地址族、频率和健康对照。确认监控本身是否正常，并建立事件时间线。范围能快速排除与所有受影响对象无共同关系的假设。

检查链路与本地配置

确认接口 up、物理/无线状态、错误丢弃、速度双工、VLAN/SSID 和最近变更。一个“连接图标”不能证明帧能够到达网关。

检查寻址、邻居解析与网关可达性

核对地址、前缀、DHCP/RA、默认路由和 DNS 配置；检查 ARP/ND 是否成功。错误掩码会让主机把远端当本地，重复地址会产生间歇性映射，错误 VLAN 会让广播请求永远到不了网关。

检查路由与路径变化

用 LPM 确认实际选中接口/下一跳，比较健康与故障路径，检查更具体路由、策略、BGP/IGP 收敛、MTU 与返回路径。traceroute 只是证据之一，应结合路由表、流日志和设备遥测。

检查传输状态与拥塞

观察 SYN/SYN-ACK、RTT、重传、SACK、rwnd/cwnd、零窗口、队列和接口利用率。握手失败与握手后 TTFB 高属于不同阶段；负载 RTT 大幅高于空闲 RTT 常提示队列。

检查 DNS、TLS 与应用语义

记录 DNS 回答/TTL/解析器，验证证书链、SAN、时间和 TLS 告警，再检查 HTTP 状态、缓存、认证、依赖和服务器 trace。不要通过关闭证书验证来“证明网络正常”。

每次只改变一个变量并验证恢复

选择能区分主要假设的最小可逆动作，例如只回滚一个 canary、切换一个解析器或禁用一条路径。操作前定义护栏和停止条件，操作后验证原始用户 SLI、对照指标与副作用。症状自然消失不等于修复有效。

网络管理与配置

资产清单、事实源与配置状态

应区分期望状态（事实源/意图）、部署状态（设备配置）与运行状态（实际邻接、路由、计数）。三者漂移会让“配置看起来正确”却不生效。清单需要稳定设备/接口身份、拓扑、地址、所有者与生命周期，不能只依赖临时发现。

自动化、模板与幂等变更

模板把重复配置参数化，自动化应幂等：重复执行把系统收敛到同一目标，而不是不断追加规则。先验证输入模型与语义，再生成厂商配置；文本相同不保证网络行为相同，文本不同也可能语义等价。

验证、回滚与变更窗口

安全变更流程包括语义 diff、静态检查、实验/数字孪生、分阶段 canary、实时护栏、明确回滚和故障域限制。回滚本身必须测试，尤其是状态迁移和协议收敛无法简单恢复旧文本时。

配置验证与策略合规

验证应检查不变量，如“管理网不可被访客 VLAN 访问”“所有外部前缀都有允许的起源”“冗余链路故障后仍可达”。配置 lint 只能发现语法/局部错误；要证明端到端性质，还需拓扑模型、转发表分析、探针和运行遥测。合规结果要绑定具体快照与时间。

def semantic_diff(current, target):
    changes = []
    for device, target_state in target.items():
        for field, target_value in target_state.items():
            current_value = current[device].get(field)
            if current_value != target_value:
                changes.append((device, field, current_value, target_value))
    return changes

            problems.append(f"{device}: invalid MTU")

            problems.append(f"{device}: implausibly low max-prefix")
        if not state["telemetry"]:
            problems.append(f"{device}: telemetry guardrail disabled")
    return problems

可观测性与可靠性工程

指标、日志、追踪与分组证据

指标适合趋势与告警，日志解释离散事件，trace 连接单次请求依赖，分组提供线上协议证据。调查通常从 SLI 指标发现异常，用 trace/日志缩小组件，再用抓包验证协议假设。每种信号都有成本和盲点，应围绕问题组合，而不是无限收集。

SLI、SLO、错误预算与告警

SLI 是用户结果的量化指标，SLO 是目标，例如 30 天内 99.9% 请求成功且满足时延门限。允许失败份额形成错误预算；burn rate 表示消耗速度。多窗口告警同时要求短窗口快速燃烧和长窗口持续异常，兼顾响应速度与抗噪声。

告警应可操作、关联用户影响并有明确负责人；CPU 高但用户 SLI 正常可能只是容量预警，不应和全面中断使用相同级别。

代码 
def error_budget_report(total, bad, objective):
    allowed_fraction = 1 - objective
    observed_bad_fraction = bad / total
    burn_rate = observed_bad_fraction / allowed_fraction
    allowed_bad = total * allowed_fraction
    remaining = allowed_bad - bad
    return {
        "success_fraction": 1 - observed_bad_fraction,
        "allowed_bad": allowed_bad,
        "remaining_bad_events": remaining,
        "burn_rate": burn_rate,
    }


objective = 0.999
short_window = error_budget_report(total=50_000, bad=210, objective=objective)
long_window = error_budget_report(total=600_000, bad=900, objective=objective)

for label, report in [("5-minute", short_window), ("1-hour", long_window)]:
    print(
        f"{label:8s}: success={report['success_fraction']:.4%}, "
        f"burn={report['burn_rate']:.1f}x, remaining={report['remaining_bad_events']:.0f} events"
    )

# 教学用多窗口条件；生产阈值取决于策略。
alert = short_window["burn_rate"] > 14 and long_window["burn_rate"] > 2
print("multi-window page:", alert)

故障域、冗余与故障注入

只有副本不共享隐藏依赖，冗余才提高可用性。应映射电源、机架、交换机、光缆路径、提供商、控制平面、DNS 区、CA、区域和操作凭据。两条同管道光纤或两个共用解析器的服务并非独立。

故障注入通过有界故障验证用户 SLI、切换时间、状态一致性和恢复。先在实验室，再用最小生产范围、canary 故障域、明确中止阈值和 on-call 协调。成功测试还必须验证故障恢复后的 failback。

事件时间线与事后复盘

时间线区分事件发生时间、观察时间与报告时间，记录用户影响、证据、假设、决策、变更、负责人和验证结果，并注明时区/时钟不确定度。它不是聊天记录，而是解释系统状态和团队认知如何变化。

复盘对个人无责，但对机制和决策要精确；说明促成条件、为何防御/检测未限制影响、做得好的地方，以及带负责人和期限的行动。优先改进安全默认值、不变量检查、canary、容量和 runbook，而非“以后更小心”。

可复现网络实验

Mininet 与网络命名空间

Mininet 在一台 Linux 主机上用 namespace 与 veth 创建虚拟主机、交换机、控制器和链路，运行真实 Linux 协议栈与普通程序。它比纯抽象模拟器更贴近配置/协议行为，但共享 CPU、时钟、网卡和物理队列，不能证明数据中心规模时序相同。

受控拓扑、时延、丢失与带宽

Linux traffic control 可对指定方向施加 delay、jitter、loss、duplication、reordering、rate 与队列限制。参数应服务于假设；独立随机丢包不能代表突发无线损失或拥塞队列。反向路径受损也会通过 ACK 限制正向 TCP。

# 示例 Mininet 结构；仅在已授权且安装 Mininet 的 Linux 实验环境运行
from mininet.net import Mininet
from mininet.link import TCLink

net = Mininet(link=TCLink)
h1, h2 = net.addHost("h1"), net.addHost("h2")
s1 = net.addSwitch("s1")
net.addLink(h1, s1, delay="20ms", loss=1, bw=10)
net.addLink(s1, h2)
net.start()
# 在这里执行有界测试并保存原始输出
net.stop()

实验清单与原始产物

清单应记录拓扑、地址、路由、配置、损伤方向/参数、工作负载、热身、持续时间、随机种子、重复次数、版本、硬件/OS、时钟源和预期输出。执行前分配 run ID，原样保存 stdout/stderr、PCAP、遥测、日志与配置快照，并用校验和检测修改。

派生表和图应能从原始产物重建。脱敏要记录转换，策略允许时保留受保护的未修改原件。

区分测量误差与系统行为

进行独立重复、随机化方案顺序、加入无损伤对照，并测量观察器开销。置信区间只量化采样不确定度，不能修复系统偏差；围绕错误时钟估计得到很窄区间，只是“精确地错”。检查抓包丢失、CPU 饱和、收集积压和同期交叉流量。

分析要使用实验真正独立的单位。一次运行中的数千分组只估计运行内变化，不能替代多次拓扑运行。报告效应量与分布，而非只报 p 值。

代码 
import hashlib
import json
import math
from statistics import mean, stdev


manifest = {
    "topology": {"hosts": ["h1", "h2"], "switches": ["s1"]},
    "link_treatment": {"direction": "h1->s1", "delay_ms": 20, "loss_percent": 1, "rate_mbps": 10},
    "workload": {"name": "bounded-https-like-transfer", "duration_s": 15, "warmup_s": 3},
    "independent_unit": "fresh topology run",
    "repetitions": 6,
    "random_seed": 5046,
    "environment": {"kernel": "record-at-runtime", "tool_versions": "record-at-runtime"},
}

canonical = json.dumps(manifest, sort_keys=True, separators=(",", ":")).encode()
run_id = hashlib.sha256(canonical).hexdigest()[:12]

# 每次独立拓扑运行只取一个 p95，而不是每个分组一行。
treatment_p95_ms = [94.2, 97.1, 92.8, 101.0, 95.5, 98.4]
control_p95_ms = [51.2, 49.8, 52.0, 50.7, 51.5, 50.3]
deltas = [treated - control for treated, control in zip(treatment_p95_ms, control_p95_ms)]

# 小样本教学区间：df=5、95% 时使用 t 临界值约 2.571。
t_critical = 2.571
standard_error = stdev(deltas) / math.sqrt(len(deltas))
interval = (mean(deltas) - t_critical * standard_error, mean(deltas) + t_critical * standard_error)

print("run ID:", run_id)
print("paired p95 effect:", f"{mean(deltas):.1f} ms")
print("95% interval across independent runs:", f"[{interval[0]:.1f}, {interval[1]:.1f}] ms")

诊断端到端性能回退

假设结账服务在部署 c42 后，客户端 p95 从 181 ms 升至 461 ms。纪律化调查如下：

  1. 范围：只有使用新结账查询的请求变慢，静态内容与对照区域健康；
  2. 客户端阶段：DNS、连接、TLS 与正文传输接近基线，TTFB 增长；
  3. 分组证据：握手 RTT、重传率和接收窗口未改变；
  4. 追踪证据：c42 的数据库 span 增长约 300 ms；
  5. 区分性动作：只回滚一个 canary 后端，其余保持不变；
  6. 验证：canary p95 和数据库 span 恢复，再进行有界回滚，并确认护栏健康。

网络属于端到端路径，却不是本例失效机制。这个结论比“ping 看起来正常”更强，因为协议匹配的客户端计时、分组证据、服务 trace、部署历史和可逆干预相互一致。

baseline = {
    "dns": 25, "connect": 40, "tls": 36, "server": 60, "body": 20,
    "retransmit_percent": 0.12, "handshake_rtt_ms": 31,
}
incident = {
    "dns": 26, "connect": 42, "tls": 38, "server": 329, "body": 25,
    "retransmit_percent": 0.13, "handshake_rtt_ms": 32,
}
canary_rollback = {
    "dns": 25, "connect": 41, "tls": 37, "server": 64, "body": 21,
    "retransmit_percent": 0.12, "handshake_rtt_ms": 31,
}


def phase_deltas(reference, observed):
    ignored = {"retransmit_percent", "handshake_rtt_ms"}
    return {
        key: observed[key] - reference[key]
        for key in reference
        if key not in ignored
    }


deltas = phase_deltas(baseline, incident)
largest_phase = max(deltas, key=deltas.get)
network_guardrails_stable = (
    abs(incident["handshake_rtt_ms"] - baseline["handshake_rtt_ms"]) <= 3
    and abs(incident["retransmit_percent"] - baseline["retransmit_percent"]) <= 0.05
)
rollback_server_recovered = abs(canary_rollback["server"] - baseline["server"]) <= 10

print("phase deltas:", deltas)
print("largest regression phase:", largest_phase)
print("network handshake guardrails stable:", network_guardrails_stable)
print("canary rollback restored server phase:", rollback_server_recovered)
print(
    "decision:",
    "expand rollback and investigate deployment c42" if network_guardrails_stable and rollback_server_recovered else "collect more evidence",
)

总结

  • 从用户可见问题开始，预先定义可证伪假设、含单位指标、基线、观察点、独立单位和成功规则；
  • RTT、单向时延、吞吐、goodput、利用率、丢失、乱序、抖动、尾时延与可用性描述不同性质；
  • 抓包只是观察点证据，卸载、snap length、捕获丢失、镜像、加密、NAT 与时钟会改变呈现；
  • ping、traceroute、iperf3、DNS/TLS 和 HTTP 探针提出不同问题，超时或响应必须在协议/策略上下文解释；
  • 计数器、流、SNMP/遥测、日志、追踪与分组在细节、成本、覆盖和隐私间权衡，必须记录 schema、采样、缺口、时钟和资源身份；
  • 时钟误差、采样、聚合、ICMP 策略、负载均衡、中间盒、缓存、热身和非平稳流量会制造自信但错误的解释；
  • 排障应界定影响、对比健康对照、排序假设、只检查相关层、改变一个变量并验证原始 SLI；
  • 配置管理要区分期望、部署和运行状态，使用语义 diff、验证、canary、幂等、回滚和变更后不变量；
  • SLO/错误预算把测量连接到用户伤害与告警紧迫性，故障域测试和复盘把事故转化为系统改进；
  • 可复现实验保存清单、版本、原始产物、独立重复、观察器限制与不确定性。
