互联网体系结构与分组的一生

浏览器把联网呈现为一个很简单的动作：输入 URL，然后收到页面。但在这个动作之下，许多由不同组织独立设计和运维的系统必须协同工作。计算机首先要接入本地网络；域名需要解析成一个或多个目的地址；分组要穿越不同机构拥有的网络；远端还必须证明自己的身份，应用程序才能信任随后收到的数据。

本章为这条完整路径建立心智模型。我们以一次 HTTPS 请求作为贯穿案例，但真正要掌握的是三个更普遍的问题：每项网络职责位于哪里、每个组件保存什么状态，以及哪一个量能够解释当前的性能问题。这些边界比单纯记忆协议名称更有价值。

注记

互联网（Internet）与万维网（Web）不是同义词。互联网是分组传递基础设施及其协议生态；Web则是建立在其上的一类应用，主要使用 URL、HTTP、HTML 与浏览器技术。

学完本章后，“网络很慢”应当显得信息不足。一次交互变慢可能源于 DNS 解析、连接建立、传播距离、拥塞队列、低速接入链路、服务器计算，或应用发起了过多串行请求。不同原因需要不同证据，也需要不同修复手段。

什么是计算机网络？

通信、资源共享与规模化

计算机网络（computer network）是一组自治计算设备，它们依据共同协议，通过通信链路交换数据。“自治”非常关键：与同一处理器中的多个核心不同，联网主机拥有各自的时钟、内存、故障模式、管理员和安全边界；任何一台主机都无法直接观察其他所有主机与链路的完整状态。

可以把网络类比为物流系统。应用程序像客户一样创建货物，协议首部像运输标签一样说明处理方式，链路是运输区段，交换机与路由器是中转设施；当到达速度暂时超过服务能力时，就会形成队列。这个类比虽不完美，却揭示了核心事实：网络让有边界的数据单元依次经过多个独立运行的阶段，而不是为每对应用永久铺设一根专用线路。

网络主要解决三类反复出现的问题：

需求 网络提供的能力 示例
通信 让不同进程交换字节或消息 浏览器向 Web 服务器请求对象
资源共享 让许多用户访问共享计算、存储、打印机或服务 数千客户端调用同一个云 API
规模化与组合 让小型网络在没有全球唯一所有者的情况下互联 家庭 Wi-Fi 经多个 ISP 访问大学服务

为什么不为每对主机铺设专用链路？对于 \(n\) 台主机，全互连需要 \(n(n-1)/2\) 条链路，规模按平方增长；通信双方空闲时容量还会被浪费，而且跨组织维护几乎不可行。共享链路、交换、分层地址和路由使网络既能扩展，又能动态选择路径。

主机、链路、交换机与路由器

网络中常见的物理与逻辑角色如下：

组件 主要职责 通常检查的信息
主机 / 端系统 运行应用，并产生或接收端到端流量 应用、传输、IP 与链路层信息
链路 在相邻接口之间承载信号 铜缆、光纤或无线电上的比特/符号
交换机 在以太网 LAN 等链路层域中转发帧 链路层地址与 VLAN 信息
路由器 在不同网络之间转发 IP 数据报 目的 IP 前缀与转发表状态
中间盒 执行 NAT、过滤、代理或负载均衡等附加功能 取决于功能，往往跨越多个层次

这些边界由功能而不是设备外壳决定。家庭“路由器”通常同时包含 Wi-Fi 接入点、以太网交换机、IP 路由器、DHCP 服务器、防火墙与 NAT。把这些职责在头脑中拆开，诊断行为会容易得多。

网络边缘、接入网与核心网

网络边缘（network edge）包含主机以及真正为用户创造价值的应用。接入网（access network）通过以太网、Wi-Fi、无源光网络、有线电视网或蜂窝无线等技术，把边缘设备连接到第一台路由器。网络核心（network core）则是由高容量路由器和链路组成的网状结构，负责在接入网之间转发流量。

这种“边缘—接入—核心”的划分解释了为什么同一应用的两个用户会获得完全不同的体验：目的服务相同，但无线状况、家庭队列、接入速率、ISP 路径或地理距离可能不同。它也预示了端到端原则：许多正确性保证只有端点拥有足够信息才能完成，而核心网应专注于可扩展地转发分组。

互联网的结构

ISP、自治系统与管理边界

互联网不是由一家公司运营的一张网络，而是许多同意承载 IP 流量的网络互联而成。互联网服务提供商（ISP）出售或提供连接，但大学、企业、云服务商、内容分发网络和政府机构同样可能运营大规模网络。

在域间路由中，一个网络被表示为一个或多个自治系统（Autonomous System, AS）。AS 是由自治系统号（ASN）标识的管理与路由策略边界，而不是“一个很大的路由器”或“单一物理网络”。运营者决定发布哪些路由、选择哪些邻居，以及接受什么样的商业流量关系。

在 AS 内部，运营者可以根据自身工程目标优化路径；AS 之间通过 BGP 交换可达性，路径受到策略和商业关系的强烈影响。因此，互联网路径不保证地理最短、双向对称或永久稳定。

互联网交换中心与对等互联

网络通常通过两种经济关系互联：

关系 含义 典型结果
转接（transit） 一个网络付费请另一个网络提供通往更广互联网的可达性 提供方向客户通告大量外部目的地
对等互联（peering） 两个网络交换彼此客户的流量，通常不按字节结算 流量可以绕过上游转接路径

互联网交换中心（IXP）提供共享物理基础设施，让多个网络建立对等会话。加入 IXP 并不意味着所有参与者自动互为对等体，路由关系仍由策略与协议决定。其价值在于本地互联、降低转接成本，并且往往能够降低时延。

一个分组会同时跨越两类边界：在每一跳（hop），路由器作出局部转发决定；在每一个管理边界，独立组织施加路由、安全和流量工程策略。最终路径是许多局部决策共同涌现的结果，而不是由某个全球控制器统一计算出来的。

协议、服务与接口

协议的语法、语义与时序

协议（protocol）定义通信实体共同遵守的规则。完整协议不能只描述报文版式，还必须包含：

  • 语法（syntax）：字段顺序、长度、编码与消息格式；
  • 语义（semantics）：字段是在请求、报告、确认还是拒绝什么；
  • 时序（timing）：谁先发送、什么事件触发响应、超时后如何处理。

例如，TCP 段拥有明确的二进制语法；SYN 标志具有建立连接的语义；重传定时器和确认规则则构成时序的一部分。两个实现即使字段位置完全一致，只要状态转换理解不同，仍然无法互操作。

服务模型与编程接口

服务（service）描述某层向上层提供什么；协议描述对等实体如何协作来提供该服务；接口（interface）描述本地程序如何使用它。三者相关但不可互换。

以浏览器使用 TCP 为例：服务是端点间有序、可靠的字节流；TCP 协议通过序号、确认、定时器和流量控制提供这一抽象；套接字 API 则是浏览器请求该服务的本地编程接口。服务回答“我可以依赖什么”，协议回答“对端如何协调”，API 回答“软件怎样调用”。

分层、封装与复用

分层通过给每一层规定较窄的契约来控制复杂度。应用发送数据时，各下层依次添加控制信息，这一过程称为封装（encapsulation）：

  1. 应用创建消息，例如 HTTP 请求。
  2. 传输层加入端点与传输状态，形成 TCP 段或 UDP 数据报。
  3. 网际层加入源、目的 IP 信息，形成 IP 数据报。
  4. 链路层把数据报放入仅用于当前一跳的帧。
  5. 物理层把帧编码为信号。

接收端按相反顺序解释并移除首部。封装不仅是术语：它解释了为何路由器无需理解网页内容就能转发加密 HTTPS 流量，也解释了为什么每经过一个路由跳，以太网地址通常会改变，而目的 IP 地址通常保持端到端不变。

图片来源：Cburnett and Kbrose, UDP encapsulation, Wikimedia Commons，采用 CC BY-SA 3.0/GFDL 许可。

逆过程称为分用（demultiplexing）。链路层类型指出 IPv4 或 IPv6；IP 的协议号/下一首部指出 TCP、UDP 或其他传输协议；传输端口帮助把数据交给正确套接字；应用层成帧再从字节流中识别消息。每层都需要足够的元数据来选择下一个接收者。

TCP/IP 与 OSI 模型

OSI 是七层参考术语体系；实际部署的互联网协议族更适合用四层或五层描述。映射只是近似关系，因为真实系统不必严格服从教学图。

互联网层次 近似 OSI 层 代表协议/技术 数据单元
应用层 应用、表示、会话 HTTP、DNS、TLS、SSH 消息 / 应用数据
传输层 传输 TCP、UDP、QUIC 的传输功能 段或数据报
网际层 网络 IPv4、IPv6、ICMP IP 数据报 / 分组
链路层 数据链路 Ethernet、Wi-Fi、PPP 帧
物理层 物理 铜缆、光纤、无线电 比特 / 符号

下图明确展示了作用域：应用与传输协议端到端运行；主机和路由器都会处理 IP；链路协议只作用于相邻接口之间，而且可以逐跳变化。

图片来源：Kbrose, IP stack connections, Wikimedia Commons，采用 CC BY-SA 3.0/GFDL 许可。

分层是一种工具，而不是自然法则。跨层信息有时能够改善性能，QUIC 等技术也会组合传输、安全和面向应用的功能。设计时真正要问的是：收益是否足以抵消更紧耦合与更困难演进所带来的成本。

from dataclasses import dataclass


@dataclass(frozen=True)
class LayerOverhead:
    """一个简化协议层所增加的首部/尾部字节数。"""

    name: str
    bytes_added: int


def encapsulation_report(payload: bytes) -> list[dict[str, int | str]]:
    """展示载荷沿典型 UDP/IPv4 协议栈向下移动时如何增长。

    这里使用最小 UDP、IPv4 首部，以及基本 Ethernet II 首部和帧校验序列。
    前导码与帧间隙属于物理链路开销而不是帧内字节，因此不计入。
    """

    layers = [
        LayerOverhead("Application payload", 0),
        LayerOverhead("UDP header", 8),
        LayerOverhead("IPv4 header", 20),
        LayerOverhead("Ethernet header + FCS", 18),
    ]

    cumulative = len(payload)
    report = []
    for layer in layers:
        cumulative += layer.bytes_added
        report.append(
            {
                "stage": layer.name,
                "added_bytes": layer.bytes_added,
                "cumulative_bytes": cumulative,
            }
        )
    return report


message = b"temperature=21.7C"
for row in encapsulation_report(message):
    print(
        f"{row['stage']:<24} +{row['added_bytes']:>2} bytes"
        f" -> {row['cumulative_bytes']:>3} bytes"
    )

分组交换

分组、数据报与存储转发

长应用消息会被拆成有边界的数据单元，以便共享链路和缓冲区。分组（packet）是通用名称；IP 数据报（datagram）是能够独立转发的网际层分组；帧（frame）则是单个链路跳上的链路层数据单元。因此，同一批字节会因讨论层次不同而获得不同名称。

多数互联网路由器采用存储转发（store-and-forward）：接收足够的分组内容以完成校验与分类，将其暂存，选择输出端口，再发送到下一条链路。长度为 \(L\) 比特的分组在速率为 \(R\) bit/s 的链路上需要

\[ d_{trans}=\frac{L}{R} \]

秒才能完成串行化，这就是传输时延。它与链路的物理长度无关：12,000 bit 的分组在 100 Mb/s 链路上始终需要 \(120\ \mu s\) 才能全部送上线，无论电缆是一米还是一百公里。

图片来源：Oddbodz, Packet Switching, Wikimedia Commons，采用 CC BY-SA 3.0 许可。

若 \(N\) 个等长分组经过 \(H\) 条等速链路，并忽略传播、处理与排队时延，第一个分组需要 \(HL/R\) 到达终点；流水线填满后，其余分组每隔一个串行化时间到达：

\[ T_{N,H}=(H+N-1)\frac{L}{R}. \]

分组化让不同链路可以同时处理不同分组，但每个分组都需要首部与处理开销，因此分组过小也会浪费容量。

统计复用

互联网流量具有突发性：用户可能短时间高速下载，然后在阅读期间保持静默。统计复用（statistical multiplexing）只把链路容量分配给当前实际存在的分组，而不是为每个潜在发送者永久预留固定份额。单个流活跃时可以接近占用整条链路；多个流同时活跃时，其分组交错发送。

这种方式提高利用率，却不再提供确定性保证。多个突发可能同时到达并形成队列，因此系统需要缓冲、拥塞控制、调度与应用自适应来管理竞争。

分组交换与电路交换

属性 分组交换 电路交换
资源分配 在活跃分组之间动态共享 为会话或电路预留
突发负载 通常更高效 空闲时预留容量可能浪费
时延 会形成队列，因而可变 建立完成后通常更可预测
接纳 通常可以立即提交分组 容量不足时可能拒绝建立电路
故障响应 后续分组可经路由转向其他路径 电路需要修复或重新建立
典型用途 通用数据网络 需要严格预留服务的工作负载

两者没有绝对优劣。分组交换适合多样且突发的互联网应用；当系统必须提供硬性服务保证，并且有接纳控制保护预留资源时，电路或资源预留仍然有价值。

队列、缓冲区与丢包

当分组到达速度超过输出链路的串行化速度时，输出队列就会增长。令 \(\lambda\) 为平均分组到达率，\(L\) 为平均分组长度，\(R\) 为输出速率，则负载为

\[ \rho=\frac{\lambda L}{R}. \]

当 \(\rho\) 接近 1 时，即使短暂突发也可能造成很大的排队时延；若长期负载超过容量，即 \(\rho>1\)，任何有限缓冲区都无法阻止队列持续增长。缓冲区满后，新到或被选中的已排队分组会被丢弃。增大缓冲可以减少短期丢包，却可能产生缓冲区膨胀（bufferbloat）：分组没有丢失，但交互时延极高。

因此，排队并非偶然实现细节，而是竞争流量与有限资源相遇的位置；它直接影响时延、公平性、丢包以及发送端可见的拥塞信号。

代码 
def packet_pipeline_time(
    packet_bytes: int,
    link_rates_mbps: list[float],
    packet_count: int,
) -> dict[str, float]:
    """计算理想存储转发流水线的完成时间。

    假设：
    1. 所有分组大小相同；
    2. 链路初始空闲且缓冲无限；
    3. 忽略处理与传播时延；
    4. 路由器收到完整分组后才开始转发。
    """

    packet_bits = packet_bytes * 8
    serialization = [
        packet_bits / (rate_mbps * 1_000_000)
        for rate_mbps in link_rates_mbps
    ]

    # 第一个分组必须在每条链路上各完成一次串行化。
    first_packet_seconds = sum(serialization)

    # 后续分组按最慢（瓶颈）链路的节奏离开流水线。
    pipeline_spacing_seconds = max(serialization)
    total_seconds = first_packet_seconds + (packet_count - 1) * pipeline_spacing_seconds

    return {
        "first_packet_ms": first_packet_seconds * 1_000,
        "bottleneck_spacing_ms": pipeline_spacing_seconds * 1_000,
        "all_packets_ms": total_seconds * 1_000,
    }


result = packet_pipeline_time(
    packet_bytes=1_500,
    link_rates_mbps=[10, 100, 20],
    packet_count=5,
)

for metric, value in result.items():
    print(f"{metric:<25} {value:8.3f}")

网络性能

处理、排队、传输与传播时延

一个分组在单个节点上的节点时延通常分解为

\[ d_{nodal}=d_{proc}+d_{queue}+d_{trans}+d_{prop}. \]

  • \(d_{proc}\)：校验字段、分类分组并选择输出的处理时间；
  • \(d_{queue}\)：等待更早分组的时间，随流量与调度策略改变；
  • \(d_{trans}=L/R\)：把 \(L\) 比特串行化到速率为 \(R\) 的链路上的时间；
  • \(d_{prop}=D/s\)：信号以介质速度 \(s\) 传播距离 \(D\) 的时间。

最常见的错误是混淆传输与传播。提高链路速率能够降低 \(L/R\)，却不能让信号超过介质传播速度；把服务部署得更近能够降低 \(D/s\)，却无法修复低速接入链路。提出优化方案之前，必须先定位主导项。

多跳路径的简化单向时延是各跳之和：

\[ d_{path}\approx\sum_{i=1}^{H}\left(d_{proc,i}+d_{queue,i}+\frac{L}{R_i}+\frac{D_i}{s_i}\right). \]

真实流量还受分组大小变化、操作系统调度、无线重传、路由变化、传输层恢复与应用依赖影响，但这项分解仍能告诉我们应该测量什么。

往返时延与抖动

往返时延（RTT）是从发送请求或探测，到收到对应响应或确认之间的时间。RTT 不一定等于单向时延的两倍，因为正反向路径可能不同，端点处理也可能不对称。

抖动（jitter）描述分组时延的变化。平均时延相同的两条路径可能带来完全不同的体验；交互语音和游戏尤其敏感，因为迟到的数据即使最终到达也可能已经无用。接收方可以用播放缓冲吸收部分波动，其代价是增加固定时延。

吞吐量、瓶颈与有效吞吐量

带宽/链路容量是物理或配置速率，吞吐量（throughput）是某段时间内实际交付的数据速率。串行路径上的持续吞吐量不可能超过最慢的有效资源：

\[ Throughput\leq\min(R_1,R_2,\ldots,R_H). \]

最小速率链路是瓶颈，但竞争流、协议开销、接收端限制、拥塞控制、丢包恢复和应用行为都可能让观测吞吐量进一步下降。

有效吞吐量（goodput）只计算单位时间内交付的有用应用载荷，不包含协议首部、重传字节、重复或不可用数据。因此链路可能非常繁忙、吞吐量很高，但应用 goodput 很差，频繁重传就是典型例子。

带宽时延积与 Little 定律

带宽时延积（BDP）估算一条路径中能够同时在途的数据量：

\[ BDP=R\times RTT. \]

100 Mb/s、RTT 为 40 ms 的路径，其 BDP 为 4,000,000 bit，约 500 kB。可靠传输协议需要允许足够多的数据在途才能填满路径；若发送窗口只有 64 kB，无论物理链路多快都无法持续达到 100 Mb/s。

Little 定律把平均系统内数量 \(N\)、平均到达率 \(\lambda\) 与平均停留时间 \(W\) 联系起来：

\[ N=\lambda W. \]

对于稳定队列，若每秒通过 2,000 个分组，每个分组平均停留 5 ms，则平均队列占用为 \(2{,}000\times0.005=10\) 个分组。该定律不会解释时延为何产生，却能在速率、停留时间和在途工作量之间提供有力的一致性检查。

from dataclasses import dataclass


@dataclass(frozen=True)
class Link:
    rate_mbps: float
    distance_km: float
    propagation_speed_m_s: float = 2.0e8  # 光纤或铜缆中的近似传播速度。


def estimate_path(
    packet_bytes: int,
    links: list[Link],
    processing_ms_per_hop: float = 0.05,
    queueing_ms_per_hop: float = 0.0,
) -> dict[str, float]:
    """估算单向分组时延及相关路径量。"""

    packet_bits = packet_bytes * 8
    transmission_s = sum(
        packet_bits / (link.rate_mbps * 1_000_000)
        for link in links
    )
    propagation_s = sum(
        (link.distance_km * 1_000) / link.propagation_speed_m_s
        for link in links
    )
    processing_s = len(links) * processing_ms_per_hop / 1_000
    queueing_s = len(links) * queueing_ms_per_hop / 1_000

    one_way_s = transmission_s + propagation_s + processing_s + queueing_s
    estimated_rtt_s = 2 * one_way_s
    bottleneck_bps = min(link.rate_mbps for link in links) * 1_000_000
    bdp_bytes = bottleneck_bps * estimated_rtt_s / 8

    return {
        "transmission_ms": transmission_s * 1_000,
        "propagation_ms": propagation_s * 1_000,
        "processing_ms": processing_s * 1_000,
        "queueing_ms": queueing_s * 1_000,
        "one_way_ms": one_way_s * 1_000,
        "estimated_rtt_ms": estimated_rtt_s * 1_000,
        "bottleneck_mbps": bottleneck_bps / 1_000_000,
        "bdp_kib": bdp_bytes / 1024,
    }


path = [
    Link(rate_mbps=100, distance_km=2),
    Link(rate_mbps=1_000, distance_km=1_200),
    Link(rate_mbps=200, distance_km=20),
]

metrics = estimate_path(
    packet_bytes=1_500,
    links=path,
    processing_ms_per_hop=0.08,
    queueing_ms_per_hop=1.2,
)

for name, value in metrics.items():
    print(f"{name:<22} {value:9.3f}")

互联网设计原则

尽力而为交付与“细腰”结构

IP 有意只提供有限的尽力而为数据报服务（best-effort datagram service）：它尝试交付，却不保证分组一定到达、只到达一次、按序到达或在截止时间前到达。这些缺失并不意味着 IP 尚未完成；恰恰是这个小而通用的服务，才能运行在大量链路技术之上，同时承载大量传输协议与应用。

这就是互联网的细腰/沙漏体系结构。IP 上方是众多应用和传输选择，下方是以太网、Wi-Fi、光纤、蜂窝、卫星及未来链路技术。共同的 IP 层让上下两侧都能独立创新，而无需每个应用理解每一种物理网络。

收益是互操作性和可演进性；代价是应用无法仅凭 IP 推断强性能或可靠性保证，必须选择合适的传输协议、应对失败，并测量真正影响用户的指标。

端到端原则

端到端论证关注某项功能在哪里才能被完整且正确地实现。若正确性依赖只有端点掌握的应用知识，那么仅在网络内部实现该功能，仍不能免除端点的责任。

可靠文件传输是经典例子。链路校验和与局部重试能够减少损坏并提升性能，但只有发送者和接收者能确认预期的完整文件是否正确保存，因此端到端校验仍不可缺少。同样，网络可以过滤或加密单条链路，但只有端点认证与端到端加密才能跨越所有中间网络保护完整应用交换。

这并不是说网络内部不应提供任何功能；低层机制可以是重要的性能增强。该原则只是提醒我们，不要把局部机制误当成端到端正确性保证。原始论述见 Saltzer、Reed 与 Clark 的 End-to-End Arguments in System Design，互联网体系结构指导还可参见 RFC 1958。

命运共享与软状态

命运共享（fate sharing）把关键通信状态放在真正依赖该通信的端点上。路由器重启时，端点传输状态不应随之消失；后续分组可以经过恢复后的路径或替代路径。这让由独立故障设备组成的网络更具韧性。

互联网核心并非字面意义上的无状态：路由器保存转发表、邻居信息、队列、计数器和控制平面状态。关键区别在于，普通 IP 路由器不需要为每个应用连接保存状态，仍可转发每个数据报。RFC 1122 描述了网关独立转发 IP 数据报、端到端可靠性状态由主机保存的体系结构假设。

软状态（soft state）若未被刷新就会自动过期。当显式清理消息可能丢失时，这种设计很有用。ARP/邻居缓存项、学习到的路由和 NAT 映射通常都有超时。过期机制帮助系统从陈旧信息中恢复，但刷新流量和超时值本身也成为设计的一部分。

可扩展性、鲁棒性与可演进性

原则 带来的能力 代价或失效方式
最小共同 IP 服务 多种链路与应用互操作 应用必须补充缺失保证
分层聚合 缩小路由与转发状态 聚合可能限制流量工程
端到端状态 中间设备故障不必摧毁连接逻辑 端点更复杂
统计共享 对突发流量保持较高利用率 排队时延与丢包会变化
开放且可扩展的协议 支持独立实现与演进 新选项可能被旧中间盒阻断
分散管理 无需单一运营者拥有互联网 难以进行全局优化和统一策略

鲁棒的体系结构不是“永不失败”，而是能够隔离、检测故障并在无需全球协调的情况下恢复。可演进体系结构还必须允许增量部署：即使全新设计很优雅，若要求所有主机、路由器和运营者同时升级，它也几乎不可能成功。

标准与协议演进

IETF、RFC 与开放标准

互操作需要独立团队都能实现的规范。互联网工程任务组（IETF）通过开放工作组、公开讨论、实现经验、评审与粗略共识制定大量互联网协议。常见流程是：

  1. 先把想法写成 Internet-Draft；
  2. 工作组讨论范围、设计、安全、运维和互操作性；
  3. 实现与部署暴露文字规范中的歧义或不现实假设；
  4. 互联网工程指导委员会评审合适的文档；
  5. RFC Editor 将获批文档发布到长期保存的 Request for Comments（RFC）系列。

RFC 不一定都是互联网标准，其中还包括最佳当前实践、信息性、实验性和历史文档。阅读时必须检查状态、更新关系和勘误。当前流程可参考 IETF standards-process guide，其正式基础来自 RFC 2026 及后续更新。

开放标准降低协调成本：不同厂商的浏览器、操作系统、路由器和服务器无需私下逐对协商即可通信。但文字规范仍不够，多实现互操作测试才能暴露描述中未写明的假设。

互操作性与协议僵化

成功部署反而可能让协议更难改变。中间盒可能假设熟悉字段永远取熟悉值、丢弃未知选项，或检查端点原本希望继续演进的信息。实现者发现新行为在部分路径上失败后便不敢采用，这就是协议僵化（protocol ossification）：实际部署的网络冻结了正式契约之外的细节。

解决办法并非简单增加扩展字段。扩展只有在旧系统能够安全忽略、端点能够发现支持，而且部署者立即获得收益时才容易成功。QUIC 展示了一条路径：在 UDP 上运行、加密大量控制信息，并让许多传输功能在端点用户态软件中演进。相较于修改每个操作系统和中间盒中的 TCP，这更易部署，但也引入新的运维与可观测性权衡。

评估协议改动时，应问四个问题：能否增量部署？与旧对端交互时能否保留有用行为？中间设备是否容忍未知值？承担部署成本的一方是否获得收益？技术质量很重要，但部署机制往往决定协议能否真正落地。

一次 HTTPS 请求的端到端旅程

下面把本章抽象串成一个具体事件。真实浏览器会并行执行、使用缓存、复用连接、竞速多个候选并联系多个服务，但这些阶段仍是推理与排障的有效框架。

接入本地网络

访问网站前，设备必须先获得本地可达性：

  1. 通过以太网连接、Wi-Fi 认证与关联，或蜂窝网络附着建立链路；
  2. 主机获取网络配置，IPv4 常用 DHCP，IPv6 常用路由器通告，也可能使用 DHCPv6；
  3. 配置给出地址与前缀、默认网关及一个或多个 DNS 解析器；
  4. 要向同一链路上的下一跳发送帧，主机用 IPv4 的 ARP 或 IPv6 的邻居发现，把下一跳 IP 映射成链路层地址。

默认网关不是“到所有目的地的完整路径”，而是在没有更具体本地路由匹配时选择的第一个本地下一跳。后续每台路由器都会独立选择自己的下一跳。

此阶段故障通常会影响所有远程服务。应检查接口是否启用、地址是否合理、默认路由是否存在、网关是否可达，以及本地 DNS 地址是否已配置。

解析名称并选择目的地

浏览器使用 www.example.com 这样的名称，而 IP 转发需要目的地址。解析通常先经过多级缓存，再由递归 DNS 解析器继续查询。回答可能包含 IPv4 的 A 记录、IPv6 的 AAAA 记录、CNAME 链或更新的服务绑定信息，以及代表副本、负载均衡或 CDN 的多个地址。

DNS 不只是全球电话簿。回答会随时间、客户端网络、解析器位置、服务策略与健康状态变化。现代客户端会异步查询 IPv4/IPv6，并竞速连接候选，使某个地址族故障时不会产生长时间可见停顿。RFC 8305 描述了广泛部署的 Happy Eyeballs v2。

DNS 完成后仍需认证。地址只说明把分组发往哪里；有效 TLS 证书以及对私钥的持有证明，才帮助客户端确认该端点有权代表所请求的主机名。

穿越链路、路由器与自治系统

主机从本地路由表选择路由，并把 IP 数据报封装进发往第一跳的帧。路由器依次执行：

  1. 输入链路校验并交付帧；
  2. 移除当前链路层封装；
  3. 校验相关 IP 字段，并递减 IPv6 Hop Limit 或 IPv4 TTL；
  4. 在转发表中执行最长前缀匹配；
  5. 把数据报放入相应输出接口队列；
  6. 为下一跳创建新的链路层帧。

因此，链路首部逐跳变化；源、目的 IP 通常标识端到端数据报，但 NAT 可在管理边界重写地址与端口。传输端口标识端点套接字，而不是沿途路由器。

ISP 或企业内部由内部网关协议帮助建立转发状态；自治系统之间则由 BGP 通告与策略共同影响 AS 路径。响应的返回路径可能不同，所以单向 traceroute 永远不能证明路径完全对称。

建立安全传输并交换内容

HTTP/1.1 或 HTTP/2 通常先完成 TCP 握手，再完成 TLS 握手。TLS 协商密码参数、认证服务器证书、派生共享流量密钥并保护后续 HTTP 字节；HTTP/2 可在一条安全连接上复用多个流。

HTTP/3 使用基于 UDP 的 QUIC。QUIC 把传输与 TLS 1.3 握手结合起来，提供互相独立的多条流，避免 TCP 在流之间产生队头阻塞，并可主要通过用户态实现演进；它仍然依赖 IP 与相同的底层分组路径。

安全传输建立后，浏览器发送含方法、目标、首部和可选正文的 HTTP 请求，边缘或源站返回状态、首部与内容。页面渲染又可能触发数十到数百个依赖请求，因此连接复用、缓存、压缩、CDN 位置与请求优先级可能和第一个对象的传输时间一样重要。

用户可见总时延是一张依赖图，而不是一个孤立数字：

\[ T_{page}\approx T_{local}+T_{DNS}+T_{connect}+T_{secure}+T_{request/response}+T_{render/dependencies}. \]

现代客户端会并发执行部分阶段，所以该表达式是诊断清单，而不是严格串行执行公式。

代码 
import socket
import ssl
from time import perf_counter


def measure_https_head(
    host: str = "example.com",
    port: int = 443,
    timeout: float = 5.0,
) -> dict[str, object]:
    """测量一次简单 HTTPS 请求的主要阶段。

    这是教学探针而不是浏览器基准。浏览器会缓存 DNS、复用连接、协商
    HTTP/2 或 HTTP/3、竞速地址并并发执行工作。仅在允许访问外部网络的
    环境运行本单元。
    """

    # 阶段 1：把主机名解析为候选 TCP 端点。
    started = perf_counter()
    candidates = socket.getaddrinfo(
        host,
        port,
        type=socket.SOCK_STREAM,
    )
    dns_ms = (perf_counter() - started) * 1_000

    # 这个简化示例只尝试解析器返回的第一个候选；生产客户端
    # 应处理失败，并可能并行竞速 IPv6/IPv4 候选。
    family, socktype, proto, _, sockaddr = candidates[0]

    context = ssl.create_default_context()
    with socket.socket(family, socktype, proto) as raw_socket:
        raw_socket.settimeout(timeout)

        # 阶段 2：建立 TCP 传输连接。
        started = perf_counter()
        raw_socket.connect(sockaddr)
        tcp_ms = (perf_counter() - started) * 1_000

        # 阶段 3：认证服务器并派生 TLS 流量密钥。
        started = perf_counter()
        with context.wrap_socket(raw_socket, server_hostname=host) as tls_socket:
            tls_ms = (perf_counter() - started) * 1_000

            request = (
                f"HEAD / HTTP/1.1\r\n"
                f"Host: {host}\r\n"
                "Connection: close\r\n\r\n"
            ).encode("ascii")

            # 阶段 4：发送 HTTP 请求并等待首个响应字节。
            started = perf_counter()
            tls_socket.sendall(request)
            first_chunk = tls_socket.recv(4_096)
            time_to_first_byte_ms = (perf_counter() - started) * 1_000

            status_line = first_chunk.split(b"\r\n", 1)[0].decode(
                "iso-8859-1",
                errors="replace",
            )

            return {
                "selected_address": sockaddr[0],
                "dns_ms": round(dns_ms, 2),
                "tcp_connect_ms": round(tcp_ms, 2),
                "tls_handshake_ms": round(tls_ms, 2),
                "request_to_first_byte_ms": round(time_to_first_byte_ms, 2),
                "tls_version": tls_socket.version(),
                "status_line": status_line,
            }


# 网络测量每次都会变化，应比较阶段而不是孤立数值。
measure_https_head()

# HTTP/TLS 行为与响应首部
curl.exe -I -v https://example.com/

任何单一工具都无法给出整条互联网路径的绝对真相。tracert 依赖路由器返回 ICMP，某些跳超时并不代表转发失败；DNS 时延可能命中热缓存；curl 与浏览器可能选择不同协议或地址。测量只是某个端点在某个时刻获得的观察。

可以按照请求阶段定位问题：

症状 可能阶段 应收集的证据
没有地址或默认路由 本地网络配置 接口状态、DHCP/RA 结果、路由表
名称失败但直接使用 IP 可通信 DNS 解析器配置、A/AAAA 回答、超时或错误码
DNS 成功但无法连接 443 路由、防火墙、服务器可达性或传输建立 所选地址、TCP 结果、另一地址族、路径探测
TCP 已连接但证书验证失败 TLS 身份、系统时间、信任库或拦截 证书链、主机名、有效期、TLS 告警
首字节很慢 排队、RTT、服务器计算、缓存未命中或上游依赖 分阶段计时、重复样本、服务器追踪、跨区域比较
很快开始但持续下载很慢 瓶颈速率、拥塞控制、丢包或接收端/应用限制 吞吐量、重传、RTT 变化、窗口与 CPU 状态

这种分层诊断可以避免常见误治：接入队列过载时去改 DNS，传播时延主导时只扩容带宽，或证书无效时把问题归咎于路由。

对比与总结

本章最重要的概念很容易在日常表达中被混为一谈：

不要混淆 关键区别
互联网与 Web 分组基础设施/协议生态，与建立其上的一种应用家族
服务、协议与 API 上层可依赖的抽象、对等实体规则、本地调用方式
分组、IP 数据报与帧 通用数据单元、网际层单元、单跳链路层单元
交换机与路由器 链路域内按帧转发，与网络间按 IP 转发
传输与传播时延 把比特串行送上线的时间，与信号跨越距离的时间
带宽、吞吐量与 goodput 容量、实际交付速率、有用应用载荷速率
Hop 与 AS 一次转发步骤，与一个管理/路由策略域
可达性与身份 能向地址发送，与端点确实获授权代表某名称

完整的心智追踪如下：

  1. 应用通过套接字等接口请求网络服务；
  2. 协议层逐层封装应用数据，加入各自作用域所需的元数据；
  3. 本地链路把帧送到下一跳，路由器逐跳转发其中的 IP 数据报；
  4. 分组交换统计共享有限链路，所以竞争时会出现队列与丢包；
  5. 端到端性能由处理、排队、串行化、传播、传输协议行为和应用依赖共同决定；
  6. 自治网络依靠开放协议与策略合作，而非一个全球控制器；
  7. IP 核心有意只提供尽力而为服务，可靠性、身份与应用语义由端点补充。

后续章节将依次深入链路与 LAN、IP 转发、路由、传输可靠性、拥塞控制、应用、安全、运维和可编程网络基础设施。分组的一生就是把这些细节连成整体的地图。
