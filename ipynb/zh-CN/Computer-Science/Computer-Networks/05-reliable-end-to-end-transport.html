可靠的端到端传输

IP 只提供尽力而为的数据报交付，而应用常希望看到进程到进程通信、完整消息、有序字节流、故障检测或并发多路流。传输层位于应用与 IP 之间，通过端口和套接字把主机可达性扩展成进程可达性，并根据应用需求选择极简数据报或复杂可靠连接。

本章先从 UDP 的消息抽象出发，再从不可靠信道逐步构造可靠数据传输：校验和发现损坏，序号区分新旧数据，ACK 表达接收状态，定时器触发重传，滑动窗口让多份数据同时在途。随后把这些原理映射到 TCP 的字节序号、连接状态、RTO、流量控制与 SACK，并以 QUIC 展示现代传输如何在 UDP 之上重新组合可靠性、安全与多流能力。

注记

可靠传输不是“分组绝不丢失”，而是端点协议在允许的故障模型下，让应用最终只观察到符合契约的数据。网络仍会丢包、重复、乱序；协议通过状态、反馈和重传隐藏或报告这些事件。

传输层服务

进程到进程通信

IP 地址把数据报带到主机接口，但同一主机可能同时运行浏览器、DNS、数据库和许多连接。传输层在端系统中运行，使用端口与连接状态把到达数据交给正确进程，并允许应用选择可靠字节流、无连接消息或多流安全传输。

路由器通常只需要转发 IP；端到端传输状态由主机保存。这种命运共享让中间路由故障不必摧毁连接逻辑，也让传输协议能独立于核心网络演进。

端口、套接字、复用与分用

端口号为 16 bit。套接字（socket）是应用访问传输服务的本地端点，通常由协议、地址和端口等状态标识。发送端把多个进程的数据复用到网络，接收端再分用到对应套接字。

UDP 常按本地地址与目的端口分用；TCP 连接通常由四元组 (源IP, 源端口, 目的IP, 目的端口) 加协议唯一标识，因此同一服务器端口可同时服务大量客户端。

无连接与面向连接的服务

无连接服务无需先建立共享会话状态，每个数据报独立携带目的信息，启动快但应用自行处理丢失、顺序和重复。面向连接服务先同步状态并在生命周期内维护序号、窗口、定时器和关闭语义，提供更强抽象，但握手、状态与失败恢复都有成本。

“连接”是端点协议状态，不是沿途预留了一条物理电路。TCP 连接的分组仍可在分组交换网络中经过变化的队列与路径。

传输保证与应用需求

应用需求 可能选择 需要权衡
完整、有序字节流 TCP 队头阻塞、连接状态与恢复时延
独立消息、最低机制 UDP 应用自行处理丢失、拥塞与安全

没有“对所有应用最好的传输”。文件复制重视完整性，交互语音重视截止时间，DNS 查询重视短消息和快速失败，Web 则需要安全、并发、移动和拥塞适应。选择应从应用可观察契约开始。

用户数据报协议

UDP 首部与校验和

UDP 首部只有源端口、目的端口、长度和校验和四个 16-bit 字段。长度覆盖首部与载荷；校验和覆盖 UDP 数据及包含 IP 地址、协议号和长度的伪首部，从而也能发现错误交付到错误端点的情况。IPv4 中发送端在特定条件下可省略 UDP 校验和，IPv6 中通常必须使用。

UDP 没有连接握手、确认、重传、排序、流量控制或内建拥塞控制。“首部小”只是表面优势，更重要的是应用能够决定哪些机制需要、在何时需要。

数据报边界与消息丢失

每次 UDP send 产生一个逻辑数据报，接收端一次读取一个数据报并保留消息边界。若接收缓冲太小，多余部分可能被截断或丢弃；IP 分片丢失、队列丢包、校验失败或套接字缓冲溢出都会让整条消息消失。数据报可能重复、乱序，也可能来自伪造源地址。

这与 TCP 字节流不同：TCP 不保留应用写入边界，一次 send 可能被分成多段，多次 send 也可能一次 recv 返回。使用 TCP 的应用必须自行定义长度字段、分隔符或固定格式来成帧。

何时 UDP 是合适抽象

UDP 适合单次请求/响应、实时媒体、组播、应用自定义可靠性以及 QUIC 这类用户态传输。它避免强制有序重传，但应用仍必须限制发送速率、应对放大攻击、设置超时、验证来源，并在需要时实现拥塞控制。UDP 不是“无需负责”，而是把机制选择权交给应用。

import ipaddress
import struct


def ones_complement_sum(data: bytes) -> int:
    """返回 UDP/TCP 使用的折叠反码和。"""
    if len(data) % 2:
        data += b"\x00"  # 填充参与校验和计算，但不计入分组长度。
    total = sum(struct.unpack(f"!{len(data) // 2}H", data))
    while total >> 16:
        total = (total & 0xFFFF) + (total >> 16)
    return total


def internet_checksum(data: bytes) -> int:
    result = (~ones_complement_sum(data)) & 0xFFFF
    return 0xFFFF if result == 0 else result


def build_udp_segment(source_ip: str, destination_ip: str,
                      source_port: int, destination_port: int,
                      payload: bytes) -> bytes:
    udp_length = 8 + len(payload)
    header_without_checksum = struct.pack(
        "!HHHH", source_port, destination_port, udp_length, 0
    )
    pseudo_header = (
        ipaddress.IPv4Address(source_ip).packed
        + ipaddress.IPv4Address(destination_ip).packed
        + struct.pack("!BBH", 0, 17, udp_length)  # 17 是 UDP 对应的 IP 协议号。
    )
    checksum = internet_checksum(pseudo_header + header_without_checksum + payload)
    return struct.pack(
        "!HHHH", source_port, destination_port, udp_length, checksum
    ) + payload


payload = b"transport"
segment = build_udp_segment("192.0.2.10", "198.51.100.20", 53000, 53, payload)
source_port, destination_port, udp_length, checksum = struct.unpack("!HHHH", segment[:8])

pseudo = (
    ipaddress.IPv4Address("192.0.2.10").packed
    + ipaddress.IPv4Address("198.51.100.20").packed
    + struct.pack("!BBH", 0, 17, udp_length)
)
verified = ones_complement_sum(pseudo + segment) == 0xFFFF

print(f"ports: {source_port} -> {destination_port}")
print(f"UDP length: {udp_length} bytes; payload: {len(payload)} bytes")

可靠数据传输原理

比特错误、丢失、重复与乱序

不可靠信道可能改变比特、丢弃报文、延迟后又送达、重复交付，或让不同路径和重传造成乱序。可靠协议必须明确故障模型：若网络能无限延迟一个报文，就无法仅凭等待区分“丢失”与“非常慢”；因此超时只是重传决策，不是丢失的绝对证明。

校验和、序号、ACK 与 NACK

校验和帮助接收端拒绝损坏报文；序号把新数据与重传/重复分开；ACK 表示已收到某些数据，NACK 明确指出错误或缺失。累计 ACK 表示“此序号之前均已连续收到”，选择确认则报告额外不连续区间。确认自身也会丢失，所以发送端不能把“没见到 ACK”直接等同于“数据没到”。

定时器与重传

发送端为未确认数据维护定时器，超时后重传。超时过短会在网络只是变慢时产生虚假重传，加重拥塞；过长则恢复缓慢。协议通常根据测得 RTT 自适应，并对连续超时指数退避。ACK 触发的快速重传可在定时器到期前发现间隙。

协议状态机与安全性质

可靠协议可表示为有限状态机：状态记录期望序号、窗口和定时器，事件包括应用提交、报文到达、ACK 到达与超时，转换产生发送、交付或重传动作。需要证明的安全性包括“不交付损坏数据”“不重复交付”“保持规定顺序”；活性则要求在信道最终能够传递且持续重试的条件下，数据最终前进。代码看似简单，边界时序却决定正确性。

def alternating_bit_with_lost_ack(message: str):
    """跟踪第一次 ACK 丢失时的一次传输。"""
    sender_sequence = 0
    receiver_expected = 0
    delivered = []
    events = []

    # 第一次发送到达接收方。
    events.append(f"send DATA({sender_sequence}, {message})")
    if sender_sequence == receiver_expected:
        delivered.append(message)
        receiver_expected ^= 1
        events.append("receiver delivers message and sends ACK(0)")

    # 信道丢失 ACK(0)，发送方不能安全推进。
    events.append("channel loses ACK(0); sender timer expires")
    events.append(f"retransmit DATA({sender_sequence}, {message})")

    # 接收方此时期待 1，因此能识别序号 0 为重复。
    if sender_sequence != receiver_expected:
        events.append("receiver suppresses duplicate and repeats ACK(0)")

    events.append("sender receives ACK(0) and advances to sequence 1")
    return events, delivered


trace, application_deliveries = alternating_bit_with_lost_ack("A")
for step, event in enumerate(trace, start=1):
    print(f"{step}. {event}")
print("application deliveries:", application_deliveries)

停等协议

交替位协议

发送端一次只允许一个未确认分组，并用 0/1 序号交替。接收端只接受当前期望位：正确新分组被交付并确认；重复分组不再次交付，但会重发相同 ACK。发送端收到匹配 ACK 后切换序号，否则超时重传。一个比特足够，是因为同时最多只有一代数据在途。

利用率与带宽时延积

若发送一个长度 \(L\) 的分组需要 \(L/R\)，收到 ACK 约需一个 RTT，则忽略 ACK 发送时间时，停等发送方利用率近似为

\[ U\approx\frac{L/R}{RTT+L/R}. \]

在高带宽、长 RTT 路径上，发送端绝大多数时间都在等待。路径的 BDP 很大，而停等协议只允许一个分组填充它。

为什么一个在途分组不够

要充分利用容量，窗口至少要覆盖约一个 BDP 的数据。允许 \(W\) 个长度为 \(L\) 的分组在途时，理想发送速率上限约为 \(WL/RTT\)，并受瓶颈链路限制。扩大窗口提高吞吐，却需要更大的序号空间、发送/接收缓冲和更精确的丢失处理，这就引出滑动窗口协议。

from math import ceil


def stop_and_wait_metrics(rate_mbps: float, rtt_ms: float, packet_bytes: int):
    rate_bps = rate_mbps * 1_000_000
    packet_bits = packet_bytes * 8
    transmission_s = packet_bits / rate_bps
    rtt_s = rtt_ms / 1_000
    utilization = transmission_s / (rtt_s + transmission_s)
    throughput_mbps = utilization * rate_mbps
    bdp_bytes = rate_bps * rtt_s / 8
    packets_for_bdp = ceil(bdp_bytes / packet_bytes)
    return transmission_s * 1_000, utilization, throughput_mbps, bdp_bytes, packets_for_bdp

    (100, 40, 1500),
    (1000, 2, 1500),
    (1000, 80, 1500),
]

        rate, rtt, packet_size

流水化可靠传输

滑动窗口

发送窗口描述当前允许发送但尚未全部确认的序号区间。ACK 到达后窗口基序号前移，新的数据获得发送资格。接收窗口描述当前可接受的序号。窗口把流量限制与序号状态结合，使多个分组同时占据路径。

回退 N 帧

Go-Back-N（GBN）允许发送端有多个未确认分组，但接收端通常只接受下一个期望序号，并对最后连续收到的数据发送累计 ACK。若分组 \(k\) 丢失，后续乱序分组被丢弃；发送端超时后从 \(k\) 起重传所有未确认分组。

GBN 接收端简单、状态少，但单个丢包会重复发送已到达数据，在大窗口或高损失路径上浪费明显。

选择重传

Selective Repeat（SR）允许接收端缓存窗口内乱序分组并分别确认；发送端只重传缺失或超时的分组。它提高链路利用率，却要求每个分组定时器/状态、更多接收缓冲以及更严格的序号回绕处理。

序号空间与窗口大小约束

序号会按模 \(N\) 回绕。对于 SR，若窗口过大，接收端可能无法区分很久以前延迟的旧分组与回绕后的新分组；常见安全约束为窗口大小不超过序号空间一半。GBN 的接收窗口较小，可允许发送窗口最多 \(N-1\)。约束来自歧义避免，而非实现习惯。

GBN 与 SR 对比

维度 Go-Back-N Selective Repeat
接收乱序数据 通常丢弃 缓存
ACK 累计确认 可逐个/选择确认
丢一个分组后的重传 从缺口起整段重传 只重传缺失项
接收状态 较少 较多
高 BDP/损失效率 较低 较高

TCP 不是两者的纯粹复制：累计 ACK、SACK、快速重传和拥塞控制共同形成混合行为。

def compare_recovery(total_packets: int, lost_packet: int):
    """统计首轮发生一次孤立丢失时的发送次数。"""
    initial = list(range(total_packets))

    # GBN 收到缺口后的分组但将其丢弃；当
    # 最早未确认定时器到期时，从缺口开始的所有分组都会重传。
    gbn_retransmissions = list(range(lost_packet, total_packets))

    # SR 缓存后续分组，只重传缺失项。
    sr_retransmissions = [lost_packet]

    return {
        "GBN": initial + gbn_retransmissions,
        "Selective Repeat": initial + sr_retransmissions,
    }


traces = compare_recovery(total_packets=6, lost_packet=2)
for protocol, transmissions in traces.items():
    print(f"{protocol:16}: {transmissions} ({len(transmissions)} transmissions)")

avoided = len(traces["GBN"]) - len(traces["Selective Repeat"])
print("transmissions avoided by selective recovery:", avoided)

传输控制协议

字节流与 TCP 段

TCP 向应用提供双向、可靠、有序字节流。它不保留应用消息边界；发送实现会按 MSS、拥塞窗口、Nagle 等因素把字节切成段，接收 API 则返回当前可用的任意连续字节数。应用必须自定义消息成帧。

TCP 首部字段

TCP 首部包含源/目的端口、32-bit 序号与确认号、首部长度、控制标志、接收窗口、校验和、紧急指针和选项。SYN/FIN 各消耗一个序号；ACK 表示确认字段有效；RST 异常终止连接；选项可协商 MSS、窗口扩大、时间戳与 SACK。

序号与确认号

TCP 序号标识段中第一个数据字节在流中的位置；确认号表示“下一个期望字节”。若 ACK 为 1500，就意味着 1500 之前的所有字节均已连续收到。初始序号随机选择，避免旧连接中的延迟段与新连接混淆，并提高抵抗伪造的难度。

累计 ACK 与选择确认

累计 ACK 遇到缺口时停在第一个缺失字节，即使更后的数据已缓存。SACK 选项额外报告已收到的不连续范围，使发送端只重传真正缺失字节。

ACK 也可以延迟或合并，因此发送端根据 ACK 进展和重复模式推断网络状态，而不能假定每个段都有独立 ACK。

class TcpLikeReceiver:
    """带累计 ACK 与 SACK 输出的小型字节区间重组器。"""

    def __init__(self, initial_sequence: int):
        self.next_expected = initial_sequence
        self.buffered = []  # 互不相交的左闭右开区间 [start, end)。

    def receive(self, sequence: int, length: int):
        self.buffered.append((sequence, sequence + length))
        self.buffered.sort()

        # 合并重叠或相邻区间。
        merged = []
        for start, end in self.buffered:
            if not merged or start > merged[-1][1]:
                merged.append([start, end])
            else:
                merged[-1][1] = max(merged[-1][1], end)
        self.buffered = [tuple(interval) for interval in merged]

        # 消费起点不晚于下一个期望字节的所有区间。
        advanced = True
        while advanced:
            advanced = False
            remaining = []
            for start, end in self.buffered:
                if start <= self.next_expected < end:
                    self.next_expected = end
                    advanced = True
                elif end > self.next_expected:
                    remaining.append((start, end))
            self.buffered = remaining

        sacks = [interval for interval in self.buffered if interval[0] > self.next_expected]
        return self.next_expected, sacks

TCP 连接生命周期

三次握手

客户端发送 SYN seq=x，服务器回复 SYN+ACK seq=y ack=x+1，客户端再发送 ACK ack=y+1。三次消息让双方确认双向可达、同步各自初始序号，并协商 MSS、窗口扩大、SACK、时间戳等选项。

两次消息不足以让服务器确认客户端已收到服务器的初始序号；三次也不是为“加密”，普通 TCP 握手不认证身份，TLS 在其后完成安全协商。

连接状态机

客户端典型状态为 CLOSED → SYN-SENT → ESTABLISHED；服务器监听时处于 LISTEN，收到 SYN 后进入 SYN-RECEIVED。关闭涉及 FIN-WAIT、CLOSE-WAIT、LAST-ACK、TIME-WAIT 等状态。状态机解释了抓包中的标志，也能定位应用忘记关闭、半开连接或积压队列问题。

优雅关闭、复位与半开连接

TCP 每个方向独立关闭。FIN 表示“我不会再发送字节”，对方仍可继续发送，因此完整优雅关闭通常交换两个 FIN 与相应 ACK。RST 表示连接不存在或必须立即终止，未读数据可能丢失。若一端崩溃或路径中断，另一端可能长时间保留半开状态，直到应用 keepalive、重传或超时发现。

TIME_WAIT 与延迟段

主动关闭一方通常进入 TIME_WAIT，等待约两个最大报文寿命：既能重发最终 ACK，又避免旧连接延迟段被同一四元组的新连接误接收。大量短连接会产生许多 TIME_WAIT，但盲目缩短可能破坏正确性；连接复用与合理服务设计通常比关闭保护机制更好。

丢失检测与重传

RTT 估计与重传超时

TCP 用指数加权平均平滑 RTT：

\[ SRTT\leftarrow(1-\alpha)SRTT+\alpha RTT_{sample}, \]

并估计偏差 \(RTTVAR\)，设置

\[ RTO=SRTT+4\,RTTVAR \]

（还受最小/最大值约束）。只跟随平均值会在抖动出现时过早超时；加入方差余量让 RTO 保持在典型 RTT 之上。

Karn 算法与指数退避

重传段被确认时，发送端无法判断 ACK 对应原发送还是重传，因此 Karn 算法不使用这类模糊样本更新 RTT。连续超时通常将 RTO 加倍，避免在已拥塞或严重故障的路径上持续高频重传。

重复 ACK 与快速重传

后续段到达但前方有缺口时，接收端重复确认相同下一个期望字节。经典 TCP 在收到三个重复 ACK 后推断某段很可能丢失，立即快速重传，无需等待 RTO。现代实现还结合 SACK、RACK 等基于范围和时间的方法，提高乱序环境下判断准确性。

虚假重传与乱序

路径变化、无线延迟、ACK 压缩或队列抖动会让段迟到而非丢失；过短 RTO 或过度依赖重复 ACK 会产生虚假重传，浪费容量并错误触发拥塞响应。时间戳、DSACK 和更精细检测可帮助识别，但协议必须在“快速恢复真实丢包”和“容忍正常乱序”之间平衡。

class RtoEstimator:
    """RFC 6298 核心估算器，同时暴露原始 RTO 与 1 秒下限 RTO。"""

    ALPHA = 1 / 8
    BETA = 1 / 4
    K = 4

    def __init__(self, clock_granularity=0.001):
        self.g = clock_granularity
        self.srtt = None
        self.rttvar = None
        self.raw_rto = 1.0
        self.rto = 1.0

    def observe(self, sample_rtt: float):
        if self.srtt is None:
            self.srtt = sample_rtt
            self.rttvar = sample_rtt / 2
        else:
            old_srtt = self.srtt
            self.rttvar = (
                (1 - self.BETA) * self.rttvar
                + self.BETA * abs(old_srtt - sample_rtt)
            )
            self.srtt = (1 - self.ALPHA) * old_srtt + self.ALPHA * sample_rtt
        self.raw_rto = self.srtt + max(self.g, self.K * self.rttvar)
        self.rto = max(1.0, self.raw_rto)
        return self.srtt, self.rttvar, self.raw_rto, self.rto

    def on_timeout(self):
        # 应用下限后，对当前真正启用的定时器执行退避。
        self.rto *= 2
        return self.rto

samples_ms = [100, 130, 90, 160, 110, 140]

        f"{sample_ms:4}ms  {srtt * 1000:6.1f}  {variation * 1000:7.1f}  "
        f"{raw_rto * 1000:7.1f}ms  {effective_rto:5.3f}s"
    )

print(f"after timeout, backed-off RTO: {estimator.on_timeout():.3f}s")

流量控制

接收窗口与缓冲占用

接收应用读取速度可能低于网络到达速度。TCP 接收方在 ACK 中通告接收窗口 rwnd，表示从当前确认点起还能接收多少字节；发送端未确认数据受 rwnd 约束，避免覆盖接收缓冲。

大 BDP 路径需要窗口扩大选项突破 65,535 字节基本字段限制。窗口是动态的：应用读取会释放空间，乱序数据也会占用缓冲。

零窗口与持续定时器

缓冲满时接收方通告零窗口。若之后的窗口更新丢失，双方可能永久等待：发送方不发数据，接收方也无新事件再次通告。因此发送方使用 persist timer 周期发送小窗口探测，迫使接收方回复当前窗口。

流量控制与拥塞控制

流量控制保护接收主机缓冲，拥塞控制保护网络路径资源。发送端实际在途限制近似为

\[ FlightSize\leq\min(rwnd,cwnd), \]

其中 cwnd 是拥塞窗口。即使接收方很快，拥塞路径也要求减速；即使路径空闲，慢应用也可能通过小 rwnd 限制发送。

from dataclasses import dataclass


@dataclass
class ReceiveBuffer:
    capacity_kib: int
    unread_kib: int = 0

    @property
    def advertised_window(self) -> int:
        return self.capacity_kib - self.unread_kib

    def receive(self, amount_kib: int) -> int:
        accepted = min(amount_kib, self.advertised_window)
        self.unread_kib += accepted
        return accepted

    def application_read(self, amount_kib: int) -> int:
        consumed = min(amount_kib, self.unread_kib)
        self.unread_kib -= consumed
        return consumed

作为现代传输协议的 QUIC

基于 UDP 的传输与用户态演进

QUIC 把可靠传输、拥塞控制、TLS 1.3 与多流封装在 UDP 数据报中，通常在应用/用户态实现。使用 UDP 让现有 NAT 与网络能够转发，而用户态发布使协议不必等待所有操作系统内核升级。QUIC 仍必须实现负责任的拥塞控制、安全和路径验证，UDP 只是承载方式。

流、连接 ID 与迁移

一条 QUIC 连接可包含多条独立双向或单向流，每条流拥有自己的有序字节空间。连接由不直接绑定 IP/端口的 Connection ID 标识，使设备从 Wi-Fi 切换到蜂窝、地址或 NAT 映射改变时可以验证新路径并迁移，而不必重建整个应用会话。

握手整合与队头阻塞

QUIC 将传输参数与 TLS 1.3 握手整合，首次连接通常用 1 RTT 建立安全状态，恢复连接可发送 0-RTT 数据，但早期数据存在重放风险，只适合幂等操作。一个分组丢失时，其中某条流等待重传，其他流仍可交付；这消除了 TCP 在多路 HTTP/2 流之间的跨流队头阻塞，但同一流内部仍保持有序。

QUIC 加密更多控制信息，减少中间盒僵化，却让传统被动监控更困难，需要端点日志、标准化自旋位或显式遥测补充可观测性。

class IndependentStream:
    """重组一条有序流，且不与其他流耦合。"""

    def __init__(self):
        self.next_offset = 0
        self.fragments = {}
        self.delivered = bytearray()

    def receive(self, offset: int, data: bytes):
        self.fragments[offset] = data
        while self.next_offset in self.fragments:
            fragment = self.fragments.pop(self.next_offset)
            self.delivered.extend(fragment)
            self.next_offset += len(fragment)
        return bytes(self.delivered)

import socket
import struct


def encode_frame(payload: bytes) -> bytes:
    return struct.pack("!I", len(payload)) + payload


def decode_frames(buffer: bytearray):
    messages = []
    while len(buffer) >= 4:
        length = struct.unpack("!I", buffer[:4])[0]
        if len(buffer) < 4 + length:
            break
        messages.append(bytes(buffer[4:4 + length]))
        del buffer[:4 + length]
    return messages


left, right = socket.socketpair()
with left, right:
    # 两条应用消息一起写入；TCP 只会暴露字节流。
    left.sendall(encode_frame(b"alpha") + encode_frame(b"beta-beta"))
    left.shutdown(socket.SHUT_WR)

    receive_buffer = bytearray()
    decoded = []
    while True:
        chunk = right.recv(5)  # 故意使读取边界与帧边界无关。
        if not chunk:
            break
        receive_buffer.extend(chunk)
        decoded.extend(decode_frames(receive_buffer))

print("decoded messages:", decoded)
print("unconsumed bytes:", len(receive_buffer))

构建最小可靠字节流

教学实现把可靠性拆为清晰状态：发送端保存下一个序号、未确认字节、发送时间与重试次数；接收端保存下一个期望序号和乱序缓冲；ACK 推进连续前缀；超时只重传尚未确认范围。代码不试图复刻完整 TCP，而是用可测试模型展示不变量。

建议用确定性事件序列测试：丢失数据、丢失 ACK、重复数据、乱序、延迟重传与序号边界。每次事件后检查“应用只收到一次且按序”“ACK 不越过缺口”“已确认数据不再保留”。可靠性来自这些状态约束，而不是调用一次 send。

代码 
from dataclasses import dataclass
import zlib


@dataclass(frozen=True)
class Segment:
    offset: int
    payload: bytes
    checksum: int

    @classmethod
    def create(cls, offset: int, payload: bytes):
        protected = offset.to_bytes(4, "big") + payload
        return cls(offset, payload, zlib.crc32(protected))

    def valid(self) -> bool:
        protected = self.offset.to_bytes(4, "big") + self.payload
        return zlib.crc32(protected) == self.checksum


class MinimalByteReceiver:
    def __init__(self):
        self.next_offset = 0
        self.fragments = {}
        self.application = bytearray()

    def receive(self, segment: Segment):
        if segment.valid() and segment.offset >= self.next_offset:
            self.fragments.setdefault(segment.offset, segment.payload)
        while self.next_offset in self.fragments:
            payload = self.fragments.pop(self.next_offset)
            self.application.extend(payload)
            self.next_offset += len(payload)
        sacks = sorted(
            (offset, offset + len(payload))
            for offset, payload in self.fragments.items()
        )
        return self.next_offset, sacks


data = b"reliable-stream"
segments = [Segment.create(offset, data[offset:offset + 4]) for offset in range(0, len(data), 4)]
receiver = MinimalByteReceiver()

# 第一轮：偏移 4 丢失，后续段被乱序缓存。

    ack, sacks = receiver.receive(segment)
