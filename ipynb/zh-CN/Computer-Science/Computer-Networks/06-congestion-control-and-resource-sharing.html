拥塞控制与资源共享

可靠传输解决端点如何从丢失、乱序中恢复，但若每个发送者只追求自身速度，有限链路和缓冲会被持续压满，时延、丢包与重传相互放大，甚至导致拥塞崩溃。拥塞控制让端点和网络共同回答：当前路径还能承载多少数据，以及多个流应怎样分享容量。

本章从队列动态和反馈信号开始，解释 AIMD、TCP 慢启动与拥塞避免，再比较 CUBIC、Vegas、BBR、DCTCP。随后把端主机控制与网络内部机制连接起来：缓冲区、调度、AQM、ECN、流量整形与 QoS。重点不是背诵窗口曲线，而是理解每种算法观察了什么、控制了什么、在何种网络模型下成立，以及它与其他算法共存时会发生什么。

警告

流量控制保护接收方，拥塞控制保护共享路径。rwnd 很大只说明接收应用有空间，并不意味着网络可以继续加速；发送端实际在途量还必须受拥塞窗口 cwnd 限制。

什么是网络拥塞？

提供负载、容量与队列增长

当多个发送者在时间区间 \(t\) 内向瓶颈队列提交 \(A(t)\) 字节，而链路只能服务 \(C(t)\) 字节时，队列近似更新为

\[ Q(t+1)=\min\{B,\max(0,Q(t)+A(t)-C(t))\}, \]

其中 \(B\) 是有限缓冲容量。若长期到达率高于服务率，队列必然增长到 \(B\) 并丢包；即使平均负载略低于容量，突发也可能形成短队列。

队列不是拥塞的唯一表现，但它是最常见的可观察状态：短队列吸收突发，持续队列表示发送者长期提供了过多在途数据。

拥塞控制与流量控制

流量控制依据接收缓冲通告 rwnd，避免快发送方淹没慢接收应用；拥塞控制根据路径上的丢包、RTT、ECN 或带宽模型调整 cwnd/发送节奏。发送约束近似为

\[ FlightSize\leq\min(rwnd,cwnd). \]

两者可能同时限制，也可能只有一个生效。诊断“窗口小”时必须确认是哪一个窗口以及为何变小。

拥塞崩溃

若丢包后发送者无节制重传，瓶颈会花费容量传送后来又被丢弃的分组；过期、重复分组甚至可能占满网络，而有用 goodput 接近零。这就是拥塞崩溃。拥塞控制需要在过载时降低注入速率，并让反馈足够及时，避免控制环持续追赶陈旧状态。

效率、时延、公平性与稳定性

好的资源共享不只追求链路满载：

  • 效率：大部分容量用于有用数据；
  • 低时延：不靠长期满队列维持吞吐；
  • 公平性：竞争流按合理规则分享资源；
  • 稳定性：受到扰动后能回到可用状态而不持续振荡。

这些目标会冲突。例如把队列保持为空可以降低时延，却可能在带宽估计偏低时损失利用率；按连接平均又可能鼓励应用开更多连接。公平必须说明是按流、用户、租户、权重还是效用定义。

from dataclasses import dataclass


@dataclass
class QueueResult:
    offered: int
    delivered: int
    dropped: int
    final_queue: int
    mean_queue_delay_steps: float


def simulate_constant_queue(offered_per_step, capacity=100, buffer=300, steps=30):
    """以分组为单位模拟一个有限 FIFO 队列。"""
    queue = 0
    delivered = 0
    dropped = 0
    delay_samples = []

    for _ in range(steps):
        # 到达数据先占用空闲缓冲空间。
        admitted = min(offered_per_step, buffer - queue)
        dropped += offered_per_step - admitted
        queue += admitted

        # 随后瓶颈最多服务 `capacity` 个单位。
        served = min(queue, capacity)
        queue -= served
        delivered += served

        # 积压量除以服务率可估算排队时延。
        delay_samples.append(queue / capacity)

    return QueueResult(
        offered=offered_per_step * steps,
        delivered=delivered,
        dropped=dropped,
        final_queue=queue,
        mean_queue_delay_steps=sum(delay_samples) / len(delay_samples),
    )

拥塞信号与控制位置

基于丢包、时延与显式信号

丢包型控制把超时或重复 ACK 视为队列溢出信号，部署简单，但只有队列已付出丢包和较高时延后才响应；无线随机损失也可能被误判为拥塞。时延型控制观察 RTT 相对最小 RTT 的增加，在溢出前减速，但需要区分反向路径、路由变化和测量噪声。显式信号由路由器在拥塞前标记分组，使端点无需等待丢包。

端到端控制与网络辅助控制

端到端算法只依赖 ACK、丢包与计时，无需沿途设备升级，符合增量部署；缺点是只能间接推断瓶颈。网络辅助机制可提供 ECN 标记、显式速率或调度隔离，信号更直接，但要求路径设备与端点共同支持，错误配置也可能产生新故障。

隐式反馈与显式拥塞通知

ECN 使用 IP 的 ECT/CE 标记与 TCP 的 ECE/CWR 协作：发送者声明可支持 ECN，拥塞队列标记 CE 而非丢弃，接收者在 ACK 中回显 ECE，发送者降低速率并以 CWR 表示已响应。ECN 能减少作为信号的丢包，但不能阻止真实缓冲溢出，也不保证所有设备诚实或正确标记。

def infer_congestion(base_rtt_ms, current_rtt_ms, sent_bytes,
                     lost_bytes=0, ce_marked_bytes=0):
    """总结端点可获得的三类观测。"""
    queue_delay = max(0.0, current_rtt_ms - base_rtt_ms)
    loss_fraction = lost_bytes / sent_bytes if sent_bytes else 0.0
    ce_fraction = ce_marked_bytes / sent_bytes if sent_bytes else 0.0

    if ce_fraction > 0:
        primary = "explicit ECN pressure"
    elif loss_fraction > 0:
        primary = "loss-based pressure"
    elif queue_delay > 0.25 * base_rtt_ms:
        primary = "delay-based early warning"
    else:
        primary = "no strong congestion signal"

    return queue_delay, loss_fraction, ce_fraction, primary

加性增大与乘性减小

拥塞窗口与在途量

cwnd 限制尚未确认的网络内数据。若窗口为 \(W\) 字节、RTT 为 \(T\)，忽略其他约束时吞吐近似 \(W/T\)。窗口只是数量限制，实际实现还用 pacing 把发送分散到时间上，避免一次 ACK 后突发发送。

AIMD 动态

未观察到拥塞时，发送者每个 RTT 近似增加固定量 \(\alpha\)；收到拥塞信号时，把窗口乘以 \(0<\beta<1\)：

\[ w\leftarrow w+\alpha,\qquad w\leftarrow\beta w. \]

加性增长谨慎探测额外容量，乘性下降按当前速率成比例释放资源。经典 TCP 常用每 RTT 增约 1 MSS、丢包后大致减半。

向效率与公平收敛

两个流的速率平面中，\(x_1+x_2=C\) 是效率边界，\(x_1=x_2\) 是等份公平线。加性增加沿对角线向容量边界移动；乘性减小沿原点方向缩放。反复组合会使轨迹靠近两线交点。

该结论依赖同步反馈、相近 RTT 和相同行为等假设。现实中的 RTT 差异、多个瓶颈、不同算法与应用并行连接会改变公平结果。

def jain_index(rates):
    numerator = sum(rates) ** 2
    denominator = len(rates) * sum(rate ** 2 for rate in rates)
    return numerator / denominator if denominator else 0.0


def simulate_two_flow_aimd(rounds=28, capacity=60, alpha=1, beta=0.5):
    """使用共享二进制信号展示 AIMD 的几何趋势。"""
    windows = [8.0, 36.0]
    trace = []

    for round_number in range(1, rounds + 1):
        congested = sum(windows) > capacity
        if congested:
            windows = [beta * window for window in windows]
            action = "multiplicative decrease"
        else:
            windows = [window + alpha for window in windows]
            action = "additive increase"

        trace.append((round_number, *windows, sum(windows), jain_index(windows), action))

    return trace

经典 TCP 拥塞控制

慢启动

新连接不知道路径容量，从较小初始 cwnd 开始；每收到确认便增加窗口，使每个 RTT 近似翻倍。名称中的“慢”是相对直接以大速率发送，增长本身是指数的。慢启动在短流中非常关键，因为连接可能在达到稳态前就已结束。

拥塞避免

当 cwnd 达到慢启动阈值 ssthresh 后，进入拥塞避免，窗口每个 RTT 约增加 1 MSS，形成加性增长。拥塞事件发生后更新阈值并降低窗口。锯齿形并非缺陷，而是持续探测未知可用容量的结果。

快速重传与快速恢复

多个重复 ACK 表示后续数据在到达，而前方存在缺口；发送端通常在三次重复 ACK 后快速重传，无需等待 RTO。快速恢复不把窗口降到最初值，因为重复 ACK 说明网络仍在交付数据；它减半附近继续运行。超时则表示更严重不确定性，通常回到较小窗口重新慢启动。

Tahoe、Reno 与 NewReno

Tahoe 在任何丢失后把 cwnd 降到最小并慢启动；Reno 对单个快速重传事件使用快速恢复；NewReno 利用部分 ACK 更好处理同一窗口中的多个丢失。SACK 进一步让发送端准确知道已接收区间。版本差异体现的核心是：拥塞信号之后保留多少关于路径仍在前进的信息。

def simplified_reno(rounds=14, initial_cwnd=10.0, initial_ssthresh=32.0):
    """按 RTT 粒度展示 Reno；这不是分组级实现。"""
    cwnd = initial_cwnd
    ssthresh = initial_ssthresh
    events = {5: "three duplicate ACKs", 10: "timeout"}
    trace = []

    for rtt in range(1, rounds + 1):
        event = events.get(rtt, "ACK progress")

        if event == "three duplicate ACKs":
            ssthresh = max(cwnd / 2, 2.0)
            cwnd = ssthresh       # 简化快速恢复后的状态
            phase = "fast recovery -> avoidance"
        elif event == "timeout":
            ssthresh = max(cwnd / 2, 2.0)
            cwnd = 1.0            # 从发生丢包时的窗口重新开始探测
            phase = "slow start restart"
        elif cwnd < ssthresh:
            cwnd = min(2 * cwnd, ssthresh)
            phase = "slow start"
        else:
            cwnd += 1.0
            phase = "congestion avoidance"

        trace.append((rtt, cwnd, ssthresh, event, phase))

    return trace

现代拥塞控制算法

CUBIC

CUBIC 用距上次拥塞事件的时间控制窗口：

\[ W(t)=C(t-K)^3+W_{max}. \]

曲线远离旧最大值时增长较快，接近 \(W_{max}\) 时变平以谨慎探测，超过后再次加速。在高速长 RTT 路径上，它比每 RTT 加 1 MSS 更快恢复容量，并减少增长对 RTT 的直接依赖。它仍主要依据丢包，可能建立较深队列。

基于时延的控制与 TCP Vegas

Vegas 比较基于最小 RTT 的期望速率与当前实际速率，用差值估计排队量；队列过少就加速，过多则减速。它可在丢包前保持低时延，但与更激进的丢包型流共存时可能先让出容量，因为后者继续填队列。

基于模型的控制与 BBR

BBR 估计瓶颈带宽 BtlBw 与最小传播 RTT RTprop，目标是在途量接近二者乘积，并用 pacing 控制发送：

\[ BDP\approx BtlBw\times RTprop. \]

它周期探测带宽和低 RTT，不把丢包直接视为唯一拥塞信号。模型估计错误、浅缓冲、公平性和不同版本共存仍是重要问题。

数据中心 TCP 与 ECN

DCTCP 依赖交换机在较浅队列阈值上标记 ECN，并估计窗口中被标记字节比例 \(\alpha\)，按比例温和减窗，而不是每次都减半：

\[ cwnd\leftarrow cwnd(1-\alpha/2). \]

这让数据中心低 RTT、突发并发环境维持低队列和高吞吐，但要求一致的 ECN/AQM 配置，不能直接假设适用于任意互联网路径。

算法选择与共存

选择算法要结合 RTT、带宽、损失类型、缓冲、ECN 部署、流持续时间和竞争者。单算法实验中的优异结果不保证与 Reno/CUBIC/BBR 共存时仍公平。评价必须同时报告吞吐、排队时延、丢包、完成时间和公平性，而不是只看峰值带宽。

from math import isclose


def cubic_window(t, w_max=100.0, beta=0.7, cubic_c=0.4):
    """RFC 9438 概念性三次曲线，窗口以 MSS 计。"""
    k = (w_max * (1 - beta) / cubic_c) ** (1 / 3)
    return cubic_c * (t - k) ** 3 + w_max


def dctcp_update(alpha, marked_fraction, cwnd, gain=1 / 16):
    """执行一次 DCTCP alpha 更新，再按比例减小窗口。"""
    alpha = (1 - gain) * alpha + gain * marked_fraction
    return alpha, cwnd * (1 - alpha / 2)

吞吐量与公平模型

窗口、RTT 与吞吐量

窗口受限流的稳态吞吐近似为

\[ x\approx\frac{W}{RTT}, \]

并受瓶颈容量、接收窗口和应用供数能力限制。相同窗口下，RTT 更短的流每秒完成更多增长轮次，通常更具优势。

丢包条件下的 TCP 吞吐量

经典 Reno 型模型常写成

\[ x\propto\frac{MSS}{RTT\sqrt{p}}, \]

其中 \(p\) 是独立丢包概率。它揭示吞吐对 RTT 成反比、对丢包平方根下降，但依赖长流、拥塞避免、随机损失等假设，不能直接用于所有现代算法或超时主导场景。

RTT 公平与流竞争

ACK 驱动增长让低 RTT 流更快增加窗口；应用开多条并行连接也会获得多份“按流公平”份额。共享同一瓶颈的流可能因起始时间、算法、MSS、接入上限和反向路径 ACK 拥塞而表现不同。因此必须先声明公平单位，再解释结果。

最大最小公平与比例公平

最大最小公平优先提升最小分配，直到某资源饱和，再在剩余流间继续；比例公平最大化 \(\sum_i\log x_i\)，允许提高一个流但要求对其他流造成的相对损失不超过收益。Jain 公平指数

\[ J=\frac{(\sum_i x_i)^2}{n\sum_i x_i^2} \]

位于 \(1/n\) 与 1 之间，可总结分配均匀程度，但不能说明分配是否符合业务权重或跨瓶颈约束。

def reno_square_root_mbps(rtt_ms, loss_probability, mss_bytes=1460):

def max_min_single_link(capacity, demands):
    """在满足各流需求上限的前提下，对单瓶颈进行水位填充。"""
    allocation = {name: 0.0 for name in demands}
    active = set(demands)
    remaining = float(capacity)

    while active:
        equal_share = remaining / len(active)
        satisfied = [
            name for name in active
            if demands[name] - allocation[name] <= equal_share
        ]

        if not satisfied:
            for name in active:
                allocation[name] += equal_share
            break

        for name in satisfied:
            needed = demands[name] - allocation[name]
            allocation[name] += needed
            remaining -= needed
            active.remove(name)

    return allocation

队列、缓冲与缓冲区膨胀

尾丢弃队列

Drop-tail 在缓冲未满时全部接收，满后丢弃新到分组。实现简单，但信号出现较晚，多个 TCP 可能同时丢包并同步减速；突发流还可能独占队列，使短小交互流等待。

缓冲区大小

传统经验把缓冲设为容量乘 RTT，但它假设少量长流和特定控制算法。大量独立流的聚合可降低所需缓冲，突发、速度差异和服务目标又可能需要额外余量。正确大小应来自业务流量、目标队列时延、链路调度和实测，而不是固定公式。

常驻队列与时延膨胀

若发送者持续把缓冲保持接近满，新增缓冲不会提高瓶颈吞吐，只会把 RTT 增加约 \(Q/C\)。这就是 bufferbloat：测速看似满速，交互、语音和 ACK 却承受数百毫秒额外延迟。

吸收突发与持续时延

缓冲的合理用途是吸收短期到达抖动，使链路不断粮；问题在于队列是否能在突发后恢复。应观察队列停留时间、低负载基线 RTT 与负载 RTT，而不是把“没有丢包”当作唯一成功标准。

def simulate_burst(buffer_size, capacity=100, steps=35):
    """比较短突发在两种队列上限下的表现。"""
    queue = delivered = dropped = 0
    queue_delays = []

    for step in range(steps):
        # 基线、四步突发，随后是略低于链路容量的流量。
        arrivals = 80 if step < 5 else (220 if step < 9 else 95)
        admitted = min(arrivals, buffer_size - queue)
        dropped += arrivals - admitted
        queue += admitted

        served = min(queue, capacity)
        queue -= served
        delivered += served
        queue_delays.append(queue / capacity)

    ordered = sorted(queue_delays)
    p95 = ordered[int(0.95 * (len(ordered) - 1))]
    return delivered, dropped, queue, sum(queue_delays) / steps, p95

队列调度

FIFO 与优先级队列

FIFO 按到达顺序服务，简单但不隔离流；大流可让短流排队。严格优先级始终先服务高优先级，适合关键控制流量，却可能让低优先级饥饿，因此需要限速、保底或层次调度。

轮询与亏空轮询

普通轮询每队列取一个分组，分组大小不同时按分组公平而非按字节公平。DRR 为每队列周期增加 quantum，只有亏空计数足以支付分组长度时才发送，未用额度保留到下轮，以近似 \(O(1)\) 成本实现按字节加权共享。

公平队列与加权公平队列

公平队列模拟比特级轮转，为每个流计算虚拟完成时间；WFQ 用权重提供不同比例。它们隔离激进流，并可给低速交互流更稳定时延，但分类状态和调度实现更复杂。

调度隔离与饥饿

隔离单位可以是五元组、用户、租户或类别。按流隔离会被多连接规避，按租户隔离则需要可信身份。任何优先级体系都要明确最低服务、突发上限和过载行为，否则“关键流量优先”会退化为低优先级永久饥饿。

from collections import deque


def deficit_round_robin(packet_queues, quanta):
    """返回变长分组的 DRR 发送轨迹。"""
    queues = {name: deque(packets) for name, packets in packet_queues.items()}
    deficit = {name: 0 for name in queues}
    transmitted = []

    while any(queues.values()):
        for name, queue in queues.items():
            if not queue:
                deficit[name] = 0
                continue

            deficit[name] += quanta[name]
            while queue and queue[0] <= deficit[name]:
                size = queue.popleft()
                deficit[name] -= size
                transmitted.append((name, size, deficit[name]))

    return transmitted

主动队列管理

随机早期检测

RED 对平均队列长度做平滑：低于最小阈值不标记，高于最大阈值全部标记/丢弃，中间按递增概率随机处理。它试图在缓冲溢出前向不同流分散发送信号，避免全局同步。

RED 对阈值、流量与链路参数敏感；平均队列不总能直接表达用户经历的停留时间。

CoDel 与 PIE

CoDel 观察分组在队列中的停留时间；若最小停留时间持续超过目标，就按控制规律丢弃/标记，区分短突发与常驻队列。PIE 使用估计排队时延与变化趋势调节概率。两者都旨在少依赖固定字节阈值，控制时延而非只防止溢出。

结合 ECN 的 AQM

当端点支持 ECN 时，AQM 可以标记而非丢弃可标记分组，在保持拥塞反馈的同时减少恢复开销。AQM 仍必须在缓冲真正溢出时丢包，并公平处理不支持或不响应 ECN 的流量。部署要验证隧道、负载均衡与防火墙是否正确保留标记。

def red_probability(avg_queue, minimum=20, maximum=80, max_probability=0.10):
    """用于说明的 RED 线性概率区间。"""
    if avg_queue < minimum:
        return 0.0
    if avg_queue >= maximum:
        return 1.0
    fraction = (avg_queue - minimum) / (maximum - minimum)
    return max_probability * fraction


def codel_persistent_delay(sojourn_ms, target_ms=5):
    """一个教学区间：仅当最小值持续偏高时才判为持久。"""
    return min(sojourn_ms) > target_ms


def simplified_pie_update(probability, delay_ms, previous_delay_ms,
                          target_ms=15, alpha=0.004, beta=0.002):
    """教学用反馈更新，并非 RFC 的完整实现。"""
    error = delay_ms - target_ms
    trend = delay_ms - previous_delay_ms
    return min(1.0, max(0.0, probability + alpha * error + beta * trend))

流量整形与服务质量

漏桶与令牌桶

漏桶以固定速率排出，平滑所有突发；令牌桶以速率 \(r\) 产生令牌、最多积累 \(b\)，发送长度 \(L\) 的分组需消费 \(L\) 个令牌。因此长期平均受 \(r\) 限制，同时允许最多约 \(b\) 的突发。

监管与整形

监管在流量超过合同后立即丢弃、重标记或计费，不增加等待但会产生损失；整形把超额流量排队并稍后发送，减少下游突发却增加时延并需要缓冲。入口边界常监管，发送端或出口常整形，二者可组合。

区分服务与服务类别

DiffServ 用 DSCP 分类，网络对类别提供不同每跳行为，例如低时延、保证转发或尽力而为。标记只有在跨域策略一致、入口验证可信并有队列/调度配合时才有意义；把所有流量标成最高优先级不会创造容量。

接纳控制与资源预留

当系统必须提供硬保证时，应在接受新流前确认容量，并为已接纳流保留资源。它提高可预测性，却需要状态、信令和拒绝机制。互联网通常依赖弹性共享，运营商、工业与实时专网则可能使用切片、带宽保证或显式预留。

def token_bucket_shape(arrivals, rate_bytes_per_second, bucket_bytes):
    """整形 `(到达时间, 分组大小)` 记录并返回离开时间。"""
    tokens = float(bucket_bytes)  # 初始令桶为满状态，因此允许一次突发
    now = 0.0
    last_update = 0.0
    departures = []

    for arrival_time, packet_size in arrivals:
        # 更早排队的分组可能让 `now` 晚于后续到达时间。
        now = max(now, arrival_time)
        tokens = min(
            bucket_bytes,
            tokens + rate_bytes_per_second * (now - last_update),
        )
        last_update = now

        if tokens < packet_size:
            # 只等待生成所缺额度所需的时间。
            wait = (packet_size - tokens) / rate_bytes_per_second
            now += wait
            tokens = 0.0
            last_update = now
        else:
            tokens -= packet_size

        departures.append((arrival_time, now, packet_size, now - arrival_time))

    return departures

def compare_window_controllers(rounds=26, event_rounds=(8, 16, 24)):
    reno = 20.0
    cubic = 20.0
    cubic_wmax = 20.0
    cubic_epoch = 0
    dctcp = 20.0
    alpha = 0.0
    trace = []

    for round_number in range(1, rounds + 1):
        event = round_number in event_rounds

        # Reno AIMD：丢包时乘性减小，否则加性增大。
        reno = reno * 0.5 if event else reno + 1

        # 使用 RFC 9438 概念曲线的简化 CUBIC epoch。
        if event:
            cubic_wmax = cubic
            cubic *= 0.7
            cubic_epoch = 0
        else:
            cubic_epoch += 1
            k = (cubic_wmax * 0.3 / 0.4) ** (1 / 3)
            curve = 0.4 * (cubic_epoch - k) ** 3 + cubic_wmax
            cubic = max(cubic, curve)

        # DCTCP 观察的是比例，而不只是二值事件。
        marked_fraction = 0.30 if event else 0.0
        alpha = (15 / 16) * alpha + (1 / 16) * marked_fraction
        dctcp = dctcp * (1 - alpha / 2) if event else dctcp + 1

        trace.append((round_number, event, reno, cubic, dctcp, alpha))

    return trace

比较吞吐量、时延与公平性

只报告平均吞吐量会掩盖队列和竞争代价。实验至少应同时记录：每流 goodput、完成时间、基线/负载 RTT、p95/p99 时延、丢包或 ECN 比例、重传、队列停留时间和 Jain 指数。短流与长流要分开，因为吞吐稳定但页面请求完成时间可能恶化。

可复现评估流程

  1. 明确假设，例如“CoDel 在保持总 goodput 的同时降低 p95 RTT”；
  2. 固定拓扑、容量、基础 RTT、缓冲、流量生成和算法版本；
  3. 设置热身期、测量期和独立重复，保存随机种子；
  4. 收集原始 per-flow 与队列时间序列，而非只保存截图；
  5. 用相同负载比较方案并报告不确定性；
  6. 检查结果是否来自 CPU、接收窗口、应用限速或测量工具本身。

观察与排查拥塞

可从“空闲基线”与“负载期间”对比开始：持续低速 ping 观察 RTT 和丢失，同时在授权端点间运行受控吞吐测试；记录接口利用率、队列丢弃、ECN、TCP 重传和应用完成时间。若吞吐达到瓶颈而 RTT 增长数百毫秒，常见原因是常驻队列；若吞吐和利用率都低，则可能是接收窗口、应用、CPU、路由或物理错误，而非拥塞。

Linux 常用 ss -ti、tc -s qdisc、ip -s link 与 iperf3；Windows 可使用 Get-NetTCPConnection、Get-NetAdapterStatistics、netstat -s 和受控 Test-NetConnection/抓包。生产测试必须限制速率、持续时间和目标，避免测量本身制造事故。

定位顺序：确认真正瓶颈链路；比较基础 RTT 与负载 RTT；区分随机链路损失和队列溢出；检查 rwnd 与 cwnd；识别所用拥塞算法与 AQM；再判断是端点、队列、调度还是容量需要改变。

总结

机制 主要信号/状态 核心目标 典型风险
AIMD/Reno 丢包、ACK、cwnd 分布式探测与共享 队列形成后才响应、RTT 偏差
CUBIC 丢包后经过时间 高 BDP 快速恢复 深队列、共存公平性
Vegas RTT 与期望/实际速率 丢包前控制队列 与激进丢包型流竞争不利
BBR 带宽与最小 RTT 模型 接近 BDP、pacing 模型误差与版本共存
DCTCP ECN 标记比例 数据中心低队列高吞吐 依赖一致 ECN 阈值
调度 分类、队列、权重 隔离和服务份额 饥饿、分类可规避
AQM/ECN 队列长度/停留时间/标记 提前反馈、控制时延 参数与端点支持
整形/监管 令牌与速率合同 控制突发和边界行为 排队时延或丢包

拥塞控制是一个反馈控制问题：发送者根据有限且延迟的观测调整负载，网络通过队列、调度、AQM 和 ECN 塑造信号。评价任何方案都必须同时看利用率、时延、公平、稳定和共存，而不能把“链路跑满”当作唯一成功标准。
