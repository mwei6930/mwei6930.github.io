流水线与冒险

第 06 章让一条指令依次经过取指、译码、执行、访存和写回。单周期处理器在一个长周期内完成全部活动，多周期处理器则在多个短周期中复用硬件。流水线（pipelining）作出第三种选择：把各阶段保留在不同硬件区域，让不同指令同时占据不同阶段。

这种重叠改变的是微体系结构，而不是 ISA 契约。无论处理器是单周期、五级流水线还是超标量，add x5, x6, x7 都必须产生完全相同的体系结构结果。内部可以存在部分执行甚至推测执行的指令，但提交后的寄存器、内存、陷阱与控制流必须与顺序程序执行不可区分。

流水线为什么提高吞吐量

流水线类似装配线。若一个工人完成全部五步后才接收下一件产品，完成间隔等于各步时间之和；若五个专业工位并发工作，第一件产品仍要经过所有工位，但只要最慢工位空闲就可加入下一件。因此主要提升的是吞吐量，即完成指令的速率，而不是单条指令延迟。

若五级组合延迟为 \(t_{IF}\)、\(t_{ID}\)、\(t_{EX}\)、\(t_{MEM}\) 与 \(t_{WB}\)，单周期实现约需

\[ T_{single}\ge t_{IF}+t_{ID}+t_{EX}+t_{MEM}+t_{WB}. \]

插入流水线寄存器后，周期由最慢阶段加寄存器开销决定：

\[ T_{pipe}\ge\max(t_{IF},t_{ID},t_{EX},t_{MEM},t_{WB})+t_{reg}. \]

\(t_{reg}\) 包括时钟到 Q、建立时间和时钟不确定性。所有阶段共用同一周期，所以取最大值而非平均值。

当长操作可分成较均衡阶段且存在许多独立工作时，流水线最有效。如果某一级仍明显更慢、寄存器开销很大，或依赖频繁阻止新工作推进，收益就会下降。这也是本章必须研究冒险，而不能把五级流水线直接当作五倍加速的原因。

五级指令流水线

经典教学流水线把标量 RISC 指令分为 IF、ID、EX、MEM、WB。这不是体系结构要求；真实处理器可以进一步拆分取指、译码、执行与访存，也可以合并简单阶段或为不同指令类别使用不同执行流水线。五级模型的价值是清楚展示数值时序与冒险。

阶段 核心问题 代表性工作 向后传递的值
IF 哪条指令应进入？ 读指令，计算顺序或预测下一 PC 指令位、PC、预测元数据
ID 指令要求什么？ 译码、读寄存器、生成立即数、检测冒险 操作数、源/目的名、控制
EX 需要何种结果、地址或决定？ ALU、地址、分支比较与目标 ALU 结果、分支结果、存储数据
MEM 是否访问数据内存？ 加载、存储或传递 ALU 结果 加载数据或先前结果
WB 哪个体系结构寄存器改变？ 选择结果并应用 RegWrite 已提交寄存器值

第一条结果要等流水线填满后出现，之后理想标量流水线每周期完成一条，虽然每条指令在机器内停留约五个周期。结果依赖尚未就绪、多个阶段竞争同一资源、预测 PC 错误或异常使年轻工作失效时，实际轨迹会偏离理想情况。

取指

取指阶段（IF）用当前 PC 请求指令字节并计算候选下一 PC。最简单 RV32I 流水线选择 \(PC+4\)；加入控制流预测后，IF 可选择预测分支或跳转目标，避免等待旧分支到达 EX。

IF 不只保存指令比特。指令自身 PC 后续还用于 PC 相对目标、jal 链接、异常的 mepc 与调试。因此 IF/ID 载荷至少包含 (valid, PC, instruction)，也可携带预测方向、预测目标和取指错误。

指令缓存未命中或权限错误会打破一周期图景。取指接口可以保持 PC、把响应标为无效，或注入异常记录直到存储层次返回。PC 与 IF/ID 必须协调更新：普通周期两者都推进；数据冒险停顿时两者都保持；分支纠正时 PC 重定向，已顺序取到的 IF/ID 条目失效。只更新其中一个会重复或丢失指令。

指令译码

指令译码阶段（ID）解释 opcode 和功能字段、重建立即数、读取 R[rs1] 与 R[rs2]，并生成后级控制。它还把源和目的寄存器名暴露给冒险单元，所以既是语义阶段，也是调度检查点。

例如 sw x10, 4(x11) 把 x11 识别为基址源、x10 识别为存储数据源，重建 S 型立即数 4，并请求 EX 做地址加法、MEM 写内存。beq x12, x13, L 则识别两个比较源、B 型偏移与条件控制流。

ID 读到的寄存器值不一定最新。旧指令可能已算出替代值但尚未写回。流水线把源名字带入 ID/EX，旁路单元在 ALU 使用前与旧指令目的名比较并替换陈旧值。若没有旁路能及时送达，互锁会让指令停在 ID。

并非每种格式都使用表面上的所有寄存器字段。冒险逻辑必须依据译码后的 uses_rs1/uses_rs2，而不能盲目比较比特位置，否则立即数比特偶然等于旧目的寄存器会制造假停顿。

执行

执行阶段（EX）完成指令主要组合变换。ALU 可以加两个寄存器、组合寄存器与立即数、计算访存有效地址或形成 PC 相对目标，分支比较器则判断相等等条件。

加载地址为

\[ EA=(R[rs1]+Imm)\bmod2^{32}. \]

对于 beq，EX 通常同时产生

\[ taken=(A=B),\qquad target=PC+Imm. \]

\(A\)、\(B\) 是旁路后的比较操作数，PC 必须是该指令保存的 PC，而不是当前取指 PC，因为已有年轻指令进入流水线。

EX 是旁路数据的主要消费者。MUX 在原 ID/EX 操作数、EX/MEM 中更新结果和 MEM/WB 中接近写回的值之间选择。分支在 EX 解析时，结果出来前已有两条年轻指令进入 IF 与 ID；把解析提前可降低惩罚，却会把比较、目标与旁路逻辑移到更早阶段。

访存

访存阶段（MEM）使用 EX 地址完成加载或存储。加载请求字节并按大小进行符号/零扩展，之后送往 WB；存储组合地址、旁路后的存储数据与字节使能。算术指令不访问数据内存，其 ALU 结果只是穿过 EX/MEM 与 MEM/WB。

内存副作用必须严格门控。内部存在的存储若 valid=0、被旧异常重定向，或自身访问失败，就不能修改内存。精确顺序流水线可以把存储使能推迟到确认指令有效且不会再被更老指令取消之后。

一周期 MEM 抽象假定缓存命中。数据缓存未命中时，预期周期末没有加载结果，流水线必须停顿依赖工作或采用通用请求/响应机制。存储层次同时影响时钟周期与平均 CPI。

写回

写回阶段（WB）选择成为体系结构寄存器可见值的结果。算术指令选 ALU，加载选内存数据，jal 选链接 \(PC+4\)。只有条目有效、RegWrite=1、没有抑制异常且 \(rd\ne0\) 时才写入：

\[ R^{+}[rd]= \begin{cases} WBValue,&valid\land RegWrite\land(rd\ne0),\\ R[rd],&\text{其他情况}. \end{cases} \]

WB 为寄存器结果提供简单有序提交点：旧指令比年轻指令先到达。但消费者不应等待已经在 EX 计算或 MEM 返回的结果走到 WB；旁路改善可用时间，却不改变寄存器文件更新的体系结构时刻。

流水线寄存器与时序

流水线寄存器不只是分隔线。每一个都要保存后级需要的完整飞行中记录：数值、寄存器名、控制位、指令 PC、异常元数据与有效位。若数据和控制错位，一条指令可能误用另一条指令的目的或内存写使能。

寄存器 典型载荷 保留原因
IF/ID valid、PC、指令、预测/取指状态 译码并识别指令
ID/EX 操作数、rs1、rs2、rd、立即数、PC、控制 用冒险感知值执行
EX/MEM ALU、分支结果/目标、存储数据、rd、控制 访存或重定向
MEM/WB 加载数据或 ALU/链接、rd、RegWrite 完成寄存器更新

\[ T_{clk}\ge t_{cq}+\max_i(t_{logic,i})+t_{setup}+t_{skew}. \]

时钟必须覆盖源寄存器输出、相邻寄存器间最慢组合路径、目的建立时间和时钟裕量。最大值而不是平均值控制周期。把 400 ps 阶段拆成两个 200 ps 阶段可能提高频率，却增加寄存器、指令延迟、飞行中状态，并扩大分支错误时要冲刷的深度。

动作 状态更新 含义
正常推进 每级捕获前级 所有有效指令前进一步
停顿 选定寄存器保持旧值 指令等待，较老级仍可继续
气泡 目的寄存器捕获 valid=0 或零副作用控制 空槽沿流水线移动
冲刷 一个或多个年轻条目失效 丢弃错误路径或异常后的工作
Python 模型：用有效位明确表达推进、停顿、气泡与冲刷 
from dataclasses import dataclass


@dataclass(frozen=True)
class PipeEntry:
    valid: bool = False
    text: str = "bubble"


def update_front_end(pc, if_id, fetched, *, stall=False, flush=False, target=None):
    """只模拟一个边沿上 PC 与 IF/ID 状态的改变。"""
    if flush:
        return target, PipeEntry()
    if stall:
        return pc, if_id
    return pc + 4, fetched


pc = 0x100
if_id = PipeEntry(True, "add x5, x6, x7")

held_pc, held_if_id = update_front_end(pc, if_id, PipeEntry(), stall=True)
assert (held_pc, held_if_id) == (pc, if_id)

new_pc, cleared_if_id = update_front_end(
    pc, if_id, PipeEntry(), flush=True, target=0x180
)
assert new_pc == 0x180 and not cleared_if_id.valid

流水线性能

分析流水线性能时，需要把理想情况下的阶段重叠与导致流水线槽位空闲的事件区分开来。对于由 \(k\) 个阶段组成、时钟周期统一为 \(T_{clk}\) 的流水线，执行 \(N\) 条彼此独立的指令时，理想执行时间为

\[ T_{ideal}(N)=(k+N-1)T_{clk}. \]

  • \(N\) 是被测指令序列中的指令数量。
  • \(k\) 是流水线的阶段数。
  • 前 \(k\) 个周期用于填充流水线，并完成第一条指令。
  • 其余 \(N-1\) 条指令在理想情况下各自只比前一条晚一个周期完成。
  • \(T_{clk}\) 将周期数换算为实际时间。

对于五级流水线和五条独立指令，所需周期数为 \(k+N-1=5+5-1=9\)，与前面理想化的对角线时序图一致。当指令序列足够长时，最初四个填充周期占总时间的比例会很小；而停顿和冲刷产生的额外周期并未包含在这个理想公式中。

延迟与吞吐量

指令延迟是指一条指令从进入 IF 到最终完成所经历的时间。在理想的固定级数模型中，

\[ L_{instruction}\approx kT_{clk}. \]

稳态吞吐量则表示流水线填满后，单位时间内能够完成多少条指令：

\[ Throughput_{ideal}\approx \frac{1}{T_{clk}}\quad\text{条指令/单位时间}. \]

两个公式回答的是不同问题。增加流水线级数 \(k\) 可能缩短每一级的组合逻辑延迟，从而提高吞吐量；但新增的寄存器开销可能使 \(kT_{clk}\) 基本不变，甚至使单条指令延迟增大。例如，时钟周期为 250 ps 的五级处理器在理想状态下每 250 ps 完成一条指令，但一条具体指令仍需约 \(5\times250=1250\) ps 才能穿过全部阶段。

指标 它回答的问题 流水线化的影响
延迟 一条指令从进入到完成需要多久？ 可能近似不变，也可能增加
吞吐量 多久能够完成一条新指令？ 流水线填满后通常提高
时钟周期 一个周期至少需要多长？ 由最慢阶段与寄存器开销决定
对依赖的响应 下一条指令现在能否继续推进？ 可能插入气泡并降低有效吞吐量

因此，“五个阶段都在工作”并不意味着每条指令快了五倍，而是机器能够让不同指令并发使用这五组阶段资源。

理想加速比

假设未流水线化的实现需要为每条指令依次完成所有阶段，其简化执行时间为

\[ T_{unpipe}(N)=N\sum_{i=1}^{k}t_i. \]

结合理想流水线时间，可以得到

\[ Speedup(N)= \frac{N\sum_{i=1}^{k}t_i} {(k+N-1)(\max_i t_i+t_{reg})}. \]

  • \(t_i\) 是第 \(i\) 个阶段在不计寄存器开销时的有效延迟。
  • \(\sum t_i\) 是未流水线化路径上的总有效工作时间。
  • \(\max_i t_i+t_{reg}\) 是该简化模型中的流水线时钟周期。
  • \(k+N-1\) 包含流水线填充与排空的影响。

只有当各阶段完全均衡、寄存器开销可以忽略且 \(N\) 足够大时，加速比才会逼近 \(k\)。现实中的阶段延迟并不相等，流水线寄存器会消耗时间和能量，各种冒险还会增加周期，因此理想上界是设计目标而不是性能保证。

Python 示例：量化阶段不均衡与寄存器开销 
def ideal_pipeline_speedup(stage_delays_ps, register_overhead_ps, instructions):
    """比较顺序完成各阶段与理想流水线执行的时间。"""
    k = len(stage_delays_ps)
    unpipelined_time = instructions * sum(stage_delays_ps)
    pipeline_clock = max(stage_delays_ps) + register_overhead_ps
    pipelined_time = (k + instructions - 1) * pipeline_clock
    return {
        "clock_ps": pipeline_clock,
        "unpipelined_ps": unpipelined_time,
        "pipelined_ps": pipelined_time,
        "speedup": unpipelined_time / pipelined_time,
    }


result = ideal_pipeline_speedup(
    stage_delays_ps=[180, 150, 220, 200, 100],
    register_overhead_ps=20,
    instructions=100,
)

assert result["clock_ps"] == 240
assert round(result["speedup"], 2) == 3.41
print(result)

例子虽然采用五级流水线，但 100 条指令的理想序列加速比只有约 \(3.41\times\)。其中 220 ps 的 EX 阶段决定了 240 ps 的时钟周期，较短阶段存在无法利用的时序余量；寄存器开销和四个填充周期进一步缩小了收益。

含停顿的 CPI

每条指令周期数（Cycles per Instruction, CPI）表示平均完成一条指令需要消耗多少个时钟周期。如果一个 \(k\) 级标量流水线完成 \(N\) 条指令的过程中出现了 \(S\) 个额外的停顿或冲刷周期，则

\[ Cycles=(k-1)+N+S, \]

\[ CPI=\frac{(k-1)+N+S}{N}. \]

  • \(k-1\) 是除每条指令理想占用的一个周期外，流水线填充与排空带来的额外开销。
  • \(N\) 只计算已经完成的体系结构指令；被冲刷的错误路径指令不计入其中。
  • \(S\) 包含值尚未就绪、资源冲突、分支纠正或缓存延迟造成的所有额外周期。
  • 当序列很长时，\((k-1)/N\) 趋近于零，因此 \(CPI\approx1+S/N\)。

执行时间仍遵循第 01 章介绍的乘积关系：

\[ CPU\ Time=N\times CPI\times T_{clk}. \]

更深的流水线可能减小 \(T_{clk}\)，但也可能增大分支预测失败的惩罚并提高 CPI。因此，仅比较时钟频率可能反而选出执行更慢的处理器。

Python 示例：合并装载-使用、分支与缓存惩罚 
def pipeline_cpi(
    instructions,
    stages,
    load_use_events=0,
    load_use_penalty=1,
    branch_misses=0,
    branch_penalty=2,
    cache_misses=0,
    cache_penalty=0,
):
    """统计填充周期和相互独立的周期损失来源。"""
    stalls = (
        load_use_events * load_use_penalty
        + branch_misses * branch_penalty
        + cache_misses * cache_penalty
    )
    cycles = (stages - 1) + instructions + stalls
    return cycles, cycles / instructions


cycles, cpi = pipeline_cpi(
    instructions=1000,
    stages=5,
    load_use_events=40,
    branch_misses=25,
    cache_misses=5,
    cache_penalty=12,
)

assert cycles == 1154
assert round(cpi, 3) == 1.154
print(f"cycles={cycles}, CPI={cpi:.3f}")

代码为了便于说明而直接相加各种惩罚，但真实事件可能彼此重叠。例如，缓存未命中造成的停顿可能已经阻塞某条分支或依赖指令，因此周期精确模拟器必须建模流水线状态，而不能机械地叠加独立概率。这个加法模型更适合作为解释 CPI 为什么高于 1 的一阶近似。

结构冒险

当同一个周期中的多个流水线阶段，请求某类硬件资源的数量或端口数超过实现所能提供的容量时，就发生了结构冒险（structural hazard）。它本质上是资源容量不足，而不要求指令之间存在寄存器依赖或控制流关系。

经典例子是统一的单端口存储器：IF 每个周期都要读取下一条指令，而 MEM 中的装载或存储指令也要在同一周期访问数据。一个端口只能接收一个请求，所以实现必须增加容量，或让其中一个请求者等待。

常见的结构冲突及设计选择如下：

冲突 硬件方案 调度方案 权衡
IF 与 MEM 都需要存储器 分离指令/数据缓存或提供两个端口 停顿 IF 或 MEM 增加容量消耗面积；停顿损失 CPI
WB 写寄存器时 ID 读寄存器 多端口寄存器堆并定义同周期读写时序 停顿或增加写到读的旁路 更多端口会增加阵列延迟与布线
EX 同时需要分支目标和算术运算 独立的目标加法器或比较器 跨周期复用 ALU 复制硬件提高吞吐量
双发射需要两个 ALU 复制执行单元 该周期只发射一条指令 只有资源匹配时宽度才有价值
Python 模型：检测对单周期资源的竞争性预留 
from collections import Counter


def structural_conflicts(stage_requests, capacities):
    """返回同周期请求数量超过容量的资源。"""
    demand = Counter(stage_requests.values())
    return {
        resource: {"demand": count, "capacity": capacities.get(resource, 0)}
        for resource, count in demand.items()
        if count > capacities.get(resource, 0)
    }


requests = {
    "IF": "unified_memory_port",
    "MEM": "unified_memory_port",  # 本周期有一条 load 位于 MEM
    "EX": "integer_alu",
}

conflicts = structural_conflicts(
    requests,
    capacities={"unified_memory_port": 1, "integer_alu": 1},
)

assert conflicts["unified_memory_port"] == {"demand": 2, "capacity": 1}
print(conflicts)

消除所有结构停顿不一定是最优方案。对于很少发生的冲突，通过调度避让可能比复制大型资源更划算。真正的工程问题是：额外容量所节省的执行时间，是否值得付出面积、能耗、关键路径和验证成本。

数据冒险

数据依赖是程序本身的性质：一条指令的含义与另一条指令的读写有关。数据冒险（data hazard）则是微体系结构中的时序问题：阶段重叠可能使操作以违反该依赖的顺序发生。同一种程序依赖在某条流水线中可能需要停顿，在另一条流水线中可以用旁路解决，而在单周期实现中甚至不需要特殊处理，因此必须区分二者。

考虑下面两条指令：

I0: add x5, x1, x2
I1: sub x7, x5, x3

I1 确实需要 I0 产生的值。顺序执行时，I0 会在 I1 读取前写入 x5；但在五级流水线中，I1 可能已经到达 EX，而 I0 尚未进入 WB。因此判断冒险时应询问：

生产者的值在哪个阶段可用，而消费者在哪个阶段需要这个值？

值 通常何时可用 消费者通常何时需要 处理方式
整数 ALU 结果 生产者 EX 结束 消费者 EX 开始 从 EX/MEM 旁路到 EX
缓存命中的装载结果 生产者 MEM 结束 消费者 EX 开始 紧随其后的消费者停顿一次
存储数据 随指令向 MEM 传递 生产结果可能在 store 的 MEM 前到达 增加存储数据旁路
分支操作数 分支比较阶段 在本设计中通常为 EX 使用类似 ALU 的旁路或停顿

冒险处理应基于“何时产生、何时需要”的时序关系，而不是死记某几个指令组合。这个视角同样适用于乘法器、缓存未命中、浮点单元和乱序执行。

RAW、WAR 与 WAW 依赖

寄存器依赖按照对同一体系结构名称的读（R）和写（W）顺序分类。

类型 程序必须维持的顺序 含义 五级顺序标量流水线中的情况
RAW 较早的写先于较晚的读 真依赖/流依赖，指令之间传递值 可能形成冒险，需要旁路或停顿
WAR 较早的读先于较晚的写 因复用名称形成的反依赖 当读写始终顺序发生时不会形成冒险
WAW 较早的写先于较晚的写 因复用名称形成的输出依赖 只有一条顺序 WB 路径时不会形成冒险

RAW 不能在不改变算法的前提下消除，因为后续指令确实需要先前结果。WAR 和 WAW 是名称依赖：两条指令碰巧使用相同的体系结构寄存器，但较早指令并未向较晚指令传递值。乱序处理器可以通过寄存器重命名为写操作分配不同物理目的寄存器，从而解除这些伪依赖。

Python 模型：根据读集合与写集合识别依赖 
from dataclasses import dataclass


@dataclass(frozen=True)
class RegisterUse:
    text: str
    reads: frozenset[str]
    writes: frozenset[str]


def dependencies(older, younger):
    """从较早指令到较晚指令识别三类寄存器依赖。"""
    return {
        "RAW": older.writes & younger.reads,
        "WAR": older.reads & younger.writes,
        "WAW": older.writes & younger.writes,
    }


add = RegisterUse("add x5,x1,x2", frozenset({"x1", "x2"}), frozenset({"x5"}))
sub = RegisterUse("sub x7,x5,x3", frozenset({"x5", "x3"}), frozenset({"x7"}))

result = dependencies(add, sub)
assert result["RAW"] == frozenset({"x5"})
assert not result["WAR"] and not result["WAW"]
print(result)

存储器依赖需要比较地址，而不能只看寄存器名称。例如，store 后跟一条访问同一地址的 load，形成了类似 RAW 的内存依赖，但处理器可能直到 EX 才知道两个地址是否相同。对于推测执行的乱序处理器，内存消歧因而成为重要挑战。

旁路

旁路（forwarding，也称 bypassing）将已经算出的结果直接从较后的流水线寄存器送到需要它的阶段，而不必等待寄存器堆写回。它改变的是值在硬件中的传输路线和到达时间，并不改变程序顺序或体系结构寄存器语义。

对于 ALU 输入 A，一个简化的优先级规则是

\[ ForwardA= \begin{cases} EXMEM, & EXMEM.RegWrite\land(EXMEM.rd\ne0)\land(EXMEM.rd=IDEX.rs1),\\ MEMWB, & MEMWB.RegWrite\land(MEMWB.rd\ne0)\land(MEMWB.rd=IDEX.rs1),\\ IDEX, & \text{其他情况}. \end{cases} \]

  • IDEX.rs1 表示当前 EX 阶段消费者需要的源寄存器。
  • EXMEM.rd 属于最近的较早指令，因此具有最高优先级。
  • MEMWB.rd 属于更早的生产者，只有 EX/MEM 不匹配时才使用。
  • RegWrite 防止把分支或 store 指令中偶然出现的 rd 位误认为有效结果。
  • \(rd\ne0\) 防止转发对 RISC-V 零寄存器 x0 的伪写入。

同样的规则可用于 rs2 和 ALU 输入 B。存储数据可能需要独立旁路，因为 store 在 MEM 阶段消费该值，而不是把它作为地址 ALU 的第二个输入。

Python 模型：选择最新的旁路操作数 
from dataclasses import dataclass


@dataclass(frozen=True)
class Producer:
    reg_write: bool
    rd: int
    value: int


def forwarded_operand(source_reg, register_value, ex_mem, mem_wb):
    """优先使用最近的有效生产者，否则保留寄存器堆读出的值。"""
    if ex_mem.reg_write and ex_mem.rd != 0 and ex_mem.rd == source_reg:
        return ex_mem.value, "EX/MEM"
    if mem_wb.reg_write and mem_wb.rd != 0 and mem_wb.rd == source_reg:
        return mem_wb.value, "MEM/WB"
    return register_value, "ID/EX"


# add x5,... 位于 EX/MEM，同时 sub ...,x5,... 进入 EX。
value, source = forwarded_operand(
    source_reg=5,
    register_value=19,              # ID 阶段读出的旧 x5
    ex_mem=Producer(True, 5, 42),   # 最新的 add 结果
    mem_wb=Producer(True, 5, 31),   # 更早的 x5 结果
)

assert (value, source) == (42, "EX/MEM")
print(value, source)

只有值已经产生时，旁路才能弥补时序差距。ALU 结果在 EX 结束时可用，可以在下一周期送到后续指令的 EX 输入；装载值直到 MEM 结束才出现，紧随其后的消费者会过早到达 EX，因此必须使用互锁。

停顿与互锁

停顿（stall）阻止选定指令继续推进；互锁（interlock）则是自动检测不安全条件并产生保持与气泡控制信号的硬件。因此，正确的软件不需要针对普通依赖手工插入与特定实现相关的空操作。

考虑装载-使用组合：

lw  x5, 0(x6)
add x7, x5, x8

load 在周期 C3 的 EX 中计算地址，但数据到 C4 的 MEM 结束时才返回；add 通常也会在 C4 开始 EX，并且一开始就需要 x5。即使存在 MEM 到 EX 的旁路，也不可能在值产生之前交付它。流水线必须把 add 延迟一个周期，随后才能把返回的装载值旁路给它。

常见的检测条件为

\[ stall=IDEX.MemRead\land(IDEX.rd\ne0)\land \left[ (uses\_rs1\land IDEX.rd=IFID.rs1)\lor (uses\_rs2\land IDEX.rd=IFID.rs2) \right]. \]

  • IDEX.MemRead 表明较早的 EX 阶段指令是一条结果较晚到达的 load。
  • IDEX.rd 是这条 load 的目的寄存器。
  • IFID.rs1 与 IFID.rs2 是正在译码的消费者源寄存器。
  • uses_rs1 与 uses_rs2 可避免比较译码后实际上不会读取的字段。

条件成立时，冒险单元保持 PC、保持 IF/ID、清除即将进入 ID/EX 的副作用控制信号，同时允许 EX/MEM 及之后的阶段继续前进。于是 load 向后推进，EX 中出现一个气泡，而消费者留在 ID 等待下一次译码。

Python 模型：检测装载-使用冒险并生成精确的互锁响应 
def load_use_hazard(load, consumer):
    """仅当已译码源操作数需要 EX 阶段 load 的结果时返回 True。"""
    if not load["mem_read"] or load["rd"] == 0:
        return False
    needs_rs1 = consumer["uses_rs1"] and consumer["rs1"] == load["rd"]
    needs_rs2 = consumer["uses_rs2"] and consumer["rs2"] == load["rd"]
    return needs_rs1 or needs_rs2


load = {"mem_read": True, "rd": 5}
consumer = {"uses_rs1": True, "rs1": 5, "uses_rs2": True, "rs2": 8}

stall = load_use_hazard(load, consumer)
control = {
    "PCWrite": not stall,       # False：保持取指地址
    "IFIDWrite": not stall,     # False：让消费者留在译码阶段
    "IDEXControls": "zero" if stall else "decoded",  # 注入气泡
}

assert stall
assert control == {"PCWrite": False, "IFIDWrite": False, "IDEXControls": "zero"}
print(control)

控制冒险

当取指阶段需要下一条 PC，而较早的分支、跳转、返回或陷阱尚未最终确定该 PC 时，就出现了控制冒险（control hazard）。等待每次决策完成当然正确，但会浪费取指机会；预测一条路径可以保持流水线忙碌，但处理器必须能够彻底撤销错误预测造成的所有影响。

如果分支到 EX 才解析，顺序取指单元在结果已知前可能让两条更年轻的指令进入流水线：一条到 ID，另一条仍在 IF。若 IF 预测 \(PC+4\)，而分支最终跳转，则两条指令均来自错误路径。惩罚大小取决于分支在哪个阶段解析、目标地址多快可用，以及需要清除多少个错误路径阶段。

jal 是无条件跳转，译码阶段通常能比条件分支完成寄存器比较更早判断控制流将改变。return 更困难，因为目标来自寄存器，通常借助返回地址栈预测；间接调用和跳转则既需要方向判断，也需要目标预测。

流水线冲刷

流水线冲刷（pipeline flush）使那些不应再影响体系结构状态的在途指令失效。若一个实际跳转的分支被预测为不跳转，处理器会选择目标 PC，并清除更年轻的顺序路径指令的有效位；较老指令和分支本身继续正常执行。

冲刷不能只忽略某个计算结果，失效条目可能产生的每一种副作用都必须被有效位屏蔽：

\[ RegWrite_{effective}=valid\land RegWrite, \]

\[ MemWrite_{effective}=valid\land MemWrite. \]

同一有效性规则也会抑制错误路径异常。例如，错误预测路径上的推测 load 可能在内部遇到访问问题，但当较早分支证明该 load 本不应执行后，它不能引发体系结构可见的陷阱。

Python 模型：重定向 PC，并且只撤销更年轻的条目 
from dataclasses import dataclass, replace


@dataclass(frozen=True)
class InFlight:
    age: int
    text: str
    valid: bool = True


def resolve_taken_branch(branch_age, target, entries):
    """保留分支与更老工作，使更年轻的错误路径工作失效。"""
    corrected = [
        replace(entry, valid=False) if entry.age > branch_age else entry
        for entry in entries
    ]
    return target, corrected


entries = [
    InFlight(0, "older add"),
    InFlight(1, "beq x5,x0,L"),
    InFlight(2, "wrong-path sub"),
    InFlight(3, "wrong-path add"),
]

pc, entries = resolve_taken_branch(1, 0x200, entries)
assert pc == 0x200
assert [entry.valid for entry in entries] == [True, True, False, False]

RV32I 不向软件暴露体系结构分支延迟槽：软件语义不要求跳转分支之后的那条指令必须执行。任何错误路径工作都只是内部推测，实现必须透明地将其移除。

静态预测

静态预测依据固定规则选择方向，不记录每条分支的运行时历史。最简单的流水线把所有条件分支都预测为不跳转，并继续顺序取指。这种方案成本低，因为 \(PC+4\) 已经可用，只有实际跳转的分支才需要纠正。

静态策略 依据 典型弱点
等待分支解析 绝不取错误路径指令 每条分支都会损失周期
总是不跳转 直线代码常见，顺序 PC 容易获得 循环中反复跳转的分支会频繁预测失败
总是跳转 目标能够较早提供时有用 向前条件分支往往不跳转
向后跳转、向前不跳转 向后分支通常构成循环 代码结构只是一种启发式信息
编译器提示或剖析决策 利用离线知识 行为可能随输入改变

对于长指令流，分支预测对 CPI 的一阶贡献可写为

\[ CPI=CPI_{base}+f_b\times m\times P. \]

  • \(CPI_{base}\) 是没有分支预测失败时的 CPI。
  • \(f_b\) 是已完成指令中条件分支所占比例。
  • \(m\) 是这些分支的预测错误率。
  • \(P\) 是每次预测失败损失的周期数。

若 20% 的指令是分支，其中 35% 预测错误，每次错误损失两个周期，则增加的 CPI 为 \(0.20\times0.35\times2=0.14\)。

Python 示例：在同一结果序列上比较静态分支策略 
def static_accuracy(outcomes, policy):
    """在 T/N 结果序列上测量总是跳转或总是不跳转策略。"""
    prediction = "T" if policy == "taken" else "N"
    correct = sum(outcome == prediction for outcome in outcomes)
    return correct / len(outcomes)


# 四次跳回循环，最后一次不跳转并退出循环。
loop = list("TTTTN")

assert static_accuracy(loop, "taken") == 0.8
assert static_accuracy(loop, "not_taken") == 0.2

branch_fraction = 0.20
misprediction_rate = 0.35
penalty = 2
added_cpi = branch_fraction * misprediction_rate * penalty
assert round(added_cpi, 2) == 0.14
print(f"added CPI = {added_cpi:.2f}")

静态方法的成本与时序非常可预测，因此适合小型处理器；但当同一分支在不同执行过程中表现不同时，它无法自适应，这就引出了动态历史预测。

动态分支预测

动态预测记录近期运行行为，并用它预测未来控制流。基础的分支历史表（Branch History Table, BHT）使用分支 PC 的若干位索引一个小状态。常见的两位饱和计数器允许一次反常结果先削弱强预测，而不会立即反转方向。

设计数器 \(c\in\{0,1,2,3\}\)。状态 0、1 预测不跳转，状态 2、3 预测跳转，其更新规则为

\[ c^{+}=\begin{cases} \min(3,c+1), & outcome=taken,\\ \max(0,c-1), & outcome=not\ taken. \end{cases} \]

  • \(c\) 是已解析分支更新预测器前的状态。
  • \(c^{+}\) 是为下一次遇到该分支而保存的新状态。
  • min 与 max 让计数器在边界饱和，而不是从强跳转绕回强不跳转。

对跳转方向的预测还不够，取指阶段还需要目标地址。分支目标缓冲区（Branch Target Buffer, BTB）缓存可能的目标，使 IF 能立即重定向；返回地址栈（Return-Address Stack, RAS）根据嵌套调用结构预测函数返回目标，通常比通用 BTB 更准确。现代预测器还会组合局部和全局历史，但概念仍相同：预测控制流是否改变、预测它将前往何处，并在稍后验证。

Python 模型：存在别名冲突的 PC 索引两位预测器 
class TwoBitPredictor:
    def __init__(self, entries=16, initial_state=1):
        self.counters = [initial_state] * entries  # 1 表示弱不跳转

    def _index(self, pc):
        # 去掉两个对齐位，再映射到有限表项范围内。
        return (pc >> 2) % len(self.counters)

    def predict(self, pc):
        return self.counters[self._index(pc)] >= 2

    def update(self, pc, taken):
        index = self._index(pc)
        old = self.counters[index]
        self.counters[index] = min(3, old + 1) if taken else max(0, old - 1)


predictor = TwoBitPredictor(entries=8)
pc = 0x100
outcomes = [True, True, True, True, False]
predictions = []

for taken in outcomes:
    predictions.append(predictor.predict(pc))
    predictor.update(pc, taken)

assert predictions == [False, True, True, True, True]
assert predictor.counters[predictor._index(pc)] == 2  # 退出后为弱跳转
print(predictions)

不同静态分支可能映射到有限 BHT 的同一个表项，这种别名冲突（aliasing）会使一条分支的结果干扰另一条分支的状态。更大的表和更丰富的历史可以提高准确率，但会消耗存储、能量和前端时序。预测器只有足够早地返回方向和目标，才能真正帮助取指。

预测器 保存的状态 能否适应输入行为？ 主要代价
总是不跳转 无 否 跳转分支需要冲刷
向后跳转、向前不跳转 分支位移符号 否 启发式判断可能出错
两位 BHT 每个索引表项一个计数器 是 预热与别名冲突
基于历史的预测器 由局部/全局模式索引的计数器 是 更多存储、更长延迟和更新逻辑

流水线中的异常

第 06 章把精确异常定义为清晰的体系结构边界：所有更老指令均已完成，故障指令没有执行普通副作用，也没有更年轻的指令改变体系结构状态。流水线使这个要求更难实现，因为三类指令可能同时处于不同阶段。

因此，每个流水线条目都应携带其 PC、有效位以及已经检测到的异常元数据，直到控制逻辑可以确定正确的年龄顺序。非法指令可能在 ID 检测，分支目标问题可能在 EX 检测，数据访问故障则可能到 MEM 才出现。如果同一周期有多条指令报告异常，体系结构上最老的有效指令必须获胜；若较老的分支预测失败或异常冲刷了更年轻指令，更年轻的故障甚至会直接消失。

简单的顺序处理流程是：

  1. 允许故障指令之前的指令完成所有被允许的体系结构更新；
  2. 抑制故障指令的 RegWrite 或 MemWrite；
  3. 写入 mepc、mcause 和 mtval 等陷阱状态；
  4. 使所有更年轻的流水线条目失效；
  5. 将取指 PC 重定向到 mtvec。

中断是异步请求，而不是当前指令直接导致的故障，但处理器仍要呈现精确边界。通常处理器会在已完成指令之间接受中断，并记录下一条可恢复指令的 PC。

Python 模型：选择最老的有效异常并推导流水线动作 
from dataclasses import dataclass


@dataclass(frozen=True)
class PipelineStatus:
    age: int
    pc: int
    text: str
    valid: bool = True
    exception: str | None = None


def precise_trap(entries, mtvec):
    """选择最老的有效异常，并划分所有在途工作。"""
    faults = [entry for entry in entries if entry.valid and entry.exception]
    if not faults:
        return None

    fault = min(faults, key=lambda entry: entry.age)
    return {
        "next_pc": mtvec,
        "mepc": fault.pc,
        "mcause": fault.exception,
        "commit_older": [entry.text for entry in entries if entry.valid and entry.age < fault.age],
        "suppress_faulting": fault.text,
        "flush_younger": [entry.text for entry in entries if entry.valid and entry.age > fault.age],
    }


snapshot = [
    PipelineStatus(0, 0x100, "older add in WB"),
    PipelineStatus(1, 0x104, "faulting load in MEM", exception="load access fault"),
    PipelineStatus(2, 0x108, "younger branch in EX"),
    PipelineStatus(3, 0x10C, "younger add in ID", exception="illegal instruction"),
]

action = precise_trap(snapshot, mtvec=0x80000000)
assert action["mepc"] == 0x104
assert action["commit_older"] == ["older add in WB"]
assert action["flush_younger"] == ["younger branch in EX", "younger add in ID"]
print(action)

精确状态是五级处理器与高度推测处理器共同遵守的不变量。更宽或乱序的机器需要显式提交机制，因为内部执行完成顺序已经不能保证体系结构顺序。

从标量流水线到超标量执行

五级设计是标量（scalar）流水线：每个周期最多有一条指令进入每个阶段，因此理想稳态完成率是一条指令/周期。超标量（superscalar）处理器的发射宽度大于 1，尝试在同一周期开始多条指令。流水线深度与发射宽度是两个独立维度：深度沿时间重叠不同阶段，宽度则复制或共享资源，让多条指令能够同时使用某个阶段。

实际完成速率常用每周期指令数（Instructions per Cycle, IPC）表示：

\[ IPC=\frac{Instructions\ retired}{Cycles}, \qquad CPI=\frac{Cycles}{Instructions\ retired}=\frac{1}{IPC}. \]

只有当两个指标描述相同时间区间、相同已完成指令流时，它们才互为倒数。双发射设计的峰值 IPC 为 2，但只有在独立指令、执行单元、寄存器堆端口、缓存带宽和正确控制流预测都充足时才可能达到。

一个发射组内部也会出现新问题。如果槽位 1 读取槽位 0 的目的寄存器，除非实现提供同周期旁路，否则两条指令不能直接并行执行。两条 load 可能争用一个数据缓存端口；更宽的旁路网络需要比较更多生产者和消费者，其布线本身可能成为限制时钟的关键路径。

乱序超标量处理器通常加入以下机制：

机制 解决的问题
寄存器重命名 消除 WAR 与 WAW 名称依赖
发射队列/调度器 等待真实操作数和执行单元就绪
多个功能单元 为并行执行提供结构容量
重排序缓冲区 按程序顺序提交结果并维持精确异常
load/store 队列 检查内存顺序，并把 store 数据转发给 load

from dataclasses import dataclass


@dataclass(frozen=True)
class IssueInstruction:
    text: str
    reads: frozenset[str]
    writes: frozenset[str]
    resource: str


def can_issue_pair(first, second, capacities):
    """检查没有寄存器重命名的顺序双发射组合。"""
    reasons = []

    if first.writes & second.reads:
        reasons.append("same-group RAW dependency")
    if first.reads & second.writes:
        reasons.append("same-group WAR dependency")
    if first.writes & second.writes:
        reasons.append("same-group WAW dependency")
    if first.resource == second.resource and capacities.get(first.resource, 0) < 2:
        reasons.append(f"only one {first.resource}")

    return not reasons, reasons


i0 = IssueInstruction(
    "add x5,x1,x2", frozenset({"x1", "x2"}), frozenset({"x5"}), "ALU"
)
i1 = IssueInstruction(
    "sub x7,x5,x3", frozenset({"x5", "x3"}), frozenset({"x7"}), "ALU"
)

allowed, reasons = can_issue_pair(i0, i1, capacities={"ALU": 2})
assert not allowed and reasons == ["same-group RAW dependency"]
print(reasons)
设计 峰值发射宽度 主要优势 主要限制
单周期标量 每个长周期一条指令 状态转换简单 时钟周期长，阶段之间没有重叠
五级标量流水线 每个短周期一条指令 以可理解的控制获得较好吞吐量 冒险提高 CPI，旁路也增加时序成本
顺序超标量 按程序顺序同时发射多条指令 利用相邻指令中明显的独立性 下一发射组存在依赖时就会阻塞
乱序超标量 动态选择多条已就绪指令 越过受阻指令寻找并行工作 重命名、调度、恢复、功耗与验证非常复杂

流水线揭示了一条普遍的性能原则：快速的常见路径必须配有在假设失败时维持正确性的恢复路径。旁路假设值已经就绪，互锁负责处理尚未就绪；预测先假设下一 PC，冲刷负责修复错误；推测提前执行内部工作，而顺序提交防止这些工作破坏体系结构状态。

本章总结。 五级流水线重叠 IF、ID、EX、MEM 和 WB，在维持顺序 ISA 契约的同时提高吞吐量。流水线寄存器跨时钟边沿携带数据、控制信号、有效位、PC 与异常元数据。理想状态下可以逼近每周期完成一条指令，但实际性能由最慢阶段、寄存器开销、填充时间、停顿和冲刷共同决定。结构冒险来自硬件容量不足；RAW 数据冒险在值已就绪时用旁路处理，尚未就绪时则需要互锁；WAR 与 WAW 会在执行可能重排时变得重要。控制冒险推动了静态和动态预测，而有效位与冲刷会抑制错误路径副作用。精确异常逻辑在进入陷阱前完成更老工作、抑制故障指令并移除更年轻工作。超标量执行进一步允许每个阶段并行处理多条指令，因此需要更多资源、更广的依赖检查，并往往需要寄存器重命名与顺序提交。第 08 章将沿着 IF 和 MEM 的请求进入缓存层次，分析命中时间如何影响流水线时钟，以及未命中如何向 CPI 中加入可变停顿周期。
