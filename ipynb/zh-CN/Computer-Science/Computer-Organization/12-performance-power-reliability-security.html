性能、功耗、可靠性与安全

前面的章节从抽象、逻辑、指令、流水线、存储、I/O 和并行执行逐步构造了一台计算机。但真实设计在“算出正确答案”时还没有完成：它还必须足够快，在能耗与散热预算内运行，面对故障仍能工作，并且不能让一个保护域推断或修改另一个保护域的数据。

这些目标彼此耦合。更大的缓存可能减少内存流量，却增加面积和漏电；推测执行可能改善平均性能，却扩大必须隔离的内部状态；冗余可能提高可用性，却增加成本、能耗和共因故障风险。本章目标不是最大化单个数字，而是在明确约束下作出可辩护的系统级决策。

一种有效推理顺序是：

  1. 定义工作负载和用户可见需求；
  2. 在受控条件下测量完整系统；
  3. 用证据定位限制资源，而不是猜测；
  4. 用定量模型预测改变能够改善多少；
  5. 检查功耗、可靠性与安全后果；
  6. 用原始工作负载验证最终设计。
设计问题 代表性证据 常见错误
是否足够快？ 延迟分布、吞吐量、错过截止期次数 只报告平均 CPU 利用率
是否节能？ 每任务焦耳数、空闲与峰值功耗 把低功耗误认为低能耗
是否可靠？ 错误覆盖、可靠度、恢复时间、可用性 认为冗余可以消除所有故障
是否受保护？ 特权检查、隔离边界、泄漏分析 只检查体系结构状态，忽略共享微体系结构状态
是否可负担？ 采购、冷却、运营和工程成本 只优化硬件价格，忽略生命周期总成本

评估完整计算机系统

计算机系统评估测量某个明确的软硬件配置能否满足特定工作负载的需求。措辞必须精确，因为性能并不是处理器型号单独固有的属性；它还取决于输入数据、编译选项、库、操作系统策略、内存容量、存储与网络行为、热状态以及观察者选择的指标。

首先要确定系统边界。CPU time 不计进程被调度出去或等待 I/O 的时间；elapsed/wall-clock time 则包含用户真正等待的一切。CPU time 适合诊断处理器工作，端到端延迟通常应使用 wall-clock。服务器还要区分单个请求延迟、总吞吐量，以及 p95、p99 等尾延迟。

主要指标回答不同问题：

  • 延迟：请求或任务开始到所需结果可用的时间；
  • 吞吐量：单位时间完成的有用工作，如 requests/s、transactions/s 或 bytes/s；
  • 尾延迟：揭示平均值掩盖的少量但重要的慢请求；
  • 利用率：资源容量被占用的比例，但高利用率不证明产生了有用进展；
  • 每任务能耗：结合功耗和执行时间，可公平比较不同速度的系统；
  • 可用性：包括维修和恢复在内，服务可用时间所占比例；
  • 正确性与安全约束：它们是准入条件而不是额外加分；快速但错误或泄漏的结果不是成功结果。

负载生成器还要保持预期到达过程。闭环测试中，客户端收到响应后才发下一请求，因此系统变慢时收到的负载反而减少，可能显得比实际更健康；开环测试独立于完成情况调度到达，更适合观察接近饱和时的队列增长和尾延迟。报告必须说明采用哪一种。

评估最终应给出面向需求的结论，而不只是分数，例如：“在 2,000 requests/s 下，99% 请求在 40 ms 内完成，且封装能耗低于每 1,000 请求 8 J。”这句话同时明确了负载、运行点、百分位与资源约束。

基准测试与工作负载选择

基准测试（benchmark）是用于比较实现或跟踪变化的受控工作负载。只有当其行为代表真实问题时，基准才有价值。对一个很小数组排序可揭示指令开销，却无法代表工作集超过内存的分析服务；完整生产轨迹更真实，却可能难以复现和诊断。

基准层级 隔离内容 主要优势 主要局限
微基准 一个操作或子系统 解释延迟、带宽或指令成本 容易被优化成不现实的特例
计算内核 矩阵乘法等重复计算 保留重要访问或计算模式 省略周围软件与 I/O
应用基准 端到端程序与输入 捕获组件交互 更难归因变化
基准套件 多个程序或工作负载类别 减少对单一程序的依赖 汇总分数可能隐藏退化
生产回放 已记录请求或数据分布 外部有效性高 隐私、漂移和可复现性挑战

公平实验必须保持非目标变量不变：源码和二进制版本、编译选项、核心亲和性、线程数、内存放置、固件设置、功耗策略、输入数据、缓存状态和后台活动。预热让代码页、JIT、缓存和热控制逐渐达到目标状态；重复测量则暴露噪声与漂移。

SPEC CPU 运行规则是实验纪律的良好范例：结果应有意义、可比较、可复现，并披露足够配置以供解释；规则还区分可迁移的一般优化与只针对基准的捷径。这个原则同样适用于其他测试：优化技术应能迁移到真实程序。

重复延迟测试应报告分布或多个百分位，而不只是最小值。合并不同基准的归一化比率时，通常使用几何平均：

\[ G=\left(\prod_{i=1}^{n}r_i\right)^{1/n}. \]

\(r_i\) 是第 \(i\) 个基准的无量纲性能比率，\(n\) 是基准数量，\(G\) 是乘法意义上的中心趋势。所有比率必须保持同一方向，例如“候选吞吐量/基线吞吐量”；混用加速比和运行时间比会颠倒含义。

Python 模型：汇总重复运行并合并归一化比率 
from math import prod
from statistics import median


def percentile(samples, fraction):
    """返回 0 <= fraction <= 1 的线性插值百分位。"""
    ordered = sorted(samples)
    position = (len(ordered) - 1) * fraction
    lower = int(position)
    upper = min(lower + 1, len(ordered) - 1)
    weight = position - lower
    return ordered[lower] * (1 - weight) + ordered[upper] * weight


def summarize_runs(runs_ms):
    # 保留运行边界，使运行间漂移可见。
    run_medians = [median(run) for run in runs_ms]
    all_requests = [latency for run in runs_ms for latency in run]
    return {
        "run_medians_ms": run_medians,
        "median_of_run_medians_ms": median(run_medians),
        "p95_request_ms": percentile(all_requests, 0.95),
        "range_of_run_medians_ms": max(run_medians) - min(run_medians),
    }


runs = [
    [10.1, 10.4, 10.2, 11.0, 10.3],
    [10.3, 10.2, 10.5, 10.8, 10.4],
    [10.2, 10.4, 10.3, 10.9, 10.5],
]
summary = summarize_runs(runs)
print(summary)

# 所有比率都是“候选吞吐量/基线吞吐量”。
ratios = [1.18, 0.96, 1.31]
geometric_mean = prod(ratios) ** (1 / len(ratios))
print(f"geometric-mean throughput ratio = {geometric_mean:.3f}x")

assert summary["median_of_run_medians_ms"] == 10.4
assert 1.13 < geometric_mean < 1.15

三次短测试并不会因此具备统计结论性；代码展示的是报告结构：保留原始样本，观察运行间漂移，报告尾部，并且只在方向和工作负载相关性确认后汇总比率。

定位性能瓶颈

瓶颈是当前限制目标指标的资源或依赖。“当前”很重要，因为消除一个限制后，瓶颈可能转移：更快 CPU 可能暴露内存带宽上限；更大缓存可能把等待转移到存储；批量 I/O 可能提高吞吐量，却增加排队延迟。

分析从应用症状开始逐步缩小范围。首先确认结果正确且变慢可复现；随后检查粗粒度资源活动，再用剖析、硬件性能计数器、队列测量和轨迹验证一个具体解释。计数器名称与体系结构相关，部分事件还会重叠，所以计数器应支持因果模型，而不是替代模型。

有效实验只改变一个相关变量，并在运行前预测方向与大致幅度。如果加倍内存带宽没有帮助所谓“带宽受限”内核，说明假设不完整；若降低 CPU 频率几乎不改变 I/O 型延迟，则支持处理器不在关键路径上的判断。

Linux perf 安全文档也提醒我们：剖析数据可能泄露地址、执行上下文、寄存器内容或工作负载行为。生产测量同样需要访问控制与数据最小化，不能因为它“只是性能数据”就无限制收集。

处理器瓶颈

当有用进展主要受指令执行、前端供给、分支恢复或执行单元容量限制，而不是长时间等待内存/I/O 时，工作负载是处理器受限。接近 100% CPU 利用率并非充分证据：核心可能在自旋锁上忙等、不断缓存未命中，或执行本应消除的工作。

指令数、周期、IPC 和 CPI 提供第一层分解：

\[ \mathrm{IPC}=\frac{\text{已提交指令}}{\text{周期}}, \qquad \mathrm{CPI}=\frac{\text{周期}}{\text{已提交指令}}=\frac{1}{\mathrm{IPC}}. \]

在同一测量区间内，宽超标量处理器可每周期提交多条指令，所以 IPC 可大于 1。低 IPC 只是症状，不是诊断；它可能来自依赖链、分支预测失败、前端断粮、缓存未命中或执行端口竞争。

概念上的互斥 CPI 栈为

\[ \mathrm{CPI} = \mathrm{CPI}_{retire} + \mathrm{CPI}_{frontend} + \mathrm{CPI}_{branch} + \mathrm{CPI}_{memory} + \mathrm{CPI}_{other}. \]

每一项把每条已提交指令消耗的周期归因到一个类别。真实硬件事件常通过采样获得或彼此重叠，因此构造实际 CPI 栈时应遵循厂商的 top-down 方法。模型的价值是询问周期去了哪里，以及哪一种体系结构改动真正针对该类别。

Python 模型：把互斥周期归因转换为 CPI 栈 
def cpi_stack(instructions, cycle_categories):
    total_cycles = sum(cycle_categories.values())
    if instructions <= 0 or total_cycles <= 0:
        raise ValueError("instructions and cycles must be positive")

    cpi_components = {
        name: cycles / instructions
        for name, cycles in cycle_categories.items()
    }
    limiting_category = max(cycle_categories, key=cycle_categories.get)
    return total_cycles / instructions, cpi_components, limiting_category


categories = {
    "useful_retirement": 320_000,
    "front_end_wait": 90_000,
    "branch_recovery": 70_000,
    "memory_wait": 410_000,
    "other_back_end": 110_000,
}
cpi, components, limit = cpi_stack(500_000, categories)

print(f"CPI = {cpi:.2f}")
for name, value in components.items():
    print(f"{name:18s}: {value:.2f} cycles/instruction")
print("largest category:", limit)

assert cpi == 2.0
assert limit == "memory_wait"

这个合成例子中最大类别是内存等待，但归因仍从处理器视角完成。下一步要判断延迟来自缓存容量、局部性、带宽饱和、NUMA 放置，还是无法并行多个未命中的依赖链。

内存瓶颈

当数据交付速率或延迟限制进展时，工作负载是内存受限。必须区分三种机制：

  • 延迟受限：继续执行依赖于某次 load 返回；
  • 带宽受限：并发请求足够多，已经饱和可用传输速率；
  • 容量或转换压力：活跃工作集无法容纳，导致缓存、TLB 或页面故障。

缓存未命中率本身并不完整。十个独立未命中可以通过内存级并行重叠，而一次指针追逐未命中就可能停止依赖链。同样，高带宽可能表示接近硬件上限的高效流式访问，也可能表示局部性差、移动了大量无用字节。有效带宽只统计参与结果的数据，物理带宽还包括重复读取、写回、一致性流量和预取。

观察 可能解释 有用验证
LLC 未命中延迟高，但带宽低于峰值 依赖型或低并发未命中 增加内存级并行或改善局部性
带宽接近持续上限 传输速率限制 减少搬运字节或提高局部性；增加核心可能无效
存在远程 NUMA 访问 数据与线程位置分离 把内存绑定到消费核心附近
TLB 未命中或页表遍历很多 转换工作集过大 测试大页面或更小活跃足迹
major page fault 很多 数据从存储设备取回 区分内存容量不足与 DRAM 性能

内存优化应同时预测搬运字节数和节省时间。压缩、分块、SoA 布局、blocking 与缓存感知遍历可能比升级处理器更有效，因为它们能同时减少多个层级的数据移动。

I/O 瓶颈

当存储、网络、设备服务或相关软件路径决定完成时间时，工作负载是I/O 受限。应用观察到的等待时间不只是设备标称介质延迟：

\[ T_{I/O} = T_{queue} + T_{software} + T_{controller} + T_{device} + T_{transfer}. \]

\(T_{queue}\) 是等待早先请求，\(T_{software}\) 包含系统调用、协议处理、中断和驱动工作，\(T_{controller}\) 是命令处理，\(T_{device}\) 是介质或端点服务，\(T_{transfer}\) 搬运有效载荷。接近饱和时，即使设备服务时间不变，排队时间也会急剧增加。

存储与网络瓶颈由工作负载形态决定。小型随机请求强调逐请求延迟与 IOPS，大型顺序请求强调传输带宽；同步访问直接暴露延迟，异步队列可重叠请求，但过深队列会提高尾延迟。压缩能减少 I/O 字节，却增加处理器工作，只有端到端测量才能判断交换是否划算。

有用证据包括队列深度、请求大小分布、未完成操作、完成延迟、bytes/s、IOPS、重传、中断率、DMA 吞吐，以及内核或协议栈 CPU 时间。即使总体 CPU 未满，一个串行驱动或网络处理线程饱和也可能成为 I/O 瓶颈；反之，低 CPU 使用加长设备队列更指向设备或外部服务。

因此，“处理器受限、内存受限、I/O 受限”都是关于关键路径的可验证假设，而不是永久贴在应用上的标签。

定量性能模型

定量模型把测量与体系结构假设转换为预测。模型有意比真实机器简单：CPU 时间方程解释指令执行，Amdahl 定律限制局部增强，Roofline 区分计算与带宽上限，排队模型解释负载下的延迟。它们的目的不是复刻机器，而是排除不可能的期望，并指出值得测量的变量。

模型应明确：

  • 响应变量，例如运行时间、吞吐量或能耗；
  • 每个输入的单位与含义；
  • 哪些项来自测量，哪些来自假设；
  • 模型适用的运行区间；
  • 哪个验证实验可以推翻预测。

模型预测 30% 加速却只测得 3%，并不说明模型毫无价值；差异通常暴露遗漏开销、瓶颈转移或工作负载假设错误。正确做法是更新模型，而不是丢弃不方便的测量。

CPU 时间方程

处理器执行的核心恒等式为

\[ T_{CPU} = IC\times CPI\times T_{cycle} = \frac{IC\times CPI}{f_{clock}}. \]

\(T_{CPU}\) 以秒为单位，\(IC\) 是已提交指令数，\(CPI\) 是每条已提交指令的平均周期数，\(T_{cycle}\) 是秒/周期，\(f_{clock}=1/T_{cycle}\) 是周期/秒。单位可以直接约去：指令 × 周期/指令 × 秒/周期 = 秒。

这个方程可避免“频率越高一定越快”的错误。复杂实现可能提高频率，却增加指令数或缓存未命中；指令扩展可能减少指令数，但延长关键路径；编译器向量化可能减少指令，却增加内存带宽压力。最终乘积而不是单个因素决定 CPU 时间。

Python 模型：用 CPU 时间方程比较两种设计 
def cpu_time_seconds(instruction_count, cpi, frequency_ghz):
    frequency_hz = frequency_ghz * 1e9
    return instruction_count * cpi / frequency_hz


baseline = cpu_time_seconds(
    instruction_count=1.20e9,
    cpi=1.80,
    frequency_ghz=3.0,
)
candidate = cpu_time_seconds(
    instruction_count=1.05e9,  # 更好的代码生成
    cpi=2.00,                  # 单条指令略昂贵
    frequency_ghz=3.4,
)
speedup = baseline / candidate

print(f"baseline CPU time = {baseline:.3f} s")
print(f"candidate CPU time = {candidate:.3f} s")
print(f"speedup = {speedup:.3f}x")

assert abs(baseline - 0.72) < 1e-12
assert 1.16 < speedup < 1.17

候选设计虽然 CPI 更差，但指令数和频率足以补偿，因此胜出。这只是 CPU 时间比较；端到端决策仍要加入内存、I/O、功耗与热行为。

重新审视 Amdahl 定律

Amdahl 定律限制任何只影响部分执行时间的优化。若基线时间中比例 \(F\) 可使用局部加速 \(S_e\) 的增强，则理想总体加速为

\[ S_{overall} = \frac{1}{(1-F)+F/S_e}. \]

即使增强部分无限快，未受影响的 \(1-F\) 仍然存在。真实加速器还需要启动、传输、格式转换、同步与回退。若归一化开销 \(O\) 相对于基线时间测量，更诚实的估计是

\[ S_{overall} = \frac{1}{(1-F)+F/S_e+O}. \]

对 GPU 或专用加速器，\(F\) 必须表示在所需精度和批量下真正可以卸载的比例，而不是看起来算术相似的比例；\(O\) 必须包括真实互连上的数据搬运和重叠损失。多核执行中的同步和负载不均起到相同作用。

Python 模型：在 Amdahl 定律中加入加速器开销 
def amdahl_speedup(enhanceable_fraction, local_speedup, overhead=0.0):
    if not 0 <= enhanceable_fraction <= 1:
        raise ValueError("fraction must be between 0 and 1")
    if local_speedup <= 0 or overhead < 0:
        raise ValueError("speedup must be positive and overhead non-negative")
    new_time = (
        (1 - enhanceable_fraction)
        + enhanceable_fraction / local_speedup
        + overhead
    )
    return 1 / new_time


for fraction in (0.40, 0.70, 0.95):
    ideal = amdahl_speedup(fraction, local_speedup=20)
    realistic = amdahl_speedup(fraction, local_speedup=20, overhead=0.04)
    print(
        f"F={fraction:.2f}: ideal={ideal:.2f}x, "
        f"with overhead={realistic:.2f}x"
    )

# 即使加速无限，未受影响的 30% 也无法消除。
ceiling_without_overhead = 1 / (1 - 0.70)
assert abs(ceiling_without_overhead - 3.3333333333) < 1e-9
assert amdahl_speedup(0.70, 20, 0.04) < ceiling_without_overhead

最值得优化的对象不一定拥有最大的局部加速，而是占据较大实测端到端时间、且无需过高额外开销即可改善的部分。

带宽与操作强度

Roofline 模型用两个上限估算可达到的计算性能：峰值算术吞吐量与持续内存带宽。操作强度（operational intensity） \(I\) 是在所建模内存边界上，每传输一个字节执行的有效操作数：

\[ I=\frac{\text{操作数}}{\text{传输字节数}}, \qquad P_{attainable} = \min(P_{peak},I\times B_{memory}). \]

\(P_{attainable}\) 和 \(P_{peak}\) 单位为 operations/s，\(B_{memory}\) 为 bytes/s，\(I\) 为 operations/byte，所以 \(IB_{memory}\) 正好是 operations/s。脊点为 \(I^*=P_{peak}/B_{memory}\)；简单模型中，脊点左侧受带宽限制，右侧受计算吞吐限制。

图片来源：Giu.natale, Wikimedia Commons，CC BY-SA 4.0。概念模型源自原始 Roofline 论文。

内存受限内核可以通过提高每字节复用、把数据分块放入缓存、融合循环或消除无用传输向右移动；在跨过脊点前，提高算术峰值几乎无效。计算受限内核则可能受益于向量化、更多算术单元、更好指令调度或适合的加速器。真实 Roofline 分析还常加入缓存带宽、指令混合与有限向量化等额外上限。

Python 模型：使用 Roofline 上界分类内核 
def roofline_bound(peak_ops_per_s, bandwidth_bytes_per_s, intensity):
    bandwidth_ceiling = bandwidth_bytes_per_s * intensity
    attainable = min(peak_ops_per_s, bandwidth_ceiling)
    limiting_resource = (
        "memory bandwidth"
        if bandwidth_ceiling < peak_ops_per_s
        else "compute throughput"
    )
    return attainable, limiting_resource


peak = 2.0e12       # 2 TOP/s
bandwidth = 100e9   # 100 GB/s
ridge_point = peak / bandwidth
print(f"ridge point = {ridge_point:.1f} operations/byte")

kernels = {
    "streaming_filter": 2.0,
    "blocked_matrix_kernel": 35.0,
}
for name, intensity in kernels.items():
    attainable, limit = roofline_bound(peak, bandwidth, intensity)
    print(f"{name}: {attainable / 1e9:.0f} GOP/s, limited by {limit}")

assert ridge_point == 20.0
assert roofline_bound(peak, bandwidth, 2.0)[0] == 200e9
assert roofline_bound(peak, bandwidth, 35.0)[0] == peak

操作强度必须在明确边界上测量。寄存器与 L1、末级缓存与 DRAM、主机与加速器之间的字节数会产生不同 Roofline，也会导向不同优化决策。

功耗与能耗

功耗（power）是能量使用速率，单位瓦特（\(1\ \mathrm{W}=1\ \mathrm{J/s}\)）；能耗（energy）是累计消耗，单位焦耳。功耗随时间变化时，

\[ E=\int_0^T P(t)\,dt \approx \sum_i P_i\Delta t_i, \qquad P_{avg}=\frac{E}{T}. \]

低功耗设计若运行足够久，仍可能消耗更多能量；高功率突发若快速完成并回到高效空闲，反而可能总能耗更低。移动设备关注电池能量，数据中心同时关注供电、冷却和能源成本，实时系统则关注限功耗配置能否满足截止期。

测量边界必须匹配问题。芯片遥测可低开销估算封装或功耗域能耗；校准外部功率计则可捕获内存、电源损耗、存储、风扇等组件。Linux powercap 框架为支持的区域暴露能量计数器和功率约束；在测量区间内计算累计能量，通常比把这类遥测误作瞬时墙上功率更有意义。

动态功耗与静态功耗

CMOS 逻辑的一阶分解为

\[ P_{total}\approx P_{dynamic}+P_{static}, \]

其中

\[ P_{dynamic}\approx\alpha C_{eff}V^2f, \qquad P_{static}\approx I_{leak}V. \]

\(\alpha\) 是每周期发生切换的有效电容比例，\(C_{eff}\) 是有效开关电容，\(V\) 是电源电压，\(f\) 是频率，\(I_{leak}\) 是漏电流。动态项中的 \(V^2\) 非常关键：提高频率往往还需要提高电压，所以功耗增长可能快于频率。

时钟门控通过停止空闲结构的时钟降低活动因子；电源门控通过断开区域降低漏电，但唤醒需要时间和能量，且可能需要保留状态。更小、更简单的结构可降低电容和漏电，激进推测则会增加最终未提交的开关工作。因此，“每瓦性能”必须基于完成的有用工作，而不是原始切换活动。

Python 模型：观察电压、频率与漏电敏感度 
def cmos_power(activity, capacitance_f, voltage, frequency_hz, leakage_a):
    dynamic = activity * capacitance_f * voltage**2 * frequency_hz
    static = leakage_a * voltage
    return {
        "dynamic_w": dynamic,
        "static_w": static,
        "total_w": dynamic + static,
    }


low = cmos_power(
    activity=0.20,
    capacitance_f=40e-9,
    voltage=0.80,
    frequency_hz=2.0e9,
    leakage_a=4.0,
)
high = cmos_power(
    activity=0.20,
    capacitance_f=40e-9,
    voltage=1.00,
    frequency_hz=3.0e9,
    leakage_a=5.0,
)

for label, point in (("low", low), ("high", high)):
    print(label, {name: round(value, 2) for name, value in point.items()})

power_ratio = high["total_w"] / low["total_w"]
frequency_ratio = 3.0 / 2.0
print(f"power ratio={power_ratio:.2f}, frequency ratio={frequency_ratio:.2f}")

assert power_ratio > frequency_ratio

这只是敏感度模型，而非晶体管级估算。真实处理器包含多个电压域、稳压器、时钟树、存储阵列、模拟组件和随温度变化的漏电。

电压与频率调节

动态电压频率调节（DVFS）在硬件支持的运行点之间选择。降低频率会减少开关速率，降低电压则带来更大的二次方动态功耗收益；但为了满足时序，电压通常不能任意下降。系统可暴露离散性能状态，由 governor 或固件根据负载、延迟目标、温度和功率上限选择。

Linux CPUFreq 文档说明了策略与机制分离：scaling driver 了解硬件性能状态，governor 在策略范围内选择目标；现代硬件也可能在操作系统之下快速自主决策。

能耗最优点取决于工作负载。计算受限任务提高频率可显著缩短运行时间；内存受限任务只提高核心时钟，可能增加功耗，却几乎不改变依赖 DRAM 的时间。“race to idle”只有在高功耗状态足够快完成、且随后空闲状态高效时才有收益。

Python 模型：选择满足截止期的最低能耗 DVFS 运行点 
def dvfs_result(voltage, frequency_ghz, static_power_w,
                compute_cycles, memory_time_s,
                activity=0.20, capacitance_f=40e-9):
    frequency_hz = frequency_ghz * 1e9
    compute_time = compute_cycles / frequency_hz
    runtime = compute_time + memory_time_s
    dynamic_power = (
        activity * capacitance_f * voltage**2 * frequency_hz
    )
    total_power = dynamic_power + static_power_w
    return {
        "runtime_s": runtime,
        "power_w": total_power,
        "energy_j": total_power * runtime,
    }


states = {
    "eco": (0.75, 1.5, 4.0),
    "balanced": (0.90, 2.5, 5.0),
    "turbo": (1.05, 3.2, 7.0),
}
results = {
    name: dvfs_result(v, f, static, 4e9, memory_time_s=0.60)
    for name, (v, f, static) in states.items()
}

deadline_s = 2.5
feasible = {
    name: result
    for name, result in results.items()
    if result["runtime_s"] <= deadline_s
}
choice = min(feasible, key=lambda name: feasible[name]["energy_j"])

for name, result in results.items():
    print(name, {key: round(value, 2) for key, value in result.items()})
print("lowest-energy state meeting deadline:", choice)

assert choice == "balanced"

结果由需求驱动：玩具模型中 eco 能耗最低却错过截止期；balanced 达标且比 turbo 能耗更低。

热约束

电功率最终变为热，而温度变化远慢于指令执行。一个简单集总热模型是

\[ C_{th}\frac{dT}{dt} = P(t)-\frac{T(t)-T_{ambient}}{R_{th}}. \]

\(T(t)\) 是器件温度，\(T_{ambient}\) 是进风或环境温度，\(P(t)\) 是发热功率，\(R_{th}\) 是摄氏度/瓦的热阻，\(C_{th}\) 是焦耳/摄氏度的热容。\(\tau=R_{th}C_{th}\) 是热时间常数，描述温度逼近新平衡的速度。

处理器可以在短基准中暂时 boost，却在长工作负载中降频，因此短而冷的运行会高估持续性能。散热设计、环境温度、风扇策略、封装接触与邻近设备都属于性能实验的一部分。Intel 的系统概览分析指南也把频率、功耗、带宽与降频观察联系起来。

Python 模型：模拟一阶热控制环 
def simulate_temperature(
    seconds=120,
    dt=0.2,
    ambient_c=25.0,
    thermal_resistance_c_per_w=1.8,
    thermal_capacitance_j_per_c=25.0,
    throttle_threshold_c=78.0,
):
    temperature = ambient_c
    samples = []

    for step in range(int(seconds / dt)):
        # 超过阈值后，控制器降低封装功耗。
        power_w = 38.0 if temperature < throttle_threshold_c else 20.0

        heat_in = power_w
        heat_out = (
            (temperature - ambient_c) / thermal_resistance_c_per_w
        )
        d_temperature = (
            (heat_in - heat_out)
            / thermal_capacitance_j_per_c
            * dt
        )
        temperature += d_temperature
        samples.append((step * dt, temperature, power_w))

    return samples


trace = simulate_temperature()
peak_temperature = max(sample[1] for sample in trace)
throttled_samples = sum(power == 20.0 for _, _, power in trace)

print(f"final temperature = {trace[-1][1]:.1f} C")
print(f"peak temperature = {peak_temperature:.1f} C")
print(f"throttled intervals = {throttled_samples}")

assert throttled_samples > 0
assert peak_temperature < 79.0

这个模型用于展示反馈，而不是预测具体封装。真实系统包含多个传感器、空间热点、测量延迟、风扇、均热器，以及带滞回的控制策略。

可靠性与容错

故障（fault）是底层缺陷或扰动，例如存储位翻转或链路失效；错误（error）是故障造成的不正确内部状态；失效（failure）是系统对外提供的服务偏离规范。容错通过检测、纠正、隔离、冗余和恢复，阻止一部分故障演化为服务失效。

故障可以是瞬态（一次性扰动）、间歇性（依赖特定条件）或永久性（持续缺陷）。辐射单粒子翻转、电压噪声、磨损、制造缺陷、过热、固件错误和链路故障需要不同机制。NASA 的小型航天器航电指南把辐射效应与 ECC、巡检、看门狗和冗余一起讨论，说明故障假设必须匹配环境。

若故障率 \(\lambda\) 为常数，指数可靠度模型为

\[ R(t)=e^{-\lambda t}, \qquad MTTF=\frac{1}{\lambda}. \]

\(R(t)\) 是系统在时间 \(t\) 内无失效存活的概率，MTTF 是平均失效前时间。可维修系统还使用

\[ A=\frac{MTBF}{MTBF+MTTR}, \]

其中可用性 \(A\) 取决于平均失效间隔和平均修复时间。高可靠度减少失效频率，快速恢复减少停机长度；即使组件可靠度不完美，只要能快速检测故障并恢复服务，系统仍可具有高可用性。

NIST 对 fault tolerant 的定义强调在软硬件故障后继续正确运行，但承诺必须明确覆盖的故障模型：一块磁盘失效、一个位损坏、一个副本不可用与区域级宕机不是可互换的主张。

奇偶校验与纠错码

奇偶校验增加一个比特，使总 1 数为偶数或奇数。它能检测任意奇数个位翻转，却无法指出错误位置，并会漏掉所有偶数个位翻转。纠错码（ECC）加入结构化冗余，以定位并纠正指定错误。

关键性质是最小汉明距离 \(d_{min}\)，即任意两个有效码字之间最少不同的位数。编码可检测最多 \(d_{min}-1\) 个位错误，并纠正最多

\[ \left\lfloor\frac{d_{min}-1}{2}\right\rfloor \]

个位错误，因为接收字必须离原始码字比任何其他有效码字更近。

对于 \(m\) 个数据位与 \(r\) 个校验位的 Hamming 码，单错纠正需要

\[ 2^r\ge m+r+1. \]

\(2^r\) 个 syndrome 必须区分 \(m+r\) 个可能错误位置以及无错误状态。在 Hamming(7,4) 中，校验位位于 1、2、4，四个数据位位于 3、5、6、7；每个校验位覆盖二进制位置索引中包含对应位的位置。

图片来源：Cburnett, Wikimedia Commons，CC BY-SA 3.0。

Hamming 码的距离为 3，可纠正单个位错误。再增加一个总奇偶位，就形成常见的 SECDED：单错纠正、双错检测。内存控制器还会巡检内存，定期读取、纠正并重写，避免同一码字中积累多个潜在错误。

Python 模型：编码、诊断并纠正 Hamming(7,4) 码字 
PARITY_POSITIONS = (1, 2, 4)
DATA_POSITIONS = (3, 5, 6, 7)


def hamming74_encode(data_bits):
    if len(data_bits) != 4 or any(bit not in (0, 1) for bit in data_bits):
        raise ValueError("data_bits must contain exactly four binary values")

    code = [0] * 8  # 索引 0 不使用；有效位置为 1 到 7
    for position, bit in zip(DATA_POSITIONS, data_bits):
        code[position] = bit

    # 偶校验：每个校验位使其覆盖集合的 XOR 为零。
    for parity_position in PARITY_POSITIONS:
        parity = 0
        for position in range(1, 8):
            if position & parity_position:
                parity ^= code[position]
        code[parity_position] = parity

    return code[1:]


def hamming74_decode(received_bits):
    code = [0] + list(received_bits)
    syndrome = 0

    for parity_position in PARITY_POSITIONS:
        parity = 0
        for position in range(1, 8):
            if position & parity_position:
                parity ^= code[position]
        if parity:
            syndrome += parity_position

    if syndrome:
        code[syndrome] ^= 1

    data = [code[position] for position in DATA_POSITIONS]
    return data, syndrome, code[1:]


data = [1, 0, 1, 1]
encoded = hamming74_encode(data)
corrupted = encoded.copy()
corrupted[5] ^= 1  # 从零开始的索引 5 是 Hamming 位置 6

decoded, corrected_position, corrected_code = hamming74_decode(corrupted)
print("encoded:", encoded)
print("received:", corrupted)
print("corrected position:", corrected_position)
print("decoded:", decoded)

assert corrected_position == 6
assert decoded == data
assert corrected_code == encoded

解码器假设最多只有一个位错误。若没有额外 SECDED 总奇偶位，某些多位错误会产生误导性 syndrome，甚至被错误纠正。

冗余与恢复

冗余可以放在信息、空间或时间上：

  • 信息冗余加入校验位、校验和或编码分片；
  • 空间冗余复制组件或副本，使另一份能够继续；
  • 时间冗余重试操作或恢复到先前检查点；
  • 多样性使用不同实现或故障域，减少共因故障。

三模冗余（Triple Modular Redundancy, TMR）运行三个模块并多数表决。若每个模块独立正确的概率为 \(R\)，且表决器完美，则三者全部正确或恰有两个正确时系统正确：

\[ R_{TMR} = R^3+3R^2(1-R) = 3R^2-2R^3. \]

图片来源：IjonTichyIjonTichy, Wikimedia Commons，CC0 1.0。

TMR 只有在假设成立时才有帮助。共享电源、共同设计缺陷、环境事件或表决器故障都可能击败全部副本。因此，副本需要故障域隔离、健康监控和维修或替换路径。

恢复机制在正常开销与丢失工作之间权衡。频繁检查点缩短故障后的回滚，却在正常执行中消耗带宽与存储；重试可处理瞬态错误，但相关故障下可能放大过载；故障转移只有在检测准确、备用副本状态足够新时才能真正减少中断。

Python 模型：比较组件可靠度、TMR 与维修可用性 
def tmr_reliability(component_reliability):
    r = component_reliability
    return 3 * r**2 - 2 * r**3


def availability(mtbf_hours, mttr_hours):
    return mtbf_hours / (mtbf_hours + mttr_hours)


component_r = 0.98
tmr_r = tmr_reliability(component_r)
service_availability = availability(
    mtbf_hours=2_000,
    mttr_hours=0.5,
)

print(f"one module reliability = {component_r:.6f}")
print(f"idealized TMR reliability = {tmr_r:.6f}")
print(f"repairable-service availability = {service_availability:.6%}")

assert tmr_r > component_r
assert service_availability > 0.999

数值收益只是上界，因为模型假设独立故障和完美表决器。完整可靠性论证还必须说明检测覆盖率、共因故障、状态修复，以及冗余已经耗尽后的行为。

硬件保护与特权

硬件保护分隔具有不同权限的主体。用户程序不应能够重新配置地址转换、访问其他进程页面、任意编程 DMA 或关闭中断。特权模式、页面权限、陷阱、物理保护与设备隔离让这些规则在应用有缺陷甚至恶意时仍可执行。

常见结构为：

  • 用户模式以受限指令和用户可访问页面执行应用；
  • 监督者/内核模式管理进程、虚拟内存、设备和系统调用；
  • 更高特权的机器/固件模式初始化平台并控制底层资源；
  • 同步异常或异步中断把控制转移到受检查的处理程序，处理程序先验证请求再执行。

PTE 通常含用户/监督者与读写执行权限。执行禁止阻止把数据页当作代码，写保护阻止意外修改，用户位阻止应用触及内核映射。物理内存保护再对物理范围执行检查，IOMMU 则把转换与权限延伸到 DMA 设备。

在 RISC-V 中，Physical Memory Protection 表项定义物理范围及读、写、执行权限。它与分页转换组合，而不是替代分页；被拒绝的操作会产生访问异常，维持体系结构边界。

Python 模型：组合特权、页面与物理范围检查 
def authorize_access(mode, operation, page, physical_region):
    if mode not in {"U", "S", "M"}:
        return False, "unknown privilege mode"

    if operation == "machine_control":
        return (
            (True, "machine privilege")
            if mode == "M"
            else (False, "privileged instruction")
        )

    if mode == "U" and not page["user"]:
        return False, "page is supervisor-only"

    required_permission = {
        "read": "r",
        "write": "w",
        "execute": "x",
    }.get(operation)
    if required_permission is None:
        return False, "unknown operation"
    if not page[required_permission]:
        return False, "page permission denied"
    if not physical_region[required_permission]:
        return False, "physical protection denied"

    return True, "all hardware checks passed"


user_code_page = {"user": True, "r": True, "w": False, "x": True}
protected_region = {"r": True, "w": False, "x": True}

assert authorize_access(
    "U", "execute", user_code_page, protected_region
)[0]
assert not authorize_access(
    "U", "write", user_code_page, protected_region
)[0]
assert not authorize_access(
    "S", "machine_control", user_code_page, protected_region
)[0]

模型省略了很多细节，但表达了组合原则：只有所有相关层级都允许，访问才会成功。软件验证很重要，硬件检查则是最终执行点。

微体系结构安全

ISA 定义软件允许观察哪些值；微体系结构为了快速实现该契约，又加入缓存、TLB、分支预测器、预取器、队列、推测缓冲、执行端口、频率控制器和性能计数器等隐藏状态。如果两个保护域共享这些状态，一个域可能通过时序或竞争推断另一个域的行为，即使体系结构权限检查完全正确。

侧信道（side channel）是与受保护信息相关的非预期观察路径。它不同于直接权限失败：攻击者可能从未在体系结构上读取受害者地址，却能观察缓存行是否变热、预测器是否改变，或共享单元是否繁忙。隐蔽信道（covert channel）则是合作双方故意使用类似设施跨越禁止边界通信。

分析微体系结构安全需要回答五个问题：

  1. 存在哪个秘密或受保护事件？
  2. 它可以影响哪种微体系结构状态？
  3. 哪个其他保护域共享或能够探测该状态？
  4. 什么计时源或计数器会暴露影响？
  5. 哪种机制可阻止、分区、清除、掩盖或限制该信道？

缓解措施可能通过 barrier、缓存分区、禁止共享、预测器清空、减少推测、降低计时精度或恒定工作量软件而牺牲性能。必须先明确安全边界与威胁模型，才有可能判断这项代价是否合理。

推测执行与侧信道

推测执行预测控制流或数据依赖，在条件完全确定前提前工作。预测正确时可隐藏延迟；预测错误时，处理器阻止推测指令提交、恢复体系结构状态并回到正确路径。安全问题在于，回滚不一定清除瞬态工作对缓存、TLB、预测器或共享资源竞争留下的影响。

Spectre 论文展示了错误训练预测如何诱导瞬态操作，把受保护数据编码进可测量的微体系结构状态；Meltdown 论文则展示了受影响实现中，故障访问的数据如何被瞬态使用。二者相关但并不相同：

属性 Spectre 风格机制 Meltdown 风格机制
瞬态原因 预测进入不安全路径 故障或禁止访问的结果被瞬态使用
被打破的假设 软件边界/控制依赖足以限制执行 权限故障会阻止一切数据相关影响
影响范围 广泛的推测实现与可利用 gadget 与权限检查时序相关的特定实现
缓解示例 推测屏障、掩码、retpoline、预测器控制 硬件修改、隔离、平台专用控制

没有一种缓解覆盖所有变体。防御需要组合硬件行为、固件、操作系统隔离、编译器转换与源代码边界纪律，并应针对明确威胁模型评估和测量，因为屏障与隔离会减少 ILP 或缓存共享。

重要的体系结构结论是：“不提交”弱于“没有可观察影响”。安全推理必须包含瞬态数据流和共享状态，而不仅是已提交寄存器与内存。

时序与缓存泄漏

缓存命中与未命中之间存在明显时差。若秘密决定访问哪个地址，后续计时就可能泄露这一选择。秘密相关分支、可变延迟指令、TLB 行为、共享端口、功耗管理或提前退出比较也会产生类似泄漏。

Intel 的时序侧信道指南建议设计密码操作，使时序和共享资源使用不依赖秘密。常数时间（constant-time）不等于简单增加延迟：必须针对目标编译器与硬件检查控制流、内存地址、指令选择和可变延迟操作。

可能的防御包括：

  • 恒定工作量算法与无查找表密码实现；
  • 分区或避免共享缓存与执行上下文；
  • 在保护域切换时清除选定状态；
  • 进程/虚拟机隔离、核心调度，以及关闭不必要共享；
  • 降低暴露的定时器或计数器精度，作为纵深防御；
  • 使用分配与替换不会跨越保护边界的硬件结构。

随机噪声只会增加攻击所需观察次数，并不能消除底层统计信道；同样，内存加密保护存储内容，却不会自动隐藏地址与时序。

Python 模型：比较秘密索引与固定足迹访问模式 
def secret_indexed_lookup(table, secret_index):
    # 被触及的位置本身取决于秘密。
    touched = [secret_index]
    return table[secret_index], touched


def fixed_footprint_select(table, secret_index):
    # 访问每个位置，并且不提前退出地选择一个值。
    # 这里只展示访问模式；Python 并非常数时间运行时。
    selected = 0
    touched = []
    for index, value in enumerate(table):
        choose = int(index == secret_index)
        selected = choose * value + (1 - choose) * selected
        touched.append(index)
    return selected, touched


table = [17, 29, 43, 61]
direct_value, direct_trace = secret_indexed_lookup(table, 2)
fixed_value, fixed_trace = fixed_footprint_select(table, 2)

print("secret-indexed touches:", direct_trace)
print("fixed-footprint touches:", fixed_trace)

assert direct_value == fixed_value == 43
assert direct_trace == [2]
assert fixed_trace == [0, 1, 2, 3]

固定足迹版本只展示设计目标，并不是生产级常数时间原语：解释器、编译器和处理器仍可能转换操作或引入其他数据相关行为。安全关键代码应使用经过审查的平台专用库。

性能、成本、功耗与安全权衡

体系结构设计是多目标优化。若候选方案在所有相关目标上都不差于另一个方案，并且至少一项严格更好，就称它支配（dominate）另一个方案；所有未被支配的设计构成 Pareto 前沿。前沿点是有效方案，却不一定适合具体项目，真正的需求会在互不可比的点之间作出选择。

几个紧凑指标可以帮助比较受约束的设计集合：

\[ EDP=E\times T, \qquad ED^2P=E\times T^2. \]

\(E\) 是每任务能耗，\(T\) 是任务时间。EDP 平衡能耗与延迟，\(ED^2P\) 对延迟施加更强惩罚。但它们不能替代硬约束：错过实时截止期或违反隔离要求的设计，无论分数多好都不可行。

体系结构选择 可能收益 可能成本或风险
更深推测与更宽发射 更高单线程性能 功耗、面积、恢复复杂度与更大瞬态攻击面
更大共享缓存 减少容量未命中，改善共享 漏电、延迟、竞争与侧信道面
更多核心 吞吐量与并行容量 一致性流量、同步和软件复杂度
加速器 特定内核的高每瓦性能 传输开销、可编程性、验证与回退路径
ECC 与冗余 故障检测、纠正与可用性 容量、延迟、能量、表决器与共因风险
更强分区与屏障 改善隔离 失去共享、降低推测、增加上下文切换开销
Python 模型：移除被支配的体系结构候选 
candidates = [
    {"name": "eco",         "performance": 100, "energy": 40,  "cost": 1, "risk": 2},
    {"name": "balanced",    "performance": 180, "energy": 65,  "cost": 2, "risk": 2},
    {"name": "server",      "performance": 260, "energy": 120, "cost": 4, "risk": 1},
    {"name": "accelerated", "performance": 320, "energy": 130, "cost": 6, "risk": 2},
    {"name": "dominated",   "performance": 150, "energy": 90,  "cost": 3, "risk": 3},
]


def dominates(left, right):
    no_worse = (
        left["performance"] >= right["performance"]
        and left["energy"] <= right["energy"]
        and left["cost"] <= right["cost"]
        and left["risk"] <= right["risk"]
    )
    strictly_better = any([
        left["performance"] > right["performance"],
        left["energy"] < right["energy"],
        left["cost"] < right["cost"],
        left["risk"] < right["risk"],
    ])
    return no_worse and strictly_better


frontier = [
    candidate
    for candidate in candidates
    if not any(
        dominates(other, candidate)
        for other in candidates
        if other is not candidate
    )
]

print("Pareto frontier:", [candidate["name"] for candidate in frontier])
assert "dominated" not in {candidate["name"] for candidate in frontier}
assert "balanced" in {candidate["name"] for candidate in frontier}

在计算前沿之前必须先定义目标及其单位。含糊的“风险”分数适合教学，真实设计则应把它替换为明确的安全属性、暴露面、缓解覆盖与验收条件。

实用的体系结构评估流程

最后，把本章内容组合为可重复的工程闭环。

  1. 定义决策。 明确工作负载、输入规模、用户可见指标、所需百分位或吞吐量、功耗与热包络、可靠性目标、安全边界和预算。
  2. 建立可复现基线。 记录硬件、固件、操作系统、编译器、库、功耗策略、亲和性、内存位置、存储状态、输入数据、预热与全部重复原始结果。
  3. 定位瓶颈。 从端到端症状逐步进入资源利用率、剖析、计数器、队列与轨迹，并形成一个因果假设。
  4. 选择最小充分模型。 根据假设使用 CPU 时间方程、CPI 归因、Amdahl、Roofline、热、可靠性或排队模型。
  5. 先预测再修改。 估算预期方向和上限，并加入传输、同步、恢复与测量开销。
  6. 一次只改变一个变量。 保持控制条件，以便将结果归因。
  7. 端到端验证。 重新检查正确性、延迟分布、吞吐量、每任务能耗、温度、故障覆盖与隔离，并寻找转移后的瓶颈和其他工作负载退化。
  8. 记录决策。 保存原始测量、模型输入、被拒方案、权衡依据与回归阈值。
Python 模型：只有全部硬约束通过时才接受候选方案 
def evaluate_candidate(baseline, candidate, constraints):
    report = {
        "speedup": baseline["latency_ms"] / candidate["latency_ms"],
        "energy_change": (
            candidate["energy_j"] / baseline["energy_j"] - 1
        ),
        "cost_change": candidate["cost"] / baseline["cost"] - 1,
    }

    checks = {
        "latency": candidate["latency_ms"] <= constraints["max_latency_ms"],
        "energy": candidate["energy_j"] <= constraints["max_energy_j"],
        "temperature": candidate["temperature_c"] <= constraints["max_temperature_c"],
        "availability": candidate["availability"] >= constraints["min_availability"],
        "security": constraints["required_controls"].issubset(
            candidate["security_controls"]
        ),
    }
    report["checks"] = checks
    report["accepted"] = all(checks.values())
    return report


baseline = {
    "latency_ms": 50,
    "energy_j": 12,
    "temperature_c": 70,
    "availability": 0.9990,
    "cost": 100,
    "security_controls": {"nx", "iommu"},
}
candidate = {
    "latency_ms": 34,
    "energy_j": 10,
    "temperature_c": 76,
    "availability": 0.9998,
    "cost": 125,
    "security_controls": {"nx", "iommu", "ecc"},
}
constraints = {
    "max_latency_ms": 40,
    "max_energy_j": 11,
    "max_temperature_c": 80,
    "min_availability": 0.9995,
    "required_controls": {"nx", "iommu"},
}

decision = evaluate_candidate(baseline, candidate, constraints)
print(decision)
assert decision["accepted"]
assert decision["speedup"] > 1.4

这个最终门槛防止一项诱人的加速悄悄换来不可接受的热、可用性或安全退化。结论应可追溯：在明确工作负载和配置下，候选方案满足每一项硬约束，并以实测幅度改善所选目标。

纵观整个计算机组成系列，有一条原则始终不变：抽象让系统可以理解，定量证据则决定实现是否真正履行其契约。
