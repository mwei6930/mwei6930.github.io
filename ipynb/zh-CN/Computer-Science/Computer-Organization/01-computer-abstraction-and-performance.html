计算机抽象与性能

一行源代码看起来可能毫不费力：把两个数相加、更新计数器，或者显示结果。然而，物理机器必须把每个值表示为比特，找到对应指令，让操作数穿过电路，产生结果，并保存下一个可观察状态。计算机体系结构与组成（computer architecture and organization）提供了一套抽象，使这一转换过程可以被理解和管理。

本章培养两种互补的思维习惯。第一，能够在不同抽象层之间自如移动，同时不把软件可见的承诺与某一种具体硬件实现混为一谈。第二，能够定量评价计算机，而不把时钟频率、核心数量或晶体管数量当作性能的完整答案。

本章围绕以下问题展开：

  1. 硬件向软件承诺了什么行为？
  2. 哪些内部部件协同实现这些行为？
  3. 一条指令如何从内存中的编码变成体系结构状态中的结果？
  4. 哪些测量指标能够公平比较两种设计？
  5. 为什么任何设计都无法同时最大化性能、能效、容量、成本与可靠性？

贯穿本章的指令是 ADD x5, x1, x2。在体系结构层，它承诺把寄存器 x1 与 x2 的和写入 x5；在组成层，具体处理器必须取出指令编码，译出寄存器编号，把数值送入算术单元，并最终提交结果。

什么是计算机体系结构与计算机组成？

计算机体系结构（computer architecture）描述硬件与软件边界上可见的行为。可以把它类比为建筑规范：规范定义房间、入口、承重限制以及住户可以依赖的服务。计算机组成（computer organization）则是满足这份规范的工程方案：横梁放在哪里、管线如何铺设、选用什么材料。

对于处理器，最重要的体系结构契约是指令集体系结构（instruction set architecture, ISA）。它规定指令、寄存器、数据表示、寻址行为，以及程序可以观察到的效果。组成在处理器层面通常称为微体系结构（microarchitecture），它决定流水线、缓存、执行单元和控制逻辑等内部结构。

考虑 ADD x5, x1, x2。其体系结构语义近似为

\[ R[5] \leftarrow \bigl(R[1] + R[2]\bigr) \bmod 2^w, \]

其中 \(R[i]\) 表示寄存器 \(i\)，\(w\) 是体系结构寄存器宽度。模运算表示定长加法后只保留低 \(w\) 位，软件可以依赖这一结果。软件通常不能依赖处理器使用的是行波进位加法器还是超前进位加法器，也不能依赖指令是否在队列中等待，或另一条指令是否同时执行；这些都属于组成层面的选择。

这种区别不仅是术语上的，也具有直接实践意义：

层次 核心问题 示例 普通程序的正确行为能否依赖它？
体系结构 / ISA 机器承诺什么？ 指令、寄存器、地址空间、异常语义 可以
微体系结构 / 组成 如何实现这些承诺？ 流水线、缓存、分支预测器、执行单元 通常不可以，时间等非功能影响除外
电路与物理实现 如何以电子方式实现组成结构？ 逻辑门、晶体管技术、电压、版图 通常不可以，性能、能耗、可靠性和泄漏除外

这种分离解决了两个问题。只要新处理器实现相同 ISA，软件就可以在替换硬件后继续运行；硬件设计者也能改进内部组成，而不要求重写所有程序。它还解释了为什么“体系结构”有时泛指完整系统设计，而“ISA”专指精确的软件可见处理器契约。

当软件为了保持正确而必须了解某项变化时，这项变化就是体系结构性的。增加新指令、改变地址宽度或异常行为属于体系结构变化。只要原有可观察行为仍成立，扩大缓存、把顺序流水线换成乱序执行引擎、改变电路工艺都属于组成变化。

抽象层次

抽象（abstraction）通过更小的接口隐藏低层细节。它并不是说被隐藏的细节不重要，而是让我们能够在局部范围内推理。程序员调用函数时不必追踪每个晶体管；处理器设计者实现指令时也不必知道未来究竟是哪一个应用执行它。

没有一张层次图可以完整描述所有现代系统，但下面的职责划分很有帮助：

层次 代表性产物 对上层隐藏的职责
应用 浏览器、数据库、科学计算程序 算法、用户工作流、领域含义
高级语言与库 Python、C、运行时库 可移植数据类型、函数和内存约定

系统会持续跨越这些边界。库函数可能请求操作系统服务；异常会把控制权从应用转交给特权软件；缓存未命中会迫使微体系结构等待更低层存储。因此，良好的抽象意味着受控交互，而不是完全隔离。

从应用到机器码

假设一个 C 函数返回两个整数参数之和。源代码表达预期计算，却不指定物理逻辑门或指令比特。编译器为目标 ISA 选择指令，汇编器对指令编码，链接器组合代码并解析符号，操作系统加载器再把可执行文件放入内存。

同一操作在 C、RISC-V 汇编和机器码中的表示 
int add_two(int a, int b) {
    return a + b;
}

在常见 RISC-V 调用约定中，参数和返回值使用寄存器 a0 与 a1：

add a0, a0, a1    # a0 接收 a0 + a1
ret                # 返回到 ra 中保存的地址

这两条指令的一种合法 32 位编码是：

00 b5 05 33    add a0, a0, a1    （指令字 0x00b50533）
00 00 80 67    jalr x0, 0(ra)     （ret 所代表的指令）

具体输出会随编译器版本、优化设置、ABI 和目标扩展而改变。这种变化是允许的，因为源语言与 ISA 定义的是行为，而不是唯一强制的指令序列。这正是优化自由度的重要来源：两个编译结果可以包含不同指令，却在源语言层面等价。

因此，转换过程并不是一步把“类似英语的代码”变成电信号，而是一系列契约：

\[ \text{源语言语义} \rightarrow \text{编译器 IR} \rightarrow \text{汇编} \rightarrow \text{机器编码} \rightarrow \text{ISA 效果} \rightarrow \text{电路状态转换}. \]

每个箭头都保留左侧层次要求的行为，同时引入右侧层次所需的细节。

作为软硬件契约的 ISA

ISA 通常不只定义指令名称列表，其契约还包括：

  • 机器状态：通用寄存器、特殊寄存器、程序计数器和特权状态；
  • 指令语义：读取哪些状态、执行什么操作、更新哪些状态；
  • 指令编码：操作码、寄存器编号和立即数如何占据比特位；
  • 内存行为：地址宽度、对齐要求、顺序规则和原子操作；
  • 异常与中断：哪些事件会转移控制，以及保存哪些状态；
  • 特权机制：只有操作系统或监控程序才能使用的操作。

ISA 会刻意不回答许多问题。它通常不规定缓存容量、流水线深度、分支预测器设计、物理寄存器数量或精确指令延迟。把这些细节留给实现，才能让多个设计在运行相同二进制程序的同时，围绕速度、功耗、面积和成本竞争。

软件可以依赖 软件通常不应假设
指令写入的结果 由哪个内部 ALU 产生结果
可见内存效果的规定顺序 是否发生缓存命中
文档定义的异常与特权行为 流水线有多少级
体系结构寄存器和地址宽度 物理寄存器或缓冲区数量

契约视角为后续章节提供了一个检查方法：每引入一种机制，都要问它改变了体系结构语义，还是只改变了产生该语义的效率。

存储程序计算机

存储程序计算机（stored-program computer）把指令表示在可寻址存储器中，而不是把整个计算过程固定在硬连线里。因此，改变程序可以只是装入不同的指令比特，不需要重新制造机器。数据与指令共享相同的一般存储模型，使一台处理器能够执行许多不同任务。

这一经典思想通常与冯·诺依曼模型相关。现代处理器内部常把指令缓存和数据缓存分开，组织形式更像 Harvard 结构，但对软件仍呈现基本统一的体系结构地址空间。这再次说明，同一种体系结构可以由更专门化的内部组成实现。

处理器、内存与 I/O

在最有用的高层视角下，通用计算机包含三个协作子系统：

  1. 处理器读取指令并转换体系结构状态。控制逻辑协调操作，算术逻辑单元执行计算与比较，寄存器文件保存快速操作数，程序计数器指出下一条指令。
  2. 内存保存指令编码与程序数据。它是可寻址的：数值地址选择一个位置或数据块。主存容量远大于寄存器，却也慢得多，因此后续章节会引入缓存和存储层次。
  3. I/O 设备把计算连接到外部世界。显示器、网络、键盘、传感器和存储设备运行速度不同，通常通过设备控制器通信。

对于 ADD x5, x1, x2，指令存储器提供编码，寄存器文件提供两个数值，ALU 产生和，寄存器文件接收结果。加载指令还需要读取数据内存；存储指令需要写入数据内存；I/O 指令或内存映射访问则可能到达设备控制器。

之所以需要这些不同部件，是因为没有一种存储或计算结构能同时做到最快、最大、最便宜且最低功耗。寄存器靠近执行单元，但数量稀少；主存容量大得多，但通信延迟更长；持久存储在断电后仍保留数据，却更加缓慢。计算机组成在很大程度上就是让这些不均等部件高效合作的艺术。

总线与互连

互连（interconnect）在部件之间传递信息。传统总线可以理解为三类逻辑职责：

  • 地址信息指出目标或存储位置；
  • 数据信息携带指令、操作数或结果；
  • 控制信息说明操作类型、大小、方向、状态和时序。

一次内存读事务展示了这种分工：处理器给出地址与读请求；内存或缓存判断自己是否负责该地址，取出所需字节，并返回数据和完成响应。写事务同时发送地址与数据。如果多个代理竞争共享资源，还必须进行仲裁。

下面两个指标不能混淆：

\[ \text{带宽} = \frac{\text{传输字节数}}{\text{经过时间}}, \]

而延迟（latency）是从发出单次请求到收到所需响应的时间。一个实用的一阶传输模型是

\[ T_{\text{transfer}} \approx T_{\text{fixed}} + \frac{B}{R}, \]

其中 \(T_{\text{fixed}}\) 是建立与响应延迟，\(B\) 是字节数，\(R\) 是每秒字节数表示的持续带宽。对于小规模、相互依赖的读取，固定项占主导，因此通常受延迟限制；大型流式传输则常由 \(B/R\) 主导，因此受带宽限制。

互连形式 优点 局限 典型用途
共享总线 简单、成本低 多个代理竞争同一通路 小型或低带宽系统
点到点链路 较高的专用带宽 部件增多时需要大量链路或交换结构 处理器—内存和外设链路
交换网络 / 片上网络 可扩展的并发路由 路由、缓冲与一致性更复杂 多核系统和大型芯片

即使现代系统采用分组与交换链路，“总线”仍是有用的概念：每次传输始终需要目标、载荷、操作类型与完成规则。

指令执行周期

指令执行周期（instruction execution cycle）把从一个体系结构状态转换到下一个状态所需的工作进行概念分解。它通常概括为取指、译码和执行；再单独列出内存访问与写回，可以更清楚地看到数据移动和状态提交。

INSTRUCTION-CYCLE
    instruction_address <- PC
    instruction <- memory[instruction_address]       // 取指
    PC <- 下一条顺序指令的地址
    operation, operands <- decode(instruction)       // 译码
    result, address, branch <- perform(operation)    // 执行
    data <- 可选的内存读取或写入                         // 内存访问
    更新体系结构寄存器或下一 PC                          // 写回

伪代码表达的是依赖关系，而不是唯一的时序实现。单周期处理器可能在一个很长的周期内完成所有工作；多周期处理器可能在多个周期中复用同一个 ALU；流水线处理器则可能让许多指令同时处于不同阶段。

取指

在取指（fetch）阶段，程序计数器提供指令地址，内存系统返回指令比特供后续译码，同时处理器形成顺序执行时的候选下一 PC。若指令固定为 32 位，该地址可能是 \(PC+4\)；可变长 ISA 则需要更复杂的长度识别。

取指看似简单，却已经依赖多种机制：地址必须合法且可执行；可能需要虚拟地址到物理地址的转换；指令缓存可能命中或未命中；分支预测器还可能给出推测的下一 PC。这些机制应加速取指，却不能改变最终体系结构行为。

译码

在译码（decode）阶段，处理器按照 ISA 解释指令字段。操作码指出操作类别；寄存器字段选择源操作数和目的位置；立即数字段提供常量、位移或分支偏移。控制逻辑随后决定需要使用哪些数据通路资源。

对于 ADD x5, x1, x2，译码识别出整数加法、源寄存器 1 和 2，以及目的寄存器 5。从寄存器文件读取数值是组成层面的操作；体系结构契约只要求指令正常完成后，最终的和出现在 x5 中。

执行

在执行（execute）阶段，功能单元完成指令要求的操作。算术指令使用 ALU；分支指令比较数值并形成目标地址；加载与存储计算有效地址；乘法或浮点指令可能使用专门单元。

因此，执行远不只是“做算术”，它会生成下一阶段需要的信息。对于 LOAD x5, 16(x1) 这样的加载指令，执行阶段可能计算

\[ \text{有效地址} = R[1] + \operatorname{signExtend}(16), \]

其中 \(R[1]\) 是基址，符号扩展把指令中的立即数字段转换到体系结构宽度，并保留其有符号数值。

内存访问与写回

只有需要与内存通信的指令才执行数据内存操作。加载指令取回字节并转换为体系结构数值；存储指令发送字节和写请求；算术指令通常直接转发 ALU 结果，不访问数据内存。

写回（write-back）使结果在体系结构状态中可见，通常是更新目的寄存器。分支改为选择下一 PC，存储指令的体系结构效果则是内存写入。真实的乱序处理器可能很早就算出结果，却延迟退休，以保证异常仍按程序顺序呈现。区分“产生结果”与“提交体系结构状态”会在后续章节中十分重要。

下面这个刻意精简的解释器把概念阶段转换成可运行的 Python。它的指令元组不是真实 RISC-V 编码，而是为了在不隐藏于完整模拟器的情况下清楚展示状态转换。

Python 实现：一个微型存储程序指令周期 
from dataclasses import dataclass, field
from typing import TypeAlias

Instruction: TypeAlias = tuple[object, ...]


@dataclass
class TinyMachine:
    """包含寄存器、数据内存、PC 和五种操作的教学模型。"""

    program: list[Instruction]
    registers: list[int] = field(default_factory=lambda: [0] * 8)
    memory: dict[int, int] = field(default_factory=dict)
    pc: int = 0
    halted: bool = False
    trace: list[str] = field(default_factory=list)

    def step(self) -> None:
        if self.halted:
            return
        if not 0 <= self.pc < len(self.program):
            raise IndexError("程序计数器超出指令存储器范围")

        # 1. 取指：用 PC 作为指令存储器索引，然后推进 PC。
        instruction_address = self.pc
        instruction = self.program[instruction_address]
        self.pc += 1
        self.trace.append(f"fetch  pc={instruction_address}: {instruction}")

        # 2. 译码：把操作码与操作数字段分开。
        opcode, *operands = instruction
        self.trace.append(f"decode opcode={opcode}, operands={operands}")

        # 执行阶段可能产生待提交的寄存器写入或内存效果。
        register_write: tuple[int, int] | None = None

        # 3. 执行：根据译码后的操作选择行为。
        if opcode == "LI":
            destination, value = operands
            register_write = (int(destination), int(value))
        elif opcode == "ADD":
            destination, left, right = map(int, operands)
            result = self.registers[left] + self.registers[right]
            register_write = (destination, result)
        elif opcode == "LOAD":
            destination, address = map(int, operands)
            # 4. 内存访问：读取有效地址处的数据。
            register_write = (destination, self.memory.get(address, 0))
        elif opcode == "STORE":
            source, address = map(int, operands)
            # 4. 内存访问：使存储操作在数据内存中可见。
            self.memory[address] = self.registers[source]
        elif opcode == "HALT":
            self.halted = True
        else:
            raise ValueError(f"未知操作码：{opcode}")

        # 5. 写回：把待提交结果写入体系结构状态。
        if register_write is not None:
            destination, value = register_write
            self.registers[destination] = value
            self.trace.append(f"write  x{destination}={value}")

    def run(self, maximum_steps: int = 100) -> None:
        for _ in range(maximum_steps):
            if self.halted:
                return
            self.step()
        raise RuntimeError("程序未能在给定步数预算内停止")


program: list[Instruction] = [
    ("LI", 1, 7),          # x1 <- 7
    ("LI", 2, 4),          # x2 <- 4
    ("ADD", 5, 1, 2),      # x5 <- x1 + x2
    ("STORE", 5, 0),       # memory[0] <- x5
    ("LOAD", 6, 0),        # x6 <- memory[0]
    ("HALT",),
]

machine = TinyMachine(program)
machine.run()

assert machine.registers[5] == 11
assert machine.memory[0] == 11
assert machine.registers[6] == 11

print("\n".join(machine.trace))

这个模型省略了缓存、二进制编码、中断、特权与时序。这样的省略是刻意的：它保留了体系结构状态转换这一核心思想，同时准确暴露出后续章节必须补充哪些细节。

性能度量

性能只有在明确工作负载和指标后才有意义。“机器 A 更快”是不完整的，除非说明执行了什么工作、使用什么输入、输出是否等价，以及“更快”究竟指较低响应时间、较高吞吐量，还是两者兼有。

延迟与吞吐量

延迟（latency）也称响应时间，是一个任务从请求到完成所经历的时间：

\[ L = t_{\text{completion}} - t_{\text{arrival}}. \]

吞吐量（throughput）是单位时间内完成的工作量：

\[ Q = \frac{N_{\text{completed}}}{\Delta t}. \]

这里 \(L\) 是延迟，\(t_{\text{arrival}}\) 与 \(t_{\text{completion}}\) 分别界定一次请求的开始和完成；\(Q\) 是吞吐量，\(N_{\text{completed}}\) 是完成任务数量，\(\Delta t\) 是观察区间。

两个指标可能朝不同方向变化。流水线系统可以让一条指令的延迟大致不变，却让许多指令在不同阶段重叠，从而提高完成速率。批处理可以提高存储或网络吞吐量，同时让单个请求等待更久。交互式系统通常重视尾延迟；服务器和加速器则往往十分看重持续吞吐量。

场景 首要指标 原因
按键到屏幕响应 延迟 用户正在等待一次响应
高负载 Web 服务器 吞吐量和尾延迟 许多请求都要完成，且不能出现极端延迟
科学批处理计算 总经过时间 / 吞吐量 整个工作负载何时完成更重要
实时控制器 有界最坏情况延迟 太晚得到的正确答案也可能没有用

时钟频率与周期时间

同步处理器使用时钟把活动划分成协调的时间区间。时钟频率 \(f_{\text{clock}}\) 表示每秒周期数，周期时间 \(T_{\text{cycle}}\) 表示每个周期所需秒数：

\[ T_{\text{cycle}} = \frac{1}{f_{\text{clock}}}. \]

3 GHz 时钟每秒产生 \(3\times 10^9\) 个周期，因此

\[ T_{\text{cycle}} = \frac{1}{3\times 10^9}\text{ s} \approx 333\text{ ps}. \]

周期必须足够长，才能容纳最慢的必要组合逻辑路径和寄存器时序余量。缩短周期可能要求把工作划分成更多流水级，这能提高时钟频率，却也可能增加流水线开销、分支代价与设计复杂度。

因此，时钟频率只是机器参数，不是完整性能结果。一种体系结构可能需要更少指令，一种微体系结构可能拥有更低 CPI，一个工作负载可能花更多时间等待内存。4 GHz 处理器并不必然比 3 GHz 处理器更快。

指令数、CPI 与 CPU 时间

经典 CPU 性能方程把三个贡献因素分开：

\[ T_{\text{CPU}} = IC \times CPI \times T_{\text{cycle}} = \frac{IC \times CPI}{f_{\text{clock}}}. \]

  • \(T_{\text{CPU}}\) 是测量工作负载在 CPU 上执行指令所花的时间。
  • \(IC\) 是动态指令数（dynamic instruction count），即实际执行的指令数量，包括循环重复。
  • \(CPI\) 是该指令流在给定组成结构上的平均每指令周期数（cycles per instruction）。
  • \(T_{\text{cycle}}\) 是每周期秒数。
  • \(f_{\text{clock}}\) 是每秒周期数，等于 \(1/T_{\text{cycle}}\)。

单位也验证了公式：

\[ \text{指令} \times \frac{\text{周期}}{\text{指令}} \times \frac{\text{秒}}{\text{周期}} = \text{秒}. \]

平均 CPI 取决于指令组合。如果类别 \(i\) 占已执行指令的比例为 \(F_i\)，平均需要 \(CPI_i\) 个周期，则

\[ CPI_{\text{avg}} = \sum_i F_i \times CPI_i, \qquad \sum_i F_i = 1. \]

高 \(CPI_i\) 的类别若很少出现，影响可能不大；一个不算高的代价若非常频繁，则影响巨大。缓存未命中与分支预测错误经常在不改变 ISA 语义或指令数的情况下提高 CPI。

Python 实现：使用完整性能方程比较 CPU 设计 
from dataclasses import dataclass


@dataclass(frozen=True)
class CpuDesign:
    name: str
    instruction_count: float
    average_cpi: float
    clock_rate_hz: float

    def cpu_time_seconds(self) -> float:
        """返回 IC x CPI / 时钟频率，单位为秒。"""
        return self.instruction_count * self.average_cpi / self.clock_rate_hz


def weighted_cpi(instruction_mix: dict[str, tuple[float, float]]) -> float:
    """把（频率，类别 CPI）组合成一个平均 CPI。"""
    total_frequency = sum(frequency for frequency, _ in instruction_mix.values())
    if abs(total_frequency - 1.0) > 1e-9:
        raise ValueError("指令频率之和必须为 1")

    return sum(
        frequency * class_cpi
        for frequency, class_cpi in instruction_mix.values()
    )


mix = {
    "integer ALU": (0.55, 1.0),
    "load": (0.25, 2.0),
    "store": (0.05, 2.0),
    "branch": (0.15, 2.0),
}

assert abs(weighted_cpi(mix) - 1.45) < 1e-9

design_a = CpuDesign("A", 2.0e9, 1.2, 3.0e9)
design_b = CpuDesign("B", 1.6e9, 1.8, 4.0e9)

time_a = design_a.cpu_time_seconds()
time_b = design_b.cpu_time_seconds()
speedup_b_over_a = time_a / time_b

assert abs(time_a - 0.80) < 1e-9
assert abs(time_b - 0.72) < 1e-9
assert abs(speedup_b_over_a - (10 / 9)) < 1e-9

print(f"Design A CPU time: {time_a:.2f} s")
print(f"Design B CPU time: {time_b:.2f} s")
print(f"B is {speedup_b_over_a:.2f}x as fast as A for this workload")

CPU 时间并不总等于墙钟时间。经过时间还可能包括 I/O 等待、操作系统调度、同步以及加速器上的工作。该方程仍然很有价值，因为它解释处理器执行时间，但所选指标必须对应用户的真实体验。

加速比与 Amdahl 定律

当执行时间越低越好时，新设计相对于旧设计的加速比是

\[ S = \frac{T_{\text{old}}}{T_{\text{new}}}. \]

加速比为 2 表示新执行时间是旧时间的一半。把分数颠倒会得到减速比，因此必须明确基准。

只优化一个组成部分，无法加速其他部分所花的时间。如果原执行时间中比例 \(p\) 的部分被加速 \(s\) 倍，而 \(1-p\) 保持不变，Amdahl 定律给出

\[ S_{\text{overall}} = \frac{1}{(1-p)+\frac{p}{s}}. \]

  • \(p\) 是原始时间中受改进影响的比例；
  • \(s\) 是受影响部分的局部加速比；
  • \(1-p\) 是未改变部分，并最终成为限制项。

若 80% 的执行时间被加速 4 倍，新的归一化时间是

\[ (1-0.8)+\frac{0.8}{4}=0.2+0.2=0.4, \]

因此整体加速比为 \(1/0.4=2.5\)，而不是 4。即使改进部分变得无限快，也无法超过 \(1/(1-0.8)=5\)，因为剩余 20% 仍然耗时。

Python 实验：局部改进与整体加速 
def amdahl_speedup(fraction_improved: float, local_speedup: float) -> float:
    """验证模型输入后，返回 1 / ((1-p) + p/s)。"""
    if not 0.0 <= fraction_improved <= 1.0:
        raise ValueError("fraction_improved 必须位于 0 和 1 之间")
    if local_speedup < 1.0:
        raise ValueError("local_speedup 必须至少为 1")

    unchanged_time = 1.0 - fraction_improved
    improved_time = fraction_improved / local_speedup
    return 1.0 / (unchanged_time + improved_time)


for local_speedup in (1, 2, 4, 8, 1000):
    overall = amdahl_speedup(0.80, local_speedup)
    print(f"local={local_speedup:>4}x -> overall={overall:.3f}x")

assert abs(amdahl_speedup(0.80, 4) - 2.5) < 1e-9
assert amdahl_speedup(0.80, 1000) < 5.0

Amdahl 定律并不限于并行处理器。被改进部分可以是浮点执行、缓存未命中、压缩、数据库查询或硬件加速。分析原则始终相同：测量优化部件实际占用了多少原始时间。

技术趋势与设计约束

体系结构受到技术在经济性和可靠性上能够实现什么的制约。早期处理器经常从更高时钟频率和更多晶体管预算中获得性能；现代设计则必须在核心、缓存、专用单元、互连、保护机制和电源管理结构之间分配这些预算。

功耗墙

晶体管翻转会消耗动态功率。常用的一阶模型是

\[ P_{\text{dynamic}} \approx \alpha C V^2 f, \]

其中 \(\alpha\) 是每周期发生翻转的电容比例，\(C\) 是有效开关电容，\(V\) 是供电电压，\(f\) 是开关频率。该公式只是近似，但直觉十分重要：

  • 更高的开关活动或电容会增加能耗；
  • 更高频率意味着每秒发生更多次翻转；
  • 电压具有平方影响，因此降压可以显著节省功率；
  • 降低电压也可能降低可可靠工作的最高频率。

静态泄漏、内存、互连和散热同样重要。功耗墙（power wall）意味着不能无限提高频率而不超过能源和温度限制。这解释了多核设计、时钟门控、动态电压频率调节以及专用加速器的兴起。

Python 实验：归一化动态功率权衡 
def normalized_dynamic_power(
    activity: float,
    capacitance: float,
    voltage: float,
    frequency: float,
) -> float:
    """返回用于设计比较的比例值 alpha*C*V^2*f。"""
    return activity * capacitance * voltage**2 * frequency


# 固定活动率和电容，以突出电压与频率的影响。
baseline = normalized_dynamic_power(0.20, 1.0, voltage=1.0, frequency=3.0)
lower_power = normalized_dynamic_power(0.20, 1.0, voltage=0.8, frequency=2.4)
ratio = lower_power / baseline

# 电压和频率都降至 80%：0.8^2 * 0.8 = 0.512。
assert abs(ratio - 0.512) < 1e-12
print(f"new dynamic power is {ratio:.1%} of baseline")

这个结果并不说明第二个设计以相同性能完成了相同工作负载。功率、能量和执行时间必须一起测量：如果运行时间大幅增长，较低的瞬时功率仍可能消耗大量能量。

内存墙

当所需数据尚未到达时，再快的处理器算术能力也会被浪费。内存墙（memory wall）描述计算速度与数据移动速度差距日益重要的现象，其中包含两种不同限制：

  • 延迟：依赖请求需要等待多久才能得到数据；
  • 带宽：许多请求并行时，每秒可以传输多少字节。

一个简单的 CPI 分解为

\[ CPI_{\text{effective}} = CPI_{\text{base}} + \text{每条指令的内存停顿周期}. \]

假设核心基础 CPI 为 1，每条指令平均发生 0.05 次高代价未命中，每次暴露的未命中平均增加 40 个周期。停顿项为 \(0.05\times 40=2\)，有效 CPI 变为 3。此时三分之二的处理器周期与内存停顿相关，再快的 ALU 也几乎无济于事。

缓存利用局部性，预取器提前请求数据，多项未决请求重叠延迟，高带宽内存支持流式访问，但没有一种机制对所有情况都最好。缓存适合重复的邻近访问；错误预取会浪费带宽；并行请求只有在存在足够独立工作时才有帮助。

成本与可靠性

一种设计必须能够制造并长期可靠工作，而不仅是在模拟中运行得快。一个粗略制造关系是

\[ \text{每颗合格裸片成本} \approx \frac{\text{晶圆成本}} {\text{每片晶圆裸片数}\times\text{良率}}, \]

其中良率（yield）是制造后满足要求的裸片比例。较大的裸片通常会减少每片晶圆可获得的数量，也让每颗裸片暴露于更多缺陷机会。封装、外部内存、散热和验证同样构成系统成本。

可靠性关注系统在一段时间内或出现故障时，是否继续产生正确结果。对于必须全部正常工作的独立部件，一个简单串联系统模型是

\[ R_{\text{system}} = \prod_{i=1}^{n} R_i, \]

其中 \(R_i\) 是所需部件 \(i\) 在给定区间内正常工作的概率。独立性假设往往不完全成立，因为温度、电源和环境事件可能同时影响多个部件，但该乘积仍说明：增加必须正常工作的部件会降低无保护系统的可靠性。

对应措施包括奇偶校验、纠错码、冗余执行、备用容量、温度监控和优雅降级。这些机制都会消耗面积、能量或时间，其价值取决于错误结果或系统不可用的代价。玩具、笔记本电脑、数据中心和航天器需要完全不同的可靠性契约。

比较计算机设计

公平比较必须从等价工作和正确输出开始。仅按广告中的最高时钟频率比较处理器违反这一原则，因为指令数、CPI、内存行为、功率限制和工作负载都可能不同。因此，基准测试应被视为受控实验。

一个实用流程是：

  1. 定义工作负载。明确程序、输入、编译器、目标 ISA 和所需输出。
  2. 选择面向用户的指标。确定延迟、吞吐量、能量、内存容量、可预测性或成本中哪一项最重要。
  3. 控制无关条件。固定软件版本、散热模式、数据位置和测量区间。
  4. 同时测量组成项和总量。记录经过时间，并在条件允许时记录指令数、CPI、缓存未命中、带宽和功率。
  5. 重复并报告波动。预热、后台工作、频率调节和随机性都可能扭曲单次结果。
  6. 解释机制。若能把观察到的变化联系到指令、周期、数据移动或资源限制，结果会更有价值。
问题 合适指标 常见误导性捷径
一个任务需要多长时间？ 端到端延迟 只看时钟频率
高负载下能完成多少任务？ 持续吞吐量与尾延迟 最好的单请求结果
CPU 执行效率如何？ \(IC\)、平均 CPI、时钟频率、CPU 时间 单独看 CPI 或指令数
给定能源预算能完成多少有效工作？ 每任务能量或每瓦性能 不限功率时的峰值性能
是否总能满足截止时间？ 有界延迟或高百分位延迟 平均延迟
某项优化是否值得实现？ 实测受影响比例与 Amdahl 加速比 局部部件加速比

因此，不同计算机可能分别适合不同契约：

设计场景 可能的优先目标 可接受的取舍
交互式笔记本 响应延迟、续航、安静散热 较低的持续峰值性能
数据中心服务 吞吐量、尾延迟、每瓦性能、可用性 更高的设计与基础设施复杂度
嵌入式控制器 可预测时序、低功耗、低成本 较小内存和较低通用吞吐量
科学计算加速器 针对特定工作负载的算术与内存吞吐量 灵活性下降且需要显式移动数据

本章总结。体系结构说明软件能够观察什么；计算机组成选择硬件如何提供这些行为。抽象层次让我们能够局部推理，同时维护明确契约。存储程序模型通过受控传输连接处理器、内存和 I/O。指令周期解释一个编码操作如何成为体系结构状态更新。性能必须分解为工作负载、指令数、CPI、时钟周期、延迟与吞吐量。Amdahl 定律防止把局部改进误认为整机加速。最后，功耗、内存、成本与可靠性说明，“最快”的设计并不自动等于最有用的设计。
