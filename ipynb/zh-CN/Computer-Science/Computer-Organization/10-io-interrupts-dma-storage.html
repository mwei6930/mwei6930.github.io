I/O、中断、DMA 与存储

第 09 章结束于一个需要从外部取得数据的存储型缺页异常。本章继续越过处理器—内存边界跟踪这份数据：请求会经过软件、控制器寄存器与队列、系统互连和设备专用引擎，最后通过完成路径让等待中的计算继续运行。

全章应始终区分三条路径：

  • 控制路径告诉设备要执行什么操作；
  • 数据路径在设备和内存之间传输有效载荷；
  • 完成路径报告成功、失败或部分进度。

现代存储请求可能用 MMIO 提交控制，用 DMA 搬运数据，再用 MSI-X 中断或轮询接收完成通知。这些机制相互协作，而不是只能三选一。

I/O 在计算机系统中的作用

处理器依照严格顺序对寄存器和内存执行指令，而外设运行在完全不同的时间尺度上。键盘只偶尔产生事件，显示器持续消费数据流，网卡在独立时钟域接收分组，存储设备可能在内部纠错后乱序完成命令。I/O 系统负责协调这些差异。

一种有效抽象是在主机与物理设备之间放置设备控制器。主机看到寄存器、队列、缓冲区、命令和完成事件；控制器把它们转换为设备专用时序、协议和错误处理。设备驱动程序是理解该控制器接口的特权软件，它向应用提供更安全的操作系统抽象。

需要协调的差异 处理器—内存一侧 设备一侧 体系结构响应
时序 指令尺度、同步状态 异步外部事件 状态位、轮询、中断、队列
速度 纳秒级执行与缓存 微秒到秒 缓冲、批处理、重叠
粒度 字节、字、缓存块 分组、扇区、页面、帧 控制器与协议描述符
表示方式 load/store 地址 设备专用命令与信号 寄存器、命令集、驱动
故障 精确体系结构异常 重试、介质错误、断连 状态码、超时、恢复
信任 受保护的进程地址空间 独立总线主设备 IOMMU、权限、验证

操作系统还要在进程间复用设备、调度请求、执行权限，并把异步完成转换为阻塞或非阻塞 API。硬件提供机制，软件决定策略。

设备控制器与系统互连

设备控制器具有两个界面。面向主机的一侧提供配置空间、MMIO 寄存器、命令/完成队列和中断能力；内部则包含状态机或固件、协议引擎、缓冲区、纠错与设备专用调度。两者分离，使实现发生显著变化时仍能维持稳定编程接口。

系统互连传输地址、数据和控制事务。片上外设总线可以连接定时器和 UART，PCI Express 则连接高吞吐端点。重要属性包括带宽、仲裁、顺序、错误报告、地址路由、热插拔，以及设备能否作为总线主设备主动发起内存事务。

简单控制器一次可能只通过控制和数据寄存器接收一条命令；高性能控制器则提供驻留内存的环形队列，使多个请求同时未完成。队列把提交与执行解耦：主机推进生产者位置，控制器按自己的速度消费条目，完成记录再指出哪些命令已经结束。

Python 模型：具有命令与状态队列的控制器 
from collections import deque


class DeviceController:
    def __init__(self):
        self.commands = deque()
        self.completed = deque()
        self.busy = False

    def submit(self, command):
        # 真实驱动会发布描述符并写入 doorbell。
        self.commands.append(command)

    def tick(self):
        # 控制器独立于 CPU 指令流推进。
        if self.commands:
            self.busy = True
            command = self.commands.popleft()
            self.completed.append({"id": command["id"], "status": "success"})
            self.busy = False

    def read_completion(self):
        return self.completed.popleft() if self.completed else None


controller = DeviceController()
controller.submit({"id": 17, "operation": "read", "lba": 4096})
assert controller.read_completion() is None
controller.tick()
assert controller.read_completion() == {"id": 17, "status": "success"}
print("controller returned command 17")

控制器状态是并发状态。驱动必须处理超时、过期完成、设备复位、队列回绕，以及完成顺序不同于提交顺序的命令。

程序控制 I/O 与内存映射 I/O

两个相互独立的问题经常被混淆：

  • 内存映射 I/O（Memory-Mapped I/O, MMIO）回答“如何寻址设备寄存器”。保留的物理地址范围被路由到设备，普通 load/store 指令即可访问控制、状态、数据或 doorbell 寄存器。
  • 程序控制 I/O（Programmed I/O, PIO）回答“谁来搬运每个有效载荷单元”。CPU 通过设备数据寄存器或 FIFO 显式读写每个字节或字。

因此，驱动完全可以使用 MMIO 配置 DMA 传输；反之，具有独立 I/O 端口地址空间的体系结构也可用专用端口指令执行 PIO。

设备寄存器不是普通变量。读取可能清除中断待处理位，写入可能开始不可逆操作，posted write 可能在到达设备前被缓冲，连续读取也可能观察到变化中的硬件状态。因此，驱动使用体系结构专用 MMIO 访问函数，阻止编译器删除或重排访问，并在协议要求处加入内存屏障。MMIO 页面通常使用适合设备的缓存属性，而不是普通写回缓存。

机制 优势 局限 典型用途
MMIO 寄存器访问 复用 load/store 的地址转换与保护 副作用和顺序不同于 RAM 控制、状态、队列 doorbell
独立 I/O 端口 设备空间与内存空间分离 需要专用指令，可移植性有限 传统 x86 外设
程序控制数据传输 少量字节的设置成本低 每个数据单元都消耗 CPU 操作 UART 字节、小 FIFO、早期启动
DMA 数据传输 无需 CPU 逐字复制大块数据 需要映射和同步设置 存储、网络、音频、显示
Python 模型：具有寄存器副作用的 MMIO 读写 
CONTROL, STATUS, DATA = 0x00, 0x04, 0x08
READY, INTERRUPT_PENDING = 0b01, 0b10


class MMIODevice:
    def __init__(self):
        self.status = READY
        self.fifo = []

    def write32(self, offset, value):
        if offset == CONTROL and value == 1:
            self.status &= ~READY  # 命令开始
        elif offset == DATA:
            self.fifo.append(value & 0xFF)  # CPU 搬运一个字节
        else:
            raise ValueError("unsupported write")

    def read32(self, offset):
        if offset != STATUS:
            raise ValueError("unsupported read")
        value = self.status
        # 模拟一次“读取即确认”的中断位。
        self.status &= ~INTERRUPT_PENDING
        return value

    def complete(self):
        self.status |= READY | INTERRUPT_PENDING


device = MMIODevice()
for byte in b"IO":
    device.write32(DATA, byte)
device.write32(CONTROL, 1)
device.complete()
first_status = device.read32(STATUS)
second_status = device.read32(STATUS)
assert first_status & INTERRUPT_PENDING
assert not second_status & INTERRUPT_PENDING
assert bytes(device.fifo) == b"IO"
print(bin(first_status), bytes(device.fifo))

轮询与中断驱动 I/O

轮询（polling）反复检查设备或队列状态，直到出现工作。它简单且能以可控延迟发现完成事件，但每次无结果检查都会消耗执行带宽、互连流量，甚至缓存容量。中断驱动 I/O让 CPU 执行其他任务或进入低功耗等待，设备在需要服务时发出信号；代价是中断传递、特权级进入、处理程序和返回开销。

若每隔 \(\Delta\) 秒轮询一次，且完成时刻在间隔内均匀分布，则平均检测延迟近似为

\[ E[T_{detect,poll}]\approx\frac{\Delta}{2}, \]

最坏延迟略小于 \(\Delta\)。缩短轮询间隔会降低检测延迟，但每秒检查次数会增至约 \(1/\Delta\)。

在时间区间 \(T\) 内，CPU 成本可粗略比较为

\[ C_{poll}\approx\frac{T}{\Delta}c_p,\qquad C_{interrupt}\approx N_ec_i, \]

其中 \(c_p\) 是每次轮询成本，\(N_e\) 是完成事件数量，\(c_i\) 是每个事件的中断进入、处理和返回成本。该模型省略批处理和缓存影响，但能说明趋势：稀疏事件适合中断；持续非空的高频队列则可能适合轮询。

实际系统经常混合二者。中断合并一次报告多个完成；自适应方案先由中断唤醒，在队列繁忙时连续轮询，流量稀疏后再恢复中断。目标不是坚持某一种机制，而是在避免为每个微小事件支付昂贵转换的同时，不让核心空耗在空队列上。

Python 示例：估算轮询次数与检测延迟 
import math


def polling_summary(completion_times, interval):
    detected_at = [math.ceil(t / interval) * interval for t in completion_times]
    delays = [detected - actual for detected, actual in zip(detected_at, completion_times)]
    # 持续轮询到最后一次检测到完成为止。
    checks = int(max(detected_at) / interval)
    return checks, sum(delays) / len(delays), delays


events = [2.2, 5.7, 9.1]
checks, average_delay, delays = polling_summary(events, interval=1.0)
interrupt_entries = len(events)

assert checks == 10
assert [round(delay, 1) for delay in delays] == [0.8, 0.3, 0.9]
assert interrupt_entries == 3
print(f"poll checks={checks}, average detection delay={average_delay:.2f}")
print(f"interrupt entries={interrupt_entries}")

异常与中断处理

异常（exception）由当前指令同步触发，例如非法操作码、系统调用或缺页；中断（interrupt）则由当前指令流之外的状态异步产生，例如定时器到期或设备完成。不同 ISA 的术语可能不同，但时序区别始终成立：异常由当前指令解释，中断由外部待处理状态解释。

典型进入过程会记录原因、异常 PC 和状态，改变特权级，屏蔽选定中断，再跳转到处理向量。软件保存自己将修改的额外寄存器，识别来源，完成紧急服务并确认事件，最后使用异常返回指令恢复原状态。精确异常保证所有更老指令看似已完成，所有更年轻指令看似尚未改变体系结构状态。

中断控制器汇集多个来源，根据使能与优先级选择，并把事件路由到某个处理器上下文。电平触发源会保持有效，直到条件被消除；边沿触发源记录一次状态转换。消息信号中断把中断编码为特殊内存写事务，天然适合 PCIe 等分组化互连。

处理程序通常只应执行时间关键工作：确认来源、捕获完成状态并安排延后处理。过长处理会提高其他来源的中断延迟并干扰被打断工作负载。对于 claim/complete 控制器，claim 返回待处理来源，complete 则通知控制器可以再次转发该来源的事件。

Python 模型：中断控制器中的优先级、claim 与 complete 
class InterruptController:
    def __init__(self, priorities):
        self.priorities = priorities
        self.pending = set()
        self.in_service = set()

    def raise_interrupt(self, source):
        self.pending.add(source)

    def claim(self, enabled):
        candidates = self.pending & set(enabled)
        if not candidates:
            return None
        source = max(candidates, key=lambda item: (self.priorities[item], -item))
        self.pending.remove(source)
        self.in_service.add(source)
        return source

    def complete(self, source):
        if source not in self.in_service:
            raise ValueError("source was not claimed")
        self.in_service.remove(source)


controller = InterruptController({1: 2, 2: 7, 3: 4})
for source in [1, 2, 3]:
    controller.raise_interrupt(source)
assert controller.claim(enabled=[1, 2, 3]) == 2
controller.complete(2)
assert controller.claim(enabled=[1, 3]) == 3
print("highest enabled priority is serviced first")

直接内存访问

直接内存访问（Direct Memory Access, DMA）允许控制器主动发起内存事务，因此 CPU 不必为有效载荷中的每个字执行一次 load 和 store。CPU 仍需准备传输：分配或固定缓冲区、取得设备可见地址、建立描述符、按要求顺序发布、通知控制器，以及处理完成和错误。DMA 消除的是重复复制，而不是全部软件参与。

描述符通常包含设备地址、内存地址、长度、方向、命令标识和标志。分散/聚集 DMA（scatter/gather DMA）把多个不连续内存区域串成一次逻辑传输，避免 CPU 预先复制到物理连续缓冲区。

IOMMU 转换设备可见的 I/O 虚拟地址，并限制设备允许访问的物理页面。它既是寻址服务，也是安全边界：有缺陷或恶意的设备不能覆盖任意内核内存。缓冲区生命周期必须持续到 DMA 完成，设备仍在使用时也不能删除页面映射。

顺序至关重要。描述符存储必须先于宣布它的 MMIO doorbell 对设备可见。在非一致系统中，设备读内存前软件可能需要清理 CPU 缓存，设备写内存后再使缓存失效；即使系统具有一致性，也可能需要内存屏障来排列有效载荷、描述符与完成记录。

对 \(N\) 个有效载荷字，CPU 工作量可粗略建模为

\[ C_{PIO}=Nc_w,\qquad C_{DMA}=c_s+Kc_d+c_c. \]

\(c_w\) 是每个 PIO 字的 CPU 成本，\(c_s\) 是 DMA 固定设置成本，\(K\) 是描述符数量，\(c_d\) 是建立每个描述符的成本，\(c_c\) 是完成处理成本。只有节省的逐字工作超过设置和同步开销时，DMA 才占优；极小传输仍可能更适合 PIO。

Python 模型：分散/聚集 DMA 复制两个源片段 
from dataclasses import dataclass


@dataclass
class Descriptor:
    source_offset: int
    destination_offset: int
    length: int


def execute_dma(source, destination, descriptors):
    completed = []
    for index, descriptor in enumerate(descriptors):
        start = descriptor.source_offset
        end = start + descriptor.length
        target = descriptor.destination_offset
        destination[target:target + descriptor.length] = source[start:end]
        completed.append(index)
    return completed


source = bytearray(b"0123456789ABCDEF")
destination = bytearray(b"." * 16)
ring = [Descriptor(0, 0, 4), Descriptor(8, 4, 8)]
completed = execute_dma(source, destination, ring)

assert completed == [0, 1]
assert destination == bytearray(b"012389ABCDEF....")
print(destination.decode())

持久存储

持久存储在处理器复位或普通电源丢失后仍保留选定数据。主机通常看到逻辑块接口，而不是裸磁畴或单个闪存单元；文件系统和数据库再在逻辑块之上构建命名、分配、元数据、顺序和恢复。

CPU 完成一次 store 并不等同于数据已经持久化。数据可能暂存在 CPU 缓存、页面缓存、控制器缓冲区或易失性驱动器缓存中。持久性协议必须定义早先写入何时稳定，并正确使用 flush、强制单元访问、屏障、日志或写时复制元数据。掉电保护可以让某些控制器缓存实际上具备持久性，但软件必须遵守设备公布的契约。

层级 常见暴露单元 可能介入的易失状态
应用/文件系统 文件与逻辑偏移 语言缓冲、页面缓存、元数据缓存
块层/驱动 逻辑块请求 请求队列与合并
设备控制器 命令与逻辑块地址 命令/数据缓存、映射元数据
HDD/SSD 介质 扇区或 NAND 页/擦除块 设备专用内部流水线

下面比较隐藏在相似块接口背后的两种截然不同的介质实现。

硬盘驱动器

硬盘驱动器（Hard Disk Drive, HDD）在旋转盘片上磁性存储数据。执行访问时，执行器先把读写磁头径向移动到目标磁道，盘片旋转使目标扇区来到磁头下方，电子电路再传输并解码数据。小型随机请求的时间主要消耗在机械运动上，所以即使接口只暴露逻辑块地址，物理局部性仍很重要。

访问时间可分解为

\[ T_{access}=T_{queue}+T_{ctrl}+T_{seek}+T_{rot}+T_{xfer}. \]

\(T_{queue}\) 是等待其他请求的时间，\(T_{ctrl}\) 是命令与控制器处理，\(T_{seek}\) 是磁头寻道，\(T_{rot}\) 是等待目标扇区旋转到磁头下方，\(T_{xfer}\) 是传输数据。这些量并非常数，会随当前磁头位置、请求顺序、块大小和驱动行为变化。

转速为每分钟 \(r\) 转时，一整转耗时 \(60/r\) 秒。若目标角位置均匀随机，平均旋转延迟是半圈：

\[ E[T_{rot}]=\frac{30}{r}\text{ 秒}=\frac{30{,}000}{r}\text{ 毫秒}. \]

7,200 RPM 时约为 4.17 ms，且尚未计入寻道和传输。顺序请求可摊薄定位成本并高效流式传输，随机小 I/O 则反复支付定位开销。请求调度器可以重排独立操作来减少寻道距离，但仍要权衡吞吐量、公平性和延迟期限。

Python 示例：估算 HDD 访问时间的组成 
def hdd_access_ms(rpm, seek_ms, transfer_bytes, media_mib_per_s, queue_ms=0, controller_ms=0.1):
    average_rotation_ms = 30_000 / rpm
    transfer_ms = transfer_bytes / (media_mib_per_s * 1024**2) * 1000
    total = queue_ms + controller_ms + seek_ms + average_rotation_ms + transfer_ms
    return {
        "rotation_ms": average_rotation_ms,
        "transfer_ms": transfer_ms,
        "total_ms": total,
    }


estimate = hdd_access_ms(
    rpm=7200,
    seek_ms=8.0,
    transfer_bytes=4 * 1024,
    media_mib_per_s=200,
)
assert round(estimate["rotation_ms"], 2) == 4.17
assert estimate["transfer_ms"] < 0.1
assert estimate["total_ms"] > 12
print({key: round(value, 3) for key, value in estimate.items()})

固态硬盘

固态硬盘（Solid-State Drive, SSD）使用非易失闪存保存数据，不含移动磁头和盘片。消除机械定位显著降低随机访问延迟，但 NAND 闪存具有另一种不对称性：数据按页读取和编程，却必须以大得多的擦除块为单位清除后才能复用；已编程页面不能直接原地覆盖。

闪存转换层（Flash Translation Layer, FTL）把主机逻辑块地址映射到当前物理闪存页。更新写入新页，映射随之改变，旧页变为无效。垃圾回收会复制一个部分失效块中的剩余有效页，再擦除整块供以后复用。额外内部流量形成写放大（write amplification）：

\[ WA=\frac{B_{NAND,written}}{B_{host,written}}, \]

其中 \(B_{NAND,written}\) 是包括复制数据在内的 NAND 内部总写入量，\(B_{host,written}\) 是主机请求写入量。\(WA=1\) 最理想，大于 1 会消耗带宽和编程/擦除寿命。

磨损均衡把擦除分散到不同块，避免少数块过早失效。预留空间为重映射与垃圾回收提供空闲页；纠错码、重试、坏块管理、多 NAND 通道、控制器 DRAM 或主机内存缓冲也都会影响可见性能。TRIM/回收命令通知 SSD 某些逻辑块已无有效主机数据，使对应物理页可在无需复制时回收。

Python 模型：玩具 FTL 中的异地更新 
class ToyFTL:
    def __init__(self, physical_pages):
        self.pages = [None] * physical_pages
        self.valid = [False] * physical_pages
        self.mapping = {}

    def write(self, lba, value):
        # NAND 更新被写入空闲物理页。
        try:
            new_page = next(i for i, page in enumerate(self.pages) if page is None)
        except StopIteration as error:
            raise RuntimeError("garbage collection required") from error

        if lba in self.mapping:
            self.valid[self.mapping[lba]] = False  # 旧版本变为无效
        self.pages[new_page] = (lba, value)
        self.valid[new_page] = True
        self.mapping[lba] = new_page
        return new_page

    def read(self, lba):
        page = self.mapping[lba]
        return self.pages[page][1]


ftl = ToyFTL(physical_pages=6)
old_page = ftl.write(42, "old")
ftl.write(7, "other")
new_page = ftl.write(42, "new")

assert old_page != new_page
assert not ftl.valid[old_page]
assert ftl.valid[new_page]
assert ftl.read(42) == "new"
print(f"LBA 42 moved from physical page {old_page} to {new_page}")

与 HDD 相比，SSD 消除了寻道和旋转延迟，并可利用多个内部通道；但其延迟仍会受排队、垃圾回收、温度降频、错误重试、缓存状态与历史写入影响。

存储性能

存储性能无法用一个数字概括。延迟表示单个请求从提交到完成的时间，IOPS是每秒完成的操作数，带宽是每秒完成的字节数，队列深度是未完成请求数，尾延迟则呈现平均值掩盖的慢百分位。

若平均请求大小为 \(S\) 字节，完成速率为每秒 \(\lambda\) 次操作，则

\[ Bandwidth=\lambda S. \]

这里 \(\lambda\) 就是 IOPS，\(S\) 是每次操作的平均字节数。因此，同样的 IOPS 对 4 KiB 随机读和 1 MiB 顺序读意味着完全不同的带宽。

Little 定律把稳态平均并发数 \(N\)、完成速率 \(\lambda\) 与平均响应时间 \(W\) 联系起来：

\[ N=\lambda W. \]

\(N\) 是平均在途请求数，\(\lambda\) 是单位时间完成数，\(W\) 使用相同时间单位。重排可得 \(\lambda=N/W\)，在设备具有足够并行服务能力时可作为理想上限估计。提高队列深度只在内部并行尚未占满时增加吞吐量；饱和后，新请求主要用于等待，吞吐量趋平而延迟继续增长。

测量必须说明工作负载形态：读写比例、随机或顺序地址、请求大小、队列深度、持续时间、预热、缓存策略、持久性要求、数据可压缩性和报告的百分位。把缓存命中的顺序基准与要求持久化的随机写直接比较没有意义。

Python 示例：联系队列深度、延迟、IOPS 与带宽 
def ideal_storage_rate(queue_depth, average_latency_ms, request_bytes, device_iops_limit=None):
    latency_seconds = average_latency_ms / 1000
    little_law_iops = queue_depth / latency_seconds
    iops = min(little_law_iops, device_iops_limit) if device_iops_limit else little_law_iops
    bandwidth_mib_s = iops * request_bytes / 1024**2
    return iops, bandwidth_mib_s


iops, bandwidth = ideal_storage_rate(
    queue_depth=32,
    average_latency_ms=0.2,
    request_bytes=4096,
    device_iops_limit=120_000,
)
assert iops == 120_000  # 设备在无约束 160k 估计之前饱和
assert round(bandwidth, 2) == 468.75
print(f"{iops:,.0f} IOPS, {bandwidth:.2f} MiB/s")

RAID 与存储可靠性

RAID 把多个驱动器组合成一个逻辑存储系统，以改变容量、性能和对特定驱动器故障的容忍能力。条带化分散数据块，镜像保存副本，奇偶校验保存足以重建缺失数据的信息。具体布局决定可用容量以及能承受的故障数量与组合。

对于 \(N\) 块相同容量 \(S\) 的驱动器，常见可用容量近似为

\[ C_{RAID0}=NS,\quad C_{RAID5}=(N-1)S,\quad C_{RAID6}=(N-2)S,\quad C_{RAID10}=\frac{N}{2}S. \]

\(N\) 是驱动器数量，\(S\) 是参与驱动器中最小容量。RAID 10 假设偶数块驱动器组成镜像对；RAID 1 容量取决于镜像分组，简单双盘镜像只暴露 \(S\)。

级别 最少驱动器 可用容量 故障容忍 重要写行为
RAID 0 2 \(NS\) 无 并行写数据，无冗余
RAID 1 2 每个镜像组一个副本 每组仍保留副本时可容忍一个或多个 更新每个镜像
RAID 5 3 \((N-1)S\) 一块 小写可能需要读—改—写数据和奇偶校验
RAID 6 4 \((N-2)S\) 两块 两组校验增加写入工作
RAID 10 4 \(NS/2\) 取决于具体故障组合 在镜像对之间条带化

RAID 5 的奇偶校验可按字节写成 \(P=D_0\oplus D_1\oplus D_2\)。若 \(D_1\) 丢失，由于 XOR 是自身的逆运算，可用 \(D_1=P\oplus D_0\oplus D_2\) 重建。分布式奇偶校验避免永久占用一块校验盘，但降级读取和重建会消耗存活驱动器带宽。大型阵列还面临漫长重建窗口和潜在介质错误，因此真实可靠性还需要校验和、巡检、热备盘、监控与备份。

Python 示例：用 XOR 重建一个丢失的 RAID-5 数据块 
def xor_blocks(*blocks):
    if len({len(block) for block in blocks}) != 1:
        raise ValueError("all blocks must have equal length")
    return bytes(a ^ b ^ c for a, b, c in zip(*blocks)) if len(blocks) == 3 else bytes(
        __import__("functools").reduce(lambda x, y: x ^ y, values)
        for values in zip(*blocks)
    )


data0 = bytes([0x10, 0x22, 0x34, 0x48])
data1 = bytes([0xAB, 0xCD, 0xEF, 0x01])
data2 = bytes([0x55, 0x66, 0x77, 0x88])
parity = xor_blocks(data0, data1, data2)
recovered_data1 = xor_blocks(parity, data0, data2)

assert recovered_data1 == data1
print("recovered:", recovered_data1.hex())

RAID 不是备份。它无法单独恢复误删文件、已复制到所有成员的应用数据损坏、被盗硬件或站点级灾难。冗余提高的是对明确组件故障的可用性，备份与恢复才保护历史数据。

跟踪端到端 I/O 请求

考虑从 NVMe SSD 读取 16 KiB，且所需文件数据不在页面缓存中。这个流程展示了本章机制如何组合；若页面缓存命中，请求将在内存中结束，完全跳过设备路径。

  1. 应用以虚拟目标缓冲区和文件偏移调用 read()。
  2. 文件系统检查页面缓存，并把文件块转换为块请求。
  3. 块层可能合并、拆分和调度请求，再交给 NVMe 驱动。
  4. 驱动固定或映射目标页面用于 DMA，填写提交队列项（SQE），并按所需内存顺序发布。
  5. MMIO doorbell 写通知控制器提交队列尾部已经推进。
  6. 控制器用 DMA 取得命令、验证命令，并通过 FTL 映射逻辑块地址。
  7. NAND 通道读取所需页面，控制器 ECC 修复可恢复错误。
  8. 控制器用 DMA 把有效载荷写入已映射主机内存页。
  9. 数据可见性得到保证后，控制器写入完成队列项并发出 MSI-X，或等待主机轮询。
  10. 驱动消费完成项、处理错误、解除 DMA 映射并唤醒任务；文件系统返回请求字节。

命令与 doorbell 构成控制路径，DMA 写构成数据路径，完成队列与中断/轮询构成完成路径。这解释了为什么中断本身不携带 16 KiB 数据，也解释了为什么没有描述符和命令标识时，DMA 无法告诉软件应该完成哪个应用请求。

第 09 章的存储型缺页会在步骤 2 附近接入：虚拟内存子系统分配页框，请求文件系统或交换子系统读入缺失页，并只在 I/O 路径填满该页框后重启故障指令。

phases = [
    ("syscall_and_cache_lookup", "control", 4),
    ("block_and_driver_setup", "control", 8),
    ("publish_sqe_and_doorbell", "control", 2),
    ("controller_and_flash_read", "device", 70),

def build_trace(items):
    now_us = 0
    trace = []
    for name, path, duration_us in items:
        trace.append({"start_us": now_us, "end_us": now_us + duration_us, "path": path, "name": name})
        now_us += duration_us
    return trace

assert trace[-1]["end_us"] == 100
assert [item["path"] for item in trace].count("data") == 1
assert trace[4]["name"] == "dma_payload_to_memory"
for item in trace:
    print(f"{item['start_us']:>3}-{item['end_us']:>3} us  {item['path']:<10} {item['name']}")

选择 I/O 传输机制

合理设计应分别选择控制、有效载荷搬运和完成机制。寄存器大小的命令通常使用 MMIO，大块数据通常使用 DMA；稀疏完成适合中断，持续繁忙队列则可能适合轮询或自适应组合。

工作负载 控制 有效载荷 完成 原因
配置定时器 MMIO 寄存器 无/极少 轮询一次或中断 设置成本占主导
键盘事件 MMIO 状态 读取小 FIFO 中断 事件稀疏且不可预测
高速网络接收 MMIO doorbell DMA 描述符环 中断后批量轮询 大量小分组摊薄转换成本
NVMe 块 I/O MMIO doorbell DMA 到映射页 轮询 CQ 或 MSI-X 队列暴露并行性
音频播放 MMIO 控制 循环 DMA 缓冲区 周期中断 有截止期的连续数据流
早期启动 UART MMIO/端口 I/O 程序控制字节传输 轮询 完整中断初始化前重视简单性

选择还必须考虑故障行为。轮询需要超时而不能无限循环；中断处理程序要容忍共享或过期事件；DMA 要限制地址、保证缓冲区生命周期、定义取消规则与复位恢复。只有把完成项与正确命令关联后，相关内存才能交还给其他所有者。

Python 示例：独立选择控制、有效载荷与完成机制 
def choose_io_strategy(payload_bytes, events_per_second, latency_critical=False):
    control = "MMIO registers/doorbell"
    payload = "programmed I/O" if payload_bytes <= 16 else "DMA"

    if events_per_second < 1_000:
        completion = "interrupt"
    elif events_per_second > 100_000 or latency_critical:
        completion = "polling or adaptive polling"
    else:
        completion = "interrupt coalescing"
    return control, payload, completion


assert choose_io_strategy(1, 20) == (
    "MMIO registers/doorbell", "programmed I/O", "interrupt"
)
assert choose_io_strategy(16 * 1024, 200_000)[1:] == (
    "DMA", "polling or adaptive polling"
)
print(choose_io_strategy(4096, 10_000))

玩具策略中的数值阈值仅用于说明，而不是硬件规则。真实选择取决于实测设置成本、事件速率、功耗预算、缓存行为、设备排队和延迟目标。

本章总结。 I/O 把同步的处理器—内存模型连接到时序、粒度、可靠性与协议各不相同的设备。控制器暴露寄存器和队列，同时隐藏设备专用执行。MMIO 决定如何寻址寄存器，PIO 决定 CPU 是否逐单元搬运数据。轮询用 CPU 注意力换取直接检测，中断则用进入开销换取高效等待。异常与当前指令同步，设备中断异步发生，并通常经过优先级控制器或消息信号路径。DMA 允许控制器在设备与映射内存间搬运大块数据，但仍需要描述符设置、顺序、生命周期、IOMMU 保护和完成处理。HDD 支付寻道与旋转成本；SSD 则面对 FTL 映射、异地写、垃圾回收、磨损均衡与通道并行。存储性能必须区分延迟、IOPS、带宽、队列深度和尾部；RAID 改变放置和指定故障容忍，但不能替代备份。第 11 章将进入多核执行，其中每核队列、中断路由、共享内存同步与缓存一致性共同决定 I/O 如何随处理器数量扩展。
