现代 NLP 系统

语言模型是一个计算组件；有用的 NLP 产品则是围绕该组件加入数据、上下文构造、检索、工具、验证、权限、可观测性与人工流程的系统。区分二者很重要，因为许多真实故障并非源于模型权重，而来自过时文档、错误提示、缺失访问控制、无效工具参数、失败的重试，或鼓励用户相信无依据输出的界面。

本章围绕一个持续案例：客服助手回答政策问题，并在用户确认后创建支持工单。示例从单次独立模型调用开始，逐步加入可信运行所需组件：

user request
-> input policy and identity checks
-> context construction
-> retrieval and reranking
-> grounded response generation
-> structured validation
-> optional tool execution
-> response and citations
-> trace, monitoring, and human escalation

目标不是追求最大架构复杂度。每个组件都应因解决具体需求而存在。确定性工作流常优于自主智能体，独立分类器也常优于生成系统。现代系统设计的核心，是选择能够在真实运行约束下满足任务契约的最小架构。

从模型到系统

模型、管线与系统

模型把输入表示映射为输出。分类器把文本映射成标签分数；语言模型把 token 前缀映射为下一 token 的概率分布。模型不知道用户是否获得授权、政策文档是否最新，也不知道预测后应采取什么行动。

管线以大致固定顺序组合多个处理阶段。经典客服管线可以检测语言、分类意图、检索政策段落并生成回答。管线让中间数据可见，也允许分别测试每个阶段。

系统包含管线，以及外部状态与运行控制：文档存储、索引、API、权限、缓存、队列、版本、用户界面、监控、回退行为与人工责任。

层级 主要职责 示例产物 典型失败
模型 统计预测或生成 模型权重与分词器 错误标签或无依据文本
管线 有序转换数据 检索－生成图 阶段顺序错误或 schema 不匹配
系统 在环境中可靠运行 服务、索引、工具、日志、政策 未授权行动或未检测退化

不同层级有不同契约。生成器可能承诺 text in -> text out；客服系统必须承诺更强内容：答案使用当前客户获准查看的正确上下文，政策陈述引用最新文档，行动需要确认，故障被记录，无法解决的案例交给人。

Python：定义系统组件间的显式接口 
from dataclasses import dataclass, field

@dataclass(frozen=True)
class UserRequest:
    request_id: str
    user_id: str
    message: str
    locale: str = "en-AU"

@dataclass(frozen=True)
class Evidence:
    document_id: str
    version: str
    text: str
    score: float

@dataclass
class SystemResponse:
    answer: str
    citations: list[str] = field(default_factory=list)
    action_status: str = "none"
    needs_human: bool = False

def validate_boundary(request: UserRequest) -> None:
    # Step 1: enforce basic input invariants at the service boundary.
    if not request.request_id or not request.user_id:
        raise ValueError("request and user identity are required")
    if not request.message.strip():
        raise ValueError("message cannot be empty")

# Step 2: downstream components exchange typed records rather than
# relying on an undocumented collection of dictionary keys.
request = UserRequest(
    request_id="req-1042",
    user_id="user-77",
    message="How long does a duplicate-charge refund take?",
)
validate_boundary(request)

类型化边界不能保证正确，但能定位错误。如果检索返回的证据对象缺少版本，就可在生成前拒绝，而不是让它变成最终回答中没有来源的陈述。

离线构建与在线推理

现代 NLP 系统通常包含两条相连路径。

离线路径准备可跨请求复用的资产：

collect and approve documents
-> parse and normalize
-> split into chunks
-> attach metadata and permissions
-> compute sparse and dense representations
-> build indexes
-> evaluate and publish a version

在线路径服务一次用户交互：

authenticate request
-> understand query
-> retrieve permitted candidates
-> rerank and construct context
-> call model or tool
-> validate response
-> return result and record trace

分离两条路径可降低延迟并使发布可复现。昂贵的文档解析和嵌入不应为每个问题重复运行；但离线索引也不能被视为永恒不变。新政策版本、删除的客户记录或变化的权限都必须传播到服务路径。

关注点 离线决策 在线后果
文档版本 哪个来源具有权威？ 哪项陈述可被引用？
分块 多少上下文存储在一起？ 可检索哪些证据？
元数据 索引哪些字段与权限？ 可应用哪些过滤器？
嵌入模型 如何表示文档？ 查询编码器必须兼容
发布关卡 哪个索引通过评估？ 在线流量使用该版本

索引更新应是显式发布，而非不可见变更。记录文档快照、解析器、分块配置、嵌入模型和评估结果；否则，即使语言模型版本不变，回答也会发生无法解释的变化。

组件与端到端数据流

只有每条箭头都有契约时，端到端图才有用。客服助手的数据流可分为处理用户请求的数据平面，以及管理版本、政策、监控与发布的控制平面。

DATA PLANE
request -> gateway -> orchestrator -> retriever -> reranker -> model -> validator
                                  \-> approved tools -> external services

CONTROL PLANE
document ingestion -> index release -----------^
prompt/model registry -> deployment config ----^
evaluation suite -> release gate --------------^
traces and feedback -> monitoring -> response -^

编排器协调组件，但不应成为包含所有政策、无法测试的黑盒。授权属于工具与数据边界，验证应紧跟不可信输出，版本信息则应出现在每条 trace 中。

有用设计评审会针对每条边询问：

  1. 什么 schema 跨越此边界？
  2. 哪个组件被允许产生它？
  3. 如何验证？
  4. 可能发生什么超时或故障？
  5. 后续回退是什么？
  6. 记录哪些版本与 trace 标识符？

答案经常揭示，“NLP 问题”部分也是分布式系统问题。高质量模型无法弥补检索器超时后静默返回空上下文，也无法防止重试重复创建同一工单。

模型接口与上下文构造

模型看到的是序列化上下文，而不是人类理解的整个应用。系统指令、检索文本、会话历史、工具定义和当前请求共同竞争有限上下文窗口。因此，上下文构造是一种编程：它定义模型预测所依据的证据与约束。

提示模板与指令上下文

提示模板应分离可信指令与不可信内容。客服助手至少有四层：

层级 示例 信任级别
系统政策 只根据提供的政策摘录回答 可信且版本化
应用上下文 locale、商品、允许工具 可信结构化数据
检索内容 政策块与元数据 外部来源，视为数据
用户内容 当前消息与引用文本 不可信输入

分隔符与字段名帮助模型解释层级，但不是安全边界。检索网页可包含看似指令的文本；应用仍须控制可用工具，并验证模型外部的每项行动。

提示应作为有版本、有测试的产物。改善语气的修改可能降低引用遵循或增加拒绝。部署前应在正常、困难与对抗案例上评估，并在 trace 中记录提示版本。

Python：根据显式信任边界构建提示 
from dataclasses import dataclass

@dataclass(frozen=True)
class ContextChunk:
    citation_id: str
    text: str

def build_support_prompt(user_message, chunks, locale="en-AU"):
    # Step 1: keep policy in code-controlled text, not user-controlled fields.
    instructions = (
        "You are a customer-support assistant. "
        "Use only the supplied evidence for policy claims. "
        "Cite each policy claim with [source_id]. "
        "If evidence is insufficient, say so and request human review."
    )

    # Step 2: serialize retrieved material as labeled evidence.
    evidence = "\n\n".join(
        f"SOURCE {chunk.citation_id}\n{chunk.text}"
        for chunk in chunks
    )

    # Step 3: mark the user message as data and keep it last.
    return f"""{instructions}

LOCALE: {locale}

<EVIDENCE>
{evidence}
</EVIDENCE>

<USER_MESSAGE>
{user_message}
</USER_MESSAGE>
"""

prompt = build_support_prompt(
    "How long does a duplicate-charge refund take?",
    [ContextChunk("refund-policy-v3#p4", "Refunds take 3-5 business days.")],
)
print(prompt)

模板使来源可检查，但系统仍须验证每个引用标识符确实被提供，而且用户有权查看相应来源。

上下文窗口与 Token 预算

模型上下文窗口限制指令、用户输入、检索证据、会话历史、工具 schema 与生成输出可用的总 token。若窗口为 \(W\)，基本预算为：

\[ B_{\text{evidence}} = W - B_{\text{instructions}} - B_{\text{history}} - B_{\text{user}} - B_{\text{tools}} - B_{\text{output}} - B_{\text{margin}}. \]

\(B_{\text{evidence}}\) 是留给检索文本的空间；其他 \(B\) 项分别为上下文组件保留 token；\(B_{\text{margin}}\) 吸收分词差异与意外元数据。若结果为负，请求无法在当前政策下容纳，必须缩短、摘要、拆分或拒绝。

更大窗口不会消除选择问题。无关上下文会干扰模型，重复文本块浪费预算，关键证据也可能被埋没。上下文质量通常比填满每个 token 更重要。

Python：按优先级规则分配上下文预算 
def allocate_context(window, instructions, user, tools, output, margin, history):
    fixed = instructions + user + tools + output + margin
    remaining = window - fixed

    if remaining <= 0:
        raise ValueError("fixed prompt components exceed the context window")

    # Step 1: cap history so an old conversation cannot consume all evidence space.
    history_budget = min(history, int(remaining * 0.35))

    # Step 2: dedicate the rest to evidence, the source of factual grounding.
    evidence_budget = remaining - history_budget

    return {
        "instructions": instructions,
        "user": user,
        "tools": tools,
        "history": history_budget,
        "evidence": evidence_budget,
        "output": output,
        "margin": margin,
    }

budget = allocate_context(
    window=8192,
    instructions=650,
    user=180,
    tools=500,
    output=700,
    margin=300,
    history=3000,
)
print(budget)
print("total:", sum(budget.values()))

token 计数应使用部署分词器，而不是词数。预算策略还必须规定先截断什么。静默截断系统政策或最新用户消息通常不可接受。

结构化输出与验证

自由文本适合解释，却不适合作为下游代码接口。当模型要选择行动、返回实体或产生决策记录时，输出应遵循 schema。

例如：

{
  "answer": "Duplicate-charge refunds take 3-5 business days.",
  "citations": ["refund-policy-v3#p4"],
  "requested_action": null,
  "needs_human": false
}

schema 约束解码可减少语法错误，但应用验证仍不可缺少。JSON 可以合法，却包含不存在的引用、未授权行动，或属于另一用户的订单标识符。

验证应从语法逐步走向语义：

parse JSON
-> check required fields and types
-> check allowed values
-> verify references against supplied context
-> enforce user and tool permissions
-> apply domain policy
-> accept, repair, retry, or escalate
Python：超越 JSON 语法验证模型回答 
import json

ALLOWED_ACTIONS = {None, "create_ticket"}

def validate_model_output(raw_output, supplied_sources):
    # Step 1: parsing establishes syntax, not trust.
    data = json.loads(raw_output)

    # Step 2: enforce the expected shape and primitive types.
    required = {"answer", "citations", "requested_action", "needs_human"}
    missing = required - data.keys()
    if missing:
        raise ValueError(f"missing fields: {sorted(missing)}")
    if not isinstance(data["citations"], list):
        raise TypeError("citations must be a list")

    # Step 3: reject references the model was never given.
    unknown = set(data["citations"]) - set(supplied_sources)
    if unknown:
        raise ValueError(f"unknown citations: {sorted(unknown)}")

    # Step 4: actions are constrained by application policy.
    if data["requested_action"] not in ALLOWED_ACTIONS:
        raise ValueError("requested action is not allowed")

    return data

raw = json.dumps({
    "answer": "Refunds take 3-5 business days [refund-policy-v3#p4].",
    "citations": ["refund-policy-v3#p4"],
    "requested_action": None,
    "needs_human": False,
})

print(validate_model_output(raw, {"refund-policy-v3#p4"}))

重试应有上限且可观测。反复要求同一模型修复无效输出，可能只增加延迟而不能解决语义误解。少量尝试后，确定性回退或人工审核更安全。

会话状态与短期记忆

完整转录不等于状态。转录记录说过什么；状态记录应用当前认为相关且有效的内容。

客服会话状态可包含：

authenticated user
active order
current intent
confirmed facts
missing fields
tool results
pending action
user confirmation

状态应包含来源。旧轮次中低置信度抽取的商品 ID，不能与经过认证账户 API 返回的 ID 同等对待；值还需要过期与纠正规则。

会话摘要可以降低 token 使用，但生成摘要有损且可能引入错误。关键结构化字段应单独保留，同时保留到原始轮次的链接，并在源轮次变化时重建摘要。

记忆形式 生命周期 适合 主要风险
最近转录 当前上下文窗口 局部连贯性 很快消耗 token
结构化对话状态 当前任务 槽位、确认、工具状态 值过时或抽取错误
会话摘要 长对话 压缩背景 遗漏或摘要幻觉
持久用户记忆 跨会话 经同意的偏好 隐私、过时假设、过度个性化

持久记忆应选择加入、可编辑、最小化且用途受限。默认存储每次对话会制造隐私与治理问题，却常只提供很少任务价值。

检索增强生成

检索增强生成（RAG）把选择外部证据的检索器，与基于证据生成答案的生成器结合。它为系统提供可独立于模型权重更新的非参数记忆。

一种简化概率视角为：

\[ p(y \mid x) = \sum_{z \in \mathcal{Z}_k(x)} p_{\eta}(z \mid x)\,p_{\theta}(y \mid x,z). \]

\(x\) 是用户查询，\(z\) 是检索文档或段落，\(\mathcal{Z}_k(x)\) 是 top-\(k\) 候选集合，\(p_{\eta}(z \mid x)\) 是检索概率或相关性分数，\(p_{\theta}(y \mid x,z)\) 是给定查询与证据时生成器对答案的概率。求和表示对哪个检索段落支持答案的不确定性。

原始 RAG 架构把查询编码器、文档索引与序列生成器结合：

查询从非参数记忆检索顶部文档，生成器以其为条件产生输出。来源：Lewis et al., Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks。

在生产中，RAG 通常是模块化管线，而非一个端到端训练图。解析、过滤、混合检索、重排序、上下文打包、引用验证与监控都会成为显式组件。

系统何时需要 RAG？

当答案依赖私有、频繁变化、无法每次全部放入提示，或必须引用的信息时，RAG 很合适，例如政策手册、商品目录、研究集合、法律文档与组织特定知识。

以下情况不一定需要 RAG：

  • 任务是稳定分类问题，且有足够带标签数据；
  • 所需上下文已经全部出现在用户输入中；
  • 确定性数据库查询可以产生精确答案；
  • 检索错误的危害高于精选固定提示；
  • 系统在法律或运行上不能暴露索引材料。

微调与 RAG 解决不同问题。微调改变模型行为、风格或任务能力；RAG 在推理时提供外部证据。用昨天的政策微调模型，不是维护今天政策的高效方式。

文档摄取、分块与元数据

RAG 质量始于检索前。摄取过程必须保留内容、结构、来源、权限与版本。丢失标题或错误连接表格列的 PDF 解析器，会改变检索器能学到的内容。

分块把文档拆成可检索单位。很小的块匹配精确却可能丢上下文；很大的块保留上下文，却稀释相关性并消耗 token 预算。章节、段落、列表项或表格行等结构边界通常优于固定字符数。

有用元数据包括：

字段 用途
文档与文本块 ID 稳定引用与去重
标题与章节路径 上下文与显示
源 URI 来源
版本与生效日期 时效
语言与领域 过滤与路由
访问控制标签 权限执行
解析器与嵌入版本 可复现性
Python：创建带来源的重叠文本块 
from dataclasses import dataclass

@dataclass(frozen=True)
class Chunk:
    chunk_id: str
    document_id: str
    version: str
    start_word: int
    text: str

def chunk_document(document_id, version, text, size=80, overlap=15):
    words = text.split()
    step = size - overlap
    if step <= 0:
        raise ValueError("overlap must be smaller than chunk size")

    chunks = []
    for start in range(0, len(words), step):
        piece = words[start:start + size]
        if not piece:
            break

        # Step 1: create a stable ID from source identity and position.
        chunk_id = f"{document_id}:{version}:w{start}"
        chunks.append(Chunk(
            chunk_id=chunk_id,
            document_id=document_id,
            version=version,
            start_word=start,
            text=" ".join(piece),
        ))

        # Step 2: stop after the final partial chunk.
        if start + size >= len(words):
            break

    return chunks

policy = "Duplicate charge refunds are processed within three to five business days. " * 20
for chunk in chunk_document("refund-policy", "v3", policy)[:2]:
    print(chunk.chunk_id, len(chunk.text.split()))

重叠可保留跨边界句子，但过多重叠会让顶部结果充满近重复。构造上下文前应执行去重与多样性感知选择。

稀疏、稠密与混合检索

稀疏检索用词汇特征表示文本，擅长精确词项、代码、名称与稀有短语；稠密检索用学习型嵌入表示语义，可以匹配改写。客服查询常混合自然语言与精确标识符，因此混合检索同时使用两者。

例如，Why was AX-1042 charged again? 同时包含有关重复收费的语义请求与精确订单式标识符。稠密检索可能理解问题，稀疏检索则更可能保留标识符。

实用检索管线为：

metadata and permission filters
-> sparse candidate search
-> dense candidate search
-> rank fusion
-> deduplication
-> reranking

只要检索引擎允许，过滤器就应尽早应用。先检索禁止文档、生成后再隐藏引用已经太迟，其内容可能已经影响回答。

重排序与上下文构造

第一阶段检索针对大型集合优化速度；重排序器在小型候选集上运行更昂贵模型，并联合查询与文档估计相关性。Cross-encoder 可以建模 token 级交互，通常比独立嵌入提供更好的相关性判断。

上下文构造随后选择哪些重排文本块放入预算。纯按最高分选择会返回冗余段落。有用目标会平衡相关性、多样性、权威、时效与 token 成本：

\[ U(d) = \lambda_r R(d) + \lambda_a A(d) + \lambda_f F(d) - \lambda_n N(d,S) - \lambda_c C(d). \]

\(R(d)\) 是相关性，\(A(d)\) 是来源权威，\(F(d)\) 是时效，\(N(d,S)\) 是与已选集合 \(S\) 的冗余，\(C(d)\) 是 token 成本。\(\lambda\) 值表达产品优先级。这是设计目标，不是通用公式。

上下文应保留文档身份与章节边界。把文本块合并成无标签文本墙，会让引用与冲突处理困难。当两个版本不一致时，系统需要版本策略，而不是让生成器猜测。

有依据生成与引用

有依据的答案所作陈述得到提供证据支持。只有当引用指向真正支持附近陈述的证据时，它才有用；仅把顶部检索来源附在回答末尾，不能建立依据。

依据控制可以包括：

  • 指示模型只对政策陈述使用提供来源；
  • 要求句子级或陈述级引用标识符；
  • 验证被引用标识符确实存在于上下文；
  • 检查陈述与引用段落之间的蕴含；
  • 证据不足或矛盾时拒答或升级；
  • 显示摘录，让用户检查来源。
Python：检查引用覆盖与来源有效性 
import re

supplied_sources = {
    "refund-policy-v3#p4": "Refunds take three to five business days.",
    "billing-guide-v2#p8": "Duplicate charges may be disputed through support.",
}

answer = (
    "Duplicate-charge refunds take three to five business days "
    "[refund-policy-v3#p4]. Contact support to open a dispute "
    "[billing-guide-v2#p8]."
)

def validate_citations(answer, supplied_sources):
    citations = re.findall(r"\[([^\]]+)\]", answer)

    # Step 1: every citation must refer to evidence actually supplied.
    unknown = [item for item in citations if item not in supplied_sources]

    # Step 2: split prose into claims and check that each has a citation.
    claims = [part.strip() for part in re.split(r"(?<=[.!?])\s+", answer) if part.strip()]
    uncited = [claim for claim in claims if not re.search(r"\[[^\]]+\]", claim)]

    return {
        "citations": citations,
        "unknown_citations": unknown,
        "uncited_claims": uncited,
    }

report = validate_citations(answer, supplied_sources)
print(report)
assert not report["unknown_citations"]
assert not report["uncited_claims"]

该验证器检查格式与覆盖，不检查语义支持。陈述－证据验证需要 NLI 模型、专用评估器或人工审核。高影响陈述可能需要从权威字段确定性抽取，而不是自由生成。

RAG 评估与失败模式

RAG 必须在多个层级评估：

层级 核心问题 示例指标或测试
摄取 来源是否正确解析并版本化？ 解析覆盖与表格测试
检索 候选集是否包含支持证据？ recall@k
排序 有用证据是否尽早出现？ MRR 或 nDCG
上下文 所选证据是否相关且不冗余？ 上下文精确率与 token 使用
生成 答案是否正确完整？ 任务量表或答案准确率
依据 陈述是否由引用证据支持？ 陈述支持率与引用精确率
系统 完整工作流是否可靠帮助用户？ 解决率、延迟、升级

常见失败链包括：

bad parse -> missing terms -> retrieval miss -> unsupported answer
stale index -> obsolete evidence -> confidently outdated answer
duplicate chunks -> narrow context -> omitted exception
weak permission filter -> private evidence -> information disclosure
good evidence + weak prompt -> uncited synthesis
good answer + invalid citation -> user cannot verify it

诊断顺序应沿管线进行。修改生成器前，先检查正确证据是否存在、被检索、重排序并包含在上下文中。

工具调用与智能体工作流

检索为模型提供信息，工具则让系统观察或改变外部环境。工具可以查询订单数据库、计算数值、创建工单、发送消息或安排预约。因为工具效果可在对话结束后持续存在，工具调用需要比文本生成更强的控制。

函数调用

函数调用要求模型产生包含工具名称与参数的结构化提案。由应用而不是模型决定是否及如何执行。

{
  "tool": "create_support_ticket",
  "arguments": {
    "category": "duplicate_charge",
    "order_id": "A-1042"
  }
}

工具 schema 约束语法并帮助模型选择参数，但不等于授权。执行前，应用必须认证用户、验证订单属于用户、检查必要确认并执行允许值约束。

Python：带政策检查地分派允许列表工具 
from dataclasses import dataclass

@dataclass(frozen=True)
class ToolRequest:
    name: str
    arguments: dict

def create_support_ticket(category, order_id):
    # A real implementation would call an idempotent external API.
    return {"ticket_id": "T-9001", "category": category, "order_id": order_id}

TOOLS = {"create_support_ticket": create_support_ticket}
ALLOWED_CATEGORIES = {"duplicate_charge", "refund", "delivery"}

def dispatch_tool(request, user_order_ids, confirmed):
    # Step 1: allow only registered tools.
    if request.name not in TOOLS:
        raise PermissionError("tool is not allowlisted")

    # Step 2: validate arguments against domain and user permissions.
    category = request.arguments.get("category")
    order_id = request.arguments.get("order_id")
    if category not in ALLOWED_CATEGORIES:
        raise ValueError("invalid ticket category")
    if order_id not in user_order_ids:
        raise PermissionError("order is not accessible to this user")

    # Step 3: require explicit confirmation for an external side effect.
    if not confirmed:
        return {"status": "confirmation_required"}

    return TOOLS[request.name](category=category, order_id=order_id)

proposal = ToolRequest(
    name="create_support_ticket",
    arguments={"category": "duplicate_charge", "order_id": "A-1042"},
)
print(dispatch_tool(proposal, {"A-1042"}, confirmed=True))

有副作用的工具应支持幂等键，避免重试创建重复工单或付款。只读与写入工具应使用不同权限，并对写操作提出更明确的用户确认要求。

推理、行动与观察

工具调用系统常以循环运行：

inspect current state
-> choose an allowed action
-> execute through the application
-> receive a structured observation
-> update state
-> stop, continue, or escalate

ReAct 证明，把推理、行动与外部环境观察交错具有价值。生产系统中，重要工程产物是可观察行动轨迹。私有内部推理无需暴露或存储；简洁的行动理由与结构化状态通常更利于审计和恢复。

示例显示，缺少新观察的推理会传播早期错误，缺少充分推理的行动则可能选择错误下一步。来源：Yao et al., ReAct: Synergizing Reasoning and Acting in Language Models。

循环必须有停止条件。最大步数、时间预算、成本预算、重复行动检测与终止成功状态可以防止无限执行。反复搜索同一查询的智能体并未变得更确定，只是在不改变状态时消耗资源。

状态与记忆

智能体工作流需要在模型调用间保留的状态对象。状态应区分：

状态类型 示例 存储规则
任务状态 工单类别与缺失字段 当前工作流期间保留
观察 订单 API 结果 记录来源与时间戳
计划或待执行步骤 验证订单，再请求确认 观察变化时修订
行动历史 工具、参数、结果 追加到 trace
持久记忆 用户偏好邮件跟进 仅在有用途与同意时存储

不要把模型生成文本当作唯一状态存储。结构化状态支持验证、确定性转移与故障后恢复，也防止旧模型消息被误认为当前工具结果。

权限与错误恢复

最小权限原则只给每个工作流当前任务所需的工具、文档与操作。回答政策的助手不需要付款工具；创建工单的工作流可能只在身份与确认检查后获得写权限。

工具错误应分类，而不是盲目重试：

错误 示例 响应
验证 缺少订单 ID 询问用户或修复参数
授权 订单属于另一账户 拒绝并记录安全事件
暂时性 服务超时 有上限地退避重试
速率限制 请求过多 等待、入队或使用回退
永久领域错误 订单不符合条件 解释结果与替代方案
结果有歧义 工具可能在超时前已成功 重试前检查幂等状态

恢复应让工作流回到已知状态。若工具部分成功，可能需要补偿操作或人工介入。模型不能因工具没有响应而虚构成功。

工作流与智能体

工作流遵循预定义的步骤与条件图；智能体根据观察动态选择行动。许多系统结合两者：确定性工作流控制授权与高影响状态转移，模型则在受限步骤内选择如何搜索或解释。

属性 确定性工作流 智能体循环
路径 预定义 运行时选择
可预测性 高 较低
灵活性 限于已知分支 适应陌生路径
测试 枚举状态转移 评估轨迹与预算
最适合 稳定业务流程 开放式信息收集
主要风险 缺少分支导致脆弱 不受控行动或循环

只有动态行动选择真正增加价值时才使用智能体。如果支持工单总是需要 collect order -> verify eligibility -> confirm -> submit，工作流能更清楚可靠地表达要求。

生产与可观测性

原型证明一个请求可以成功；生产工程则询问服务能否在负载、故障、版本变化、对抗输入与成本限制下持续有用。可观测性把结果连接到产生它的精确模型、提示、索引、工具与决策。

延迟、吞吐与成本

端到端延迟近似等于顺序阶段加队列等待之和：

\[ T_{\text{total}} = T_{\text{gateway}} + T_{\text{retrieval}} + T_{\text{rerank}} + T_{\text{generation}} + T_{\text{tools}} + T_{\text{validation}} + T_{\text{queue}}. \]

每项是一个组件的经过时间。并行执行组件贡献的是最大值而非总和，例如稀疏与稠密检索可以并发。

平均延迟会隐藏尾部糟糕体验。服务通常监控 p50、p95 与 p99 等百分位。若 p95 为 8 秒，即使平均值低得多，每二十个请求仍有一个至少需要这么久。

吞吐量是单位时间完成的工作，例如每秒请求数或生成 token 数。成本包括模型输入输出 token、嵌入、重排序、存储、网络调用、工具与人工审核：

\[ C_{\text{request}} = C_{\text{model}} + C_{\text{retrieval}} + C_{\text{tools}} + C_{\text{infrastructure}} + C_{\text{review}}. \]

优化必须保持质量。减少检索证据可降低 token，却可能增加无依据答案和人工升级，从而提高总成本。

缓存、批处理与模型路由

当输入与版本匹配时，缓存避免重复工作。可缓存文档嵌入、稳定公开查询的检索结果与确定性模型回答。缓存键必须包含会改变结果的所有因素，例如模型、提示、索引、locale、权限与解码配置。

若缓存回答包含私有上下文，绝不能跨用户共享。权限感知检索结果需要在键中加入用户或访问范围，这会降低复用率，却能保持隔离。

批处理把兼容请求分组以提高硬件利用率。动态 batching 短暂等待以合并请求，在延迟与吞吐间权衡。流式输出逐步返回 token，可降低感知生成延迟，但结构化输出验证与工具决策可能需要先缓冲。

模型路由根据任务、风险、复杂度、语言或预算选择模型。小分类器可处理意图路由，紧凑生成器可回答简单有依据问题，更强模型则接收有歧义或多文档案例。路由本身必须评估，因为把困难案例交给能力不足模型会产生隐藏质量损失。

追踪与版本管理

trace 记录一个请求跨组件的路径。日志回答局部问题，trace 则把分布式事件连接成一条因果时间线。

至少记录：

request and trace IDs
timestamps and duration per stage
model and tokenizer version
prompt and policy version
index and document versions
retrieved and selected chunk IDs
tool proposals, approvals, and results
validation and fallback decisions
token use, cost estimate, and final status

敏感文本应最小化、脱敏、加密、访问控制，并只保留必要时间。可观测性不能成为无人治理的用户会话副本。

Python：为一个请求记录结构化 Trace 事件 
from dataclasses import dataclass, asdict
from datetime import datetime, timezone
import json

@dataclass(frozen=True)
class TraceEvent:
    trace_id: str
    stage: str
    status: str
    version: str
    duration_ms: int
    details: dict
    timestamp: str

def event(trace_id, stage, status, version, duration_ms, **details):
    # Step 1: create one versioned event without storing raw private text.
    return TraceEvent(
        trace_id=trace_id,
        stage=stage,
        status=status,
        version=version,
        duration_ms=duration_ms,
        details=details,
        timestamp=datetime.now(timezone.utc).isoformat(),
    )

trace = [
    event("tr-1042", "retrieval", "ok", "index-2026-07-16", 43,
          selected_chunk_ids=["refund-policy:v3:w160"]),
    event("tr-1042", "generation", "ok", "model-4.2+prompt-18", 812,
          input_tokens=980, output_tokens=96),
    event("tr-1042", "citation_validation", "ok", "validator-3", 4,
          citation_count=1),
]

# Step 2: emit structured records that monitoring and audit tools can query.
for item in trace:
    print(json.dumps(asdict(item)))

监控、回退与人工升级

监控应覆盖服务健康、模型行为、检索、安全、成本与用户结果。

信号 示例告警
可用性 错误率超过服务目标
延迟 p95 生成延迟翻倍
检索 索引发布后无结果率上升
依据 无依据陈述抽样率超过阈值
工具 重复或未授权行动尝试增加
成本 每个已解决案例 token 急剧增加
质量 人工纠正或重新打开率增加
漂移 新语言或商品切片增长

指标需要责任人与响应。检索失败时，回退可以展示搜索结果或转人工；生成器超时时，确定性确认消息可能比无限重试更好；证据冲突时，系统应暴露冲突，而非制造确定性。

人工升级是架构的一部分，不代表自动化失败。应定义低置信度、缺少证据、政策冲突、高影响行动、重复工具失败、用户明确请求或检测到痛苦等触发器。审核者需要相关证据与 trace，而不只是最终模型答案。

部署应渐进进行。离线评估、影子流量、canary 发布与回滚可缩小影响范围。每次模型、提示、索引或工具变化后，都应监控平均行为与关键切片。

选择系统架构

架构选择始于需求，而不是组件。询问系统是否需要外部知识、知识是否变化、是否必须执行行动、行动路径是否已知，以及错误答案或行动有多严重。

独立模型、RAG 与工具调用系统

架构 增加什么 最适合 主要新失败模式
独立模型 模型调用与验证 稳定分类、改写、给定上下文任务 模型错误或无依据生成
模型加固定上下文 精选指令与示例 狭窄稳定政策 过时或过大提示
RAG 外部索引、检索、引用 变化或私有知识 检索与依据失败
确定性工具工作流 经验证的 API 行动 稳定业务流程 集成与状态转移失败
受限智能体 动态工具选择与观察 开放式多步调查 循环、错误行动与成本增长

复杂度需要被证明合理。如果答案来自精确数据库字段，就直接查询；如果用户需要文档，提供搜索；如果需要带证据的综合答案，加入 RAG；如果需要行动，加入受约束工具工作流；只有路径无法有效预先表示时，才加入智能体规划。

架构决策矩阵

需求 仅模型 RAG 工作流＋工具 受限智能体
分类或改写提供的文本 非常适合 不必要 不必要 不必要
根据变化文档回答 较弱 非常适合 可选 可选
提供可审计引用 较弱 非常适合 可选 可行但复杂
执行已知交易 无法行动 无法独立行动 非常适合 通常过度
通过未知步骤调查 有限 只负责检索 脆弱 非常适合
可预测延迟与行为 最强 中等 中等到强 最弱
最容易进行组件测试 最强 中等 中等 最困难

风险会改变选择。低影响研究助手可容忍动态探索；金融或临床行动则应在每个模型选择步骤周围加入确定性验证与人工授权。

端到端 NLP 系统案例

现在可以把客服助手组装成受限架构：

1. authenticate user and create trace
2. classify request and select workflow
3. retrieve permitted policy chunks
4. rerank, deduplicate, and fit context budget
5. generate a structured answer with citations
6. validate schema, citations, and policy
7. if an action is requested, gather missing fields
8. ask for explicit confirmation
9. execute one allowlisted idempotent tool
10. return result or escalate with complete trace
Python：勾勒完整、有依据的客服工作流 
def handle_support_request(request, services):
    trace_id = services.tracing.start(request.request_id)

    try:
        # Step 1: establish identity and the resources this user may access.
        identity = services.auth.authenticate(request.user_id)
        access_scope = services.auth.policy_scope(identity)

        # Step 2: retrieve first, then verify that sufficient evidence exists.
        candidates = services.retrieval.search(
            query=request.message,
            access_scope=access_scope,
            index_version="policy-index-42",
        )
        evidence = services.reranker.select(candidates, token_budget=2400)
        if not evidence:
            return services.handoff.create(
                trace_id=trace_id,
                reason="no_authoritative_evidence",
            )

        # Step 3: generate a structured proposal, not an executable side effect.
        prompt = services.prompts.build(
            template_version="support-grounded-18",
            request=request,
            evidence=evidence,
        )
        raw_output = services.model.generate(
            prompt,
            model_version="support-model-4.2",
        )

        # Step 4: validate citations and requested actions against real context.
        response = services.validation.validate(
            raw_output,
            supplied_sources={item.chunk_id for item in evidence},
            allowed_actions={None, "create_support_ticket"},
        )

        # Step 5: keep write actions behind deterministic confirmation policy.
        if response.requested_action == "create_support_ticket":
            if not request.confirmed:
                return services.responses.request_confirmation(response)

            tool_result = services.tools.execute(
                name="create_support_ticket",
                arguments=response.action_arguments,
                identity=identity,
                idempotency_key=request.request_id,
            )
            response.action_status = tool_result.status

        services.tracing.finish(trace_id, status="ok")
        return response

    except services.transient_errors as error:
        # Step 6: known transient failures use a bounded fallback path.
        services.tracing.finish(trace_id, status="fallback", error=type(error).__name__)
        return services.responses.safe_fallback(
            "The support service is temporarily unavailable. No action was taken."
        )
    except Exception as error:
        # Step 7: unknown failures preserve evidence and escalate.
        services.tracing.finish(trace_id, status="error", error=type(error).__name__)
        return services.handoff.create(trace_id=trace_id, reason="system_error")

示例有意保持模块化。每个服务可以独立替换、测试、版本化与观测。模型很重要，但不能负责认证用户、虚构来源或执行任意函数。

实用架构评审可以用六项检查结束：

  1. 必要性： 每个组件是否解决已声明需求？
  2. 契约： 输入、输出、版本与故障状态是否明确？
  3. 证据： 事实陈述能否追溯到获准来源？
  4. 权限： 模型提案是否与应用授权分离？
  5. 恢复： 超时、无效输出与部分行动能否回到已知状态？
  6. 可观测性： 团队能否重建、监控并改善完整路径？

现代 NLP 系统并不由模型调用数量定义，而由统计语言能力如何被审慎连接到证据、软件、人和真实后果来定义。
